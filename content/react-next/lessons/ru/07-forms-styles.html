01 Управляемые и неуправляемые поля

У каждого поля ввода есть значение, и кто-то должен быть его хозяином. Есть два варианта.

  • Управляемое поле (controlled): значение хранит React в состоянии. В поле вы пишете value={name} и onChange, который кладёт новое значение в setName. Любой символ проходит через React: можно сразу проверить, отформатировать или заблокировать.
  • Неуправляемое поле (uncontrolled): значение хранит сам браузер (DOM). React ничего не знает, пока вы не спросите: при отправке формы (FormData) или через ref. Начальное значение задаёт defaultValue.
import { useState, type ChangeEvent } from 'react'

export default function NameField() {
  const [name, setName] = useState('')

  function handleChange(event: ChangeEvent<HTMLInputElement>) {
    setName(event.target.value)
  }

  return (
    <label>
      Имя
      <input value={name} onChange={handleChange} />
    </label>
  )
}

import type { FormEvent } from 'react'

export default function QuickOrder({ onOrder }: { onOrder: (phone: string) => void }) {
  function handleSubmit(event: FormEvent<HTMLFormElement>) {
    event.preventDefault() // без этого браузер перезагрузит страницу
    const data = new FormData(event.currentTarget)
    onOrder(String(data.get('phone')))
  }

  return (
    <form onSubmit={handleSubmit}>
      <input name="phone" defaultValue="+992" />
      <button>Перезвоните мне</button>
    </form>
  )
}

Обратите внимание: data.get('phone') возвращает FormDataEntryValue | null (строка, файл или null), поэтому его нужно привести к строке или проверить. Значения из полей — всегда строки: число из type="number" тоже приходит строкой, и его нужно преобразовать (Number(value)).

Подпись, отправка и кнопки

  • У каждого поля есть <label>: оберните поле им или свяжите htmlFor с id. Для уникальных id в компоненте, который рисуется много раз, используйте хук useId(). Подсказка в placeholder подписью не является: она исчезает при вводе.
  • Кнопка внутри <form> без type по умолчанию отправляет форму. Кнопке «Закрыть» внутри формы нужен type="button".
  • Флажок читают из checked, а не из value; для select значение — event.target.value.
  • В React 19 у <form> есть prop action для серверных функций: им мы займёмся в уроке 18 (Next.js). В SPA, как в «Дастархоне», форму обрабатывает onSubmit.
Аналогия из жизни

Управляемое поле — продавец на бозоре, который записывает каждое ваше слово в тетрадь и тут же зачитывает вам обратно. Неуправляемое — листок с заказом: вы заполняете его сами, а продавец читает его один раз, когда вы протянули его через прилавок.

Типичные ошибки

1. value без onChange: поле «не печатает». В консоли dev-режима:

You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field. If the field should be mutable use `defaultValue`. Otherwise, set either `onChange` or `readOnly`.

2. Начальное значение undefined, а потом строка: поле «переезжает» из неуправляемых в управляемые. Начинайте со строки: useState('').

A component is changing an uncontrolled input to be controlled. This is likely caused by the value changing from undefined to a defined value, which should not happen. Decide between using a controlled or uncontrolled input element for the lifetime of the component. More info: https://react.dev/link/controlled-components

3. Нет event.preventDefault() в onSubmit: страница перезагружается и состояние пропадает. 4. Одновременно value и defaultValue у одного поля. 5. Число из поля складывают как строку: "2" + "3" даёт "23".

ЗАДАЧА 1.1

Проверь себя: управляемые поля

средняя

Поле записано как <input value={city} /> без onChange. Что произойдёт?

  1. Поле будет работать как обычно
  2. Поле станет только для чтения: React каждый раз вернёт city, а в консоли появится предупреждение
  3. Значение будет сохраняться в localStorage
  4. Форма не отправится

У управляемого поля единственный источник значения — состояние. Без onChange состояние не меняется, и React возвращает прежнее значение после каждого нажатия.

В каких случаях разумно выбрать управляемое поле? Выберите два.

  1. Список ресторанов должен фильтроваться на каждый введённый символ
  2. Форма из двух полей, которая проверяется только при отправке
  3. Поле телефона должно форматироваться на лету, например +992 90 123 45 67
  4. Нужно получить значение один раз, когда пользователь нажал «Отправить»

Если значение нужно в момент ввода (фильтр, маска, зависимое поле), оно должно быть в состоянии. Если достаточно прочитать при отправке, хватит неуправляемого поля.

Что вернёт new FormData(form).get('qty') для поля <input name="qty" type="number" defaultValue="2" />?

  1. Число 2
  2. true
  3. Строку "2"
  4. undefined

Значения полей — строки (или файлы). Число нужно получить самому: Number(...). Сервер и схема должны знать, что пришла строка.

02 Валидация: от ручной проверки к схеме Zod

Проверка формы отвечает на два вопроса: что считать верным и когда показывать ошибку. Начнём с того, как это выглядит без библиотек.

type OrderValues = {
  name: string
  phone: string
  address: string
}

type Errors = Partial<Record<keyof OrderValues, string>>

function validate(values: OrderValues): Errors {
  const errors: Errors = {}
  if (values.name.trim().length < 2) {
    errors.name = 'Введите имя: не меньше 2 букв'
  }
  if (!/^\+992\d{9}$/.test(values.phone)) {
    errors.phone = 'Телефон в формате +992901234567'
  }
  if (values.address.trim().length < 5) {
    errors.address = 'Укажите улицу и дом'
  }
  return errors
}

Это работает, но видны две слабости. Во-первых, тип и правила живут отдельно: добавили поле в тип, забыли в validate, и TypeScript промолчит. Во-вторых, всё остальное (когда проверять, какие поля «тронуты», как фокусировать первое ошибочное, как отправлять) вам придётся писать самим. Вторую часть берёт React Hook Form (раздел 3), первую — схема.

Когда показывать ошибку

  • При отправке: самый спокойный вариант и значение по умолчанию. Пользователь не видит красного, пока не закончил.
  • После ухода с поля (onBlur, в React Hook Form режим onTouched): ошибка появляется, когда поле «потрогали», а дальше исчезает сразу при исправлении.
  • На каждый символ: только там, где это помогает (силу пароля, счётчик символов). Красная ошибка на первой же букве имени раздражает.

Схема как единый источник правды

Zod — библиотека, в которой правила описываются один раз в виде схемы. Схема умеет три вещи: проверить значение во время работы программы, выдать понятные ошибки и дать TypeScript тип проверенных данных. Типы TypeScript исчезают при сборке, а схема остаётся кодом и проверяет настоящие данные, пришедшие из формы или с сервера.

import { z } from 'zod'

export const PAYMENTS = ['cash', 'card'] as const

export const orderSchema = z.object({
  name: z.string().trim().min(2, 'Введите имя: не меньше 2 букв'),
  phone: z.string().regex(/^\+992\d{9}$/, 'Телефон в формате +992901234567'),
  address: z.string().trim().min(5, 'Укажите улицу и дом'),
  comment: z.string().max(200, 'Не больше 200 символов'),
  payment: z.enum(PAYMENTS, { error: 'Выберите способ оплаты' }),
})

// тип получаем из схемы: второй раз его не пишем
export type OrderForm = z.infer<typeof orderSchema>

OrderForm — это ровно { name: string; phone: string; address: string; comment: string; payment: 'cash' | 'card' }. Изменили правило в схеме, и тип изменился сам. Прочитайте это как «тип значений, которые гарантированно прошли схему».

Как Zod отвечает на плохие данные

schema.parse(data) возвращает данные или выбрасывает ошибку, а schema.safeParse(data) ничего не выбрасывает и возвращает объект с полем success. Формам нужен второй вариант: ошибки — обычная ситуация, а не исключение.

const result = orderSchema.safeParse({
  name: 'А',
  phone: '123',
  address: 'пр. Рудаки, 45',
  comment: '',
  payment: 'cheque',
})

if (!result.success) {
  console.log(z.flattenError(result.error).fieldErrors)
}

Запомните форму результата: имя поля → список сообщений. React Hook Form раскладывает ошибки так же, а вам остаётся показать errors.name?.message. Если поле пропущено совсем, Zod пожалуется стандартным текстом Invalid input: expected string, received undefined: пользователю он ничего не говорит, поэтому в форме у каждого поля есть значение по умолчанию.

Несколько приёмов Zod

  • z.string().trim().min(2, 'текст'): цепочка проверок, сообщение вторым аргументом. trim() ещё и обрезает пробелы в результате.
  • z.email('текст'): проверка адреса (в Zod 4 это короткая запись; прежняя z.string().email() работает, но помечена устаревшей, как и параметр message вместо error).
  • z.enum([...] as const): одно из значений, тип получается union-ом из урока 2.
  • .refine(проверка, { path: ['confirm'], error: '...' }): правило, которое смотрит на несколько полей сразу (пароль и повтор пароля). Вы используете его в домашнем задании.
  • Необязательное текстовое поле: пустое поле формы — это '', а не undefined, поэтому его описывают как z.string() без минимума, как comment выше.

TypeScript: тип из одного источника

Приём «тип берётся из значения» работает и без Zod: as const и typeof вы уже видели в уроке 2 на CUISINES. z.infer — то же самое, только значением является схема. Потренируйтесь на простом примере в задачах ниже.

Аналогия из жизни

Схема — это приёмщик на складе в Душанбе: один человек с одним списком правил. Он проверяет каждую машину (значение), выписывает акт с причинами отказа (сообщения) и ставит штамп «принято» (тип). Если бы правила держали в голове и водитель, и кладовщик, и бухгалтер, они бы рано или поздно разошлись.

Типичные ошибки

1. Тип формы написан руками рядом со схемой: при правке схемы тип «отстаёт». Берите z.infer. 2. Валидация только на клиенте: форму обходят запросом напрямую, сервер обязан проверить всё заново (урок 18). 3. Числа из полей: схема получает строку, а не число; для чисел нужно преобразование, и тогда тип на входе и на выходе у схемы разный. Пока оставляйте поля строками. 4. Сообщения на английском по умолчанию: пишите свои, как Invalid input: expected string, received undefined пользователю ничего не говорит. 5. Обязательное поле описано как z.string(): пустая строка проходит. Добавьте .min(1, 'текст') или более точное правило.

ЗАДАЧА 2.1

Проверь себя: схема и тип

средняя

Зачем получать тип через z.infer, а не написать type OrderForm = { … } рядом со схемой?

  1. Так код быстрее выполняется
  2. Правила и тип нельзя рассинхронизировать: меняется схема, меняется и тип
  3. Без этого Zod не работает
  4. Рукописный тип нельзя использовать в компоненте

Два описания одного и того же рано или поздно расходятся. Схема — единственный источник: из неё и проверка, и тип.

Почему тип OrderForm сам по себе не защищает от неверных данных от пользователя?

  1. Типы TypeScript существуют только при сборке: во время работы проверяет только схема
  2. Потому что TypeScript ошибается
  3. Потому что тип нельзя импортировать
  4. Потому что тип работает только для чисел

В браузере от типов остаётся обычный JavaScript. Данные из формы или сети проверяются кодом: схемой Zod или руками.

Когда лучше показывать ошибку в обычной форме заказа?

  1. На каждый введённый символ, чтобы человек сразу видел проблему
  2. Только после перезагрузки страницы
  3. При отправке и после ухода с поля, а после этого убирать при исправлении
  4. Никогда: хватит одной общей надписи «Форма заполнена неверно»

Красное на первой букве пугает, а общая надпись не говорит, что исправлять. Ошибка при отправке или после ухода с поля — спокойный и понятный вариант.

03 React Hook Form: форма без ручной рутины

Если писать форму вручную, на каждое поле нужны useState, onChange, onBlur, флаги «тронуто», сбор ошибок и перенос фокуса. React Hook Form (RHF) делает это за вас и при этом не перерисовывает форму на каждую букву: поля остаются неуправляемыми, а библиотека читает их через ref. Она вместе с Zod ставится в проект:

npm install react-hook-form zod @hookform/resolvers

На момент урока это react-hook-form 7.91, zod 4.6 и @hookform/resolvers 6.0. Пакет @hookform/resolvers — мост между RHF и схемой: функция zodResolver(schema) говорит форме «проверяй значения этой схемой».

import { zodResolver } from '@hookform/resolvers/zod'
import { useForm } from 'react-hook-form'
import { orderSchema, type OrderForm } from './orderSchema'

export default function MiniForm() {
  const {
    register,
    handleSubmit,
    formState: { errors, isSubmitting },
  } = useForm<OrderForm>({
    resolver: zodResolver(orderSchema),
    defaultValues: { name: '', phone: '+992', address: '', comment: '', payment: 'cash' },
  })

  async function onSubmit(values: OrderForm) {
    // сюда попадают только значения, прошедшие схему
    console.log(values)
  }

  return (
    <form noValidate onSubmit={handleSubmit(onSubmit)}>
      <input {...register('name')} />
      {errors.name && <p role="alert">{errors.name.message}</p>}
      <button disabled={isSubmitting}>Отправить</button>
    </form>
  )
}

Осторожно с watch(): он подписывает компонент на значения и снова делает перерисовку на каждую букву. Если значение нужно только при отправке, оно уже есть в onSubmit. Есть и вторая причина быть осторожным: watch() хранит скрытое изменяемое состояние, поэтому React Compiler (урок 6) такие компоненты пропускает, а правило линтера react-hooks/incompatible-library предупреждает о них. Если значение нужно показывать на экране, берите хук useWatch. Это одна из причин, почему в основном проекте курса компилятор не включён.

TypeScript следит за именами полей

Раз тип формы взят из схемы, опечатка в имени поля перестаёт быть тихой. Вот что говорит компилятор, если написать register('nmae') или забыть, что ошибка может отсутствовать:

src/MiniForm.tsx(12,30): error TS2345: Argument of type '"nmae"' is not assignable to parameter of type '"address" | "comment" | "name" | "payment" | "phone"'.
src/MiniForm.tsx(13,24): error TS18048: 'errors.name' is possibly 'undefined'.

Вторая ошибка полезна: errors.name есть только тогда, когда поле неверно, поэтому читайте errors.name?.message или проверяйте наличие, как в примере выше.

Ошибка сервера и «молчащая» форма

Схема проверяет форму на клиенте, но сервер знает больше (ресторан закрыт, номер заблокирован). Ошибку сервера ловят в try/catch вокруг запроса и кладут в форму через setError('root.server', …). Вторая типичная беда: в схеме есть поле, а в разметке его нет (или оно названо иначе). Тогда handleSubmit не вызывает onSubmit, а ошибку показывать некому: форма «молчит». Чтобы поймать это, передайте вторым аргументом обработчик неверной отправки: handleSubmit(onSubmit, (errors) => console.log(errors)). Вы проделаете это в практике.

Аналогия из жизни

RHF — администратор в приёмной клиники. Вы заполняете карточку на листках (поля), он не читает каждую букву, пока вы пишете. Когда вы протянули карточку, он сверяет её с правилами (схема), и если что-то не так, молча подводит вас к первому неверному полю и показывает, что исправить.

Типичные ошибки

1. Нет defaultValues: поля стартуют с undefined, а схема ждёт строку. 2. register('name') без распаковки: пишите {...register('name')}. 3. Своё onChange у поля register перебивает RHF: передайте его внутрь register('name', { onChange }). 4. Поле в схеме есть, в форме нет: форма молчит, как описано выше. 5. Старые примеры с ref={register} (RHF версии 6) в ответах ИИ: в версии 7 это не работает. 6. Типизированный onSubmit = (data: any): тип берите из схемы.

Проверь себя: React Hook Form

средняя

  3. Страница перезагружается
  4. Форма отправляется на сервер с пометкой «ошибка»

Ваш onSubmit получает только проверенные значения. Всё остальное библиотека берёт на себя.

В схему добавили email: z.email(), а поле в разметке забыли. Что увидит пользователь?

  2. Заказ отправится без email
  3. Ничего: форма не отправляется, а ошибку показывать некому
  4. Сообщение от TypeScript в браузере

  1. Вызвать watch() без аргументов в теле компонента
  2. Поля остаются неуправляемыми: значения читаются через ref
  3. Хранить каждое поле в своём useState
  4. Читать значения в onSubmit, а не следить за ними через watch

Экономия RHF — как раз в неуправляемых полях. watch() и отдельные useState возвращают рендер на каждый символ.

04 Модальные окна и порталы

Модальное окно — блок поверх страницы, который требует ответа: пока он открыт, остальная страница «заморожена». Рисовать его там, где вы его объявили (внутри карточки или корзины), опасно: у родителей бывают overflow: hidden, transform или собственный z-index, и окно обрежется или окажется под другим слоем. Поэтому окно выносят в конец <body>. В React для этого есть портал.

import { createPortal } from 'react-dom'

function Hint({ children }: { children: ReactNode }) {
  return createPortal(
    <div className="fixed inset-0 z-50">{children}</div>,
    document.body,
  )
}

Первый аргумент — что рисовать, второй — настоящий DOM-элемент, куда это поместить. Компонент остаётся там же, где вы его написали: в дереве React он потомок своего родителя, а в DOM его разметка лежит в document.body.

События и контекст идут по дереву React

Самое неожиданное в порталах: событие из портала всплывает по дереву React, а не по DOM. Если у карточки есть onClick, а окно из портала внутри неё, клик по кнопке в окне дойдёт до onClick карточки, хотя в DOM окно лежит в body. Если родителю это мешает, остановите всплытие в окне: event.stopPropagation(). Контекст (урок 8) через портал тоже проходит.

Куда рисовать и что говорит TypeScript

Проще всего — document.body: он всегда есть. Можно завести контейнер <div id="modal-root"> в index.html, но тогда document.getElementById вернёт HTMLElement | null, а портал принимает только Element или DocumentFragment:

src/Hint.tsx(3,33): error TS2345: Argument of type 'HTMLElement | null' is not assignable to parameter of type 'DocumentFragment | Element'.
  Type 'null' is not assignable to type 'DocumentFragment | Element'.

А если опечататься в id и обойти компилятор через as HTMLElement, в браузере будет ошибка во время работы:

Uncaught Error: Target container is not a DOM element.

В SPA с Vite document всегда есть. В Next.js компоненты сначала рисуются на сервере, где document нет: там порталы подключают после монтирования (вернёмся к этому в уроке 16). Типы остальных частей окна: children: ReactNode, обработчики KeyboardEvent<HTMLDivElement> и MouseEvent<HTMLDivElement>.

Свой диалог или встроенный <dialog>

В браузерах есть тег <dialog> с методом showModal(): он сам даёт слой поверх страницы, закрытие по Esc, затемнение ::backdrop и запрет фокуса на странице под ним. Для новых проектов это отличный вариант, и стоит его знать. В курсе мы пишем окно через портал: так видно, из чего состоит доступность (раздел 5), а портал нужен и для подсказок, выпадающих меню и уведомлений. В дальнейшем библиотеки интерфейса (Radix, Headless UI) решают то же самое готовыми компонентами.

Ролик на русском: как устроен портал и как собрать на нём окно. Фокус и доступность в нём затронуты слабо: их мы добавим в разделе 5.

Аналогия из жизни

Портал — как объявление на стене чойхоны. Заказ вы приняли за своим столом (место в дереве React), но табличку «Столик занят» вешают на главную стену у входа (body), чтобы её видели все и ни один стол её не загораживал. Если на табличку нажмёт гость, вопрос всё равно дойдёт до вашего стола: событие идёт по дереву React.

Типичные ошибки

1. Окно внутри карточки с overflow: hidden: оно обрезано. 2. Клик в окне срабатывает на карточке под ним (всплытие по дереву React). 3. Закрытие по клику на фон срабатывает и от клика внутри окна: сравнивайте event.target === event.currentTarget. 4. document.getElementById('modal-root') без проверки на null. 5. Окно всегда смонтировано и скрыто стилем: форма внутри сохраняет старое состояние. Рисуйте {open && <Modal />}: при закрытии состояние сбросится, а фокус вернётся (раздел 5).

ЗАДАЧА 4.1

Проверь себя: порталы

средняя

Кнопка внутри окна, выведенного порталом в document.body, нажата. У компонента-родителя, из которого рисуется портал, есть onClick. Что будет?

  1. Родитель не узнает о клике: в DOM окно лежит отдельно
  2. Родительский onClick сработает: событие всплывает по дереву React
  3. Сработают только нативные обработчики
  4. React выбросит ошибку

Поэтому портал не отменяет stopPropagation, когда родителю клик в окне не нужен.

Что решает портал? Выберите два пункта.

  1. Обрезание окна родителем с overflow: hidden
  2. Фокус возвращается на кнопку сам
  3. Закрытие по Esc появляется само
  4. Перекрытие окна чужим z-index и transform у родителей

Портал отвечает только за место разметки в DOM. Фокус, Esc и aria вы добавляете сами (или берёте у <dialog> и готовых библиотек).

Зачем в обработчике клика по фону сравнивать event.target === event.currentTarget?

  1. Чтобы окно открывалось быстрее
  2. Чтобы запретить закрытие по Esc
  3. Чтобы клик внутри окна, всплывший к фону, не закрывал окно
  4. Чтобы избежать ошибки TypeScript

target — элемент, по которому кликнули, currentTarget — тот, у кого висит обработчик. Совпадают они только при клике ровно по фону.

05 Базовая доступность: фокус, Esc и aria

Не все пользователи работают мышью и смотрят на экран. Кто-то переключается клавишей Tab, кто-то слушает страницу экранным диктором (VoiceOver, NVDA, TalkBack), кто-то просто держит в руке чай и нажимает Esc, чтобы закрыть окно. Хорошая новость: базовая доступность — это пять привычек, и они делают форму удобнее для всех.

Привычка 1. У каждого поля есть подпись

Диктор читает «Имя, поле ввода» только если поле связано с <label>. Связь делает htmlFor + id или обёртка. В повторяющемся компоненте id берут из useId(), чтобы два поля не получили один id.

Привычка 2. Ошибка связана с полем

  • aria-invalid="true" у неверного поля: диктор скажет «недопустимое значение»;
  • aria-describedby="id-ошибки": диктор прочитает текст ошибки вместе с полем;
  • role="alert" у блока ошибки, который появляется после действия: диктор озвучит его сразу, без перехода на него. Для текста, который лежит на странице всегда, роль не нужна;
  • цвет — не единственный признак: рядом с красной рамкой есть текст.
const id = useId()
const errorId = `${id}-error`

<label htmlFor={id}>Имя</label>
<input
  id={id}
  aria-invalid={error ? true : undefined}
  aria-describedby={error ? errorId : undefined}
/>
{error && <p id={errorId} role="alert">{error}</p>}

Привычка 3. Окно объявляет себя диалогом

У панели окна пишут role="dialog", aria-modal="true" и aria-labelledby со ссылкой на заголовок окна. Тогда диктор говорит «Оформление заказа, диалог», а содержимое страницы под ним для него отключается.

Привычка 4. Фокус: внутрь, по кругу, обратно

  1. Внутрь. При открытии переведите фокус в окно (на панель с tabIndex={-1} или на первое поле). Иначе клавиатурный пользователь остаётся «позади» окна и жмёт Tab по невидимой странице.
  2. По кругу. Tab с последнего элемента окна ведёт на первый, Shift+Tab с первого — на последний (ловушка фокуса, focus trap). Современная альтернатива — атрибут inert на остальной странице: браузер сам не пускает фокус под окно.
  3. Обратно. При закрытии верните фокус на кнопку, которая окно открыла. Если кнопки уже нет (корзину очистили после заказа), отдайте фокус осмысленному месту, например полю поиска.

Привычка 5. Закрытие без мыши и без прокрутки фона

Esc закрывает окно, у окна есть видимая и озвученная кнопка «Закрыть» (aria-label, если на ней только «×»), а пока окно открыто, фон не прокручивается (document.body.style.overflow = 'hidden' и возврат при закрытии: это настоящая внешняя система, и тут эффект с очисткой уместен, как в уроке 5).

useEffect(() => {
  const opener =
    document.activeElement instanceof HTMLElement ? document.activeElement : null
  dialogRef.current?.focus()
  document.body.style.overflow = 'hidden'
  return () => {
    document.body.style.overflow = ''
    if (opener?.isConnected) {
      opener.focus()
    }
  }
}, [])

Пустой массив зависимостей здесь честный: эффект ничего реактивного не читает. Запоминать opener нужно в самом начале: потом activeElement уже будет внутри окна. Проверка isConnected — на случай, когда кнопки уже нет на странице.

TypeScript: ref на элемент

useRef<HTMLDivElement>(null) даёт ref, у которого current — элемент или null (в React 19 типы это отражают: RefObject<HTMLDivElement | null>). Для <dialog> тип HTMLDialogElement, для <form> — HTMLFormElement. Поиск внутри контейнера тоже типизируется: container.querySelectorAll<HTMLElement>(selector). Каждый раз, когда current может быть null, TypeScript заставит проверить это: dialogRef.current?.focus().

Аналогия из жизни

Модальное окно — отдельный столик в чойхоне, за который вас усадили. Пока вы за ним, вы не бегаете по залу (ловушка фокуса). Вы вошли — официант сразу подошёл именно к вам (фокус внутрь). Вы встали — вернулись на своё место, а не потерялись в зале (фокус обратно). И всегда можно просто сказать «спасибо, хватит» (Esc).

Типичные ошибки

1. Подпись-«placeholder»: после ввода её не видно, а диктор подпись не считает. 2. outline: none без замены: клавиатурный пользователь не видит, где фокус. 3. Кнопка «×» без aria-label: диктор читает «кнопка, умножение». 4. Окно открыто, а фокус остался на кнопке под ним: Tab уходит в фон. 5. При закрытии фокус пропал в начало страницы. 6. div с onClick вместо button: до него нельзя добраться клавишей Tab. 7. role="alert" у всех текстов подряд: диктор говорит без остановки.

06 ИИ-блок: схема Zod из требований и проверка доступности

Форма — территория, где агент работает быстро и ошибается тихо. Он легко пишет поля и схему, но часто путает версии библиотек, дублирует типы руками, забывает фокус и подписи, а в «форме оплаты» может потребовать номер карты. Две задачи, в которых агент особенно полезен: перевести требования в схему и проверить готовую форму на доступность. В обеих результат проверяете вы.

Формула промпта: контекст → задача → ограничения → формат → проверка

Для схемы агенту нужны точные правила: что обязательно, какие длины и форматы, какие тексты ошибок. Без них он придумает свои. Для проверки доступности нужен список критериев и просьба показать, что именно в коде не так, а не «всё хорошо».

Схема из требований

сделай схему zod для формы заказа
Контекст: проект Vite 8 + React 19 + TypeScript (strict), прочитай AGENTS.md. Установлены zod 4 и react-hook-form 7 с @hookform/resolvers. Форма оформления заказа в «Дастархоне». Задача: напиши src/orderSchema.ts со схемой orderSchema и типом OrderForm. Проверка доступности

проверь, нормальная ли у меня форма
Контекст: ниже код модального окна и формы заказа на React 19 + TypeScript (Modal.tsx, CheckoutForm.tsx, TextField.tsx). Пользователи работают с клавиатуры и экранными дикторами. Формат ответа: таблица «пункт списка → выполнено или нет → строка кода → исправление». Проверка: для каждого найденного замечания напиши, как проверить исправление клавиатурой за одну минуту.

Как проверять формы, написанные агентом

  1. Версии API. Нет ref={register} (RHF 6), нет yupResolver там, где договорились о Zod, нет message: и z.string().email() в Zod 4 без причины. Открывайте документацию версии, которая стоит в package.json.
  2. Тип из схемы. В коде z.infer, а не второй рукописный type. Нет any в onSubmit(data: any) и as OrderForm на данных.
  3. Каждое поле схемы есть в форме. Иначе форма молчит (раздел 3). Проверка: отправьте пустую форму, все ошибки должны быть видны.
  4. defaultValues заданы для всех полей, у form стоит noValidate, если проверяет схема.
  5. Лишние перерисовки. Нет watch() на всю форму без причины, нет состояния рядом с RHF, которое дублирует значения.
  6. Окно. Есть role="dialog", имя, Esc, фокус внутрь и обратно, портал в document.body; окно рисуется условно, а не прячется стилем.
  7. Безопасность. Валидация есть и на сервере; цену считает сервер, а не форма; текст ошибок выводится как обычный текст JSX, не через dangerouslySetInnerHTML; данные формы и пароль не пишутся в console.log и в localStorage; номера карт форма не собирает (платёж — через провайдера).
Типичные ошибки при работе с агентом

1. Принять схему без тестовых значений: правила «вроде бы такие» не проверены. 2. Просить «добавь валидацию» без списка правил: агент придумает минимальные длины и форматы по своему вкусу. 3. Поверить ответу «доступность в порядке» без проверки Tab и Esc: агент не видит экран. 4. Оставить в форме autoFocus везде: фокус прыгает. 5. Скопировать из ответа проверку «только на клиенте», где серверу «доверяют».

      typeof order?.phone === 'string' && /^\+992\d{9}$/.test(order.phone)

      order.name.trim().length >= 2 &&

      order.items.length > 0 &&

        (i) =>
          Number.isInteger(i?.itemId) && Number.isInteger(i?.qty) && i.qty > 0,
      )
    if (!validPhone || !validText || !validItems) {
      return send(400, { message: 'Проверьте имя, телефон, адрес и корзину' })
    }
    // цену считаем на сервере: клиенту верить нельзя
    let total = 0
    for (const { itemId, qty } of order.items) {
      const dish = menu.find((m) => m.id === itemId)
      if (!dish) {
        return send(400, { message: `Блюда №${itemId} нет в меню` })
      }
      const restaurant = restaurants.find((r) => r.id === dish.restaurantId)
      if (!restaurant?.open) {
        return send(400, {
          message: `${restaurant?.name ?? 'Ресторан'} сейчас закрыт`,
        })
      }
      total += dish.price * qty
    }
    return send(201, { id: nextOrderId++, total })
  }
