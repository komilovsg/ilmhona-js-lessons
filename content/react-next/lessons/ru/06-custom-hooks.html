01 Свой хук: функция, которая вызывает другие хуки

В уроке 5 вы написали эффект загрузки, эффект горячей клавиши и эффект прокрутки, и все три лежат в App. Компонент растёт: он и рисует интерфейс, и знает, как ходить в сеть, и подписывается на окно браузера. Следующий проект потребует той же загрузки, и вы скопируете эффект целиком. Копипаста логики с состоянием — главный повод для своего хука.

Свой хук (custom hook) — обычная функция, которая вызывает другие хуки (useState, useEffect, useRef, чужие хуки). Никакой новой возможности в React для этого нет, вы просто даёте логике имя и выносите её из компонента. У хука два признака:

  1. Имя начинается с use (useToggle, useFetch). Это не украшение: по префиксу линтер понимает, что внутри вызываются хуки, и применяет к функции правила хуков (урок 4).
  2. Внутри вызываются хуки. Функция formatPrice(n) без хуков — просто функция, ей не нужен префикс. А useToggle без единого хука внутри — ошибка проектирования: назовите её иначе.

Сравните «до» и «после» на самом простом примере. Два переключателя в одном компоненте повторяют одну и ту же пару «состояние + функция»:

function Filters() {
  const [openOnly, setOpenOnly] = useState(false)
  const [delivery, setDelivery] = useState(false)

  return (
    <div>
      <button onClick={() => setOpenOnly((v) => !v)}>Открытые: {String(openOnly)}</button>
      <button onClick={() => setDelivery((v) => !v)}>Доставка: {String(delivery)}</button>
    </div>
  )
}

import { useState } from 'react'

export function useToggle(initial = false) {
  const [on, setOn] = useState(initial)

  function toggle() {
    setOn((value) => !value)
  }

  return [on, toggle] as const
}

// в компоненте
const [openOnly, toggleOpenOnly] = useToggle()
const [delivery, toggleDelivery] = useToggle()

Каждый вызов хука получает своё состояние

Главное, что нужно понять про свои хуки: хук делит код, а не состояние. Две строки useToggle() в одном компоненте (или в двух разных) создают два независимых useState. Помните из урока 4: React хранит состояние компонента как список «ячеек» по порядку вызова хуков. Свой хук просто кладёт в этот список свои ячейки. Если нужно, чтобы два компонента видели одно и то же значение, состояние поднимают вверх (урок 4) или выносят в Context (урок 8), а не прячут в хук.

import { useState } from "react";

function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  function toggle() {
    setOn((value) => !value);
  }
  return [on, toggle];
}

export default function App() {
  const [a, toggleA] = useToggle(false);
  const [b, toggleB] = useToggle(true);
  return (
    <div>
      <button onClick={toggleA}>A: {String(a)}</button>
      <button onClick={toggleB}>B: {String(b)}</button>
    </div>
  );
}

Нажмите «A»: меняется только A. У каждого вызова свой useState, и начальные значения у них разные.

Что вернуть из хука: кортеж или объект

Если возвращаете два значения в «классическом» порядке (значение и функция), используйте кортеж и as const: тогда TypeScript выведет точный тип readonly [boolean, () => void], а вызывающий код сам даст имена при деструктуризации ([openOnly, toggleOpenOnly]), как у useState. Без as const тип получился бы массивом (boolean | (() => void))[], и деструктуризация дала бы бесполезный union. Если значений три и больше или они разной природы, возвращайте объект ({ state, retry }): имена видны сразу, порядок не важен. Именно так будет устроен useFetch в разделе 3.

Когда выносить, а когда нет

  • Выносите, если у логики есть состояние или эффект, и она нужна в двух местах (или компонент без неё стал бы заметно проще и читаемее).
  • Не выносите код «на всякий случай»: хук из одного вызова одного состояния без эффекта — лишний файл. Три похожие строки лучше преждевременной абстракции.
  • Не прячьте в хук то, что должно быть видно в компоненте: например, JSX. Хук возвращает данные и функции, а разметку рисуют компоненты.
  • Назовите по смыслу, а не по реализации: useDebounce, а не useTimeoutState.
Аналогия из жизни

Хук — как рецепт плова на карточке в чойхоне. Рецепт один и тот же у всех поваров, но казан у каждого повара свой: два повара готовят по одной карточке и получают два разных плова. Скопировать рецепт в другую кухню можно сколько угодно раз, а вот общий казан для двух кухонь — это уже «поднять состояние вверх».

Типичные ошибки

1. Назвать хук без use (toggle()): линтер не проверит внутри него правила хуков, а читателю непонятно, что это хук. 2. Вызвать хук в условии или после раннего return: в консоли Rendered more hooks than during the previous render, в линтере react-hooks(rules-of-hooks). 3. Ждать, что два компонента с одним и тем же хуком будут видеть одно состояние: оно у каждого своё. 4. Вернуть массив без as const и получить в деструктуризации union вместо значения и функции. 5. Сделать хук «на случай» — после первой же замены окажется, что он используется в одном месте.

ЗАДАЧА 1.1

Проверь себя: свои хуки

лёгкая

Два разных компонента вызывают useToggle(). Что произойдёт, когда один из них переключит значение?

  1. Значение изменится и во втором компоненте: хук общий
  2. Второй компонент ничего не заметит: у каждого вызова хука своё состояние
  3. React выдаст ошибку: хук нельзя вызывать из двух мест
  4. Оба компонента перерисуются, но значения останутся прежними

Хук делит только код. Состояние хранится в ячейках конкретного компонента, поэтому у каждого вызова оно своё. Общее состояние поднимают в родителя или кладут в Context.

Что из этого можно оформить как свой хук с именем useЧтоТо?

  1. Функцию formatPrice(n), которая превращает число в строку «45 сомони»
  2. Компонент Rating, который возвращает JSX
  3. Функцию, которая внутри вызывает useState и useEffect и возвращает значение для компонента
  4. Константу CUISINES со списком кухонь

Хук — это функция, которая вызывает другие хуки. Обычная функция без хуков хуком не является, а компонент возвращает JSX и называется с заглавной буквы.

Зачем писать return [on, toggle] as const вместо return [on, toggle]?

  1. Чтобы тип стал кортежем readonly [boolean, () => void], а не массивом union-значений
  2. Чтобы хук работал быстрее
  3. Чтобы массив нельзя было деструктурировать
  4. Это обязательное требование React

Без as const TypeScript выводит (boolean | (() => void))[], и после деструктуризации у on и toggle один и тот же union. С as const позиции получают свои типы.

02 TypeScript: дженерики на минимуме

Хуки useFetch и useLocalStorage работают с данными разных типов: рестораны, блюда, корзина. Если написать unknown, вызывающий код получит значение, с которым ничего нельзя делать. Если написать any, пропадёт проверка типов. Для таких случаев в TypeScript есть дженерики (generics): тип-параметр, который подставляется при использовании. Вы уже встречали их: useState<Cuisine | null>(null), Array<T> и ваш LoadState<T> из урока 5. Теперь научимся писать свои.

Функция с типом-параметром

Допустим, нужна функция «первый элемент массива». Для строк, чисел и ресторанов она одна и та же. Тип-параметр T пишут в угловых скобках после имени функции: это «переменная для типа», как параметр функции — переменная для значения.

function first<T>(items: T[]): T | undefined {
  return items[0]
}

const name = first(['Navruz', 'Rohat']) // T = string, тип name: string | undefined
const rating = first([4.8, 4.5]) // T = number
const none = first<string>([]) // T указан явно: пустой массив ничего не подсказывает

Обратите внимание на два способа задать T. Чаще всего TypeScript выводит его сам по аргументам (first(['Navruz', 'Rohat'])), и писать угловые скобки не нужно. Явный тип (first<string>([])) нужен там, где вывести не из чего: пустой массив, useState<User | null>(null), useLocalStorage<CartItem[]>(…).

Ограничение: T extends

Внутри функции с «голым» T про него ничего не известно, поэтому обращаться к полям нельзя. Нужен id? Ограничьте тип: T extends { id: number } означает «любой тип, у которого есть числовое поле id». Подойдут и Restaurant, и MenuItem, а строка не подойдёт:

function findById<T>(items: T[], id: number): T | undefined {
  return items.find((item) => item.id === id)
}

src/find.ts(2,38): error TS2339: Property 'id' does not exist on type 'T'.

function findById<T extends { id: number }>(items: T[], id: number): T | undefined {
  return items.find((item) => item.id === id)
}

findById(restaurants, 2) // Restaurant | undefined
findById(menu, 8) // MenuItem | undefined
findById(['Navruz'], 1) // ошибка: string не имеет поля id

Дженерик-тип и значение по умолчанию

Типы тоже бывают параметризованными. Вы уже писали LoadState<T>; вот ещё один популярный шаблон, «результат операции». Второй параметр E = string имеет значение по умолчанию: если его не указать, ошибкой будет строка.

type Result<T, E = string> =
  | { ok: true; value: T }
  | { ok: false; error: E }

function parsePrice(text: string): Result<number> {
  const n = Number(text)
  return Number.isNaN(n) ? { ok: false, error: 'цена не число' } : { ok: true, value: n }
}

const result = parsePrice('45')
if (result.ok) {
  console.log(result.value + 1) // здесь result.value: number
} else {
  console.log(result.error) // здесь result.error: string
}

Правило «на минимуме»

Дженерики легко превратить в головоломку. Для курса хватит четырёх приёмов: функция с <T>, ограничение extends, дженерик-тип (Result<T>, LoadState<T>) и явный тип в скобках, когда вывод не справился. Не заводите <T>, если тип в функции используется один раз и никуда не возвращается: хватит unknown или конкретного типа. И никогда не пишите <T = any>: это тот же any с лишним шагом (раздел 8).

Аналогия из жизни

Дженерик — это лепёшка с пустым местом под начинку. Форма теста одна, а начинку вы выбираете при заказе: мясо, тыква, картошка. extends — это условие «лепёшка с чем-нибудь, что можно запечь»: песок в начинку не положишь. А «неизвестная» начинка unknown — это запечатанный пакет: пока не откроете и не проверите, есть его нельзя.

Типичные ошибки

1. Обратиться к полю у «голого» T: TS2339: Property 'id' does not exist on type 'T'. Нужен extends. 2. Писать явный тип там, где TypeScript выводит его сам: first<string>(['a']) — шум. 3. Не указать тип там, где вывод не работает: useState(null) даёт тип null, а не «ресторан или null». 4. Привести результат JSON.parse к T через as T: компилятор замолчит, а данные могут оказаться чем угодно. Правильный путь в разделе 4: unknown и type guard. 5. Сделать всё дженериком: function show<T>(x: T) ничем не лучше unknown.

ЗАДАЧА 2.1

Проверь себя: дженерики

средняя

Для чего нужно ограничение T extends { id: number } в функции findById?

  1. Чтобы функция работала быстрее
  2. Чтобы внутри функции можно было читать item.id, а при вызове нельзя было передать массив без id
  3. Чтобы тип T нельзя было вывести автоматически
  4. Чтобы функция принимала только объект Restaurant

Ограничение задаёт минимальные требования: подойдёт любой тип с числовым id (рестораны, блюда), а внутри функции компилятор знает, что поле есть.

Когда нужно писать тип явно, как в useLocalStorage<CartItem[]>('cart', [], isCartItems)?

  1. Когда TypeScript не может вывести тип по аргументам: например, начальное значение [] или null
  2. Всегда, иначе код не скомпилируется
  3. Никогда: явный тип запрещён
  4. Только в файлах .tsx

Пустой массив ничего не говорит о типе элементов. В таких местах вывод не справляется, и тип в угловых скобках нужен. В остальных случаях лишние скобки — шум.

Что не так с function read<T>(text: string): T { return JSON.parse(text) as T }?

  1. Ничего, это хороший приём
  2. Нельзя использовать <T> в стрелочной функции
  3. Компилятор поверит, что внутри лежит T, хотя на самом деле там может быть что угодно: проверки нет
  4. Функция вернёт undefined

as T — это обещание без проверки. Безопасный вариант: читать значение как unknown и принимать функцию-проверку (type guard), которая подтверждает, что значение имеет тип T.

03 useFetch<T>: загрузка данных в своём хуке

В уроке 5 загрузка ресторанов жила прямо в App: состояние load, счётчик attempt, эффект с AbortController, функция retry. Это около 20 строк, которые понадобятся каждому экрану с данными (меню, заказы, профиль). Соберём их в один хук useFetch<T>: он принимает адрес и функцию проверки ответа, а возвращает состояние LoadState<T> и функцию «Повторить».

Сигнатура: что хук принимает и возвращает

Хук не знает, что именно он загружает, поэтому тип результата T ему нужен от вызывающего кода. Но писать as T нельзя (раздел 2): проверку данных хук получает аргументом, функцией parse. Её тип (data: unknown) => T одновременно сообщает TypeScript, чему равен T, так что угловые скобки при вызове не нужны:

function useFetch<T>(url: string, parse: (data: unknown) => T): {
  state: LoadState<T>
  retry: () => void
}

// T выводится из parseRestaurants: (data: unknown) => Restaurant[]
const { state, retry } = useFetch('/api/restaurants', parseRestaurants)

Загрузка: производное значение вместо setState в эффекте

В уроке 5 было правило: «загрузка» не выставляется внутри эффекта. Но что делать, когда адрес меняется (например, выбрали другой ресторан)? Новый запрос ушёл, а на экране ещё лежит ответ от старого. Хук решает это так: каждый ответ сохраняется вместе с ключом запроса (адрес и номер попытки). Если ключ сохранённого ответа не равен текущему, значит, ответ «чужой» или ещё не пришёл, и состояние — loading. Это вычисляется в рендере, а не хранится.

import { useCallback, useEffect, useState } from 'react'
import { errorMessage, fetchJson, isAbortError } from '../api'
import type { LoadState } from '../types'

type Result<T> = { key: string; state: LoadState<T> }

export function useFetch<T>(url: string, parse: (data: unknown) => T) {
  const [attempt, setAttempt] = useState(0)
  const [result, setResult] = useState<Result<T> | null>(null)
  const key = `${url}#${attempt}`

  useEffect(() => {
    const controller = new AbortController()
    fetchJson(url, parse, controller.signal)
      .then((data) => setResult({ key, state: { status: 'success', data } }))
      .catch((error: unknown) => {
        if (isAbortError(error)) return
        const state: LoadState<T> = {
          status: 'error',
          message: errorMessage(error),
        }
        setResult({ key, state })
      })
    return () => controller.abort()
  }, [url, parse, key])

  const retry = useCallback(() => setAttempt((n) => n + 1), [])

  // ответ относится к другому запросу или ещё не пришёл: показываем загрузку
  const state: LoadState<T> =
    result !== null && result.key === key
      ? result.state
      : { status: 'loading' }

  return { state, retry }
}

Разберите хук по частям, все они вам знакомы по уроку 5. Эффект синхронизируется с сетью: контроллер создаётся внутри, очистка вызывает abort(), AbortError молча игнорируется. Зависимости честные: адрес, функция проверки и ключ. «Повторить» — это увеличение attempt: ключ меняется, эффект перезапускается, а состояние само становится loading, потому что ключ ответа больше не совпадает. Функция retry обёрнута в useCallback: хук возвращает функцию наружу, и стабильная ссылка пригодится вызывающему коду (раздел 5).

Ловушка: функция проверки должна быть стабильной

parse входит в зависимости эффекта. Если передать стрелку прямо в вызов, она будет новой при каждом рендере (урок 5: функции из тела компонента всегда новые), и эффект начнёт перезапускаться снова и снова:

const { state } = useFetch('/api/restaurants', (data) => parseRestaurants(data))

Ответ приходит, состояние меняется, компонент рендерится, создаётся новая стрелка, эффект видит новую зависимость, отменяет запрос и отправляет новый. На экране всё выглядит нормально, а в Network запросы идут бесконечно. Мы проверили: за пять секунд такой вызов отправил 10 запросов вместо двух (два как раз из-за StrictMode). Решение простое: передавайте функцию, объявленную вне компонента (parseRestaurants лежит в api.ts). Линтер такую ошибку не покажет, поэтому правило стоит записать в AGENTS.md и проверять в ревью.

Аналогия из жизни

Ключ запроса — это номерок в гардеробе. Вы отдали куртку и получили номерок №17. Когда гардеробщик возвращается с курткой, он сверяет номерок: если №17, куртка ваша, а если в руках номерок прежнего посетителя, он не отдаст её вам, а скажет «ещё ищу». Пока нужной куртки нет, вы видите «загрузку», и никто не хранит отдельный флаг «ищем».

Типичные ошибки

1. Стрелка в аргументе parse: запросы идут по кругу. 2. as T после response.json() вместо проверки: сервер может прислать что угодно, а компилятор не заметит. 3. Три отдельных состояния data, loading, error вместо union: возможны невозможные комбинации (загрузка закончилась, а ни данных, ни ошибки нет). 4. setLoad({ status: 'loading' }) в эффекте при смене адреса: лишний рендер и предупреждение set-state-in-effect. 5. Забытый abort(): при быстрой смене адреса на экране может оказаться ответ на старый запрос.

Проверь себя: хук загрузки

средняя

Почему useFetch принимает функцию parse, а не просто возвращает response.json() как T?

  1. Чтобы запрос выполнялся быстрее
  2. Потому что fetch не умеет читать JSON
  3. Чтобы данные проверялись во время работы программы: тип T сам по себе существует только при компиляции
  4. Чтобы хук нельзя было вызвать с неправильным адресом

Типы TypeScript стираются при сборке. Приведение as T ничего не проверяет, а функция parse реально смотрит на поля и выбрасывает ошибку, если форма ответа не та.

Что случится, если вызвать useFetch(url, (data) => parseRestaurants(data)) со стрелкой прямо в компоненте?

  1. Ничего: стрелка и объявленная функция равнозначны
  2. Эффект будет перезапускаться после каждого рендера, и запросы пойдут по кругу
  3. TypeScript выдаст ошибку компиляции
  4. Хук вернёт loading навсегда без запросов

Стрелка создаётся заново при каждом рендере, а parse входит в зависимости эффекта. Каждая новая ссылка отменяет запрос и запускает следующий. Функцию нужно вынести за компонент.

  1. Ответ хранится вместе с ключом запроса (адрес и номер попытки)
  2. Хук перезагружает страницу
  3. Состояние loading записывается в эффект первой строкой
  4. Если ключ сохранённого ответа не равен текущему, состояние вычисляется как loading

04 useLocalStorage<T> и useDebounce<T>

Ещё два хука из плана урока решают две частые задачи. Первая: сохранить значение в браузере, чтобы оно пережило перезагрузку (корзина, выбранная тема, последний фильтр). Вторая: не реагировать на каждое нажатие клавиши, а подождать, пока пользователь закончит вводить.

localStorage: что нужно знать до хука

localStorage — маленькое хранилище «ключ → строка» в браузере: 5–10 МБ на сайт, данные остаются после закрытия вкладки. Из этого следуют четыре правила для хука:

  1. Хранятся только строки. Объекты и массивы превращают в строку через JSON.stringify и читают обратно через JSON.parse.
  2. Прочитанному верить нельзя. Пользователь или другая версия вашего сайта могла записать что угодно. JSON.parse возвращает any: принимайте его как unknown и проверяйте type guard (урок 5).
  3. Доступ может сломаться. В приватном режиме, при выключенных данных сайта или при переполнении квоты getItem и setItem бросают исключение. Оба вызова оборачивают в try/catch, а приложение продолжает работать без сохранения.
  4. Не кладите секреты. Любой скрипт на странице читает хранилище: токены доступа и персональные данные в нём хранить небезопасно.

useLocalStorage<T>

Хук ведёт себя как useState, но начальное значение берёт из хранилища, а каждое изменение записывает обратно. Чтение выполняется один раз, при создании состояния: для этого в useState передают функцию (ленивая инициализация), а не результат вызова: тогда localStorage читается один раз, а не при каждом рендере. Запись — настоящий эффект: синхронизация с внешней системой, браузерным хранилищем.

import { useEffect, useState, type Dispatch, type SetStateAction } from 'react'

export function useLocalStorage<T>(
  key: string,
  initialValue: T,
  isValid: (value: unknown) => value is T,
): [T, Dispatch<SetStateAction<T>>] {
  const [value, setValue] = useState<T>(() => {
    try {
      const raw = localStorage.getItem(key)
      if (raw === null) return initialValue
      const parsed: unknown = JSON.parse(raw)
      return isValid(parsed) ? parsed : initialValue
    } catch {
      return initialValue
    }
  })

  useEffect(() => {
    try {
      localStorage.setItem(key, JSON.stringify(value))
    } catch {
      // квота исчерпана или приватный режим: работаем без сохранения
    }
  }, [key, value])

  return [value, setValue]
}

Три детали типов. isValid: (value: unknown) => value is T — type guard как параметр: внутри хука T нигде не приводится, а подтверждается проверкой. Dispatch<SetStateAction<T>> — тип сеттера useState: он принимает и значение, и функцию «из предыдущего в следующее», поэтому вызывающий код работает с хуком так же, как с useState. Явный тип при вызове: useLocalStorage<CartItem[]>('cart', [], isCartItems). Мы проверили, что без угловых скобок TypeScript пытается вывести T из начального значения и ругается на несовместимость с guard.

Там, где код выполняется не в браузере (например, при серверном рендеринге в Next.js), localStorage не существует и выбрасывается ReferenceError: try/catch в хуке защищает и от этого случая. Ещё одно ограничение: ключ key считается постоянным, потому что чтение выполняется один раз, а смена ключа заново ничего не прочитает. Синхронизация между вкладками (событие storage) здесь не реализована.

useDebounce<T>

Дебаунс (debounce) — «подождать тишины». Пока значение меняется чаще, чем раз в N миллисекунд, ничего не происходит, а через N мс после последнего изменения срабатывает действие. Для хука это значение с задержкой: пользователь набирает «nav», в query попадает каждая буква сразу, а в debouncedQuery только «nav» через 250 мс после последней нажатой клавиши. Реализация — это эффект с таймером и очисткой (урок 5): каждое новое значение отменяет таймер предыдущего.

import { useEffect, useState } from 'react'

export function useDebounce<T>(value: T, delayMs: number): T {
  const [debounced, setDebounced] = useState(value)

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delayMs)
    return () => clearTimeout(id)
  }, [value, delayMs])

  return debounced
}

Зачем это в проекте, где всего шесть ресторанов? Честный ответ: сегодня незачем, фильтрация мгновенная. Хук нужен, когда каждое изменение запрашивает сервер (поиск по API, урок 10) или запускает тяжёлый пересчёт. Сейчас мы тренируем приём на реальном поле поиска, а в уроке 10 он пригодится по назначению. Не путайте с useDeferredValue: этот встроенный хук откладывает отрисовку тяжёлого списка и не имеет таймера в миллисекундах, а значит, не годится для сокращения запросов к серверу.

Аналогия из жизни

Дебаунс — как официант в чойхоне, который стоит у стола, пока вы перечисляете заказ: «плов, и ещё лагман... и чай... и самбусу». Он не бежит на кухню после каждого слова, а ждёт паузы и только тогда уходит с заказом. А localStorage — блокнот на стойке: переживёт вашу отлучку, но любой, кто подходит к стойке, может его прочитать и дописать, поэтому паспорт туда не кладут.

Типичные ошибки

1. JSON.parse(raw) as T без проверки: после обновления сайта в хранилище остаётся старый формат, и приложение падает на .map is not a function. 2. localStorage.getItem без try/catch: в приватном режиме и на сервере страница белеет. 3. Читать хранилище прямо в теле компонента: чтение выполняется при каждом рендере. Нужна ленивая инициализация useState(() => …). 4. Забыть clearTimeout в дебаунсе: таймеры копятся, и «старое» значение прилетает после нового. 5. Хранить в localStorage токены и пароли. 6. Ждать, что дебаунс ускорит рендер: он отложит обновление, а сам рендер дешевле не станет.

ЗАДАЧА 4.1

Проверь себя: хранилище и дебаунс

средняя

Зачем в useLocalStorage чтение хранилища передаётся в useState функцией useState(() => …), а не значением?

  1. Чтобы код выглядел короче
  2. Чтобы чтение и разбор JSON выполнялись один раз при создании состояния, а не при каждом рендере
  3. Чтобы обойти ошибку QuotaExceededError
  4. Чтобы значение можно было менять напрямую

Ленивая инициализация вызывает функцию только при первом рендере. Без неё getItem и JSON.parse работали бы после каждого нажатия клавиши, хотя их результат используется один раз.

В хранилище лежит строка {"bad":1}, а хук ждёт массив CartItem[]. Что должно произойти?

  1. Приложение упадёт: данные неверные
  2. Хук вернёт эти данные как CartItem[]
  3. Проверка isValid вернёт false, хук возьмёт начальное значение
  4. Хук очистит весь localStorage

Данные из хранилища недоверенные. Type guard проверяет их форму, и при несовпадении хук откатывается к начальному значению. Приложение продолжает работать.

Что делает clearTimeout(id) в очистке эффекта дебаунса?

  1. Отменяет таймер предыдущего значения, чтобы сработал только таймер последнего
  2. Ускоряет таймер
  3. Удаляет значение из состояния
  4. Ничего: таймер и так отменится сам

05 Производительность: memo, useMemo и useCallback

В уроке 3 вы узнали: когда состояние компонента меняется, React заново вызывает этот компонент и всех его потомков, даже если их props остались прежними. Обычно это дёшево, и оптимизировать нечего. Но бывает, что дочерний компонент тяжёлый (шестьсот карточек ресторанов, большая таблица), а родитель перерисовывается по несвязанной причине: клик «В корзину» не должен пересчитывать каталог. Для таких случаев есть три инструмента.

Прежде чем их брать, пройдите три шага в порядке от дешёвого к дорогому:

  1. Поправьте структуру. Опустите состояние ниже, в маленький компонент, которому оно нужно. Передавайте тяжёлую часть через children: родитель с состоянием перерисуется, а готовый элемент из children React переиспользует (урок 3). Часто этого достаточно.
  2. Измерьте. Откройте Profiler (раздел 6): сколько миллисекунд стоит рендер и кто перерисовался без причины. Если лишней работы нет или она занимает доли миллисекунды, остановитесь.
  3. Мемоизируйте точечно и измерьте снова. Мемоизация — это кэш, а у кэша есть цена: код сложнее, зависимости надо вести честно, а неверная зависимость даёт устаревшие данные.

memo: пропустить рендер, если props те же

memo(Component) оборачивает компонент так: когда родитель перерисовался, React сравнивает новые props с прежними по очереди через Object.is (поверхностное сравнение). Если все равны, компонент пропускается вместе со всем поддеревом. Сравнение идёт по ссылке, а не по содержимому (урок 5): число 3 равно 3, а два объекта {} всегда разные.

import { memo } from 'react'

function RestaurantList({ restaurants, onSelect }: RestaurantListProps) {
  // …
}

export default memo(RestaurantList)

Теперь главное: новый массив, объект или функция в теле родителя — это новая ссылка при каждом рендере. Если передать такое значение в memo-компонент, сравнение не пройдёт и мемоизация не сработает. Поэтому memo почти никогда не бывает одна: ей нужны стабильные ссылки.

useMemo: запомнить результат вычисления

useMemo(() => вычисление, [зависимости]) хранит результат между рендерами и пересчитывает его, только когда изменилась хотя бы одна зависимость (сравнение тоже через Object.is). Он нужен в трёх случаях: вычисление действительно дорогое (в консоли console.time показывает 1 мс и больше за действие), результат передаётся в memo-компонент как prop (нужна стабильная ссылка), или результат сам является зависимостью другого хука.

const visible = useMemo(
  () =>
    restaurants.filter(
      (r) =>
        (cuisine === null || r.cuisine === cuisine) &&
        r.name.toLowerCase().includes(debouncedQuery.toLowerCase()),
    ),
  [restaurants, cuisine, debouncedQuery],
)

Вычисление внутри useMemo должно быть чистым: React в dev-режиме StrictMode вызывает его дважды. Кэш — подсказка, а не гарантия: React может его выбросить, поэтому код должен работать и без него (если значение нужно сохранить обязательно, это useState или useRef).

useCallback: запомнить функцию

useCallback(fn, [зависимости]) то же самое для функций: возвращает ту же функцию, пока зависимости не изменились. Это useMemo(() => fn, deps) в сокращённой записи. Документация React называет три случая: функция уходит в memo-компонент, функция — зависимость другого хука (например, эффекта) или вы пишете свой хук, который возвращает функции, чтобы вызывающий код мог оптимизироваться (так сделан retry в useFetch).

const handleSelect = useCallback((id: number) => {
  setSelectedId(id)
}, []) // setSelectedId — сеттер useState: ссылка на него стабильна и в зависимости не нужна

Хорошая новость: сеттер useState и dispatch редьюсера уже стабильны. Передавая onSelect={setSelectedId} напрямую, вы получаете стабильную ссылку без всякого useCallback. Стрелка-обёртка onSelect={(id) => setSelectedId(id)} разрушает стабильность: вы в практике увидите это в Profiler.

Три правила мемоизации

  • Зависимости честные. Линтер exhaustive-deps проверяет их так же, как у useEffect. Пропущенная зависимость даёт устаревшее значение: хуже, чем лишний рендер.
  • Один слабый узел ломает цепочку. Если из трёх props два стабильных, а один новый, memo не сработает. Мемоизировать нужно всё, что идёт в проп, или передавать примитивы.
  • Не ставьте везде. useMemo вокруг дешёвой операции (сложение двух чисел) стоит дороже самой операции: React хранит значение и сравнивает зависимости.
Аналогия из жизни

Мемоизация — как заготовка плова на целый день в чойхоне. Если гостей много и заказ повторяется, заготовка экономит часы. Но для одного гостя, который заказал чай, готовить заготовку глупо: уйдёт больше сил, чем сэкономите. И заготовка портится: если забыли поменять сырьё (пропущенная зависимость), гости получат вчерашний плов.

Типичные ошибки

1. memo без стабильных props: компонент всё равно рендерится, а код усложнился. 2. useCallback для функции, которая уходит в обычный (не memo) компонент или onClick тега: смысла нет. 3. Зависимости с пропусками или комментарий «disable lint»: устаревшее значение. 4. Объект или массив в useMemo, который создаётся из нового объекта в зависимостях: кэш сбрасывается каждый рендер. В Oxlint это видно по предупреждению: React hook useMemo depends on `restaurants`, which changes every render. 5. Мутировать результат useMemo: он общий для всех рендеров. 6. Оптимизировать без измерения: вы не знаете, помогло или повредило.

  4. onSelect={handleSelect}, где const handleSelect = useCallback((next: number) => setId(next), [])

Стрелка и function-выражение в теле компонента создаются заново при каждом рендере. Стабильны сеттер useState и функция из useCallback с честными зависимостями.

06 React DevTools Profiler: измеряем, а не гадаем

Профайлер отвечает на три вопроса: что перерисовалось, сколько это заняло и почему. Вы установили расширение React DevTools в уроке 1, а в уроке 5 смотрели вкладку Components. Теперь откройте вкладку Profiler.

Как записать сессию

  1. Откройте страницу приложения, DevTools (F12) и вкладку Profiler.
  2. Нажмите круглую кнопку записи (Start profiling), выполните одно действие (например, нажмите «В корзину»), нажмите «Stop». Если за время записи не было ни одного рендера, профайлеру нечего показать.
  3. Вверху отображается столбчатая диаграмма коммитов: каждый столбик — один коммит (урок 3: триггер, рендер, коммит). Высокие жёлтые столбики дольше синих. Выбирайте столбики стрелками или кликом.

  5. Серый цвет в Flamegraph означает, что компонент не рендерился в этом коммите. Именно серый вы хотите видеть у тяжёлых частей страницы при несвязанных действиях.

«Почему перерисовался»

Включите в настройках Profiler (значок шестерёнки) опцию Record why each component rendered while profiling («записывать, почему каждый компонент перерисовался»). После записи выберите компонент: в боковой панели появится причина. Типичные формулировки: «The parent component rendered» (родитель перерисовался), «Props changed» с перечнем изменившихся props, «State changed», «Hooks changed». Это ключ к мемоизации: если у RestaurantList причина «Props changed: restaurants», значит, memo стоит, но проп нестабилен; если «The parent component rendered», значит, memo нет вообще.

Ещё один быстрый способ увидеть лишние рендеры: на вкладке Components в настройках включите Highlight updates when components render. Компоненты, которые рендерятся, на странице вспыхивают рамкой.

07 React Compiler: автоматическая мемоизация

Ручная мемоизация утомляет: нужно расставить memo, useMemo, useCallback, вести зависимости и не забыть ни одной ссылки. React Compiler — отдельный инструмент сборки (плагин Babel), который делает это сам. Версия 1.0 вышла 7 октября 2025 года. Во время сборки он анализирует ваш компонент и добавляет кэширование значений и JSX-элементов с тонкой детализацией: если входные значения для куска разметки не менялись, React переиспользует готовый элемент и не заходит в его поддерево. Документация React говорит, что в большинстве случаев React.memo, useMemo и useCallback с компилятором не нужны.

Что нужно компилятору от вашего кода

Компилятор работает только с кодом, который следует «Правилам React»: компоненты и хуки чистые, состояние и props не мутируются, хуки вызываются на верхнем уровне. Это те самые правила, которые вы изучали в уроках 3–5. Если компонент нарушает правила, компилятор пропускает его и оставляет как есть, не ломая. Вот почему чистый код окупается дважды: меньше багов сегодня и бесплатная оптимизация завтра.

Что компилятор не отменяет

  • Структуру и измерения. Опущенное состояние, children и Profiler остаются главными инструментами.
  • Эффекты. Компилятор не решает, нужен ли useEffect: лишние эффекты (урок 5) остаются вашей задачей.
  • Ручную мемоизацию там, где нужна гарантия ссылки. Если значение — зависимость эффекта, компилятор может не заметить вашу логику; существующие useMemo и useCallback он сохраняет и учитывает.
  • Библиотеки, которые не дружат с мемоизацией. Например, функция watch() из React Hook Form (урок 7) хранит скрытое изменяемое состояние. Правило react-hooks/incompatible-library предупреждает о таких случаях, а сам компилятор пропускает такие компоненты. Для формы рекомендуют useWatch.
  • Локальное отключение. Директива 'use no memo' первой строкой функции исключает её из оптимизации, пока вы разбираетесь с проблемой.

Поэтому в основном проекте курса мы не включаем компилятор постоянно: в уроке 7 появятся формы на React Hook Form, и осознанное решение лучше случайной оптимизации. В практике вы включите его на отдельной ветке exp/compiler, измерите результат и вернётесь к основной ветке. Решение, оставлять ли компилятор в своём проекте, за вами: вы будете знать, как он работает и чем отличается от ручной мемоизации.

08 ИИ-блок: вынести логику в хук и проверить по Profiler

Просьба «вынеси логику загрузки в хук» кажется безобидной, но именно на хуках агенты чаще всего пишут код, который работает на демо и ломается в жизни. Вот типичный ответ на такую просьбу:

export function useFetch<T = any>(url: string, options: RequestInit = {}) {
  const [data, setData] = useState<T | null>(null)
  const [loading, setLoading] = useState(true)
  const [error, setError] = useState<any>(null)

  useEffect(() => {
    setLoading(true)
    fetch(url, options)
      .then((res) => res.json())
      .then((json) => setData(json as T))
      .catch((e) => setError(e))
      .finally(() => setLoading(false))
  }, [url, options])

  return { data, loading, error }
}

Здесь собрано почти всё, о чём шла речь в уроке: T = any и error: any отключают проверку типов; options = {} — новый объект при каждом вызове, он в зависимостях, и запросы идут по кругу (раздел 3); нет проверки response.ok; json as T — обещание без проверки; нет AbortController, значит возможна гонка запросов; три отдельных состояния допускают невозможные комбинации; setLoading(true) стоит в эффекте. Хороший промпт запрещает эти дефекты заранее и просит доказательство.

Формула промпта: контекст → задача → ограничения → формат → проверка

Для хуков важны ограничения на типы и ссылки: что нельзя принимать как any, какие значения должны быть стабильными, чем проверять результат. И просьба о примере использования заставляет агента показать, как хук работает в вызывающем коде.

Как проверять хуки, написанные агентом

  1. Имя и правила. Начинается с use, внутри есть хук, вызовы на верхнем уровне. Линтер react-hooks/rules-of-hooks молчит.
  2. Типы. Нет any, <T = any>, as T и @ts-ignore. Данные снаружи (сеть, localStorage) приходят как unknown и проходят type guard. Угловые скобки нужны только там, где вывод не справляется.
  3. Зависимости и ссылки. Нет объектов и функций из тела хука (или аргументов по умолчанию вроде options = {}) в зависимостях эффекта. Аргументы-функции документированы как «должны быть стабильными».
  4. Эффекты. У каждого эффекта есть внешняя система (сеть, хранилище, таймер) и очистка. Нет setState «пересчёта» производных данных.
  5. Состояние. Не три флага loading/error/data, а union. Нет невозможных комбинаций.
  6. Мемоизация. Если агент добавил useMemo или useCallback, спросите: где замер, какой компонент в memo получает это значение? Мемоизация «на всякий случай» — шум. Проверьте по Profiler: до и после, «Why did this render».
  7. Безопасность. В localStorage нет токенов и паролей, чтение и запись в try/catch, нет ключей API в клиентском коде, текст с сервера выводится как текст, а не как HTML.
Типичные ошибки при работе с агентом

1. Принять хук с any потому, что «компилируется»: ошибки откроются на проверке, а не в редакторе. 2. Просить «оптимизируй» без цели: агент расставит useMemo и useCallback везде, а код станет длиннее. Просите сначала назвать узкое место по данным Profiler. 3. Не просить пример использования: без него не видно, что хук неудобен или нестабилен. 4. Не проверить Network: бесконечные запросы не видны на экране. 5. Принять «исправление» гонки, которое просто выключает StrictMode.

import { errorMessage, fetchJson, isAbortError } from '../api'
import type { LoadState } from '../types'

type Result<T> = { key: string; state: LoadState<T> }

export function useFetch<T>(url: string, parse: (data: unknown) => T) {
  const [attempt, setAttempt] = useState(0)
  const [result, setResult] = useState<Result<T> | null>(null)
  const key = `${url}#${attempt}`

  useEffect(() => {
    const controller = new AbortController()
    fetchJson(url, parse, controller.signal)
      .then((data) => setResult({ key, state: { status: 'success', data } }))
      .catch((error: unknown) => {
        if (isAbortError(error)) return
        const state: LoadState<T> = {
          status: 'error',
          message: errorMessage(error),
        }
        setResult({ key, state })
      })
    return () => controller.abort()
  }, [url, parse, key])

  const retry = useCallback(() => setAttempt((n) => n + 1), [])

  // ответ относится к другому запросу или ещё не пришёл: показываем загрузку
  const state: LoadState<T> =
    result !== null && result.key === key ? result.state : { status: 'loading' }

  return { state, retry }
}

    import { useEffect, useState, type Dispatch, type SetStateAction } from 'react'

export function useLocalStorage<T>(
  key: string,
  initialValue: T,
  isValid: (value: unknown) => value is T,
): [T, Dispatch<SetStateAction<T>>] {
  const [value, setValue] = useState<T>(() => {
    try {
      const raw = localStorage.getItem(key)
      if (raw === null) return initialValue
      const parsed: unknown = JSON.parse(raw)
      return isValid(parsed) ? parsed : initialValue
    } catch {
      return initialValue
    }
  })

  useEffect(() => {
    try {
      localStorage.setItem(key, JSON.stringify(value))
    } catch {
      // квота исчерпана или приватный режим: работаем без сохранения
    }
  }, [key, value])

  return [value, setValue]
}

function isCartItem(value: unknown): value is CartItem {
  if (!isRecord(value) || !isRecord(value.item)) return false
  const { item, qty } = value
  return (
    typeof qty === 'number' &&
    typeof item.id === 'number' &&
    typeof item.restaurantId === 'number' &&
    typeof item.title === 'string' &&
    typeof item.price === 'number'
  )
}

}
