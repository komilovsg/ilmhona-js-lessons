01 Зачем нужны типы и что такое TypeScript

JavaScript не следит за тем, что вы кладёте в переменную. Строка, число, undefined — ему всё равно, пока код не выполнится. Ошибка всплывёт у пользователя, в самый неудобный момент. Запустите блок:

const price = "45";          // цена пришла строкой, например из поля формы
const delivery = 10;
console.log("К оплате:", price + delivery);   // ожидали 55

const restaurant = { name: "Navruz" };
console.log(restaurant.adress.toUpperCase()); // опечатка в adress

Первая строка выводит 4510 вместо 55: JavaScript склеил строку с числом. Вторая падает с TypeError, но только в момент запуска. TypeScript — это тот же JavaScript плюс типы: пометки о том, какие значения допустимы. Он читает код, не запуская его, и подсвечивает такие места красным ещё в редакторе.

Теперь тот же код с типами. Нажмите «Запустить»: вы увидите ошибки компилятора до выполнения кода.

const price: number = "45";
const delivery: number = 10;
console.log("К оплате:", price + delivery);

const restaurant = { name: "Navruz" };
console.log(restaurant.adress);

Компилятор сообщит о двух ошибках: Type 'string' is not assignable to type 'number'. (TS2322) и Property 'adress' does not exist on type '{ name: string; }'. (TS2339). Читать их нужно так: «строку нельзя положить туда, где ожидается число» и «у этого объекта нет поля adress». Англоязычные тексты ошибок — не проблема: в них повторяются одни и те же слова, и скоро вы узнаете их с первого взгляда.

Типы живут только до запуска

Браузер не понимает TypeScript. Перед запуском типы вырезаются, и остаётся обычный JavaScript. Поэтому типы ничего не стоят пользователю: они помогают вам писать код. А ещё они работают как документация: по типу функции сразу видно, что ей передать и что она вернёт.

Ролик на английском, включите субтитры (2 минуты): что такое TypeScript и зачем он нужен. Ролик 2022 года, он объясняет идею; команды и настройки берите из этого урока.

Аналогия из жизни

Типы — как проверка на входе в аэропорт. В зале ожидания шумно, но по дороге к самолёту у каждого проверяют паспорт и билет. Ошибка найдена в аэропорту, а не в воздухе. JavaScript без типов пускает всех, а проблему замечает, когда самолёт уже летит.

Типичные заблуждения

1. «TypeScript — отдельный язык, который заменяет JavaScript». Нет, это надстройка: любой JavaScript — уже корректный TypeScript. 2. «Типы проверяются в браузере у пользователя». Нет, только при разработке и сборке. 3. «Если типы сошлись, багов нет». Типы ловят класс ошибок про формы данных, но не логические: цену можно умножить на неверное число и получить правильный по типу, но неверный по смыслу результат. 4. «Типы замедляют работу». На скорость приложения они не влияют, их нет в итоговом коде.

ЗАДАЧА 1.1

Проверь себя: что делают типы

лёгкая

Когда TypeScript сообщает об ошибке типа?

  1. Когда пользователь нажимает кнопку в браузере
  2. Только при деплое на хостинг
  3. Ещё до запуска: в редакторе и при проверке tsc, по тексту кода
  4. Когда сервер возвращает ответ

Компилятор читает код, не выполняя его. Поэтому ошибка видна в момент набора, а не у пользователя.

Что происходит с типами, когда Vite собирает приложение?

  1. Они превращаются в проверки, которые работают в браузере
  2. Они вырезаются, в браузер уходит обычный JavaScript
  3. Они отправляются на сервер
  4. Браузер сам проверяет типы при загрузке страницы

Типы нужны разработчику, не пользователю. Данные, которые приходят во время работы (например, из формы), типы сами не проверят: для этого нужен код.

02 Базовые типы и вывод типов

Типы, которые нужны каждый день: string (строка), number (любое число, целое и дробное), boolean (true/false). Тип пишется после имени и двоеточия: const name: string = "Navruz".

Вывод типов: чаще всего тип писать не нужно

Если вы сразу присваиваете значение, TypeScript сам определяет тип. Это называется выводом типов (type inference). Писать тип вручную в таких местах — лишний шум.

let city = "Душанбе";    // TypeScript решил: city — string
city = "Худжанд";        // можно: снова строка
city = 5;                // ошибка: число в string-переменную

const rating = 4.8;      // number
const isOpen = true;     // boolean
console.log(city, rating, isOpen);

У let и const вывод немного разный. let city = "Душанбе" получает тип string, потому что значение можно менять. А const city = "Душанбе" получает точный тип "Душанбе" (литерал): значение никогда не изменится. В разделе 4 вы увидите, зачем это нужно.

Когда тип пишут руками

  • Параметры функций: TypeScript не знает, что вы передадите, поэтому параметры нужно описывать всегда (раздел 6).
  • Данные, которые пришли «снаружи»: ответ API, поле формы. Их форму вы описываете сами (раздел 3).
  • Пустые значения: пустой массив [] и значение null несут мало информации, поэтому тип указывают явно.

Массивы

Тип массива — тип элемента и квадратные скобки: number[] (массив чисел), string[] (массив строк). Если вы положите в такой массив элемент другого типа, будет ошибка. Методы map, filter, find знают тип элементов сами: в prices.map((p) => p * 2) параметр p — число, типизировать его не нужно.

const cuisines: string[] = ["плов", "шашлык"];
cuisines.push("самбуса");       // можно

const prices: number[] = [45, 8, 12];
const doubled = prices.map((p) => p * 2);   // p — number, doubled — number[]
console.log(cuisines.length, doubled);
Тип any: запрещён в курсе

any означает «любое значение»: компилятор перестаёт проверять эту переменную. Он выключает защиту, ради которой мы подключили TypeScript, и «заражает» код: всё, что вычислено из any, тоже становится any. Мы не пишем any ни в учебных примерах, ни в проекте. Если не получается подобрать тип, это повод спросить: «что именно приходит сюда?», а не сдаться.

03 Объекты: type, interface, необязательные поля

Данные в приложении — это объекты: ресторан, блюдо, позиция корзины. Форму объекта описывают именем типа. Так он пишется один раз и используется везде.

type Restaurant = {
  id: number;
  name: string;
  rating: number;
  open: boolean;
  address?: string;        // ? — поле необязательное
  readonly createdAt: number;   // readonly — после создания менять нельзя
};

const navruz: Restaurant = { id: 1, name: "Navruz", rating: 4.8, open: true, createdAt: 2024 };
console.log(navruz.name, navruz.address);   // address может быть undefined
navruz.rating = 4.9;                        // можно
navruz.createdAt = 2025;                    // ошибка: readonly

Что здесь важно:

  • Поле address?: string необязательное: его можно не указывать, а его тип — string | undefined. Читая такое поле, вы обязаны учесть, что значения может не быть (раздел 5).
  • readonly запрещает менять поле после создания. Это защита от случайных правок.
  • Лишнее поле или поле с опечаткой в литерале объекта тоже ошибка: { name: "A", nmae: "B" } компилятор не пропустит.
  • Объект, у которого поля вложены, описывается так же: type CartItem = { item: MenuItem; qty: number }.

interface и type: что выбрать

Описать форму объекта можно двумя способами: type и interface. Для объектов они почти равны:

interface Dish {
  id: number;
  title: string;
  price: number;
}

interface Drink extends Dish {   // Drink получает все поля Dish и добавляет своё
  volumeMl: number;
}

const tea: Drink = { id: 7, title: "Чай", price: 8, volumeMl: 300 };
console.log(tea.title, tea.volumeMl);

Правило курса: всегда type. Он умеет всё, что нужно для props и данных, включая union, а один способ проще держать в голове. interface вы будете встречать в чужом коде и в документации библиотек: понимать его надо, использовать необязательно.

Аналогия из жизни

Тип объекта — это бланк заказа в чойхоне: «блюдо (обязательно), количество (обязательно), пожелания (необязательно)». Заполнить бланк неправильно (без блюда, с «количеством» из слов) официант не примет. А readonly — штамп «подтверждено»: после него заказ править нельзя.

Типичные ошибки

1. Писать name?: string «на всякий случай»: тогда везде придётся проверять, есть ли имя. Делайте поле необязательным только если данные реально бывают без него. 2. Описывать форму объекта в каждом файле заново: тип пишут один раз в types.ts и импортируют. 3. Ставить точку с запятой между полями в одних местах и запятую в других: в объектных типах работают оба варианта, выберите один (в проекте Prettier приведёт всё к одному виду). 4. Типы в имени: IRestaurant, TRestaurant — устаревшая привычка, мы пишем просто Restaurant.

Проверь себя: type и interface

средняя

Что умеет type, но не умеет interface?

  1. Описывать объект с полями
  2. Делать поле необязательным
  3. Описывать union, например "new" | "done"
  4. Содержать вложенные объекты

  4. any

Знак вопроса делает поле необязательным, и при чтении TypeScript заставит учесть undefined.

04 Union, literal-типы и as const

Часто значение может быть не «любой строкой», а одним из нескольких вариантов: статус заказа, кухня, размер порции. Для этого у TypeScript есть union (объединение) и literal-типы (точные значения).

type OrderStatus = "new" | "cooking" | "delivering" | "done";   // только эти 4 строки

let status: OrderStatus = "new";
status = "cooking";        // можно
status = "ready";          // ошибка: такого варианта нет

type Id = number | string;  // union из типов: число или строка
const id: Id = 42;
console.log(status, id);

Такой тип лучше, чем просто string: опечатка "cookng" становится ошибкой компилятора, а не тихим багом. Редактор ещё и подсказывает варианты при наборе.

Сужение типа (narrowing)

С union-значением нельзя делать то, что подходит не всем вариантам. Сначала нужно проверить, какой вариант перед вами. После проверки TypeScript «сужает» тип внутри ветки.

function showPrice(price: number | string): string {
  // price.toFixed(2) здесь было бы ошибкой: у string нет toFixed
  if (typeof price === "string") {
    return price;                  // внутри if — это string
  }
  return price.toFixed(2) + " сомони";   // здесь остался number
}
console.log(showPrice(45));
console.log(showPrice("по запросу"));

Union с меткой: «или то, или другое»

Когда варианты — объекты с разными полями, в каждый кладут общее поле-метку с литералом. По метке TypeScript понимает, какой именно вариант перед вами. Так описывают состояния загрузки данных (в уроке 5 это пригодится):

type LoadState =
  | { status: "loading" }
  | { status: "error"; message: string }
  | { status: "ok"; count: number };

function describe(state: LoadState): string {
  if (state.status === "error") return "Ошибка: " + state.message;   // здесь есть message
  if (state.status === "ok") return "Найдено: " + state.count;       // здесь есть count
  return "Загрузка…";                                                // остался loading
}
console.log(describe({ status: "ok", count: 3 }));

as const: список значений один раз

Допустим, кухни хранятся в массиве, и их же нужно использовать как тип. Дублировать список в двух местах опасно: добавили в одном и забыли в другом. Решение — as const («считай это константой»): массив становится «только для чтения», а его элементы — точными литералами. Тип можно вывести из значения:

type Cuisine = (typeof CUISINES)[number];   // "плов" | "шашлык" | "самбуса"

const favorite: Cuisine = "плов";
const wrong: Cuisine = "суши";              // ошибка: такого варианта нет
console.log(favorite, CUISINES.length);

05 null, undefined и необязательные значения

Самая частая причина падения JavaScript-приложений — Cannot read properties of undefined. Значения «нет» бывают двух видов: undefined («не задано», так ведёт себя пропущенное поле или find, не нашедший элемент) и null («намеренно пусто»). В strict-режиме TypeScript считает их отдельными типами: в string нельзя положить null. Если «пусто» возможно, его нужно написать в типе: string | null.

const dishes = [
  { id: 1, title: "Плов", note: "без острого" },
  { id: 2, title: "Чай" },
];

const found = dishes.find((d) => d.id === 2);   // тип: объект | undefined
// console.log(found.title);    // ошибка: 'found' is possibly 'undefined'

if (found) {
  console.log(found.title);     // внутри if значение точно есть
}

let selected: string | null = null;   // «пока ничего не выбрано»
selected = "Navruz";
console.log(selected);

Три инструмента для «значения может не быть»

ИнструментЧто делаетПример
Проверка ifСужает тип: внутри значение точно естьif (found) { found.title }

Nullish ??Подставляет запасное значение, только если слева null или undefinedfound?.title ?? "нет блюда"

?? и || — не одно и то же. || подставляет запасное значение для любого «ложного» (0, пустая строка, false). Для рейтинга 0 это ошибка: rating || 5 превратит 0 в 5. Оператор ?? заменяет только null и undefined, и rating ?? 5 оставит 0.

Не заглушайте, а проверяйте

Восклицательный знак после значения (found!.title, «поверь мне, значение есть») и приведение as Restaurant заставляют компилятор замолчать, но не делают значение безопасным. Если вы ошиблись, приложение упадёт у пользователя. Исключение, которое вы уже видели, — document.getElementById('root')! в main.tsx: корневой элемент точно есть в index.html. В остальном кода выбирайте проверку, ?. или ??.

Реальные тексты: 'found' is possibly 'undefined'. (TS18048), 'x' is possibly 'null'. (TS18047), Type 'null' is not assignable to type 'string'. (TS2322).

06 Типы в функциях

У функции типизируют параметры. Тип результата TypeScript обычно выводит сам, и ручная запись нужна, когда хочется зафиксировать «контракт» функции (для экспортируемых и сложных функций).

function lineTotal(price: number, qty: number): number {
  return price * qty;
}

// необязательный параметр: ? или значение по умолчанию
function greet(name: string, city: string = "Душанбе"): string {
  return `Салом, ${name} из города ${city}!`;
}

const double = (n: number) => n * 2;   // стрелочная: результат number выведен сам

console.log(lineTotal(45, 2), greet("Зарина"), double(21));
  • Параметры без типа в strict-режиме — ошибка Parameter 'price' implicitly has an 'any' type. (TS7006) (в деструктуризации: Binding element 'name' implicitly has an 'any' type. (TS7031)).
  • Вызов с неверным числом аргументов — Expected 2 arguments, but got 1. (TS2554).
  • Неверный тип аргумента — Argument of type 'string' is not assignable to parameter of type 'number'. (TS2345).
  • Необязательные параметры ставят в конец списка.
  • void — «ничего не возвращает». Типично для обработчиков и колбэков.

Тип функции: для колбэков

Функцию можно передать другой функции или компоненту. Тип такого параметра описывает «форму» функции: что она принимает и что возвращает. Записывают как стрелку: (id: number) => void. Именно так в React описывают onSelect и onChange.

type OnPick = (id: number) => void;

function renderButtons(ids: number[], onPick: OnPick): void {
  for (const id of ids) {
    onPick(id);       // «нажимаем» каждую кнопку
  }
}

renderButtons([1, 2, 3], (id) => console.log("выбран:", id));   // id — number выведен сам

Обратите внимание: у стрелки внутри вызова параметр id типизировать не пришлось. TypeScript берёт тип из OnPick. Такой вывод вы будете видеть в React постоянно.

Аналогия из жизни

Тип функции — это заявка на маршрутку: «примет пассажира (число), довезёт, ничего не вернёт». Любой водитель с таким маршрутом подходит. Если в заявке написано «принимает номер маршрута», а вы пришли со строкой «автобус», диспетчер сразу скажет: не подходит.

07 TypeScript в React: props, children, события, useState

В React всё то же самое, только типы применяются к компонентам. Компонент — это функция: её параметр — объект props, а результат — JSX. Поэтому типизировать нужно props.

Props: тип рядом с компонентом

import type { Restaurant } from './types'

type RestaurantCardProps = {
  restaurant: Restaurant
  onSelect: (id: number) => void   // колбэк: родитель получит id
}

export default function RestaurantCard({ restaurant, onSelect }: RestaurantCardProps) {
  return (
    <article className="card">
      <h3>{restaurant.name}</h3>

    </article>
  )

  • Имя типа props — ИмяКомпонентаProps, он лежит в том же файле. Если тип нужен в двух файлах, выносите в types.ts.
  • Тип результата компонента не пишем: TypeScript выводит его сам. Старую запись React.FC в новом коде не используют.
  • Тип Restaurant — это тип, поэтому он импортируется через import type (в проекте включён verbatimModuleSyntax).

children

Всё, что вы пишете между тегами компонента (<Section>…</Section>), приходит в prop children. Его тип — ReactNode: это «всё, что React умеет отрисовать» (строка, число, элемент, массив элементов, null).

import type { ReactNode } from 'react'

type SectionProps = {
  title: string

export default function Section({ title, children }: SectionProps) {
  return (

      <h2>{title}</h2>

События

У обработчика события есть свой тип: у onChange поля ввода это ChangeEvent<HTMLInputElement>. В угловых скобках указано, на каком элементе случилось событие (это даёт доступ к event.target.value). Если обработчик пишется прямо в JSX, тип выводится сам, и записывать его не нужно:

import type { ChangeEvent } from 'react'

type SearchBoxProps = {
  value: string
  onChange: (value: string) => void
}

export default function SearchBox({ value, onChange }: SearchBoxProps) {
  // вынесенный в функцию обработчик: тип события пишем сами
  function handleChange(event: ChangeEvent<HTMLInputElement>) {
    onChange(event.target.value)
  }
  return <input value={value} onChange={handleChange} placeholder="Найти ресторан" />
  // та же логика в JSX: onChange={(e) => onChange(e.target.value)} — тип e выведен
}

Другие частые события: MouseEvent (клик), FormEvent (отправка формы), KeyboardEvent. Если не знаете тип — напишите обработчик прямо в JSX и наведите курсор на параметр: редактор покажет тип.

useState

Если начальное значение говорит само за себя, тип выводится: useState(0) — число, useState('') — строка. Когда состояние может быть «пусто» или принимает значения из списка, тип указывают в угловых скобках: useState<Restaurant | null>(null). Без скобок TypeScript решил бы, что состояние всегда null, и не разрешил бы положить ресторан.

const [count, setCount] = useState(0)                          // выведено: number

const [cuisine, setCuisine] = useState<Cuisine | null>(null)         // кухня из списка или «все»

08 ИИ-блок: переводчик ошибок TypeScript

Тексты ошибок TypeScript часто длинные и на английском. Это идеальная работа для ИИ-агента: объяснить, что сказал компилятор. Но у агента есть соблазн «починить любой ценой»: он ставит any, as, ! или // @ts-ignore, и ошибка исчезает. Проблема остаётся, просто вы её больше не видите. Наша цель — понять ошибку и выбрать решение самим.

Правила работы с ошибками типов

1. Сначала объяснение, потом правка: просите перевести ошибку и показать причину. 2. Копируйте ошибку целиком, вместе с кодом TSxxxx и путём к файлу, плюс 10–20 строк вокруг. 3. Просите два варианта решения и объяснение, чем они отличаются. 4. Запретите заглушки: без any, as, !, @ts-ignore, без отключения strict. 5. После правки запускайте npm run typecheck: агент мог перенести ошибку в другое место.

Сравните два запроса к агенту (формула: контекст → задача → ограничения → формат ответа → проверка).

исправь ошибки TypeScript в проекте

Ограничения: без any, as, ! и @ts-ignore; не отключай правила в tsconfig. Формат ответа: «что значит ошибка» (2–3 предложения), затем таблица «вариант — что изменить — когда подходит». Проверка: после моего выбора внеси правку и запусти npm run typecheck, покажи вывод целиком.

Хороший запрос даёт агенту всё, чтобы объяснить: ошибку целиком, место, ограничения и желаемый формат. Плохой оставляет агенту выбор «как заставить компилятор замолчать», и самый быстрый способ — именно заглушка.

Как проверять типы, которые написал агент

  1. Заглушки. В коде нет any, as (кроме as const), ! после значений, @ts-ignore, @ts-expect-error без причины. Быстрая проверка: grep -rnE "\bany\b|@ts-ignore|@ts-expect-error" src.
  2. Слишком широкие типы. Для статуса или кухни — union из литералов, а не string. Для объектов — свой type, а не object или {}.
  3. Дубли типов. Тип ресторана описан один раз в types.ts. Если агент создал вторую копию в компоненте — это повод объединить.
  4. Необязательные поля. Каждое ? объясняется данными: не появилось ли оно «чтобы не ругался компилятор».
  5. Props. Есть отдельный type XxxProps, children: ReactNode, колбэки с точной сигнатурой, а не Function.
  6. Устаревший стиль. Нет React.FC, enum, префиксов I в названиях типов, propTypes.
  7. Проверка запуском. npm run typecheck, npm run lint, npm run build без ошибок и пустая вкладка Console в браузере.
Типичные ошибки

1. Принять «готово», не запустив npm run typecheck. 2. Согласиться на as unknown as Restaurant: это ложь компилятору, а не исправление. 3. Просить агента «переписать на TypeScript» целый проект одним шагом: на выходе сотни изменений без проверки. 4. Не читать объяснение: если вы не можете пересказать ошибку своими словами, вы её не поняли, а значит, она вернётся.

✓ Шпаргалка урока

  • TypeScript = JavaScript + типы. Проверяет код до запуска (tsc, редактор), типы вырезаются при сборке, в браузере их нет.
  • Базовое: string, number, boolean, string[]. Вывод типов работает сам, писать тип вручную нужно у параметров функций и «пустых» значений. any запрещён.
  • Объекты: type Имя = { поле: тип; необязательное?: тип; readonly id: number }. interface … extends встречается в чужом коде, в курсе используем type. Типы данных лежат в types.ts.
  • Варианты: "a" | "b" — union литералов; сужение через typeof, ===, поле-метку; as const и (typeof X)[number] выводят тип из массива. enum не используем.
  • Пусто: T | null, T | undefined, ?., ??, проверка if. ! и as — не лечение. ?? реагирует только на null и undefined.
  • Функции: параметры типизируем, результат выводится; необязательный параметр x?: T или x = значение в конце; тип функции (id: number) => void.
  • React: type ИмяProps рядом с компонентом, children: ReactNode, колбэки (…) => void, события ChangeEvent<HTMLInputElement>, useState<T | null>(null). Типы только для импорта — import type.
  • Частые ошибки: TS2322 (не тот тип), TS2339/TS2551 (нет поля), TS2345 (не тот аргумент), TS2554 (число аргументов), TS2741 (нет поля или prop), TS2367 (сравнение без смысла), TS18047/TS18048 (может не быть значения), TS7006/TS7031 (неявный any), TS1484 (нужен import type).
  • С агентом: сначала просите объяснить ошибку целиком, с кодом TSxxxx; два варианта решения; запрет на any, as, !, @ts-ignore; после правки — npm run typecheck.
