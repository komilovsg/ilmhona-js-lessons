01 JSX и элементы: что на самом деле возвращает компонент

JSX — это не HTML и не шаблон. Это синтаксис JavaScript, который при сборке превращается в вызовы функций. Vite делает это автоматически: ваш <h1>Navruz</h1> становится вызовом jsx('h1', …) из пакета react/jsx-runtime. Результат вызова — элемент React: обычный объект, который описывает, что показать. Это не кусок DOM и не готовый HTML.

const element = <h1 className="title">Navruz</h1>

// после сборки это вызов jsx('h1', { className: 'title', children: 'Navruz' }),
// а в итоге обычный объект примерно такого вида:
const sameElement = {
  type: 'h1',
  props: { className: 'title', children: 'Navruz' },
}

Элемент дёшево создать и нельзя изменить: чтобы показать другое, компонент просто возвращает новый объект. Из таких объектов складывается дерево, которое React потом сравнивает с предыдущим и переносит различия в DOM (раздел 4).

лёгкая

Что возвращает компонент function Card() { return <h1>Navruz</h1> }?

  1. Строку с HTML-кодом "<h1>Navruz</h1>"
  2. Готовый DOM-элемент, вставленный на страницу

Компонент получил reviews = 0 и вернул <p>{reviews && <b>есть отзывы</b>}</p>. Что появится на странице?

  4. <input type="text">

02 Компоненты, props, children и композиция

Функциональный компонент — обычная функция, которая принимает один объект props и возвращает JSX (или null, если показывать нечего). У неё два жёстких правила: имя с большой буквы и вызов только через разметку (<Card />, а не Card()). Маленькая буква означает «это HTML-тег».

src/Bad.tsx(9,10): error TS2339: Property 'restaurantCard' does not exist on type 'JSX.IntrinsicElements'.
<restaurantCard /> is using incorrect casing. Use PascalCase for React components, or lowercase for HTML elements.

Первая строка — ошибка TypeScript, вторая — предупреждение React в консоли браузера. Props только читаются: значения по умолчанию задают в параметрах, а изменять props нельзя (раздел 5).

type RatingProps = {
  value: number
  max?: number // необязательный prop
}

export default function Rating({ value, max = 5 }: RatingProps) {
  return (
    <span>
      ★ {value.toFixed(1)} / {max}
    </span>
  )
}

children и композиция

children — это всё, что вы положили между открывающим и закрывающим тегом компонента. Так делают «обёртки»: Layout, Card, Modal, которые знают, как выглядеть, но не знают, что внутри. Тип children — ReactNode (его вы разобрали в уроке 2): подходит всё, что React умеет показать. Из-за флага verbatimModuleSyntax (урок 1) импортируйте его как тип.

import type { ReactNode } from 'react'

type LayoutProps = {
  header: ReactNode // слот: любой JSX
  children: ReactNode // основное содержимое
  footer?: ReactNode
}

export default function Layout({ header, children, footer }: LayoutProps) {
  return (
    <div>
      <header>{header}</header>
      <main>{children}</main>
      {footer && <footer>{footer}</footer>}
    </div>
  )
}

// использование:
// <Layout header={<Logo />} footer={<Contacts />}>
//   <RestaurantList />
// </Layout>

Композиция лучше «настроек»: вместо компонента с десятью prop-флагами (showHeader, showLogo, isCompact…) вы даёте ему слоты, и страница сама решает, что показать. Это основной приём React вместо наследования.

Не объявляйте компонент внутри компонента

Если написать function Counter() прямо в теле App, то при каждой перерисовке App создаётся новая функция Counter. Для React это уже другой компонент: старый удаляется вместе со своим состоянием, новый создаётся с нуля. Симптом: «состояние сбрасывается, когда меняется что-то снаружи». Объявляйте компоненты на верхнем уровне файла, а лучше в отдельном файле: один компонент — один файл, имя файла совпадает с именем компонента.

Типичные ошибки

1. Вызывать компонент как функцию ({Rating({ value: 4 })}) вместо <Rating value={4} />: хуки и состояние так не работают. 2. Компонент в компоненте (см. выше). 3. Передавать в children лишние данные: объект вместо JSX даст ошибку «Objects are not valid as a React child». 4. Делать компонент-«комбайн» на 400 строк: границы компонента разберём в разделе 7. 5. Класть в один файл компонент и обычные константы или функции: правило Oxlint react/only-export-components предупредит, что Fast Refresh (горячая замена) может перестать работать.

03 Списки и key: как React узнаёт элементы

Список в React — это обычный массив JavaScript: filter оставляет нужное, map превращает каждый объект в элемент. Единственное, что добавляет React, — key.

{restaurants
  .filter((r) => r.open)
  .map((r) => (
    <RestaurantCard key={r.id} restaurant={r} />
  ))}

Зачем нужен key. При перерисовке React получает новый список элементов и должен понять, кто есть кто: какой элемент остался, какой добавился, какой удалился. Без ключа он сравнивает по позиции, с ключом — по идентичности. Ключ — это «паспорт» элемента.

04 Когда и как React перерисовывает компонент

«Рендер» — самое перегруженное слово в React. Давайте разделим его на три шага. Триггер: что-то запросило показ (первый запуск через createRoot().render() или изменение состояния через setState). Рендер: React вызывает функции ваших компонентов и получает новое дерево элементов. Это только вычисление, экран ещё не тронут. Коммит: React сравнивает новое дерево со старым и вносит в DOM только различия. Если ничего не отличается, DOM не трогают вообще.

Ролик на русском (2023 год, 10 минут): фазы render и commit на примерах. Идея не изменилась в React 19.

Состояние — это снимок

Каждый рендер видит свои значения props и состояния: они «заморожены» на момент вызова функции. setQty(qty + 1) не меняет переменную qty прямо сейчас, а просит React выполнить новый рендер с новым значением. Поэтому три вызова подряд получают одно и то же qty.

const [qty, setQty] = useState(0)

function addThree() {
  setQty(qty + 1) // qty здесь равно 0 → попросили 1
  setQty(qty + 1) // qty всё ещё 0 → попросили 1
  setQty(qty + 1) // и снова 1
}
// после клика на экране 1, а не 3

function addThreeRight() {
  setQty((q) => q + 1) // функция получает последнее значение из очереди
  setQty((q) => q + 1)
  setQty((q) => q + 1)
}
// после клика на экране 3

Что перерисуется

Компонент рендерится заново, когда изменилось его состояние или перерисовался его родитель. Второй пункт важен: по умолчанию React перерисовывает всех потомков компонента, у которого поменялось состояние, даже если их props остались прежними. Это не страшно: рендер — дешёвый вызов функции, а коммит всё равно затронет только реальные различия. Чаще всего ничего оптимизировать не нужно. Если же тяжёлый компонент без нужды рендерится на каждый клик, первое лекарство самое простое — опустить состояние ниже: вынести ту часть, которой оно нужно, в отдельный маленький компонент. Инструменты вроде React.memo, Profiler и React Compiler разберём в уроках 6 и 12.

Ещё три факта о рендере. 1. Если вызвать setQty с тем же значением (сравнение через Object.is), React пропустит перерисовку. Новый массив или объект с тем же содержимым — это уже новое значение. 2. В dev-режиме с StrictMode (он есть в вашем main.tsx) React вызывает каждый компонент дважды, чтобы вскрыть нечистые функции (раздел 5). Поэтому console.log в компоненте печатается дважды (если установлены React DevTools, второй вызов выделен серым). В сборке для пользователей двойного вызова нет. 3. Изменить состояние без setState (например, items.push(x)) не запустит рендер вообще: React не узнает об изменении. Про правильное обновление объектов и массивов поговорим в уроке 4.

ЗАДАЧА 4.1

Проверь себя: модель рендера

средняя

Что происходит на шаге «рендер»?

  1. React вставляет новые элементы в DOM браузера
  2. Браузер рисует пиксели на экране
  3. React вызывает функции компонентов и получает дерево элементов, DOM при этом не меняется
  4. React скачивает данные с сервера

Рендер — это вычисление. Менять DOM начинает коммит, а пиксели рисует уже браузер.

Что заставляет React снова вызвать функцию компонента Menu? Выберите два варианта.

  1. Изменилось его собственное состояние
  2. Прошла одна секунда
  3. Перерисовался его родитель (по умолчанию потомки рендерятся вместе с ним)
  4. Пользователь навёл мышь на страницу

Два триггера: своё состояние и перерисовка родителя. Время и мышь сами по себе рендер не запускают.

Что выведет компонент после одного клика, если в обработчике три раза подряд вызвано setQty(qty + 1), а qty было равно 0?

  1. 3
  2. 1
  3. 0
  4. Ошибку

В одном рендере qty — это снимок, он равен 0 во всех трёх вызовах. Каждый вызов просит «поставь 1». Чтобы получить 3, передайте функцию: setQty((q) => q + 1).

05 Чистые компоненты

Компонент должен быть как формула: те же props и то же состояние — тот же JSX. И ещё одно условие: во время рендера он не меняет ничего, что существовало до него. 06 Стили в React: CSS Modules и Tailwind CSS

В обычном CSS все классы глобальные: .card из одного файла красит .card во всём приложении, а имена рано или поздно совпадают. В проектах на React с этой проблемой справляются двумя способами, и в «Дастархоне» вы подключите оба. Шаблон Vite умеет и то, и другое.

CSS Modules: свой CSS у каждого компонента

Файл с именем Что-то.module.css — это CSS Module. Vite понимает его сам, ничего ставить не нужно. Его классы локальны: при сборке к имени добавляется уникальный хэш, и конфликтовать с чужим .card он не будет.

.card {
  padding: 1rem;
  border-radius: 1rem;
}

.closed {
  opacity: 0.6;
}

import styles from './RestaurantCard.module.css'

// styles.card — это строка вида '_card_yj5l5_1', её и вставляем в className
const className = open ? styles.card : `${styles.card} ${styles.closed}`

Хэш в имени класса вы увидите в DevTools. Типы для импорта *.module.css уже подключены: в tsconfig.app.json есть "types": ["vite/client"]. Но обратите внимание: TypeScript знает только, что styles.что-угодно — строка. Опечатка styles.carrd ошибкой типов не станет: класс просто не применится, и вы заметите это глазами. Несколько классов склеивают шаблонной строкой (как выше) или массивом: [styles.card, !open && styles.closed].filter(Boolean).join(' ').

Tailwind CSS 4: утилитарные классы

Tailwind даёт готовые маленькие классы на каждое свойство: p-4 (отступ), rounded-xl, text-lg, font-bold, flex, gap-2. Вы собираете вид прямо в className, а Tailwind при сборке находит в исходниках используемые классы и включает в итоговый CSS только их. Текущая версия — 4.3; подключение к Vite занимает три шага (в практике вы выполните их сами):

npm install tailwindcss @tailwindcss/vite

import tailwindcss from '@tailwindcss/vite'
import react from '@vitejs/plugin-react'
import { defineConfig } from 'vite'

export default defineConfig({
  plugins: [react(), tailwindcss()],
})

@import 'tailwindcss';

Файл tailwind.config.js и PostCSS в четвёртой версии не нужны. Все настройки лежат в CSS.

Он ищет в файлах готовые слова-классы. Если собирать имя из кусочков, класса в итоговом CSS не будет, и ошибки тоже не будет: стиль просто не применится.

// хорошо: оба варианта записаны целиком
const good = open ? 'bg-green-100' : 'bg-stone-100'

Аналогия из жизни

CSS Modules — это отдельная кухня для каждого повара: у каждого свои кастрюли с подписью, чужие не перепутаешь. Tailwind — общий набор приправ в ящике на стене: берёте щепотку «p-4», щепотку «font-bold» и собираете блюдо на месте, а список приправ (тема) один на всю кухню.

Где проходит граница компонента

  1. Повторяется. Если кусок экрана показан много раз (карточка, бейдж), это компонент: он пишется один раз, а данные идут через props.
  2. Имеет имя и одну ответственность. Вы можете назвать его одним словом и сказать, что он делает, без «и». «Карточка ресторана» — да, «карточка и фильтр и корзина» — нет.

Как проверять код компонентов от агента

  1. key. В каждом map стоит key из id, а не из индекса. Oxlint подскажет пропущенный.
  2. Компонент внутри компонента. Нет function X() внутри тела другой функции-компонента.
  3. Мутации. Нет .sort(), .push(), .reverse() на props и состоянии без копии.
  4. Типы. Нет any, props описаны типом, ReactNode и другие типы импортированы через import type.
  5. Классы Tailwind. Нет имён, собранных из кусочков (`bg-${x}-600`), нет двух способов стилизации одного свойства.
  6. Размер. Компонент длиннее 80–100 строк или с шестью и более props: повод вернуться к границам.
  7. Лишнее. Нет нового useState, useEffect, новых пакетов и React.memo, о которых вы не просили: в этом уроке мы только раскладываем экран на компоненты.
Типичные ошибки

1. Просить сразу код: вы не увидите границ и получите 400 строк в одном файле. 2. Принять дерево, не поспорив: агент часто делит «по тегам», а не по смыслу. 3. Не сверить дерево с макетом: пропал подвал или бейдж. 4. Давать агенту картинку или данные с реальными личными данными. 5. Считать, что агент «знает» ваши правила: если не сказать про Tailwind и CSS Modules, он выберет сам.

✓ Шпаргалка урока

  • JSX превращается в вызовы функций и даёт элементы: обычные объекты-описания. Правила: один корень (Fragment <>), все теги закрыты, className, style — объект, в {} только выражения, имя компонента с большой буквы.
  • Условный вывод: тернарный оператор, &&, return null. {n && …} при n = 0 выведет «0»: пишите n > 0 && …. null, undefined, true, false не рисуются, объект — ошибка.
  • Компонент — функция, принимающая props и возвращающая JSX. children: ReactNode — содержимое между тегами; слоты — props с JSX. Композиция вместо десятка флагов. Компонент внутри компонента не объявляют: состояние сбрасывается.
  • Списки: filter + map, key из id на элементе в map, уникален среди соседей. Индекс — только для статичных списков, Math.random() в ключе — никогда. Пустой список обрабатывают отдельно.
  • Рендер: триггер (первый запуск или setState) → рендер (вызов функций) → коммит (различия в DOM). Состояние — снимок: для серии обновлений setQty((q) => q + 1).   • Чистота: те же props и состояние дают тот же JSX, во время рендера ничего внешнего не меняем. Не items.sort(), а [...items].sort(). Побочные эффекты — в обработчиках событий и в useEffect (урок 5).
