01 Состояние и props: у кого какие данные

У компонента есть два источника данных. Props — это то, что ему передал родитель: компонент только читает их, как аргументы функции. Состояние (state) — это память самого компонента: значение, которое он хранит между рендерами и может менять сам. Меняется состояние — React вызывает компонент заново (триггер из урока 3) и показывает результат.

Почему не обычная переменная

Можно подумать: «зачем useState, ведь есть let qty = 1». У обычной переменной две проблемы. Во-первых, её присваивание не запускает рендер: React не узнает, что экран нужно обновить. Во-вторых, при следующем рендере функция компонента выполняется с начала, и let qty = 1 снова станет единицей. useState решает обе: React хранит значение вне функции, возвращает его при каждом рендере, а вызов setQty запускает новый рендер.

Нужно ли данным состояние: четыре вопроса

  1. Оно меняется со временем? Если нет, это константа или prop.
  2. Его передал родитель через props? Тогда оно не ваше: не копируйте его в своё состояние, а читайте prop.
  3. Его можно вычислить из другого состояния или props? Тогда это не состояние, а производные данные (раздел 4).
  4. Оно влияет на то, что видно на экране? Если нет (например, номер таймера), ему место не в состоянии (позже для таких значений будет useRef, урок 5).

Состояние у каждого экземпляра своё

Два одинаковых компонента на странице не делят состояние: каждый вызов <Portions /> получает собственную «ячейку» памяти. Состояние привязано к месту компонента в дереве: пока компонент стоит на том же месте, React его помнит, а когда компонент пропадает из разметки, состояние выбрасывается (вспомните задачу про key и «компонент внутри компонента» из урока 3).

Аналогия из жизни

Официант в чойхоне принёс на два стола по чайнику. Чайник на столе — это состояние: он принадлежит столу, и сколько в нём чая, знают только за этим столом. Гостей за столом (props) приводит администратор, и официант их не выбирает. Если компанию пересадили за другой стол, чайник остаётся на прежнем: так и компонент, который переехал на другое место в дереве, для React новый и начинает с пустой памяти.

02 Иммутабельные обновления: не менять, а заменять

Когда вы вызываете setCart(newCart), React сравнивает новое значение со старым по ссылке (как Object.is). Если ссылка та же, React решает, что ничего не изменилось, и пропускает рендер. Поэтому состояние с массивом или объектом нельзя менять «на месте»: нужно создать новый массив или объект и передать его в set…. Это называется иммутабельное обновление. Старое значение считайте замороженным снимком.

Что меняет на месте, а что создаёт копию

Мутирует (не использовать с состоянием)Возвращает новое (использовать)
Массивpush, pop, shift, unshift, splice, sort, reverse, arr[i] = …[...arr, x], filter, map, slice, concat, [...arr].sort()
Объектobj.qty = 5, obj.qty++, delete obj.qty{ ...obj, qty: 5 }

Все операции над корзиной выражаются этими четырьмя приёмами. Здесь CartItem — тип из урока 2 ({ item: MenuItem; qty: number }):

// добавить в конец
setCart([...cart, { item, qty: 1 }])

// убрать по id
setCart(cart.filter((entry) => entry.item.id !== itemId))

// изменить одну запись: у остальных вернуть тот же объект
setCart(
  cart.map((entry) =>
    entry.item.id === itemId ? { ...entry, qty: entry.qty + 1 } : entry,
  ),
)

// вставить в начало
setCart([{ item, qty: 1 }, ...cart])

// отсортировать: сначала копия, потом sort
setCart([...cart].sort((a, b) => a.item.price - b.item.price))

Копия поверхностная: { ...entry, qty: 5 } создаёт новый объект записи, но вложенный объект entry.item остаётся тем же. Это нормально, если вы меняете только верхний уровень. Если нужно изменить поле вложенного объекта, копируйте каждый уровень на пути к нему:

// поменять цену блюда внутри записи корзины
setCart(
  cart.map((entry) =>
    entry.item.id === itemId
      ? { ...entry, item: { ...entry.item, price: 50 } }
      : entry,
  ),
)

Глубокая вложенность быстро становится неудобной. Поэтому в состоянии стараются держать данные плоскими, а для сложных случаев есть библиотека Immer: она позволяет писать «как будто с мутацией», а на деле делает копии. Вы встретите её в Redux Toolkit (урок 9). Пока достаточно map, filter и spread.

Типы помогают: readonly

TypeScript умеет запрещать мутации. Тип readonly CartItem[] (или ReadonlyArray<CartItem>) убирает у массива методы-мутаторы и запрещает присваивание по индексу. Если объявить так параметр функции, компилятор не даст случайно изменить пришедший массив:

src/ro.ts(3,9): error TS2339: Property 'push' does not exist on type 'readonly CartItem[]'.
src/ro.ts(4,3): error TS2542: Index signature in type 'readonly CartItem[]' only permits reading.

readonly — защита времени компиляции, в работающей программе массив остаётся обычным. Поле объекта защищается так: readonly qty: number. Тип Readonly<T> делает все поля объекта T доступными только для чтения (утилитные типы подробнее — урок 9).

Аналогия из жизни

Меню в чойхоне печатают на листе. Если на нём ручкой зачеркнуть блюдо, администратор, сверяющий листы по номеру партии, не заметит правки: номер тот же. Поэтому для нового меню печатают новый лист с новым номером. Лист — массив, номер партии — ссылка, а типографская печать — spread и map.

Типичные ошибки

1. cart.push(item); setCart(cart): ссылка прежняя, рендера нет. 2. entry.qty += 1; setCart([...cart]): массив новый, но объекты внутри изменены, а значит, «старый снимок» тоже испорчен. Другие части программы, которые держат ссылку на запись, увидят чужое изменение. 3. const sorted = cart.sort(…): sort меняет сам массив и возвращает его же. 4. setUser(user.name = 'Алишер'): присваивание — выражение, оно вернёт строку, а не объект. 5. Копировать массив через const copy = cart: это ещё одна ссылка на тот же массив, а не копия.

ЗАДАЧА 2.1

Проверь себя: иммутабельность

средняя

Разработчик написал cart.push(item); setCart(cart); и жалуется, что экран не меняется. Почему?

  1. Метод push не работает с массивами объектов
  2. Нельзя вызывать setCart два раза подряд
  3. Ссылка на массив осталась прежней, React сравнивает ссылки и не видит изменения
  4. Нужно вызвать forceUpdate

React решает, нужен ли рендер, сравнением нового значения со старым по ссылке. Передайте новый массив: setCart([...cart, item]).

Какие записи обновляют состояние корректно? Выберите два варианта.

  1. cart[0].qty = 5; setCart(cart)
  2. setCart(cart.map((e) => (e.item.id === 1 ? { ...e, qty: 5 } : e)))
  3. setCart(cart.sort((a, b) => a.qty - b.qty))
  4. setCart([...cart].sort((a, b) => a.qty - b.qty))

В первом варианте мутация, в третьем sort меняет исходный массив и возвращает ту же ссылку. Во втором и четвёртом создаются новые значения.

В коде setCart(cart.map((e) => { e.qty += 1; return e; })) массив новый. Что не так?

  1. Объекты внутри изменены на месте: старый снимок испорчен, другие ссылки на эти объекты увидят чужое изменение
  2. Ничего: массив новый, значит, всё правильно
  3. map нельзя использовать с состоянием
  4. Нужно вернуть массив, а не объект

Новый массив не отменяет мутацию объектов внутри него. Для записи нужен новый объект: { ...e, qty: e.qty + 1 }.

ЗАДАЧА 2.4

readonly не даёт мутировать

средняя

Функция принимает массив как readonly и всё равно пытается сделать push: компилятор отказывается. Верните новый массив, не трогая пришедший. Нажмите «Запустить»: ошибок типов быть не должно.

03 Подъём состояния: один источник правды

Бывает, что двум компонентам нужны одни и те же данные. В «Дастархоне» меню добавляет блюда в корзину, а корзина их показывает. Пока у каждого своё состояние, они не синхронизируются: меню «не знает», что лежит в корзине. Решение называется подъёмом состояния (lifting state up): перенесите состояние в ближайшего общего родителя, а детям передайте значение через props и функцию-обработчик через колбэк.

Алгоритм из четырёх шагов: 1) найти все компоненты, которым нужны эти данные; 2) найти их ближайшего общего родителя; 3) объявить состояние там; 4) передать значение вниз через props, а изменение — через функцию (onAdd, onChange). Дочерний компонент не хранит копию, он показывает то, что получил, и сообщает о событии.

function PortionControl({ qty, onChange }: { qty: number; onChange: (qty: number) => void }) {
  return (
    <div>
      <button onClick={() => onChange(qty - 1)}>−</button> {qty}{' '}
      <button onClick={() => onChange(qty + 1)}>+</button>
    </div>
  )
}

function OrderTotal({ qty, price }: { qty: number; price: number }) {
  return <p>Итого: {qty * price} сомони</p>
}

export default function App() {
  const [qty, setQty] = useState(1) // состояние живёт у родителя
  return (
    <>
      <PortionControl qty={qty} onChange={setQty} />
      <OrderTotal qty={qty} price={45} />
    </>
  )
}

Не поднимайте состояние выше, чем нужно. Если данные нужны только одному компоненту, пусть живут в нём. Другая крайность: состояние поднято на самый верх, и приходится передавать его через пять уровней компонентов, которым оно не нужно. Это называется prop drilling. Для него есть Context (урок 8), но сначала проверьте, нельзя ли решить задачу композицией: передать готовый JSX через children (урок 3).

04 Производные данные: не храните то, что можно посчитать

Чем меньше состояния, тем меньше мест, где данные могут разойтись. Правило: если значение можно вычислить из props или другого состояния, не заводите для него отдельное состояние, а считайте прямо в теле компонента при каждом рендере. Рендер дешёвый, а расхождение данных дорогое.

05 useReducer: действия вместо россыпи setState

Корзине нужны четыре операции: добавить блюдо, убрать, изменить количество, очистить. С useState каждая превращается в отдельную функцию-обработчик со своим setCart(…), и логика «как меняется корзина» рассыпана по компоненту (а при подъёме состояния ещё и по пропсам). useReducer собирает её в одном месте.

Редьюсер — обычная функция (state, action) => newState: берёт текущее состояние и действие (action), возвращает следующее состояние. Действие — объект, который описывает что произошло, а не как менять: { type: 'add', item }, { type: 'remove', itemId: 3 }. Компонент не меняет состояние сам, а отправляет действие через dispatch.

const [state, dispatch] = useReducer(reducer, initialState)

dispatch({ type: 'add', item })   // «произошло: добавили блюдо»
// React вызовет reducer(state, { type: 'add', item }) и возьмёт результат как новое состояние

Правила редьюсера

  1. Чистая функция. Только вычисление: никаких запросов к серверу, Date.now(), Math.random(), записи в localStorage и вывода на экран. Эти вещи делают в обработчиках и эффектах (урок 5). Идентификатор или время вычислите до dispatch и положите в действие.
  2. Не мутирует состояние. Возвращает новое значение (раздел 2). Если действие ничего не меняет, верните тот же state: React пропустит рендер.
  3. Описывает событие. { type: 'add' }, а не { type: 'setCartToThisArray', cart: … }: действие называют по смыслу, и редьюсер сам решает, что с состоянием делать.
  4. Содержит всё необходимое для обновления. Редьюсер не обращается к внешним переменным, только к state и action.

В режиме разработки React вызывает редьюсер дважды для одного и того же действия (в StrictMode, урок 3) чтобы ошибки нечистоты проявились сразу (мутирующий редьюсер добавит блюдо дважды, в разделе практики вы увидите это своими глазами). Поэтому console.log внутри редьюсера печатает больше строк, чем было кликов:

reducer add
reducer add
reducer add
reducer add

Это не баг: в продакшен-сборке двойного вызова нет. Но именно поэтому редьюсеру запрещены побочные эффекты: повторный вызов не должен ничего ломать. Точное число строк зависит от версии React и режима, считать его не нужно.

Оба хука равноправны: useState внутри устроен так же.

ЗАДАЧА 5.1

Проверь себя: useReducer

средняя

Что такое «действие» (action) в useReducer?

  1. Функция, которая сразу меняет состояние
  2. Объект, описывающий, что произошло ({ type: 'add', item }); как менять состояние, решает редьюсер
  3. Новое значение состояния целиком
  4. Обработчик события браузера

Действие — описание события. Логика перехода состояния находится в редьюсере, а не в компоненте.

Что запрещено делать внутри редьюсера? Выберите два варианта.

  1. Менять переданный массив состояния на месте (state.push)
  2. Возвращать новый массив через map и filter
  3. Отправлять запрос на сервер или вызывать Math.random()
  4. Использовать switch

Редьюсер должен быть чистым и не мутировать состояние. React в dev-режиме вызывает его дважды, чтобы такие ошибки вылезли сразу.

Когда стоит перейти с useState на useReducer?

  1. Всегда: useReducer быстрее
  2. Когда состояние — число
  3. Когда нужны эффекты
  4. Когда одно состояние меняют несколько обработчиков по нетривиальным правилам и логику хочется собрать в одном месте

Скорость одинаковая. Редьюсер выигрывает читаемостью и тестируемостью, когда правил много, а для одного флага useState проще.

06 TypeScript: типы состояния и действий

Редьюсер без типов — это switch по строке, где опечатка в 'add' молча не сработает. С типами компилятор сверяет каждое действие и каждую ветку. Основной приём — discriminated union (размеченное объединение, вы видели его в уроке 2): набор объектных типов с общим полем-меткой type, у каждого типа своя литеральная строка и свои дополнительные поля.

import { assertNever } from './assertNever'
import type { CartItem, MenuItem } from './types'

export type CartAction =
  | { type: 'add'; item: MenuItem }
  | { type: 'remove'; itemId: number }
  | { type: 'setQty'; itemId: number; qty: number }
  | { type: 'clear' }

export function cartReducer(state: CartItem[], action: CartAction): CartItem[] {
  switch (action.type) {
    case 'add': {
      const exists = state.some((entry) => entry.item.id === action.item.id)
      if (!exists) {
        return [...state, { item: action.item, qty: 1 }]
      }
      return state.map((entry) =>
        entry.item.id === action.item.id
          ? { ...entry, qty: entry.qty + 1 }
          : entry,
      )
    }
    case 'remove':
      return state.filter((entry) => entry.item.id !== action.itemId)
    case 'setQty': {
      if (action.qty <= 0) {
        return state.filter((entry) => entry.item.id !== action.itemId)
      }
      return state.map((entry) =>
        entry.item.id === action.itemId ? { ...entry, qty: action.qty } : entry,
      )
    }
    case 'clear':
      return []
    default:
      return assertNever(action)
  }
}

Проверка полноты: never в default

Самая ценная польза: если вы добавите в объединение новое действие, а в switch ветку забудете, компилятор покажет это. Для этого в default вызывают маленькую функцию, которая принимает значение типа never («значения, которого не может быть»). Пока все ветки разобраны, в default тип action — never, и всё компилируется. Стоит появиться необработанному действию, тип перестаёт быть never:

export function assertNever(value: never): never {
  throw new Error(`Unexpected value: ${JSON.stringify(value)}`)
}

src/cartReducer.ts(37,26): error TS2345: Argument of type '{ type: "applyPromo"; code: string; }' is not assignable to parameter of type 'never'.

Текст ошибки на «never» сбивает с толку, но читайте его по-другому: в скобках видно, какое именно действие не обработано. Если же случайно удалить ветку, ошибка называет её же: Argument of type '{ type: "clear"; }' is not assignable to parameter of type 'never'. Функция assertNever защищает и в работе: если в редьюсер всё-таки придёт невозможное значение (например, из JavaScript-кода), она выбросит ошибку, а не вернёт молча неверное состояние.

Как передать dispatch дочернему компоненту

Два способа. Первый — передавать колбэки с понятными именами (onAdd, onRemove): компонент ничего не знает про редьюсер и его можно использовать с любым источником данных. Этим мы пользуемся в практике. Второй — передать сам dispatch с типом Dispatch<CartAction> (тип импортируется из react через import type). Он проще, но привязывает компонент к конкретным действиям. Оба варианта компилируются; выбирайте колбэки, когда компонент должен быть универсальным.

  dispatch: Dispatch<CartAction>
}

export default function ClearButton({ dispatch }: ClearButtonProps) {
  return <button onClick={() => dispatch({ type: 'clear' })}>Очистить</button>
}
Типичные ошибки

1. Тип действия { type: string } вместо литералов: сужение в switch не работает, а опечатки не ловятся. 2. Один тип с необязательными полями ({ type: 'add' | 'remove'; item?: MenuItem; itemId?: number }): в каждой ветке придётся проверять undefined; объединение чище. 3. default: return state вместо assertNever: новое действие тихо игнорируется. 4. Привести тип через as, чтобы «заглушить» ошибку: ошибка нужна, она показывает забытую ветку. 5. Описывать состояние как any: тогда типы не помогают нигде.

07 Правила хуков: почему не где попало

Функции useState, useReducer, useEffect и другие, чьё имя начинается с use, называются хуками. У них два правила.

  1. Вызывайте хуки только на верхнем уровне. Не внутри условий (if, тернарного оператора, &&), не в циклах, не во вложенных функциях и не после раннего return.
  2. Вызывайте хуки только из компонентов или других хуков. Не из обычных функций, обработчиков событий и классов. Свои хуки (функции с именем useЧто-то) вы будете писать в уроке 6.

Почему так

React не знает имён ваших переменных. Он хранит состояние компонента как список ячеек, а каждый вызов хука при рендере берёт следующую ячейку по порядку: первый useState получает ячейку 1, второй — ячейку 2. Поэтому порядок вызовов должен быть одним и тем же при каждом рендере. Если хук окажется в if, при другом значении условия порядок сдвинется, и хук получит чужую ячейку.

Вам не придётся запоминать это на слух: линтер ловит нарушения правил. Правило react-hooks/rules-of-hooks входит в Oxlint, который настроен в проекте с урока 1. Вот что он печатает для хука после раннего return, внутри цикла и в обычной функции:

src/components/Bad.tsx:11:5: error react-hooks(rules-of-hooks): React Hook "useState" may be executed more than once. Possibly because it is called in a loop. React Hooks must be called in the exact same order in every component render.

Аналогия из жизни

В камере хранения на вокзале Душанбе багаж выдают по номеру ячейки в порядке очереди: «первый чемодан, второй чемодан». Если пассажир в какой-то день пропустил первый чемодан и сразу потребовал второй, ему отдадут чужую сумку из первой ячейки. React выдаёт состояние хукам по такой же очереди, и очередь нельзя менять.

Типичные ошибки

1. Ранний return выше хука (самая частая). 2. useState внутри if «чтобы не создавать лишнего». 3. Хук в обработчике события: onClick={() => { const [x, setX] = useState(0) }}. 4. Хук в .map по списку: вынесите элемент списка в отдельный компонент, и хуки пойдут в него. 5. Отключить правило линтера комментарием, а не исправить код.

ЗАДАЧА 7.1

Проверь себя: правила хуков

средняя

Почему нельзя вызывать useState внутри if?

  1. React сопоставляет хуки с ячейками состояния по порядку вызовов; условие может сдвинуть порядок и перепутать данные
  2. Потому что if нельзя писать в компонентах
  3. Потому что useState работает только с числами
  4. Потому что условие замедляет рендер

У React нет имён переменных, только порядок вызовов. Одинаковый порядок при каждом рендере — условие работы хуков.

Где нарушены правила хуков? Выберите два варианта.

  1. Компонент начинается с const [qty, setQty] = useState(1), потом if (!open) return null
  2. Компонент: if (open) { const [qty] = useState(1) }
  3. Хук вызывается на верхнем уровне компонента Cart
  4. В обработчике onClick вызван useReducer(…)

Хуки нельзя вызывать в условиях и в обработчиках событий. Первый вариант корректен: все хуки выше раннего return.

08 ИИ-блок: тестовые данные, редьюсер по описанию и ревью иммутабельности

Две задачи, с которыми агент справляется хорошо, если ему правильно их поставить: сгенерировать тестовые данные и написать редьюсер по описанию действий. Формула промпта: контекст → задача → ограничения → формат → проверка

Сначала просите описание действий в таблице, без кода: так вы сверите правила (что делает «добавить» для уже лежащей позиции, что значит количество 0) раньше, чем увидите 80 строк чужого кода. И только потом просите редьюсер, который реализует утверждённую таблицу.

сделай корзину на useReducer и тестовые данные
Контекст: проект Vite 8 + React 19 + TypeScript (strict), прочитай AGENTS.md. Типы данных лежат в src/types.ts (MenuItem, CartItem, Restaurant), рестораны в src/data.ts с id от 1 до 6, корзина — CartItem[] в useReducer. Задача: 1) сгенерируй 12 блюд для массива menu: MenuItem[] — по два на каждый ресторан; 2) опиши действия корзины таблицей, код редьюсера пока не пиши. Как проверять тестовые данные

  1. Уникальные id. Повторяющийся id даст дубли ключей и неверную корзину. Проверьте глазами или через new Set(menu.map((m) => m.id)).size === menu.length.

  3. Реалистичные значения. Целые цены в сомони, а не 12.99 и не доллары; нет названий вроде «Блюдо 1».

  5. Крайние случаи. Попросите добавить в данные и такие, что ломают интерфейс: очень длинное название, блюдо за 0 сомони. Затем решите, нужны ли они в проекте.
  6. Личные данные. Агенту не нужны реальные имена и телефоны клиентов: тестовые данные должны быть выдуманными.

Как проверять редьюсер от агента

  1. Мутации. Ищите push, splice, sort без копии, присваивания вида entry.qty = …, item.qty++, state[i] = …. Самый коварный случай: const entry = state.find(…); entry.qty += 1; return [...state] — массив новый, объект старый.
  2. Побочные эффекты. Нет Date.now(), Math.random(), crypto.randomUUID(), localStorage, fetch, console.log в итоговом коде.
  3. Полнота. В default стоит assertNever(action), а не return state: иначе новое действие тихо игнорируется.
  4. Типы действий. Размеченное объединение с литеральными метками, без type: string и без as.
  5. Правила из таблицы. Повторное добавление увеличивает количество, а не создаёт дубль; qty ≤ 0 убирает позицию; неизвестный id не ломает состояние.
  6. Лишнее. Нет новых пакетов (immer, uuid, zustand) и нового useState, о которых вы не просили.
  7. Своя проверка. Мысленно (или в консоли) прогоните сценарий из пяти действий. Если вы не можете объяснить, почему результат верен, принимать код рано.
Типичные ошибки

1. Принять «работает на странице» за «написано верно»: двойной вызов в StrictMode часто маскирует мутацию. 2. Просить редьюсер и данные в одном сообщении: ошибки в одном не видны за размером другого. 3. Не сверить таблицу правил с кодом: агент мог реализовать «похожее». 4. Оставить в данных выдуманный restaurantId: меню ресторана №7 никогда не покажется. 5. Отправить агенту настоящие данные клиентов «для реалистичности».

export function cartReducer(state: CartItem[], action: CartAction): CartItem[] {
  switch (action.type) {
    case 'add': {
      const exists = state.some((entry) => entry.item.id === action.item.id)
      if (!exists) {
        return [...state, { item: action.item, qty: 1 }]
      }
      return state.map((entry) =>
        entry.item.id === action.item.id
          ? { ...entry, qty: entry.qty + 1 }
          : entry,
      )
    }
    case 'remove':
      return state.filter((entry) => entry.item.id !== action.itemId)
    case 'setQty': {
      if (action.qty <= 0) {
        return state.filter((entry) => entry.item.id !== action.itemId)
      }
      return state.map((entry) =>
        entry.item.id === action.itemId ? { ...entry, qty: action.qty } : entry,
      )
    }
    case 'clear':
      return []
    default:
      return assertNever(action)
  }
}

  • Состояние и props: props приходят сверху и только читаются, состояние — память компонента (useState), у каждого экземпляра своё. Обычная переменная не запускает рендер и обнуляется. В состояние идёт только то, что меняется, не пришло из props и не вычисляется из другого.
