01 Почему «у меня работает» не считается

Вы нажали кнопку, форма отправилась, запись появилась. Работает? Вы проверили один путь: под своим аккаунтом, с правильными данными, в одном браузере, один раз. Настоящие пользователи делают всё иначе: вводят пустое поле, заходят под другой ролью, нажимают «Назад», открывают сайт с телефона. А главное, код меняется каждый день. Вчера всё работало, сегодня агент «слегка поправил» соседний файл, и вход сломался. Проверять всё руками после каждой правки невозможно: вы устанете уже на третьей.

С ИИ-кодом это особенно важно. Агент пишет уверенно и коротко сообщает «готово, всё работает». Но он не всегда запускал код, а если запускал, то мог проверить не то. Нейросеть может написать правдоподобный ответ о результате, которого не было. Поэтому в вайбкодинге действует правило: работает то, что подтвердил запуск, а не слова агента. Проверка результата — главный навык человека в паре с ИИ.

Аналогия из жизни

Повар в чойхоне пробует плов ложкой с края казана: вкусно. Но гости получат порцию со дна, где подгорело. Автотест — это проверка по списку перед подачей: рис, мясо, морковь, соль, температура. Каждый раз одинаково, даже когда повар устал или торопится.

Типичные ошибки новичков

1. Верить строке «я всё проверил» от агента без запуска. 2. Проверять только то место, которое правили. 3. Тестировать только под администратором. 4. Считать тесты «лишней работой на потом»: именно после третьей правки они спасают. 5. Просить агента «пройти тесты» и не открывать вывод: он может подогнать тест под сломанный код.

ЗАДАЧА 1.1

Проверь себя: что считается проверкой

лёгкая

Вы попросили агента добавить поле «комментарий» в форму заказа. Он ответил: «Готово, форма работает». Что считать доказательством?

  1. Сам ответ агента: он видел код, а значит, знает, что всё правильно
  2. Запуск сценария («войти, создать заказ, увидеть его в списке») и зелёный результат, который вы видите сами
  3. То, что файл открывается в редакторе без красных подчёркиваний
  4. Отсутствие жалоб в течение первого дня

Слова агента — это гипотеза, а запуск — проверка. Подчёркиваний в редакторе мало: код может быть синтаксически верным и всё равно ломать сценарий. А ждать жалоб значит проверять на пользователях.

Какие из этих ошибок руками обычно не заметны, пока не проверишь специально? Выберите все верные.

  1. Обычный пользователь открывает /admin и видит страницу
  2. Заголовок на главной написан с опечаткой, и вы смотрите на него каждый день
  3. Пустая форма создаёт запись без названия
  4. Кнопка «Войти» не нажимается, и на неё сразу же заметно

Заметно то, на что вы смотрите. Незаметны проверки под другой ролью и с неверными данными: их никто не делает «заодно».

02 Сценарный тест руками: сначала понять, что проверяем

Автотест нельзя написать, пока вы сами не знаете, что должно происходить. Поэтому сначала сценарий проходят руками и записывают. Сценарий — это путь человека по продукту ради одной цели: «покупатель выбирает товар и оформляет заказ», «клиент записывается на приём», «менеджер добавляет клиента в CRM». Главный сценарий вашего выпускного проекта вы описали в ТЗ (урок 16) и сделали в спринте 2 (урок 18).

  • Ошибочный ввод: пустое поле, неверный пароль (шаг 5). Приложение должно ответить понятно, а не упасть.
  • Доступ: гость и обычный пользователь не получают чужого (шаги 1 и 6). Это связь с уроком 19: правило «защита на сервере» тоже проверяется тестом.
Аналогия из жизни

Маршрутка №8 в Душанбе: водитель знает маршрут по остановкам. Диспетчер, который проверяет рейс, идёт по тому же списку: «Рудаки, Исмоили Сомони, Садбарг, конечная». Сценарий — это список остановок вашего продукта: если какая-то остановка пропала, рейс не засчитывается.

Типичные ошибки новичков

1. Сценарий на пятьдесят шагов: тест будет хрупким и медленным. Хороший сценарий — 4–8 шагов к одной цели. 2. Ожидание «всё работает»: нужно конкретное, что видно на экране. 3. Только счастливый путь. 4. Тестовые данные из жизни (настоящая почта, чужие записи).

03 Автотест главного сценария: Playwright

Playwright — бесплатный инструмент, который открывает настоящий браузер и делает то, что делали бы вы: заходит на страницу, вводит текст, нажимает кнопки и проверяет, что на экране появилось нужное. Такие тесты называют e2e (end-to-end, «от края до края»): они проходят весь путь от браузера до базы данных. Вы запускаете одну команду, браузер на секунды открывается и закрывается, а в терминале виден список: что прошло, что нет.

Установка в проект Next.js

Официальный путь из документации Next.js: npm init playwright@latest в корне проекта. Команда задаст вопросы: язык (выбирайте TypeScript), папка с тестами (tests), нужен ли файл GitHub Actions (пока нет, к нему вернёмся в бонусе) и скачивать ли браузеры (да). Она добавит Playwright в package.json, создаст playwright.config.ts и пример tests/example.spec.ts. Браузеры весят сотни мегабайт, загрузка занимает несколько минут.

npm init playwright@latest
npx playwright test

Конфиг: запускаем сайт сами

Чтобы не открывать второй терминал, в конфиге есть блок webServer: Playwright запускает команду, ждёт, пока адрес ответит, и только потом начинает тесты. А baseURL позволяет писать в тестах короткие адреса вроде /login. Подправьте сгенерированный файл так (остальное сгенерированное можно оставить):

import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  // один браузер: быстрее и проще читать результат
  projects: [{ name: 'chromium', use: { ...devices['Desktop Chrome'] } }],
  use: {
    baseURL: 'http://localhost:3000',
    trace: 'on-first-retry',
  },
  webServer: {
    command: 'npm run dev',
    url: 'http://localhost:3000',
    reuseExistingServer: !process.env.CI,
    timeout: 120 * 1000,
  },
});

Документация Next.js советует гонять тесты на собранной версии (npm run build и npm run start), потому что она ближе к боевой. Для урока достаточно npm run dev: проще. Если на dev тесты иногда падают по времени, потому что страницы собираются при первом открытии, замените команду на npm run build && npm run start.

Как выглядит тест

Тест — это функция с именем, внутри которой шаги пользователя и проверки. Шаги: goto (открыть адрес), fill (ввести текст), click (нажать). Проверки: expect(...) с toBeVisible() («виден на странице») или toHaveURL() («адрес такой»). Элементы ищут так, как их видит человек: getByRole('button', { name: '...' }) («кнопка с таким названием»), getByLabel('...') («поле с такой подписью»), getByText('...'). В документации Playwright именно getByRole стоит первым в списке рекомендаций, а CSS-селекторы и XPath оставлены на крайний случай. Проверки expect умеют ждать: если элемент появляется через секунду, тест подождёт, а не упадёт сразу.

import { test, expect } from '@playwright/test';

// тест 1: гость на закрытой странице уходит на вход
test('guest is redirected to login', async ({ page }) => {
  await page.goto('/dashboard');
  await expect(page).toHaveURL(/\/login/);
});

// тест 2: вход и создание записи (главный сценарий)
test('user signs in and creates an item', async ({ page }) => {
  const title = 'e2e-item-' + Date.now(); // уникальное имя, чтобы тесты не мешали друг другу
  await page.goto('/login');
  await page.getByLabel('Email').fill(process.env.E2E_EMAIL!);
  await page.getByLabel('Password').fill(process.env.E2E_PASSWORD!);
  await page.getByRole('button', { name: 'Sign in' }).click();
  await expect(page).toHaveURL(/\/dashboard/);

  await page.getByRole('button', { name: 'New item' }).click();
  await page.getByLabel('Title').fill(title);
  await page.getByRole('button', { name: 'Save' }).click();
  await expect(page.getByText(title)).toBeVisible();
});

Подписи в кавычках («Sign in», «New item») в примере английские: у вашего проекта они свои, например «Войти». Тест должен искать то, что написано на экране вашего сайта. Пароль и почта тестового пользователя берутся из process.env, то есть из файла .env.test (он закрыт в .gitignore так же, как .env.local), а не из кода: это то же правило про секреты, что и в уроке 19.

Запуск, отчёт и разбор падения

  • npx playwright test запускает все тесты в тихом режиме (без окна браузера).
  • npx playwright test --ui открывает окно, где видно каждый шаг теста и снимок страницы на нём: лучший способ понять, что произошло.
  • npx playwright test --headed показывает настоящее окно браузера.
  • npx playwright show-report открывает HTML-отчёт: список тестов, причина падения, снимок и шаги.

Как читать красный результат

  1. Название теста. По нему понятно, какой шаг сценария сломан.
  2. Строка ошибки. Например, expect(locator).toBeVisible() failed и Timeout 5000ms exceeded: ждали-ждали и не дождались.
  3. Что искали. Строка Locator: показывает, какой элемент. Если текст на сайте поменяли, тест не нашёл кнопку.
  4. Решение: баг или устаревший тест? Если сломан сайт, чините код. Если вы сознательно изменили текст, обновляйте тест. Не «чините» тест, чтобы он стал зелёным, не разобравшись.

Если не хочется писать шаги, Playwright умеет записывать их: команда npx playwright codegen http://localhost:3000 открывает браузер и окно Playwright Inspector. Вы кликаете по сайту, а клики превращаются в код, который можно скопировать. В панели есть кнопки проверок (видимость, текст, значение): так вы добавляете expect. Запись даёт черновик; прочитайте его и переименуйте тест понятным именем.

Почему тест «флакает»

Бывает, что тест то зелёный, то красный без правок кода. Такой тест называют флакающим (flaky), и он хуже отсутствия теста: ему перестают верить. Частые причины:

  • Жёсткая пауза вместо ожидания: waitForTimeout(2000). Сегодня хватает двух секунд, завтра сервер медленнее. Правильно ждать конкретное: await expect(...).toBeVisible().
  • Общие данные: два теста создают запись с одним названием или удаляют данные друг друга. Лечится уникальными именами (Date.now()) и независимыми тестами.
  • Хрупкий поиск: «третья кнопка на странице» (nth) или длинная цепочка CSS-классов. Добавили кнопку, и тест нашёл другую. Лучше getByRole с названием.
  • Медленный первый запуск сервера разработки: страница собирается при первом заходе. Лечится увеличением timeout или запуском на собранной версии.
  • Зависимость от порядка: тест 2 работает только если до него прошёл тест 1.
Аналогия из жизни

Весы на бозоре. Если они показывают то 1 кг, то 1,2 кг на одном и том же товаре, вы не станете им верить и перестанете смотреть на стрелку. Флакающий тест — такие же весы: команда привыкает «перезапустить, может позеленеет» и пропускает настоящую поломку.

Типичные ошибки новичков

1. Тест без expect: он «проходит», потому что ничего не проверяет. 2. Пароль или ключ прямо в тесте и в репозитории. 3. Тест против боевой базы с настоящими данными: создали мусор или удалили чужое. 4. Тест, который проверяет текст кнопки, а не результат («кнопка есть» вместо «запись появилась»). 5. Перезапускать, пока не позеленеет, не выяснив причину.

ЗАДАЧА 3.1

Мини-раннер тестов: почини функцию, чтобы все проверки прошли

средняя

Это игрушечная версия того, что делает Playwright: функция test запускает проверку и печатает PASS или FAIL с причиной. Функция applyDiscount(price, percent) должна считать цену со скидкой в процентах и округлять до целого. Сейчас она ошибается: тест покажет, где именно. Исправьте только функцию (первые строки), не трогая тесты ниже.

function applyDiscount(price, percent) {
  // TODO: percent это проценты (10 значит 10%), результат округлить до целого
  return price - price * percent;
}

let passed = 0;
let total = 0;
function test(name, fn) {
  total++;
  try {
    fn();
    passed++;
    console.log("PASS " + name);
  } catch (e) {
    console.log("FAIL " + name + " -> " + e.message);
  }
}
function expectEqual(actual, expected) {
  if (actual !== expected) {
    throw new Error("expected " + expected + ", got " + actual);
  }
}

test("10% off 200", () => expectEqual(applyDiscount(200, 10), 180));
test("0% changes nothing", () => expectEqual(applyDiscount(200, 0), 200));
test("100% gives 0", () => expectEqual(applyDiscount(50, 100), 0));
test("rounds to whole somoni", () => expectEqual(applyDiscount(99, 15), 84));

console.log("passed: " + passed + " of " + total);
Ожидаемый результат
PASS 10% off 200
PASS 0% changes nothing
PASS 100% gives 0
PASS rounds to whole somoni
passed: 4 of 4
Подсказка 1

Запустите как есть и прочитайте строки FAIL: там написано, что ожидали и что получили. Процент нужно разделить на 100.

Подсказка 2

Правильная строка: return Math.round(price - price * percent / 100);. Math.round округляет до ближайшего целого.

ЗАДАЧА 3.2

Что проверяет этот тест

средняя

Прочитайте тест, который агент написал для формы заказа.

import { test, expect } from '@playwright/test';

test('order form works', async ({ page }) => {
  await page.goto('/orders/new');
  await page.getByLabel('Title').fill('Test order');
  await page.getByRole('button', { name: 'Save' }).click();
  await page.waitForTimeout(2000);
});

Что на самом деле проверяет этот тест?

  1. Что заказ создаётся и появляется в списке
  2. Что после нажатия «Save» открывается страница со списком заказов
  3. Почти ничего: он лишь убеждается, что страница открывается, поле находится и кнопка нажимается. Результат не проверен, поэтому он зелёный и при сломанном сохранении
  4. Что сервер отвечает за две секунды

В тесте нет ни одного expect после нажатия. Пауза в 2 секунды ничего не проверяет, она только тратит время. Исправление: убрать паузу и добавить await expect(page.getByText('Test order')).toBeVisible();.

Вы просите агента: «Добавь в этот тест проверку». Какая формулировка даст хорошую проверку?

  1. «Сделай, чтобы тест был зелёным»
  2. «После нажатия Save проверь, что на странице виден текст заказа; пауза не нужна, жди появления текста»
  3. «Добавь побольше проверок на всякий случай»
  4. «Проверь, что всё работает»

Хорошая просьба называет, что именно должно появиться на экране, и запрещает паузы. «Сделай зелёным» приглашает агента подогнать тест под результат, а «проверь всё» не говорит, что считать успехом.

ЗАДАЧА 3.3

Почему тест флакает

сложная

Тест создаёт заказ с названием 'Test order' и ищет его в списке через getByText('Test order'). С первого запуска зелёный, при втором и третьем красный: Playwright пишет «strict mode violation: resolved to 3 elements». В чём причина?

  1. Каждый запуск оставляет запись с тем же названием; в списке уже несколько одинаковых, и поиск находит больше одного элемента. Нужно уникальное название на каждый запуск ('e2e-' + Date.now()) и уборка тестовых записей
  2. У Playwright закончилась лицензия
  3. Браузер Chromium устарел
  4. Агент неправильно записал слово test

Это классическая ошибка общих данных: первый запуск прошёл, а следующие видят следы предыдущих. Лечится уникальным названием и удалением созданного (в конце теста или отдельным шагом очистки).

Тест нажимает «Save» и сразу же проверяет toBeVisible() текст в списке. На быстром компьютере зелёный, на медленном иногда красный. Агент предлагает вставить waitForTimeout(3000) перед проверкой. Что правильнее?

  1. Поставить паузу 10 секунд: чем больше, тем надёжнее
  2. Запускать тест по пять раз и считать успехом хотя бы один зелёный
  3. Удалить тест: он слишком капризный
  4. Не вставлять паузу, а ждать конкретный признак: проверка expect(...).toBeVisible() сама ждёт появления, поэтому нужно проверить, что отправка действительно завершилась (например, дождаться сообщения об успехе), а при медленном сервере увеличить таймаут

Фиксированная пауза либо слишком короткая, либо тратит время зря. Проверки Playwright повторяются до таймаута, так что достаточно ждать конкретное событие. «Один зелёный из пяти» скрывает поломку.

04 Логи и ошибки на продакшене: Vercel Logs

Тесты ловят поломки до релиза. Но иногда сайт на Vercel ведёт себя не так, как у вас на компьютере: нет переменной окружения, другая версия данных, неожиданный ввод. Пользователь видит «Something went wrong», а вы не видите ничего. Здесь нужны логи: журнал, куда сервер записывает, что происходило. Это дневник сервера: время, адрес, код ответа и сообщения, которые вы сами вывели через console.log и console.error.

Где смотреть на Vercel

  1. Откройте панель Vercel, выберите проект.
  2. В боковом меню проекта откройте Logs. Здесь Runtime Logs: журнал вызовов серверных функций (ваши route.ts, серверные действия, страницы с отрисовкой на сервере) в боевой и в предпросмотровой версиях.
  3. Слева фильтры: время, уровень (Error, Warning), маршрут (Route), путь запроса, код ответа (Status Code), окружение (production или preview). Есть поиск по тексту сообщений и режим Live mode: записи появляются на глазах.
  4. Нажмите на строку: справа откроются подробности (метод, путь, код, регион, имя функции) и снизу Log Messages: ваши console.log и console.error.

Как читать коды: 2xx успех, 4xx ошибка запроса (401 «не вошли», 403 «нельзя», 404 «нет такого»; Vercel подсвечивает их как предупреждение), 5xx ошибка сервера (подсвечена как ошибка; это почти всегда баг у вас). Строка console.error(...) отмечена уровнем error, а console.log(...) уровнем info.

На бесплатном тарифе логи живут недолго

По документации Vercel, на тарифе Hobby Runtime Logs хранятся 1 час, на Pro — 1 день. Поэтому привычка такая: произошла ошибка, откройте логи сразу, а не «завтра посмотрю». Чтобы повторить ошибку, сами сделайте тот же запрос на боевом сайте и сразу найдите его в Logs.

Что писать в логи, чтобы потом найти причину

export async function POST(request: Request) {
  try {
    // ... проверка входа, чтение данных, запись в Supabase
    return Response.json({ ok: true });
  } catch (error) {
    // понятная метка + сообщение; без паролей, токенов и целых объектов пользователя
    console.error('orders.create failed:', error instanceof Error ? error.message : error);
    return Response.json({ error: 'Something went wrong' }, { status: 500 });
  }
}
  • Метка места в начале: orders.create failed легко искать в поиске.
  • Сообщение ошибки, а не просто «ошибка».
  • Не писать секреты: пароль, токен, ключ, полный e-mail и данные клиентов в лог не попадают. Логи видит каждый, у кого есть доступ к проекту.
  • Не молчать: пустой блок catch {} прячет ошибку от вас самих.

Логи из терминала и вместе с агентом

У Vercel есть консольная программа (Vercel CLI). В папке подключённого проекта команда vercel logs показывает последние записи (по умолчанию за 30 минут), а флаги сужают поиск. Пример из документации Vercel: vercel logs --environment production --query 'level:error' --since 1h. Вывод можно показать агенту: «вот логи, найди причину в коде». Но саму находку проверяйте: агент догадывается, а лог показывает факт.

Типичные ошибки новичков

1. Искать серверную ошибку в консоли браузера и наоборот. 2. Открыть логи через сутки на Hobby: записей уже нет. 3. Логировать пароль «для отладки». 4. Ограничиться «500 в логах» и не прочитать текст в Log Messages. 5. Править код наугад, не воспроизведя запрос.

Пользователь пишет: «Нажала кнопку, ничего не сохранилось». Где искать причину сначала?

06 ИИ-блок: агент пишет тесты, вы проверяете

Правила работы с агентом над тестами

1. Тест пишет агент, а читаете и запускаете вы. Попросите его объяснить каждый тест одной фразой: если не понимаете, что проверяется, тест вам не принадлежит. 2. Требуйте проверку результата (expect на то, что видит человек), а не «страница открылась». 3. Запрет: не менять код приложения, чтобы тест позеленел, и не ослаблять проверки без вашего согласия. 4. Красный тест лучше не «чинить» вслепую: вставьте в чат полный текст ошибки и спросите, где баг: в коде или в тесте. 5. Итерация, а не перезапуск: один тест за раз, зелёный, commit, следующий.

Плохой промпт даёт тест, который ничего не проверяет, или два десятка тестов на всё подряд:

Напиши тесты для моего проекта

Шаг 1. Настройка (один раз):

Контекст: выпускной проект Next.js 16 (App Router, TypeScript) с Supabase и деплоем на Vercel, правила проекта в @AGENTS.md. Нужны e2e-тесты Playwright. Главный сценарий описан в @docs/test-scenarios.md. Цель: установить и настроить Playwright по официальной документации (npm init playwright@latest, один браузер chromium), в playwright.config.ts задать baseURL http://localhost:3000 и webServer с командой npm run dev. Добавить в package.json скрипт "test:e2e": "playwright test". Учётные данные тестового пользователя читать из переменных окружения E2E_EMAIL и E2E_PASSWORD из файла .env.test; убедиться, что .env.test закрыт в .gitignore, и добавить .env.test.example без значений. Ограничения: 1) код приложения не менять; 2) не печатать пароли в консоль и не вставлять их в код; 3) не устанавливать лишних библиотек; 4) сначала покажи план из 3–5 пунктов. Проверка: после настройки запусти npx playwright test с примером и покажи вывод целиком.

Шаг 2. Тесты по одному:

Контекст: Playwright настроен (@playwright.config.ts), сценарий в @docs/test-scenarios.md, код страниц в @app. Подписи кнопок и полей брать из реальных страниц проекта, не выдумывать. Цель: написать три теста в tests/main-flow.spec.ts: 1) гость открывает закрытую страницу и попадает на страницу входа; 2) тестовый пользователь входит, создаёт запись с уникальным названием ('e2e-' + Date.now()) и видит её в списке; 3) обычный пользователь не видит админскую страницу (редирект или 403, как сделано в проекте). Первым напиши только тест 1, запусти его, потом по очереди остальные. Ограничения: 1) искать элементы через getByRole, getByLabel, getByText; 2) никаких waitForTimeout: ждать через expect; 3) после каждого действия есть проверка результата; 4) тесты независимы друг от друга; 5) код приложения не менять. Проверка: после каждого теста запусти npx playwright test и покажи вывод. В конце одной фразой объясни, что проверяет каждый тест и что он НЕ проверяет.

Шаг 3. Красный тест:

07 Практика: три автотеста, баг, логи, README

Правила безопасности практики

Тесты запускаются только против учебного проекта Supabase и вашего сайта, никаких чужих сайтов и боевых данных. Пароль тестового пользователя живёт в .env.test, который не попадает в git. Тестовые записи называем с префиксом e2e-, чтобы их было легко найти и удалить.

Подготовка

  1. Ветка: git switch main, git pull, git switch -c tests.
  2. Проверьте Node: node -v (22 или новее). Если версия старая, обновите Node с сайта nodejs.org.
  3. Запишите главный сценарий в docs/test-scenarios.md и пройдите его руками (задача 2.1).
  4. В панели Supabase откройте Authentication, раздел Users, создайте нового пользователя (кнопка «Add user», затем создание с e-mail и паролем; названия на экране могут отличаться). Почта придуманная, например e2e-test@example.com, пароль длинный и случайный. Если в проекте включено подтверждение почты, отметьте подтверждение при создании. Роль у пользователя обычная.
  5. Создайте файл .env.test с двумя строками E2E_EMAIL=… и E2E_PASSWORD=…. Проверьте командой git check-ignore -v .env.test, что файл игнорируется (она должна вывести правило из .gitignore). Если вывода нет, добавьте строку в .gitignore до первого commit.

Установка и первый запуск

  1. Скопируйте промпт «Шаг 1» из раздела 6 в Cursor (режим Agent, правила проекта в контексте). Агент поставит Playwright, настроит конфиг и скрипт test:e2e.
  2. Запустите сами: npm run test:e2e. Дождитесь результата. Пример теста должен пройти (если агент оставил пример) или команда должна сказать «No tests found»: оба варианта означают, что установка работает.
  3. Если пишет «Executable doesn't exist», выполните npx playwright install: так скачиваются браузеры.

Три теста по одному

  1. Промпт «Шаг 2» из раздела 6. Попросите начать с теста 1 (гость уходит на вход). Запустите npm run test:e2e, прочитайте тест и объясните его себе вслух: что он делает и что проверяет. Commit: add guest redirect test.
  2. Тест 2: вход и создание записи. Запустите npm run test:e2e -- --ui (параметры после -- передаются Playwright) и посмотрите шаги в окне. Должно быть: вошли, нажали «создать», запись появилась в списке. Commit: add create item test.
  3. Тест 3: обычный пользователь не видит админку. Запустите. Commit: add admin access test.
  4. Запустите весь набор трижды подряд. Три зелёных прогона: тесты стабильны. Если один раз упал, это флакающий тест: найдите причину по разделу 3 (чаще всего паузы и общие данные).
Тестовые записи не должны копиться

Если тест создаёт запись, она остаётся в базе. Попросите агента: «Добавь в конец теста удаление созданной записи через интерфейс или хуком test.afterEach; если удалить нельзя, оставь префикс e2e- и опиши в README, как чистить». Для учебной базы хватает префикса и ручной уборки раз в неделю.

Если сломалось

Timeout waiting for http://localhost:3000. Сервер не поднялся за отведённое время или порт занят: закройте другие npm run dev и увеличьте timeout в webServer. Error: locator.fill: Timeout … waiting for getByLabel('Email'). На странице нет поля с такой подписью: откройте страницу, посмотрите настоящую подпись и исправьте её в тесте (агент мог выдумать). E2E_EMAIL is undefined. Файл .env.test не подхвачен: попросите агента подключить его в playwright.config.ts (например, через пакет dotenv или встроенную загрузку Node) и показать, что переменная читается, не печатая её значение. Invalid login credentials. Пользователь создан в другом проекте Supabase или пароль не совпадает. Любую ошибку отправьте агенту целиком с вопросом «баг в приложении или в тесте?».

Ловим и чиним баг

Теперь главное доказательство пользы тестов: изменение, которое должен поймать красный тест.

  1. Попросите агента сделать небольшую настоящую правку, например: «Добавь в форму создания записи обязательное поле, а пустое название не принимай и показывай ошибку». Или сами поменяйте подпись кнопки «Сохранить». Реалистичная правка чаще всего задевает соседний сценарий.
  2. Запустите npm run test:e2e. Хотя бы один тест должен стать красным. Откройте npx playwright show-report, прочитайте ошибку и строку Locator:.
  3. Решите: баг в приложении или тест устарел. Используйте промпт «Шаг 3» из раздела 6.
  4. Почините (код или тест, но осознанно), запустите ещё раз: три зелёных. Commit: fix create form after validation (или ваш вариант).
  5. Запишите в docs/test-scenarios.md одну строку: что сломалось, какой тест поймал, как починили.

Логи на Vercel

  1. Закоммитьте тесты, отправьте ветку: git push -u origin tests. Vercel соберёт предпросмотровую версию (Preview) для ветки; ссылка в панели проекта, раздел Deployments.
  2. Убедитесь, что серверный маршрут вашего главного сценария пишет console.error в блоке catch (пример в разделе 4). Если нет, попросите агента добавить метку и сообщение, без секретов и персональных данных.

Безопасный способ: откройте консоль браузера (F12, вкладка Console) на своём сайте вне входа и выполните fetch('/api/orders', { method: 'POST' }) с адресом своего маршрута. Ожидаемо придёт 401 или 403.

08 Фишка урока: «Красная кнопка»

Идея: проверить не код, а тесты. Если преподаватель нарочно ломает проект, ваши тесты обязаны покраснеть. Если остались зелёными, они проверяют слишком мало. Время: 20–30 минут, играют парами или командами по 3–4 человека.

Правила безопасности игры

Ломаем только в локальной ветке red-button, созданной от рабочей ветки с тестами. Поломку не отправляем на GitHub и на Vercel и не сливаем ни во что. После игры ветку удаляют: git switch tests (или main), затем git branch -D red-button. Принудительный push не используем.

Раунды (преподаватель выбирает поломку)

РаундПоломкаКакой тест должен поймать
1Убрать проверку входа со страницы /dashboard (гость её видит)Тест 1
2Переименовать кнопку «Сохранить» или поле «Название»Тест 2
3Из серверного маршрута убрать сохранение в базу, оставив ответ «ok»Тест 2 (запись не появится в списке)
4Убрать проверку роли с /admin (обычному пользователю открывается)Тест 3
5Пустое название принимается и создаёт запись «без названия»Нужен новый тест на ошибочный ввод (задание со звёздочкой)

Как играть и считать очки

  1. Преподаватель объявляет раунд и поломку. Каждый вносит её руками или просит агента (промпт: «Внеси в проект только эту поломку: …; больше ничего не меняй») в ветке red-button.
  2. Таймер 3 минуты. Запустите npm run test:e2e. Если нужный тест покраснел: +2 очка и назовите, какой тест и какая строка ошибки показала поломку.
  3. Если тесты остались зелёными, очков нет: значит, поломку никто не ловит. За 5 минут напишите новый тест (с агентом), который краснеет на этой поломке и зеленеет без неё: +3 очка.
  4. Между раундами вернитесь: git restore . (сбросит неотправленные правки в файлах) или git reset --hard на commit с зелёными тестами (только для локальной ветки).
  5. Пары по кругу (по желанию): ломайте проект друг друга по секрету. Задача соседа: по красному отчёту найти поломку за 5 минут. Кто нашёл быстрее, получает +1.
Что запомнить после игры

Зелёный тест сильнее, когда вы видели его красным. Привычка профессионала: написал тест, сломал код на минуту, убедился, что тест покраснел, вернул. Тогда зелёный цвет что-то значит.

  • Синтаксис: page.goto, fill, click; поиск getByRole (предпочтительно), getByLabel, getByText; проверки expect(...).toBeVisible(), toHaveURL(), toHaveText() сами ждут.
  • Флакающие тесты: причины: паузы waitForTimeout, общие данные, хрупкие селекторы (nth), медленный dev-сервер, зависимость от порядка. Лечение: ждать конкретное, уникальные данные, независимые тесты.
  • Красный тест: прочитать ошибку и Locator, решить «баг или устаревший тест», не ослаблять проверку, чтобы позеленело.
  • Агент и тесты: просить проверку результата, один тест за раз, запрет менять код ради теста; вывод запуска смотрит человек; пароли в .env.test, а не в коде.
  • Vercel Logs: проект, Logs в боковом меню; фильтры (уровень, маршрут, путь, код, окружение), Live mode, Log Messages; Hobby хранит 1 час; в терминале vercel logs. Build logs, Runtime Logs и консоль браузера показывают разное.
  • В логах: console.error('метка:', message); без секретов; 4xx предупреждение, 5xx ошибка сервера.
  • README: что это, ссылка, снимок, роли, стек, запуск, переменные (только имена), тесты, ограничения; все команды проверены в чистой копии.
  • Красная кнопка: поломка в локальной ветке должна покраснеть в тестах; не поймали, значит, нужен ещё тест.
