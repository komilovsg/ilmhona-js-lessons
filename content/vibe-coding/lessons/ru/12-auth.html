01 Кто вы и что вам можно: два разных вопроса

В уроке 11 страница /admin открывалась любому, кто знал ссылку. Чтобы это исправить, сайту нужно ответить на два разных вопроса, и их часто путают.

Аутентификация (authentication)
Проверка личности: «вы действительно Мадина?» Доказательство: пароль, код из письма, вход через Google. Результат: сайт знает, кто перед ним.
Авторизация (authorization)
Проверка прав: «а что Мадине можно?» Читать свои заявки — да, читать чужие — нет, открывать /admin — только администратору. Результат: сайт знает, что разрешено.

Порядок всегда один: сначала аутентификация, потом авторизация. Нельзя решить, что можно Мадине, пока не знаешь, что это она.

Ролик на русском, меньше минуты: то же самое другими словами.

Аналогия из жизни

Вход в бизнес-центр в Душанбе. У турникета охранник сверяет ваш паспорт с пропуском: это аутентификация. Дальше пропуск открывает только ваш этаж, а на этаж директора лифт не едет: это авторизация. Паспорт есть у многих, но права у всех разные.

Типичные ошибки новичков

1. Думать, что «вошёл» значит «можно всё»: вошедший Фирдавс не должен видеть заявки Мадины. 2. Прятать кнопку «Админка» в меню и считать, что страница защищена: адрес всё равно можно набрать руками. 3. Проверять права только в интерфейсе (скрыть кнопку), но не на сервере и не в базе. Интерфейс видно и можно обойти, поэтому настоящая проверка живёт там, куда посетитель не дотянется.

02 Способы входа: e-mail с паролем и вход через Google

Supabase Auth — готовая служба входа, встроенная в ваш проект Supabase. Вы не пишете хранение паролей сами: служба принимает e-mail и пароль, хранит не пароль, а его хеш (необратимый «отпечаток»), и ни вы, ни владелец проекта пароль увидеть не можете. Пользователи лежат в служебной таблице auth.users, которую вы в панели смотрите в разделе Authentication → Users.

В коде это одна функция на действие (клиент supabase вы настроите в практике):

// Регистрация: имя уйдёт в служебные данные пользователя
const { data, error } = await supabase.auth.signUp({
  email,
  password,
  options: { data: { full_name: fullName } },
});

// Вход
const { error } = await supabase.auth.signInWithPassword({ email, password });

// Выход
await supabase.auth.signOut();

Каждая функция возвращает { data, error }, как запросы из урока 11: если error не пустой, показываем понятное сообщение («неверный e-mail или пароль»), а не alert с техническим текстом.

Подтверждение e-mail и лимит писем (важно для занятия)

По умолчанию на новом проекте включена настройка Confirm email: после регистрации пользователь получает письмо со ссылкой и войти может только после клика. Для настоящего продукта это правильно: так никто не зарегистрирует чужой адрес. Но на занятии у неё есть жёсткое ограничение.

Встроенная почта Supabase не рассчитана на группу

По документации Supabase (проверено в октябре 2026), встроенный отправитель писем даёт сейчас 2 письма в час, причём доставляет их только адресам участников команды (организации) вашего проекта, остальным приходит ошибка Email address not authorized. Он нужен для пробы и демо, а не для работы группы из 15 человек. Цифры Supabase меняет без предупреждения: актуальные смотрите в документации.

Поэтому на уроке есть два пути:

  • Путь 1 (делаем на уроке): отключить подтверждение. В панели Authentication → Sign In / Providers → Email выключите переключатель Confirm email (название раздела в панели может слегка отличаться: ищите настройки провайдера Email). Тогда после регистрации пользователь входит сразу, письма не нужны. Для учебного сайта с вымышленными данными это нормально.
  • Путь 2 (для настоящего продукта): свой SMTP. В настройках Authentication есть раздел SMTP: вы подключаете любой почтовый сервис, у которого есть SMTP-доступ (хост, порт, логин, пароль и адрес отправителя). После этого письма уходят любым адресам; лимит сначала ставится 30 писем в час и поднимается в разделе Rate Limits. Для настоящего домена добавляют записи SPF, DKIM и DMARC, чтобы письма не попадали в спам.

Помните: при выключенном подтверждении любой может зарегистрироваться на чужой адрес. Когда сайт станет настоящим продуктом с живыми пользователями, подтверждение нужно вернуть и подключить свой SMTP. Документация Supabase прямо советует не отключать подтверждение «под давлением» в рабочем проекте.

Ещё две настройки на этой же странице. Минимальная длина пароля: поставьте не меньше 8 символов. И URL Configuration: туда вписывают адрес сайта (Site URL) и разрешённые адреса возврата (Redirect URLs). Они нужны для входа через Google и для ссылок из писем (раздел 7, шаг 3).

Аналогия из жизни

Вход через Google — как пропуск в бизнес-центр по паспорту, который проверил кто-то другой. Охранник не знает ваш пароль от почты, он доверяет Google, что вы это вы. Ваш сайт получает от Google подтверждение «это Мадина, вот её e-mail», а пароль остаётся у Google.

Типичные ошибки новичков

1. Хранить пароли самим в своей таблице (users.password): так делать нельзя, используйте Auth. 2. Писать пароль в console.log или присылать его ИИ при поиске ошибки. 3. Оставить Confirm email включённым без своей почты и зависнуть на регистрации второго пользователя. 4. Тестировать на настоящих паролях: придумайте учебный вроде Test-2026-pass и не используйте его нигде больше. 5. Сказать пользователю «пароль неверен» или «такого e-mail нет» раздельно: так подсказывают, какие адреса зарегистрированы. Лучше «неверный e-mail или пароль».

03 Сессии и токены: как сайт «помнит», что вы вошли

Из урока 10 вы знаете, что каждый запрос к серверу независим: сервер сам по себе не помнит предыдущий. Так как же он понимает на странице /account, что это вы? Через сессию: после входа вы получаете «билет», и браузер прикладывает его к каждому запросу.

Сессия
Период, пока вы «вошли»: от входа до выхода (или пока билет не отозван).
Access-токен (JWT)
Короткоживущий «билет» с вашими данными внутри: id пользователя, e-mail, роль в базе (authenticated), срок действия. Подписан Supabase, поэтому подделать его нельзя. В Supabase по умолчанию живёт 1 час.
Refresh-токен
«Билет на новый билет»: когда access-токен кончается, по refresh-токену выдаётся новая пара. Каждый refresh-токен меняется на новый только один раз, а повторное использование считается кражей и закрывает сессию.
Cookie
Маленький файл, который браузер хранит и сам отправляет сайту с каждым запросом. В Next.js с @supabase/ssr токены лежат именно в cookie, поэтому сервер видит их при отрисовке страницы.

Токен можно прочитать, но нельзя подделать

JWT состоит из трёх частей через точку: заголовок, данные и подпись. Данные не зашифрованы, а лишь закодированы: любой может их прочитать. Зато подпись сделана секретом Supabase, и если изменить хоть один символ данных, подпись перестанет сходиться и сервер токен отвергнет. Поэтому никогда не кладите в токен или в публичные данные ничего секретного, и никогда не доверяйте «данным, которые прислал браузер» без проверки подписи. Попробуйте сами:

Два метода проверки: getClaims и getSession

В серверном коде проверять вошедшего нужно через supabase.auth.getClaims(): он проверяет подпись токена и возвращает его данные (claims), среди них sub — id пользователя. Метод getSession() просто читает cookie без проверки подписи, и по документации Supabase доверять ему в серверном коде нельзя: cookie может прислать кто угодно.

Аналогия из жизни

Подделать печать на талоне нельзя, а прочитать, что там написано, может любой. Потеряли абонемент — кассир видит, что им воспользовались дважды, и блокирует.

Типичные ошибки новичков

1. Верить getSession() на сервере вместо getClaims(). 2. Выкладывать токены в чат, на скриншот или в Git: тот, у кого есть ваш access-токен, действует от вашего имени до окончания срока. 3. Забыть, что выход (signOut()) по умолчанию закрывает сессию на всех устройствах (область global; для текущего только { scope: "local" }). 4. Класть в localStorage свои «токены» вместо готовых средств Supabase: так вы заново изобретаете то, что уже сделано и проверено.

ЗАДАЧА 3.2

Проверь себя: сессии и токены

средняя

Токен JWT не зашифрован, любой может прочитать его данные. Почему его всё равно нельзя подделать?

  1. Потому что его знает только владелец
  2. Потому что он подписан секретом Supabase: при любом изменении данных подпись перестанет сходиться
  3. Потому что он хранится на сервере
  4. Потому что браузер не даёт его изменять

Читать может каждый, менять незаметно нельзя: подпись проверяется на сервере.

Что делает refresh-токен?

  1. Обменивается на новую пару токенов, когда access-токен устарел (по умолчанию он живёт час)
  2. Заменяет пароль при входе
  3. Хранит данные профиля
  4. Шифрует cookie

Короткий срок access-токена безопаснее при утечке, а refresh-токен позволяет не просить пароль каждый час.

Серверная страница должна узнать, кто вошёл. Что вызвать?

  1. getSession(): он быстрее
  2. Прочитать cookie руками и взять id оттуда
  3. getClaims(): он проверяет подпись токена
  4. Ничего: Next.js сам знает пользователя

Cookie приходит из браузера и может быть подделан. getClaims() проверяет подпись, поэтому ему доверяют.

04 Защищённые страницы: три слоя замка

Закрыть страницу «одной проверкой» ненадёжно. Профессионально защиту делают тремя слоями: если один подвёл, остальные держат.

Слой 1: proxy.ts (в Next.js 16)

Файл в корне проекта (рядом с app), который выполняется до отрисовки страницы. В Next.js 16 он называется proxy.ts, а функция внутри — proxy. В версиях до 16 это был middleware.ts с функцией middleware: старые руководства и ответы ИИ часто пишут именно так. По документации Supabase, если в проекте Next.js 16 лежит файл со старым именем, он не вызывается, и сессии перестают обновляться. Ещё один важный момент: сам Next.js предупреждает, что proxy годится для быстрых «оптимистичных» проверок, но не должен быть единственной защитой.

В proxy делают две вещи: обновляют токены в cookie (через getClaims()) и отправляют незваных гостей на /login.

Слой 2: проверка на самой странице

Серверная страница сама спрашивает getClaims(). Нет пользователя — redirect("/login"). Нужна роль администратора — читаем её из таблицы profiles (раздел 5) и показываем страницу или notFound().

Слой 3: RLS

Вы уже знаете RLS из урока 11. Теперь у него появляется главный инструмент: функция auth.uid(), которая внутри базы возвращает id вошедшего пользователя (берёт его из токена, который подписан и подделать нельзя). Правило «каждый видит только свои строки» пишется так: using ((select auth.uid()) = user_id).

Аналогия из жизни

Хранилище в банке. Охранник у входа отсекает случайных прохожих (proxy). Операционист проверяет паспорт и карту клиента (страница). А сам сейф открывается только ключом именно этого клиента (RLS). Если операционист ошибся, сейф всё равно не откроется чужому.

Типичные ошибки новичков

1. Проверять вход только в proxy: матчер можно написать неточно, и какая-то страница останется открытой. 2. Не писать RLS вообще, полагаясь на то, что «ссылку никто не знает». 3. Оставить в proxy код из старого руководства под именем middleware.ts и недоумевать, почему «сессия вылетает». 4. Редиректить на адрес из параметра ?next= без проверки: злоумышленник подставит чужой сайт. Допускайте только пути, которые начинаются с одного /.

05 Роли: пользователь и администратор

Роль — ярлык, по которому сайт решает, что вам можно. У нас их две: user (обычный клиент) и admin (владелец ресторана, видит все заявки). Роль нужно где-то хранить, и вот здесь новички допускают самую опасную ошибку.

Главное правило раздела

Нельзя хранить роль в user_metadata (данные, которые пользователь передаёт при регистрации через options.data): по документации Supabase, пользователь может сам их изменить. Достаточно одной строчки в консоли браузера, и он «станет админом». Роль храните в таблице, которую пользователь изменить не может, или в app_metadata, который доступен для записи только серверу.

Мы выберем таблицу profiles: она же нужна для личного кабинета. Одна строка на пользователя: id совпадает с auth.users.id, плюс имя, телефон и роль.

Как создаётся профиль и как выдаётся админство

  • Профиль создаёт триггер. Триггер — действие, которое база выполняет сама при событии. «После новой строки в auth.users добавь строку в profiles» (SQL в практике). Роль при этом всегда user: из регистрации её не взять.
  • Админа назначаете вы вручную в SQL Editor: update profiles set role = 'admin' where …. SQL Editor работает от имени владельца базы, а не от пользователя сайта.
  • Что может пользователь. Читать и менять только свой профиль и только имя с телефоном. Столбец role ему недоступен: ему не выдаётся право менять его (grant update (full_name, phone)).
  • Как база узнаёт админа. Небольшая функция is_admin() смотрит роль в profiles, а правила для заявок и профилей вызывают её.
Аналогия из жизни

Бейджи на конференции. Ваше имя на бейдже вы пишете сами, а цвет бейджа («организатор» или «гость») выдаёт регистрация. Если цвет можно подкрасить маркером на месте, кто угодно станет организатором. Поэтому роль хранится там, где маркер не достанет.

Типичные ошибки новичков

1. Роль в user_metadata или в localStorage. 2. Правило «пользователь обновляет свою строку» без ограничения столбцов: тогда он поменяет свою role на admin. 3. Проверять админа только в меню интерфейса. 4. Назначить админом себя на настоящем сайте с реальными пользователями и забыть сменить пароль на надёжный. 5. Дать ИИ секретный ключ, чтобы «админка заработала»: роль решается правилами, а не ключом, который обходит RLS.

Проверь себя: где хранить роль

средняя

Где безопасно хранить роль admin?

  1. В таблице profiles, столбец role которой пользователь не может менять
  2. В user_metadata при регистрации
  3. В localStorage браузера
  4. В скрытом поле формы регистрации

Всё, что пользователь может изменить сам (метаданные пользователя, браузер, формы), для хранения прав не годится.

/* 1. Профили: по одной строке на пользователя */
create table profiles (
  id uuid primary key references auth.users (id) on delete cascade,
  full_name text check (char_length(full_name) <= 80),
  phone text check (char_length(phone) <= 30),
  role text not null default 'user' check (role in ('user', 'admin')),
  created_at timestamptz not null default now()
);
alter table profiles enable row level security;

/* 2. Триггер: профиль создаётся сам при регистрации, роль всегда user */
create function public.handle_new_user()
returns trigger
language plpgsql
security definer
set search_path = ''
as $$
begin
  insert into public.profiles (id, full_name)
  values (new.id, left(new.raw_user_meta_data ->> 'full_name', 80));
  return new;
end;
$$;

create trigger on_auth_user_created
after insert on auth.users
for each row execute function public.handle_new_user();

/* 3. Функция: админ ли вошедший пользователь */
create function public.is_admin()
returns boolean
language sql
stable
security definer
set search_path = ''
as $$
  select exists (
    select 1 from public.profiles
    where id = (select auth.uid()) and role = 'admin'
  );
$$;
revoke execute on function public.is_admin() from public, anon;
grant execute on function public.is_admin() to authenticated;

/* 4. Права на таблицу profiles: читать, менять только имя и телефон (не role!) */
grant select on table profiles to authenticated;
grant update (full_name, phone) on table profiles to authenticated;

create policy "read own profile or admin"
on profiles for select to authenticated
using ((select auth.uid()) = id or (select public.is_admin()));

create policy "update own profile"
on profiles for update to authenticated
using ((select auth.uid()) = id)
with check ((select auth.uid()) = id);

/* 5. Заявки получают владельца */
alter table bookings
  add column user_id uuid references auth.users (id) on delete set null
  default auth.uid();

/* анонимная заявка не может прикинуться заявкой чужого пользователя */
drop policy if exists "anyone can create a new booking" on bookings;
create policy "anon creates a new booking"
on bookings for insert to anon
with check (status = 'new' and guests between 1 and 20 and user_id is null);

grant select, insert on table bookings to authenticated;
grant update (status) on table bookings to authenticated;
grant select on table restaurant_tables to authenticated;

create policy "authenticated creates own booking"
on bookings for insert to authenticated
with check (
  user_id = (select auth.uid())
  and status = 'new'
  and guests between 1 and 20
);

create policy "read own bookings or admin"
on bookings for select to authenticated
using (user_id = (select auth.uid()) or (select public.is_admin()));

create policy "admin updates bookings"
on bookings for update to authenticated
using ((select public.is_admin()))
with check ((select public.is_admin()));

create policy "logged-in users read tables"
on restaurant_tables for select to authenticated
using (true);

Главные места: триггер всегда ставит роль user и не читает её из данных регистрации; право update выдано только на два столбца профиля, поэтому role пользователь поменять не сможет; у заявки есть владелец user_id, который по умолчанию равен auth.uid() и для анонима остаётся пустым; каждое правило называет роль (to authenticated).

import { cookies } from "next/headers";

export async function createClient() {
  const cookieStore = await cookies();

  return createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY!,
    {
      cookies: {
        getAll() {
          return cookieStore.getAll();
        },
        setAll(cookiesToSet) {
          try {
            cookiesToSet.forEach(({ name, value, options }) =>
              cookieStore.set(name, value, options),
            );
          } catch {
            // вызвано из серверного компонента: ничего страшного,
            // токены обновляет proxy.ts
          }
        },
      },
    },
  );
}

import { createServerClient } from "@supabase/ssr";
import { NextResponse, type NextRequest } from "next/server";

export async function updateSession(request: NextRequest) {
  let supabaseResponse = NextResponse.next({ request });

  const supabase = createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY!,
    {
      cookies: {
        getAll() {
          return request.cookies.getAll();
        },
        setAll(cookiesToSet) {
          cookiesToSet.forEach(({ name, value }) =>
            request.cookies.set(name, value),
          );
          supabaseResponse = NextResponse.next({ request });
          cookiesToSet.forEach(({ name, value, options }) =>
            supabaseResponse.cookies.set(name, value, options),
          );
        },
      },
    },
  );

  // Между createServerClient и getClaims() ничего не вставляйте:
  // иначе пользователей будет случайно «выкидывать» из сессии.
  const { data } = await supabase.auth.getClaims();
  const user = data?.claims;

  const path = request.nextUrl.pathname;
  const isProtected = path.startsWith("/account") || path.startsWith("/admin");

  if (!user && isProtected) {
    const url = request.nextUrl.clone();
    url.pathname = "/login";
    url.searchParams.set("next", path);
    return NextResponse.redirect(url);
  }

  // Верните именно этот объект: в нём обновлённые cookie
  return supabaseResponse;
}

08 Бонус: вход через Google (пошаговая инструкция)

Этот раздел необязателен. Он даёт кнопку «Войти через Google»: пользователю не нужно придумывать пароль, а вам не нужны письма. Настройка делается один раз, около 30 минут. Для Google нужен адрес возврата (redirect URI) именно вашего проекта Supabase, поэтому порядок такой: узнать адрес в Supabase, создать клиент в Google, вернуть данные в Supabase.

Секреты и аккаунт

Client Secret из Google — это пароль вашего приложения: он вставляется только в панель Supabase и в менеджер паролей, не в код, не в Git и не в чат. Используйте личный аккаунт Google, для учебного проекта рабочий не нужен. Названия разделов в Google Cloud Console меняются: ищите их по смыслу, ориентируясь на документацию Supabase.

  1. Адрес возврата из Supabase. В панели: Authentication → Sign In / Providers → Google. Скопируйте Callback URL (вид https://ВАШ-ПРОЕКТ.supabase.co/auth/v1/callback). Страницу не закрывайте.
  2. Проект в Google Cloud. Откройте Google Cloud Console (console.cloud.google.com), создайте проект с любым названием (например mfs-course) и выберите его.
  3. Google Auth Platform. В консоли откройте раздел Google Auth Platform и пройдите начальную настройку: название приложения, ваш e-mail для связи, Audience (для обычных аккаунтов Google выбирается External). В разделе Data Access (Scopes) должны быть openid, .../auth/userinfo.email и .../auth/userinfo.profile: этого достаточно для входа, лишние права не добавляйте (они требуют долгой проверки). Если приложение в статусе тестирования (Testing), войти смогут только пользователи из списка Test users: добавьте туда свои адреса, либо опубликуйте приложение.
  4. Клиент OAuth. В Google Auth Platform откройте раздел Clients → Create client, тип приложения Web application, имя любое.
  5. Authorized JavaScript origins. Добавьте адреса сайта без пути: http://localhost:3000 и https://ваш-сайт.vercel.app.
  6. Authorized redirect URIs. Вставьте Callback URL из шага 1 (адрес Supabase, а не вашего сайта!). Нажмите Create и сохраните Client ID и Client Secret.

import { NextResponse } from "next/server";
import { createClient } from "@/lib/supabase/server";

export async function GET(request: Request) {
  const { searchParams, origin } = new URL(request.url);
  const code = searchParams.get("code");
  const next = searchParams.get("next") ?? "/account";
  // только свои пути: начинаются с одного «/»
  const safeNext = next.startsWith("/") && !next.startsWith("//") ? next : "/account";

  if (code) {
    const supabase = await createClient();
    const { error } = await supabase.auth.exchangeCodeForSession(code);
    if (!error) return NextResponse.redirect(`${origin}${safeNext}`);
  }
  return NextResponse.redirect(`${origin}/login?error=oauth`);
}

09 Фишка урока: «Взломай соседа»

Игра для пар: сначала вы специально делаете в своём сайте «ленивые» правила с дырами, сосед пытается их использовать, потом вы закрываете дыры правилами по id пользователя, и сосед пробует снова. Всё на учебных данных. Время: около 60 минут. Проводится в аудитории или онлайн.

Правила безопасности игры

Взламываем только сайт соседа, который сам разрешил, и только в учебной базе с вымышленными данными. Нельзя пробовать это на чужих настоящих сайтах: это нарушение закона и правил любого сервиса. «Ленивые» правила и страница /hack нужны только на время игры: после неё всё удаляется.

Ролик на английском, меньше минуты (включите субтитры): что такое RLS. Смотрите перед игрой.

Подготовка (по 10 минут у каждого)

  1. Панель атаки. Попросите ИИ создать страницу /hack (временную, только для игры): клиентский компонент на createClient из lib/supabase/client.ts с пятью кнопками и окном результата (JSON). Кнопки: A «прочитать все профили» (from("profiles").select("*")); B «прочитать все заявки» (from("bookings").select("*")); C «сменить имя чужому профилю» (поле id, update({ full_name: "Взломано" }).eq("id", id).select()); D «сделать меня админом» (update({ role: "admin" }) для своего id, с .select()); E «показать мой id» (из getClaims()). Результат или ошибка печатаются под кнопками.
  2. «Ленивые» правила. В SQL Editor выполните блок ниже: он намеренно добавляет четыре дыры. Это допустимо только потому, что у вас учебная база с вымышленными данными.
  3. Деплой и обмен. Задеплойте сайт на Vercel (так сосед получит живую ссылку). Обменяйтесь адресами сайтов. В вашей базе должны быть данные соседу на «воровство»: оставьте в профиле выдуманное имя и телефон +992 900 00 00 01 и пару тестовых заявок.
/* дыра 1 и 2: любой вошедший читает все профили и все заявки */
create policy "lazy read profiles"
on profiles for select to authenticated using (true);

create policy "lazy read bookings"
on bookings for select to authenticated using (true);

/* дыра 3 и 4: любой вошедший меняет любые поля любого профиля, включая role */
grant update on table profiles to authenticated;

create policy "lazy update profiles"
on profiles for update to authenticated
using (true) with check (true);

Раунд 1: атака (15 минут)

  1. Откройте сайт соседа, зарегистрируйтесь там новым пользователем (e-mail выдуманный, например hacker1@example.com) и откройте /hack.
  2. Нажимайте кнопки по очереди и записывайте в «протокол взлома»: что получилось, какой текст вернулся. A: видны ли профили соседа с телефонами и ролями? B: видны ли чужие заявки? C: сменилось ли чужое имя (найдите id в результате A)? D: получилось ли сделать себя админом, и открывается ли теперь /admin?
  3. Не удаляйте и не портите данные: меняем только имя на «Взломано» и роль у своего пользователя-взломщика.

Раунд 2: защита (15 минут)

Получив протокол от соседа, закройте дыры. Блок ниже убирает «ленивые» правила и возвращает права на столбцы.

drop policy if exists "lazy read profiles" on profiles;
drop policy if exists "lazy read bookings" on bookings;
drop policy if exists "lazy update profiles" on profiles;

/* забираем лишнее право и снова даём только два столбца */
revoke update on table profiles from authenticated;
grant update (full_name, phone) on table profiles to authenticated;

Что осталось: вошедший видит свой профиль и (для админа) все; обновляет только свои имя и телефон; заявки видит свои. Эти правила написаны в практике (раздел 7) и работают, пока их не «обходят» ленивыми.

Раунд 3: повторная атака (10 минут)

Сосед снова нажимает A–E на вашем сайте (может быть тем же пользователем: нужно выйти и войти, или просто обновить). Ожидаемый результат защиты: A возвращает один (его собственный) профиль; B только его заявки (или пустой список); C обновляет 0 строк (список пустой: RLS молча пропустила чужую строку); D ошибка permission denied (нет права менять role). Если какая-то кнопка всё ещё пробивает защиту, найдите правило и исправьте.

  2. Добавьте вторую закрытую страницу и данные, принадлежащие пользователю, с правилами по user_id.

  4. Сыграйте в «Взломай соседа» (или проверьте сами по кнопкам A–E) и запишите протокол в README.
  5. Задеплойте, пропишите адрес Vercel в URL Configuration Supabase, проверьте живой сайт.
  6. Вставьте ссылки ниже и отметьте чек-лист.
Типичные ошибки в домашнем задании

1. Роль в user_metadata или проверка «админ» только в интерфейсе. 2. Правило using (true) на личных данных. 3. Забытое право update на все столбцы profiles: пользователь делает себя админом. 4. Файл middleware.ts вместо proxy.ts. 5. getSession() вместо getClaims() на сервере. 6. В репозитории Client Secret Google, пароль или токен. 7. На Vercel не добавлен адрес сайта в URL Configuration. 8. Страница /hack осталась на живом сайте. 9. Настоящие данные друзей в базе.

Как проверяют

Проверяющий откроет сайт, зарегистрируется, посмотрит кабинет, попробует открыть /account и /admin без входа и от имени обычного пользователя, затем изучит репозиторий: proxy.ts, правила в README, отсутствие секретов. Баллы: за три слоя защиты, за правильное хранение роли, за правила RLS по user_id, за работающий кабинет и за то, что вы можете объяснить своё решение.

✓ Шпаргалка урока

  • Аутентификация — «кто вы?» (пароль, Google). Авторизация — «что вам можно?» (роли, правила). Сначала первое, потом второе.
  • Supabase Auth: signUp, signInWithPassword, signOut; пароли хранятся только как хеш; пользователи в auth.users.
  • Confirm email: по умолчанию включён; встроенная почта Supabase даёт сейчас около 2 писем в час и только участникам команды проекта, поэтому на занятии подтверждение выключаем, а в настоящем продукте включаем обратно и подключаем свой SMTP.
  • Сессия: access-токен (JWT, по умолчанию час) + refresh-токен (одноразовый обмен на новую пару); лежат в cookie. JWT читается всеми, но подделать его нельзя из-за подписи.
  • Next.js 16: proxy.ts с функцией proxy (раньше middleware.ts). Токены проверять через getClaims(), не getSession(). Клиенты: createBrowserClient и createServerClient из @supabase/ssr.
  • Три слоя защиты: proxy (быстрый заслон), страница (getClaims() и роль), RLS (последняя линия). Интерфейс не защита.
  • Роли: таблица profiles с role; не в user_metadata; grant update (full_name, phone) закрывает role; админа назначает SQL; is_admin() для правил.
  • RLS по пользователю: using ((select auth.uid()) = user_id), всегда с ролью (to authenticated). Правила для anon на вошедшего не действуют.
  • Google (бонус): проект в Google Cloud, Google Auth Platform, клиент Web application, redirect URI = Callback URL из Supabase, Client ID и Secret в Supabase, signInWithOAuth и обработчик /auth/callback с exchangeCodeForSession.
  • «Взломай соседа»: проверяйте защиту атакой изнутри (кнопки A–E), записывайте протокол, закрывайте дыры, удаляйте временные страницы и правила.
