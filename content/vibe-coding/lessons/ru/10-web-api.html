01 Клиент и сервер: как страница попадает в браузер

До сих пор данные в ваших проектах лежали прямо в коде: массив товаров, список врачей, текст вкладок. Настоящие сайты берут данные у других компьютеров: курс валют, погоду, заказы, сообщения. Эти компьютеры работают постоянно и отвечают на запросы. Их называют серверами, а того, кто спрашивает (ваш браузер или ваша программа), — клиентом.

Разговор всегда устроен одинаково: клиент отправляет запрос (request), сервер возвращает ответ (response). Ни один не может «просто позвонить» первым: сервер молчит, пока его не спросили. Для такого разговора придумали «язык» с общими правилами — протокол HTTP (его защищённая версия — HTTPS, замочек в адресной строке).

Ролик на русском (около 16 минут, 2025 год): общая картина «клиент, сервер, API» другими словами. Можно посмотреть сейчас или после практики.

Из чего состоит запрос

  • Метод — что вы хотите сделать: получить, создать, изменить, удалить.
  • Адрес (URL) — куда: https://api.open-meteo.com/v1/forecast?latitude=38.56&longitude=68.77. Здесь https:// — протокол, api.open-meteo.com — домен сервера, /v1/forecast — путь (какой «раздел» нужен), всё после ? — параметры через & (какой город, какие поля).
  • Заголовки (headers) — служебные записки: в каком формате вы шлёте данные, кто вы. Сюда же часто кладут ключ доступа.
  • Тело (body) — сами данные, если вы что-то отправляете (например, заявку из формы). У запроса «дай» тела обычно нет.

Смотрим запросы своими глазами: вкладка Network

Для проверки API многие ставят отдельную программу. Нам она не нужна: всё есть в браузере. Откройте любой сайт, нажмите F12 (в Chrome) и выберите вкладку Network. Обновите страницу (F5): появится список всех запросов. Чтобы оставить только запросы за данными, включите фильтр Fetch/XHR. Щёлкните по строке: справа вкладка Headers покажет метод и код ответа, Preview и Response — сами данные.

Аналогия из жизни

Клиент и сервер — это покупатель и продавец на бозоре. Вы подходите к прилавку и говорите: «Сколько стоят абрикосы?» (запрос GET). Продавец называет цену (ответ 200 и данные). Если вы спросили про товар, которого нет на рынке, он разводит руками (404). Если просите продать то, что вам не положено, он отвечает «нельзя» (403). А если у продавца закончилась электроэнергия и весы не работают, это уже его авария (500).

Типичные ошибки новичков

1. Думать, что страница «содержит» все данные сразу: многие данные приходят отдельными запросами уже после загрузки страницы. 2. Путать ошибку клиента (4xx) с ошибкой сервера (5xx): при 404 ищите опечатку в адресе, а не «сломавшийся интернет». 3. Не смотреть в Network: половина загадок «почему ничего не показывается» решается за минуту, если открыть вкладку и увидеть красный статус. 4. Вставлять в адрес пробелы и кириллицу вручную: в параметрах их кодируют, браузер и fetch обычно делают это сами, но ломать адрес руками не надо.

ЗАДАЧА 1.1

Проверь себя: HTTP

лёгкая

Пользователь нажал кнопку «Оформить заказ» на сайте, и заказ нужно создать на сервере. Какой метод подходит лучше всего?

  1. GET, потому что он самый простой
  2. DELETE, потому что заказ «исчезает» из корзины
  3. POST, потому что мы отправляем данные, чтобы создать новую запись
  4. Метод не нужен, достаточно открыть страницу

GET только получает данные, а создание новой записи делают через POST: данные едут в теле запроса. DELETE удаляет, а не создаёт.

Запрос к API вернул 404. Что это означает и с чего начать поиск ошибки?

  1. Сервер упал; нужно подождать и повторить запрос
  2. Такого адреса или записи нет; сначала проверить адрес и параметры на опечатки
  3. Нужен ключ доступа; нужно зарегистрироваться
  4. Слишком много запросов; нужно подождать минуту

Код 4xx говорит, что проблема в запросе. 404 — «не найдено»: опечатка в пути или записи с таким номером нет. Падение сервера — это 5xx, ключ — 401/403, лимит — 429.

Где в браузере посмотреть, какие запросы за данными отправила страница и с каким кодом они завершились?

  1. DevTools (F12), вкладка Network, фильтр Fetch/XHR
  2. DevTools, вкладка Elements: там видны только запросы
  3. В исходном коде страницы, внутри тега <title>
  4. Нигде, браузер скрывает запросы от пользователя

Network записывает каждый запрос: метод, адрес, код, время, заголовки и сам ответ. Это и есть замена отдельным программам для проверки API.

02 JSON, API и ключ доступа

JSON: язык, на котором серверы отдают данные

Ответ сервера — это текст. Чтобы и человек, и программа понимали его одинаково, текст записывают по правилам JSON. В уроке 6 вы уже читали настройки в таком виде, правила те же: фигурные скобки { } с парами «ключ: значение», ключи в двойных кавычках, списки в квадратных скобках [ ], никаких комментариев и запятой после последней пары.

{
  "latitude": 38.56,
  "current": {
    "time": "2026-10-27T15:30",
    "temperature_2m": 20.4,
    "weather_code": 2
  }
}

Чтобы достать значение, идём по ключам через точку: data.current.temperature_2m. В JavaScript две функции переводят туда и обратно: JSON.parse(текст) превращает текст в объект, а JSON.stringify(объект) превращает объект в текст, который можно отправить на сервер.

Тренировка без интернета: вот «ответ сервера» в виде текста. Разберите его и выведите три строки, а затем превратите объект обратно в текст.

API: «меню» сервера

API (Application Programming Interface) — это набор адресов и правил, по которым одна программа может попросить что-то у другой. Сервер как кухня ресторана: вы не заходите на кухню и не берёте продукты сами, вы смотрите меню и делаете заказ официанту. Меню — это документация API, официант — адрес и метод запроса, блюдо на подносе — JSON с данными. Кухня решает, что вам можно получить и в каком виде.

Бывают три удобных для новичка вида API:

  • Открытые, без ключа. Достаточно знать адрес. В уроке понадобятся такие: Open-Meteo (погода), open.er-api.com (курсы валют, есть сомони), TVMaze (сериалы и фильмы-шоу), JSONPlaceholder (учебные записи для тренировки POST).
  • С ключом доступа. Нужно зарегистрироваться на сайте сервиса и получить ключ (API key): длинную строку. Сервер по ней узнаёт, кто спрашивает, и считает ваши запросы по тарифу.
  • Платные. Тот же ключ, но за запросы списываются деньги. Пока работаем только с бесплатным.
Ключ доступа — это пароль от вашего «счёта» в сервисе

Если ключ утёк, чужие запросы будут идти за ваш счёт или исчерпают ваш бесплатный лимит, а сервис может заблокировать ваш аккаунт. Поэтому ключ нельзя: вставлять в код, который уходит на GitHub; отправлять в чат; показывать на скриншотах. Как хранить его правильно, разберём в разделе 5. Данные пользователей из открытых API тоже не стоит вставлять в чужие сервисы без необходимости.

Почему иногда браузер не пускает: CORS

Браузер охраняет пользователя. Если ваша страница на mysite.vercel.app просит данные у другого домена, браузер сначала смотрит в ответ: есть ли там разрешение от сервера для вашего сайта (заголовок Access-Control-Allow-Origin). Нет разрешения? Запрос уходит, но браузер не отдаёт вашему коду ответ и пишет в консоли красную ошибку со словом CORS. Все API из этого урока разрешают запросы с любого сайта, поэтому у вас всё сработает. Если когда-нибудь встретите API без такого разрешения, запрос нужно делать не из браузера, а с вашего сервера (в Next.js это обычная серверная функция, разберём в разделе 4).

Проверь себя: JSON, API, ключ, CORS

средняя

Какая запись является корректным JSON?

  1. {name: "Мадина", age: 22}
  2. {'name': 'Мадина', 'age': 22}
  3. {"name": "Мадина", "age": 22}
  4. {"name": "Мадина", "age": 22,}

Для чего сервису нужен ключ доступа (API key)?

  1. Чтобы ответ приходил красиво оформленным
  2. Чтобы сервис знал, кто именно делает запросы, и мог ограничить их количество или списывать оплату
  3. Чтобы данные приходили быстрее
  4. Чтобы код можно было опубликовать на GitHub

Ключ — это «имя и пароль» вашего приложения для сервиса. Именно поэтому его нельзя публиковать: любой, кто его увидит, сможет пользоваться сервисом от вашего имени.

  2. Нужно сменить браузер на более новый

  4. Запрос стоит делать со своего сервера (например, из серверной функции Next.js) или выбрать API, который разрешает запросы с чужих сайтов

Правило действует только в браузере: сервер к серверу запрашивает данные без этих ограничений. Метод запроса и браузер тут ни при чём, решение у владельца API или в обходе через ваш сервер.

03 fetch и async/await: «подожди ответ сервера»

Ответ сервера приходит не мгновенно: запрос идёт по проводам или по воздуху, сервер думает. Это занимает от десятков миллисекунд до нескольких секунд. Если бы страница в это время «замерзала», пользоваться сайтом было бы невозможно. Поэтому JavaScript работает иначе: он отправляет запрос, получает взамен «талончик» (в программировании его зовут Promise, «обещание») и спокойно занимается другими делами, пока сервер не ответит.

Нам же в нужный момент надо сказать: «подожди ответ и только потом иди дальше». Это делает слово await. Правила короткие:

  • fetch(адрес) отправляет запрос и возвращает Promise-«талончик».
  • await перед ним ставит эту функцию на паузу, пока не придёт ответ. Результат: объект response (ответ целиком: код, заголовки, тело).
  • Тело ответа тоже читается не мгновенно, поэтому await response.json() — вторая пауза: превращаем текст JSON в готовый объект.
  • await можно писать только внутри функции, объявленной со словом async. В примерах прямо на этой странице разрешён await и на верхнем уровне, как будто всё внутри async-функции.

Нажмите «Запустить». Обратите внимание, в каком порядке выводятся строки: пока идёт запрос, программа не стоит, а второй console.log выполняется сразу.

console.log("1. Отправили запрос");

const url = "https://api.open-meteo.com/v1/forecast?latitude=38.56&longitude=68.77¤t=temperature_2m";
const ticket = fetch(url);                       // запрос ушёл, в руках «талончик»
console.log("2. Это Promise:", ticket instanceof Promise);

const response = await ticket;                   // ждём ответ сервера
console.log("3. Ответ пришёл, код:", response.status);

Проверка ответа и ошибки: шаблон из пяти строк

Главная ловушка fetch, о которую спотыкаются почти все: ответ с кодом 404 или 500 для него не ошибка. Запрос дошёл до сервера и вернулся, поэтому Promise завершается «успешно», а response.ok просто равен false. Ошибкой (исключением) fetch считает только случай, когда ответа вообще нет: нет интернета, адрес сервера не существует. Поэтому всегда пишите проверку:

async function loadData(url) {
  const response = await fetch(url);                              // 1. ждём ответ
  if (!response.ok) throw new Error("HTTP " + response.status);   // 2. 404, 500: это тоже ошибка
  return await response.json();                                   // 3. ждём и разбираем JSON
}

try {
  const data = await loadData(url);
  console.log("Получили", data);
} catch (error) {                                                 // 4. сюда попадаем при любой ошибке
  console.log("Не получилось:", error.message);
}
Верно
  • const response = await fetch(url);
  • const data = await response.json();
  • if (!response.ok) throw new Error(…)
Неверно
  • const data = fetch(url).json(); — у «талончика» нет метода json
  • const data = response.json(); без await — вместо данных в переменной снова «талончик»
  • Обернуть в try/catch и считать, что 404 попадёт в catch: не попадёт

ЗАДАЧА 3.4

Проверь себя: fetch и async/await

средняя

Что напечатает код const r = fetch(url); console.log(r); без await?

  1. Данные с сервера
  2. Promise: запрос ещё идёт, это «талончик», а не ответ
  3. Ошибку: без await fetch не работает
  4. Число 200

fetch всегда возвращает Promise. Данные появятся только после await (или .then).

Сервер ответил кодом 404. Что произойдёт в коде const response = await fetch(url);?

  1. Сработает catch, потому что код не 200
  2. Программа остановится с красной ошибкой
  3. Ничего не сломается: response придёт, а response.ok будет false; проверять нужно самим
  4. response будет равен null

fetch бросает исключение, только если ответа нет вообще (сети нет, домен не найден). Любой ответ сервера, даже 404 или 500, для него успешно полученный: код смотрим в response.ok и response.status.

Почему слово await нельзя написать внутри обычной функции function load() { … }?

  1. Потому что функция должна быть объявлена как async function load(): так JavaScript понимает, что внутри будут паузы
  2. Потому что await работает только в Next.js
  3. Потому что await нужно писать только после try
  4. Нельзя только для fetch, для остальных функций можно

await ставит выполнение функции на паузу, а делать паузы умеют только функции со словом async (и верхний уровень модуля). Ошибка так и называется: «await is only valid in async function».

04 Запросы в Next.js: в браузере или на сервере

В Next.js запрос за данными можно сделать в трёх местах. Из урока 8 вы знаете, что компоненты бывают серверными (по умолчанию) и клиентскими ("use client"). От выбора зависит, где выполняется fetch, кто видит ключ и что видит пользователь, пока данные грузятся.

Вариант 1: серверный компонент (самый простой)

Страница сама становится async и ждёт данные. Пользователь получает уже готовую страницу, ни useState, ни useEffect не нужны.

Две важные детали из документации Next.js. Первая: без указания cache при сборке проекта (npm run build) страница без динамических данных «запоминает» ответ один раз, и на сайте погода будет застывшей. Для живых данных пишите { cache: "no-store" }. Вторая: пока сервер ждёт ответ, страница не показывается. Чтобы пользователь видел «Загрузка…», рядом со страницей кладут файл loading.tsx, который Next.js показывает на время ожидания.

Вариант 3: Route Handler, «своя серверная функция»

Это файл с названием route.ts в папке под app/api/…. Он создаёт адрес вашего сайта, по которому отвечает не страница, а данные. Внутри можно безопасно прочитать секретный ключ из переменной окружения, сходить в чужой API и отдать браузеру только то, что нужно. Названия функций совпадают с HTTP-методами: GET, POST, PUT, PATCH, DELETE.

export async function GET() {
  const key = process.env.WEATHER_KEY; // читается на сервере, в браузер не попадает

  const response = await fetch(
    "https://api.example.com/weather?city=Dushanbe",
    { headers: { Authorization: "Bearer " + key }, cache: "no-store" },
  );

  if (!response.ok) {
    return Response.json({ error: "Сервис погоды недоступен" }, { status: 502 });
  }

  const data = await response.json();
  return Response.json({ temperature: data.temp }); // отдаём только нужное
}

Адрес api.example.com здесь условный: подставьте адрес и способ передачи ключа из документации вашего API (ключ кладут в параметр адреса, в заголовок Authorization или в свой заголовок: как именно, сказано в документации сервиса). Браузер тогда ходит на /api/weather вашего же сайта, и ключа в его коде нет. Эту схему вы ещё много раз используете в модулях 4 и 5: для базы данных и AI-чата.

Аналогия из жизни

Серверный компонент и route handler — это повар на кухне, у которого есть ключ от склада. Клиентский компонент — зал, где сидят гости. Гость (браузер) просит блюдо, а ключ от склада (API-ключ) остаётся у повара: приносить его в зал нельзя, потому что любой гость может его забрать. Поэтому «ходить на склад» (в закрытый API) должен повар, а в зал выносят только готовую тарелку (данные).

Типичные ошибки новичков

1. Сделать fetch с ключом в клиентском компоненте: ключ окажется в коде страницы. 2. Поставить "use client" и async на один компонент: клиентский компонент не может быть async, а серверные хуки useState и useEffect в серверном не работают. Выбирайте одно. 3. Не указать cache: "no-store" и удивляться, что после деплоя погода «застыла». 4. Забыть про «Загрузка…» и «Ошибка»: тогда при медленном интернете пользователь видит пустой экран. 5. Сделать запрос внутри useEffect без пустого списка зависимостей []: запросы пойдут бесконечным циклом, а Network покажет сотни строк подряд.

05 Переменные окружения: где прятать ключи

Ключ доступа нужен коду, но показывать его никому нельзя. Решение у всех разработчиков одно: хранить ключ снаружи кода, в переменной окружения (environment variable). В коде остаётся только имя: process.env.WEATHER_KEY, а значение подставляется в момент запуска программы. На вашем компьютере оно берётся из файла, на хостинге (Vercel) — из настроек проекта. Код один, а секреты у каждой среды свои.

Файл .env.local

В корне проекта (рядом с package.json) создайте файл с именем .env.local. Точка в начале имени обязательна. Каждая строка — одна переменная в формате ИМЯ=значение, без пробелов вокруг знака равенства и обычно без кавычек:

WEATHER_KEY=abc123-not-a-real-key
NEXT_PUBLIC_SITE_NAME=Дашборд Душанбе

Next.js сам читает такие файлы при запуске и кладёт значения в process.env. Если вы изменили файл, а значение не подхватилось, остановите npm run dev (Ctrl+C) и запустите заново.

Главное правило: NEXT_PUBLIC_

  • Обычная переменная (WEATHER_KEY) доступна только в серверном коде: в серверных компонентах и route handlers. В клиентском компоненте process.env.WEATHER_KEY даст undefined.
  • С приставкой NEXT_PUBLIC_ значение при сборке проекта «вшивается» прямо в JavaScript, который уходит в браузер. Его увидит любой, кто откроет код страницы. Поэтому приставку ставят только на то, что не секрет: название сайта, публичный идентификатор, адрес.
  • Значение с NEXT_PUBLIC_ фиксируется на этапе сборки (next build): если поменять его потом, нужна новая сборка.
Правильно
  • WEATHER_KEY=… и чтение в серверном коде
  • NEXT_PUBLIC_SITE_NAME=… для названия сайта
Опасно
  • NEXT_PUBLIC_WEATHER_KEY=…: секрет попадёт в браузер и в код страницы
  • Ключ прямо в коде: const key = "abc123…"

.gitignore: файл, который Git не видит

В уроке 4 вы познакомились с .gitignore: это список файлов и папок, которые Git не добавляет в репозиторий. Проект, созданный командой create-next-app, уже содержит там строку .env*: она закрывает все файлы, имя которых начинается с .env, в том числе .env.local. Поэтому git add . и git push его не отправят. Но надеяться нельзя, надо проверять, особенно если проект создан не вами (например, ИИ-агентом или скопирован из шаблона).

Проверяем, что ключ не попал на GitHub

Три проверки по порядку. Они занимают минуту, и делать их нужно перед каждым первым git push нового проекта.

  1. Игнорируется ли файл. В терминале в папке проекта: 
    git check-ignore -v .env.local
    Команда печатает строку с правилом, например .gitignore:34:.env* .env.local. Если вывод пустой, файл не игнорируется: добавьте в .gitignore строку .env* и повторите.
  2. Нет ли файла в репозитории и в истории. 
    git ls-files | grep env
git log --all --oneline -- .env.local
    Обе команды должны ничего не вывести. Первая ищет среди отслеживаемых файлов, вторая — среди всех прошлых коммитов, ведь удалённый файл остаётся в истории. На Windows вместо grep env используйте findstr env.
  3. Посмотрите глазами. Откройте репозиторий на GitHub в режиме инкогнито (так видно то, что видит любой человек): среди файлов в корне не должно быть .env.local, а в коде не должно быть строки с ключом. Быстрый способ проверки: откройте поиск по коду на странице репозитория и введите начало вашего ключа.
Если ключ уже попал на GitHub

Удалить файл новым коммитом недостаточно: старый коммит с ключом остаётся в истории, и копии могли уже забрать автоматические боты (они сканируют GitHub круглые сутки). Порядок действий: 1. Сразу зайдите на сайт сервиса и отзовите ключ (revoke, delete, regenerate), выпустите новый. Старый ключ с этого момента бесполезен. 2. Новый ключ запишите в .env.local и в Vercel. 3. Уберите файл из Git: git rm --cached .env.local, убедитесь, что .env* есть в .gitignore, сделайте commit и push. 4. Расскажите ИИ-ассистенту, что произошло, но сам ключ в чат не вставляйте.

Переменные окружения на Vercel

Ваш сайт на Vercel не видит файл .env.local: он остался у вас на компьютере. Значит, каждую переменную нужно добавить в проект на Vercel вручную. Шаги по официальной документации:

  1. Откройте проект на Vercel (из панели управления, dashboard) и перейдите в его настройки. В боковом меню выберите Environment Variables.
  2. В поле Name впишите имя (например, WEATHER_KEY), в поле Value — значение. Имя в точности такое же, как в .env.local, с учётом регистра.
  3. Отметьте окружения, к которым относится переменная: Production (боевой сайт), Preview (проверочные версии из других веток), Development (локальная работа). Для ключа обычно достаточно первых двух.
  4. Нажмите Save. В зависимости от настроек вам могут предложить тип переменной: Secret (значение после сохранения не показывается) удобнее для ключей.
  5. Сделайте новый деплой. По документации Vercel изменения переменных не применяются к уже готовым версиям сайта, только к новым. Откройте вкладку Deployments, у последнего деплоя выберите Redeploy или просто сделайте новый git push.
Аналогия из жизни

Переменная окружения — это сейф с кодом, который стоит в каждой «комнате»: дома у вас, на сервере Vercel. Код сейфа не пишут на двери (в публичном коде) и не оставляют на проходной (на GitHub). Каждому «помещению» вы передаёте код лично. Сменили код на домашнем сейфе, на работе он сам не поменяется: придётся поменять и там, и перезапустить работу (Redeploy).

Типичные ошибки новичков

1. Назвать файл env.local или .env.local.txt (без точки, с лишним расширением): Next.js его не увидит. Проверьте имя в проводнике. 2. Положить файл не в корень, а в app/. 3. Поставить пробелы или лишние кавычки: KEY = "abc". 4. Поставить NEXT_PUBLIC_ перед секретом «чтобы заработало»: оно заработает, но ключ станет публичным. Вместо этого вынесите запрос в серверный компонент или route handler. 5. Закоммитить .env или .env.local «на минутку». 6. Добавить переменную на Vercel и не сделать Redeploy: на сайте всё ещё старое значение или undefined. 7. Показать .env.local на скриншоте, в видеозвонке или в чате с ИИ.

Каждый показывает результат за 90 секунд: открыть страницу, вызвать ошибку режимом Offline, показать в Network строку запроса и назвать метод, код и поле, откуда взяли самое интересное значение. Сосед заполняет мини-оценку.

09 Домашнее задание: страница-дашборд с живыми данными (ДЗ-10)

Соберите страницу-дашборд, которая показывает живые данные минимум из двух разных публичных API. Результат сдаётся двумя ссылками: на репозиторий GitHub и на опубликованный сайт на Vercel.

Требования

  • Два и больше API: например, погода и курс валют, либо любые из списка квеста. Минимум 3 карточки или блока с данными. Выбор тематики свободный (город, спорт, кино, мода, игры).
  • Серверный запрос: минимум одна карточка получает данные в серверном компоненте через async/await с cache: "no-store" (если данные должны быть свежими).
  • Клиентский запрос: минимум один блок делает запрос из браузера по действию пользователя (поиск, выбор города, кнопка «Обновить») и показывает состояния loading, error (с кнопкой «Повторить») и пустой результат.
  • Ошибки: проверка response.ok везде; ошибка в одной карточке не ломает всю страницу; нет «белого экрана».
  • Данные настоящие: по Network видно живые запросы. Захардкоженных (записанных в коде) значений вместо данных API нет.
  • Секреты: ключей в коде нет. В проекте есть .env.local (хотя бы с заглушкой), он не в репозитории (git check-ignore -v .env.local подтверждает). Если вы используете API с ключом, ключ читается только на сервере, без NEXT_PUBLIC_, и добавлен в Environment Variables на Vercel.
  • Порядок: консоль браузера без красных ошибок, npm run build проходит, вид на 390 px нормальный, источник данных указан в подвале ссылкой на документацию API.
  • Бонус: route handler app/api/…/route.ts, через который клиентский компонент получает данные; автообновление раз в минуту; сохранение последнего выбора в localStorage; API с ключом (регистрация на сайте сервиса, ключ только в .env.local и на Vercel).

Что нужно сделать

  1. Выберите тему и два API. Откройте адреса в браузере и убедитесь, что приходит JSON. Выпишите нужные поля.
  2. Опишите задачу ИИ по формуле и приложите кусок настоящего JSON. Попросите сначала план: где серверный запрос, где клиентский, какие состояния.
  3. Стройте по шагам: одна карточка с серверными данными, commit; вторая карточка, commit; клиентский блок с состояниями, commit. После каждого шага проверка во вкладке Network.
  4. Проверьте руками: режим Offline, неправильный ввод (бессмыслица в поиске), медленная сеть, окно 390 px.
  5. Проверьте секреты: три команды из раздела 5, поиск ключа в diff перед commit.
  6. Опубликуйте (push на GitHub, Vercel как в уроке 5), добавьте нужные переменные в Environment Variables, сделайте Redeploy, откройте сайт на телефоне и сдайте две ссылки ниже.

Нет «загрузки» и «ошибки», при медленной сети пустой экран. 4. Ключ в коде или в NEXT_PUBLIC_. 5. .env.local в репозитории. 6. ✓ Шпаргалка урока

  • Клиент и сервер: клиент отправляет запрос, сервер возвращает ответ. Запрос: метод + адрес (+ заголовки, тело). Методы: GET получить, POST создать, PUT/PATCH изменить, DELETE удалить. Коды: 2xx успех, 4xx ошибка клиента (400 запрос, 401/403 ключ и права, 404 не найдено, 429 лимит), 5xx ошибка сервера.
  • JSON: ключи и строки в двойных кавычках, без запятой в конце. JSON.parse текст → объект, JSON.stringify объект → текст. Значение достаём по ключам: data.current.temperature_2m.
  • API и ключ: API — адреса и правила, по которым программа просит данные. Ключ — пароль приложения для сервиса: не в коде, не в чате, не на GitHub. CORS: браузер не отдаёт ответ чужого сервера без разрешения, решение — запрос с вашего сервера.
  • async/await: fetch возвращает Promise, await ждёт ответ. await только внутри async. Шаблон: await fetch, if (!response.ok) throw, await response.json(), try/catch. 404 и 500 в catch сами не попадают.
  • Next.js: запрос в серверном компоненте (async, cache: "no-store" для свежих данных, loading.tsx на время ожидания), в клиентском (useEffect + status) или в route handler (app/api/…/route.ts с GET). Секретные запросы — только с сервера.
  • Состояния: loading, error (с «Повторить»), empty, success. Проверяем режимами Offline и Slow 4G во вкладке Network.
  • .env: секреты в .env.local (корень проекта, ИМЯ=значение), читаются через process.env.ИМЯ на сервере. Приставка NEXT_PUBLIC_ отдаёт значение в браузер: секреты без неё. После правки файла перезапустите dev-сервер.
  • Не на GitHub: git check-ignore -v .env.local, git ls-files | grep env, git log --all --oneline -- .env.local. Ключ утёк: сразу отозвать и выпустить новый.
  • Vercel: Settings → Environment Variables → Name, Value, окружения, Save. Новое значение видят только новые деплои: Redeploy или push.
  • С ИИ: давать адрес и пример JSON, называть все состояния и место запроса, ключ только в .env.local и не показывать ему сам ключ, проверять во вкладке Network.
