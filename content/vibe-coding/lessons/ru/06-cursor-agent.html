Cursor на максимум: Agent, правила проекта, MCP

К концу урока у вас будет своя система работы с ИИ-агентом: файл правил проекта (AGENTS.md), привычка «сначала план, потом код», подключённый браузер, через который агент сам открывает вашу страницу и проверяет результат, и страховка, которая позволяет безболезненно откатить любую его ошибку. Лендинг из урока 5 вы улучшите одним большим промптом, а настоящую ошибку из терминала почините вместе с ИИ.

  • Отличать плохой промпт («сделай сайт») от хорошего (роль, стек, требования, проверка) и переписывать слабые промпты
  • Выбирать режим чата: Agent, Ask или Plan, и работать по схеме «сначала план, потом код»
  • Подключать контекст через @ и объяснять агенту правила проекта в файлах .cursor/rules и AGENTS.md
  • Читать и править простой JSON (пары «ключ — значение») и подключить к Cursor MCP-сервер с браузером
  • Откатывать изменения агента тремя способами: checkpoint в Cursor, «Discard Changes» в Source Control и commit перед большой задачей
  • Разбирать ошибку из терминала с ИИ и просить помощи в чате группы так, чтобы вам ответили с первого раза
Как проходить этот урок

Нужны: проект dental-landing из урока 5 (он открывается в Cursor, лежит на GitHub и опубликован на Vercel), Node.js, интернет и около 2,5 часов. 01 Режимы чата: сначала план, потом код

В уроке 5 агент писал страницу по одному промпту. Это работает, пока задача маленькая. На большой задаче («переделай лендинг») агент может сразу бросить писать код в неверном направлении, и вы потратите время на откат. Опытные разработчики поэтому делят работу на два шага: сначала план, потом код. Cursor поддерживает это встроенным режимом.

Agent
Основной режим: агент сам читает файлы проекта, правит их и запускает команды в терминале. Именно его вы использовали на уроке 5.
Plan
Режим планирования: агент задаёт уточняющие вопросы, изучает проект и составляет план работ. Код меняется только после того, как вы проверили план и нажали кнопку запуска (по документации Cursor — «собрать план»). Включается переключателем режимов или сочетанием Shift+Tab в поле ввода чата.
Ask
Режим вопросов: объяснить код, предложить идею, ничего не меняя в файлах. Подходит, когда нужно понять, а не сделать. Набор режимов зависит от версии: в списке могут быть и другие (например, Debug для поиска причины сбоя).

Короткий ролик на английском (2 минуты, включите субтитры): как выглядит режим Plan в редакторе. Интерфейс меняется, но порядок «вопросы → план → запуск» остаётся.

Когда какой режим

ЗадачаРежимПочему
Поменять цвет кнопки, подправить текстAgentМаленькая задача, результат виден сразу, откат простой
Понять, что делает кусок кодаAskФайлы не меняются, можно спрашивать сколько угодно
Переделать лендинг, добавить новый блок, разбить страницу на компонентыPlan, затем запуск планаЗатрагивается много файлов: нужно сверить план до первой строки кода
Аналогия из жизни

Планировать до кода — как ремонт квартиры в Душанбе. Мастер, который сразу начал ломать стену, может сломать несущую. Хороший мастер сначала обходит квартиру, задаёт вопросы («куда ставить кухню? розетки где?»), рисует схему и только после вашего «да» берёт молоток. Режим Plan — это такой мастер.

Типичные ошибки новичков

1. Нажать «запуск» не читая план: смысл режима в проверке. 2. Включать Plan для правки одного слова: лишние минуты. 3. Отвечать на вопросы агента «как хочешь»: ответ «как хочешь» даёт среднюю страницу, а не вашу. 4. Не править план, когда в нём есть лишнее: можно написать «убери шаг 4, он не нужен» и план обновится.

ЗАДАЧА 1.1

Проверь себя: режимы

лёгкая

Нужно разбить страницу на несколько файлов-компонентов и добавить два новых блока. Что разумно сделать первым?

  1. Сразу отправить задачу в режиме Agent и ждать результата
  2. Переключиться на Ask: он быстрее всех пишет код
  3. Включить Plan, ответить на вопросы агента, прочитать и поправить план, потом запустить его
  4. Вручную переписать все файлы

Задача затрагивает много файлов, поэтому ошибку лучше поймать на плане. Ask ничего не меняет в файлах, а ручное переписывание противоречит смыслу курса.

Что происходит с файлами проекта, пока план в режиме Plan ещё не запущен?

  1. Они меняются по ходу составления плана
  2. Остаются без изменений: агент изучает проект и предлагает шаги, а правки начинаются после вашего решения
  3. Удаляются и создаются заново
  4. Отправляются на GitHub

План — это текст-предложение. Только после того как вы его проверили и запустили, агент начинает править файлы.

02 Плохой и хороший промпт, @-контекст

Агент не читает мысли: он видит ваш текст и те файлы, которые нашёл или которые вы показали. Чем точнее запрос, тем меньше правок. В уроке 2 вы изучили формулу «контекст → цель → ограничения → примеры → проверка». Для агента в проекте её удобно разложить на четыре части: роль, стек, требования, проверка.

Плохой промпт
  • «сделай сайт» / «улучши лендинг»
  • Нет роли: непонятно, для кого результат
  • Нет стека: агент может предложить другие библиотеки
  • Нет требований и проверки: «красиво» каждый понимает по-своему
Хороший промпт
  • Роль: «ты — фронтенд-разработчик, который помогает новичку»
  • Стек: Next.js, Tailwind, один файл или папка
  • Требования: список, что именно сделать, и чего не трогать
  • Проверка: npm run build и итоговый отчёт
улучши лендинг, чтобы был красивый и современный
Роль: ты — опытный фронтенд-разработчик, который помогает новичку, объясняй коротко и по-русски. Стек: Next.js (App Router, TypeScript) и Tailwind CSS, как в проекте. Новые библиотеки не добавляй. Задача: улучшить лендинг стоматологии «Улыбка» в app/page.tsx. Требования: 1) вынести секции hero, услуги, врачи, отзывы и форму в отдельные компоненты в папке app/components; 2) добавить плавное появление карточек и эффект при наведении (только Tailwind-классы transition, hover:); 3) на ширине 390 px нет горизонтальной прокрутки; 4) у каждого поля формы есть подпись; 5) тексты и стиль не менять. Проверка: после правок запусти npm run build, исправь ошибки и коротко перечисли созданные файлы.

Хороший промпт длиннее, но экономит время: ИИ не угадывает. Главное правило курса остаётся в силе: если результат не тот, правьте промпт в том же чате, а не начинайте с нуля.

@-контекст: показать агенту нужное

Агент сам ищет по проекту, но иногда он берёт не тот файл. В поле чата введите знак @: появится список того, что можно приложить к сообщению. По документации Cursor это файлы и папки (например, @page.tsx или @app/components/), вывод терминала (@Terminals), предыдущие чаты (@Chats), изменения в Git (@Commit и @Branch) и встроенный браузер (@Browser). Картинку, например скриншот ошибки или макет, можно перетащить в поле чата или вставить из буфера обмена.

Правила работы с агентом

1. Большая задача — сначала Plan. 2. Файл, который нужно править, приложите через @. 3. Просите проверить результат: npm run build и описание изменений. 4. Не принимайте код, который не можете объяснить: попросите агента пояснить. 5. Секреты (ключи доступа) никогда не пишите в промптах и не прикладывайте файлы .env. 6. Если ответ не тот, уточняйте в том же чате.

Аналогия из жизни

Промпт «сделай сайт» — как заказать такси словами «довези куда-нибудь». Хороший промпт — «от Рудаки до аэропорта, багаж два чемодана, тихо». А @-файлы — как показать водителю адрес на карте: меньше шансов уехать не туда.

Типичные ошибки новичков

1. Приложить через @ всю папку проекта «на всякий случай»: лишний шум мешает агенту. 2. Писать несколько несвязанных задач в одном сообщении. 3. Ругаться на агента вместо уточнения: фраза «ты всё сломал» ничего не объясняет, а «секция услуг пропала, верни её, остальное оставь» — объясняет. 4. Не называть стек: тогда может появиться другая библиотека.

ЗАДАЧА 2.1

Проверь себя: промпт и контекст

лёгкая

Какой промпт лучше всего подходит для агента в проекте?

  1. «Ты — фронтенд-разработчик. Стек: Next.js и Tailwind. Вынеси форму в компонент в app/components, стиль не меняй, запусти npm run build»
  2. «Сделай форму красивой»
  3. «Сделай как у больших сайтов»
  4. «Переделай всё, как считаешь нужным»

В лучшем промпте есть роль, стек, конкретное требование, граница («стиль не меняй») и проверка сборки. Остальные оставляют агенту слишком много места для догадок.

Что делает знак @ в поле чата?

  1. Отправляет сообщение на почту
  2. Запускает проект на Vercel
  3. Включает режим Plan
  4. Позволяет приложить к сообщению файл, папку, вывод терминала и другой контекст

После @ появляется список того, что можно приложить. Так агент точно знает, на какой файл смотреть.

03 Правила проекта: .cursor/rules и AGENTS.md

Каждый новый чат агент начинает «с чистого листа»: он не помнит, что вы просили вчера. Чтобы не повторять одно и то же («пиши по-русски», «только Tailwind», «запускай build»), эти договорённости записывают в файл правил, и Cursor подкладывает его в каждый запрос. Это как инструкция для нового сотрудника, который каждый день приходит заново.

AGENTS.md
Обычный текстовый файл в корне проекта (формат Markdown, без служебных полей). Cursor читает его, и другие ИИ-агенты тоже: это общий «стандарт». Вложенные файлы AGENTS.md в подпапках действуют внутри этих папок, и более конкретный файл важнее. Начните именно с него: он проще всего.
.cursor/rules
Папка с правилами Cursor. Каждое правило — отдельный файл с расширением .mdc (по документации, обычный .md в этой папке не работает). В начале файла — служебные поля: description (описание), globs (для каких файлов, например app/**/*.tsx) и alwaysApply (применять ли всегда). Тип правила выбирают в настройках: всегда, по смыслу, для определённых файлов или вручную.
.cursorrules
Старый способ: один файл в корне. Он ещё встречается в старых статьях, но считается устаревшим: не начинайте с него.

Как создать правило

Самый простой способ — попросить самого агента: в чате введите /create-rule и опишите правило словами. Или откройте настройки Cursor (раздел «Customize», пункт «Rules») и добавьте правило кнопкой «Add Rule». А AGENTS.md — это просто файл: создайте его в корне проекта и запишите правила обычными пунктами.

# Проект: лендинг стоматологии «Улыбка»

## Стек
- Next.js (App Router, TypeScript) и Tailwind CSS. Другие библиотеки не добавлять без вопроса.

## Стиль
- Стили только классами Tailwind, без отдельных CSS-файлов.
- Секции страницы лежат в app/components, по одному компоненту на файл.
- Тексты на сайте на русском, данные вымышленные.

## Безопасность
- Никаких ключей и паролей в коде. Секреты только в .env, а .env не коммитить.

## Проверка
- После правок запускай npm run build и исправляй ошибки.
- В конце коротко перечисли изменённые файлы.

Видео на русском: фрагмент про правила (Rules) в Cursor. Смотрите 6–8 минут с отмеченного места; весь ролик очень длинный (около 2,5 часа) и целиком не нужен.

Хорошее правило — короткое и конкретное

  • Конкретно: «Секции в app/components, один компонент на файл» лучше, чем «пиши аккуратно».
  • Коротко: по документации Cursor, правило лучше держать короче 500 строк, а большое делить на несколько.
  • Растёт по необходимости: добавляйте пункт, когда агент второй раз делает одну и ту же ошибку.
  • Без секретов: файлы правил уходят в Git и на GitHub, поэтому ключей в них быть не должно.
Аналогия из жизни

Файл правил — как памятка на двери чайханы для нового официанта: «чай подаём первым», «заказ повторяем вслух», «без заказа в кухню не входить». Официант каждый день может быть новый, а порядок остаётся.

Типичные ошибки новичков

1. Сложить в правила всё подряд на тысячу строк: агент теряет главное. 2. Положить правило в .cursor/rules с расширением .md и удивляться, что оно не работает: нужен .mdc. 3. Записать в правила пароль или ключ. 4. Написать расплывчато («делай хорошо»): такое правило ничего не меняет. 5. Писать противоречащие правила: агент выберет любое из них.

ЗАДАЧА 3.1

Проверь себя: правила проекта

лёгкая

Зачем нужен файл AGENTS.md в корне проекта?

  1. В нём хранится пароль от Vercel
  2. В нём записаны договорённости для ИИ-агента: стек, стиль, запреты, проверка; их читают вместе с каждым запросом

Хорошее правило проверяемо: по нему видно, выполнено оно или нет. Расплывчатые пожелания агент может «выполнить» как угодно.

04 JSON на пальцах: ключ и значение

Настройки MCP в Cursor хранятся в файле формата JSON. Бояться нечего: это «анкета» из пар ключ — значение. Вы уже видели такое в package.json. Вот один человек в виде JSON:

{
  "name": "Madina",
  "age": 22,
  "city": "Dushanbe",
  "student": true,
  "languages": ["tg", "ru", "en"],
  "contacts": { "telegram": "@madina_example" }
}
  • Фигурные скобки { } — «коробка» с парами. Внутри пары "ключ": значение, разделённые запятыми.
  • Ключ — всегда в двойных кавычках: "name". Это название поля.
  • Значение — строка в двойных кавычках ("Madina"), число (22), true или false, список в квадратных скобках [ ] или другая коробка { } внутри.
  • Запятая нужна между парами, а после последней пары её нет. Одинарные кавычки и комментарии в JSON запрещены.

Попробуйте сами. Ниже — маленькая программа, которая читает JSON. Запустите её, потом замените в тексте имя, добавьте в список args ещё одно слово и снова запустите. Затем нарочно сломайте JSON (например, уберите кавычку у ключа) и посмотрите на сообщение об ошибке.

// текст в формате JSON: настройка сервера, как в mcp.json
const text = `{
  "name": "playwright",
  "command": "npx",
  "args": ["@playwright/mcp@latest"]
}`;

try {
  const cfg = JSON.parse(text);          // превращаем текст в объект
  console.log("Имя:", cfg.name);          // значение по ключу name
  console.log("Команда:", cfg.command);
  console.log("Слов в args:", cfg.args.length);
} catch (e) {
  console.log("Ошибка в JSON:", e.message); // сюда попадаем, если JSON сломан
}
Как не ошибиться в JSON

Редактор подчёркивает красным лишнюю или пропущенную запятую и кавычку. Если файл не работает, скопируйте его в чат и попросите: «найди ошибку в этом JSON и покажи исправленный вариант». Агент справляется с этим мгновенно.

Аналогия из жизни

JSON — как анкета на пропуск: «Фамилия: Рахимова», «Возраст: 22», «Языки: таджикский, русский». Слева название графы (ключ), справа ответ (значение). Список языков — графа, в которой несколько ответов, а контакты — анкета внутри анкеты.

Типичные ошибки новичков

1. Запятая после последней пары: "b": 2, перед закрывающей скобкой. 2. Одинарные кавычки 'name' вместо двойных. 3. Ключ без кавычек: name: "Madina". 4. Комментарии // внутри JSON: их там не бывает. 5. Забытая закрывающая скобка: у каждой { должна быть пара }.

ЗАДАЧА 4.1

Проверь себя: JSON

лёгкая

Какой из вариантов — корректный JSON?

  1. { name: "Madina", age: 22 }
  2. { 'name': 'Madina', 'age': 22 }
  3. { "name": "Madina", "age": 22 }
  4. { "name": "Madina", "age": 22, }

В JSON ключи и текстовые значения пишут в двойных кавычках, а запятой после последней пары быть не должно.

Что означает строка "args": ["-y", "pkg"]?

  1. У ключа args значение — список из двух текстовых элементов
  2. Два ключа с названиями «-y» и «pkg»
  3. Ошибка: списков в JSON не бывает
  4. Комментарий для редактора

Квадратные скобки — список значений. В настройках MCP в args перечисляют слова, которые добавляются к команде.

Читать подробнее: MDN: работа с JSON.

05 MCP: даём агенту браузер и документацию

Без дополнительных инструментов агент «слепой»: он читает и пишет файлы, но не видит, как страница выглядит в браузере, и знает документацию только «по памяти», которая может устареть. MCP (Model Context Protocol) — общий стандарт, по которому к ИИ-агенту подключают внешние инструменты. Один подключённый MCP-сервер — один набор возможностей: «открыть страницу в браузере», «найти актуальную документацию библиотеки», «прочитать задачу в трекере».

Подключаем в два шага

Настройки MCP лежат в JSON-файле (раздел 4 пригодился). По документации Cursor есть два места:

  • .cursor/mcp.json в папке проекта — инструменты только для этого проекта;
  • ~/.cursor/mcp.json в домашней папке — инструменты для всех проектов.

Внутри файла верхний ключ — mcpServers, а в нём каждый сервер под своим именем. Для браузера используют сервер Playwright от Microsoft (нужен Node.js 18 или новее; он у вас с урока 4):

{
  "mcpServers": {
    "playwright": {
      "command": "npx",
      "args": ["@playwright/mcp@latest"]
    }
  }
}

После сохранения файла откройте настройки Cursor: в версиях со страницей «Customize» сервер виден там, в других — в настройках в разделе MCP. Ищите слово MCP: у сервера должен быть включён переключатель и не гореть красная ошибка. Если сервер не появился, полностью перезапустите Cursor. Добавлять серверы можно и из каталога (Marketplace) в один клик, но у ручного способа есть плюс: вы видите, что именно запускается на вашем компьютере.

Видео на английском, включите субтитры (4 минуты): подключение Playwright MCP в Cursor на живом примере. Если окна отличаются, ориентируйтесь на файл mcp.json выше.

Что ещё можно подключить

В Cursor сегодня есть и встроенный инструмент «Browser»: агент может открывать страницы, нажимать, делать скриншоты и читать ошибки консоли без настройки. Если подключение Playwright не удалось, попросите агента проверить страницу «во встроенном браузере». А вот чтобы ИИ не придумывал устаревший код, подключают сервер документации, например Context7. Ему нужен бесплатный ключ (по описанию проекта, ключ рекомендуется для лимитов), поэтому он идёт в личный файл ~/.cursor/mcp.json, но не в проект. После подключения в промпт добавляют слова «use context7».

Безопасность MCP

1. MCP-сервер — это программа, которая запускается на вашем компьютере или получает доступ к сервисам от вашего имени. Ставьте только серверы из надёжных источников: официальный репозиторий разработчика или каталог Cursor. 2. Ключи доступа не пишите в файл внутри проекта: он уходит на GitHub. Если ключ нужен, файл кладут в домашнюю папку (~/.cursor/mcp.json). 3. Cursor по умолчанию спрашивает разрешение на использование инструмента. Нажмите на стрелку рядом с названием, прочитайте, что агент собирается сделать, и только потом разрешайте. 4. Не включайте автоматический запуск всего подряд: сначала приучитесь читать запросы.

Аналогия из жизни

Агент без MCP — как сотрудник, запертый в комнате с компьютером: умный, но ничего не видит снаружи. MCP — окно во двор и телефон: агент выглядывает в браузер («что на странице?») и звонит в справочную («как правильно в этой версии?»). А ваше разрешение — как вахтёр: решает, кого впускать.

06 Как откатить изменения агента

Агент ошибается, и это нормально. Опасно не ошибаться, а не уметь вернуться. Есть три уровня страховки, от быстрого к надёжному.

1. Checkpoint в Cursor

Перед значительными изменениями агент автоматически создаёт checkpoint: снимок изменяемых файлов. По документации Cursor, нажмите на запрос в истории чата (или кнопку «Restore Checkpoint» у предыдущего сообщения) и подтвердите возврат: файлы вернутся к тому состоянию. Сообщения чата при этом не удаляются. Важная оговорка из документации: checkpoint хранится локально, отдельно от Git, и подходит только для отмены правок агента. Постоянная история — это Git.

2. «Discard Changes» в Source Control

Откройте Source Control (Ctrl+Shift+G; на macOS — Control+Shift+G), как на уроке 4. В списке «Changes» наведите курсор на файл и нажмите значок отмены (стрелка назад) — «Discard Changes». Файл вернётся к последнему commit. Редактор попросит подтверждение: отменённые правки вернуть нельзя. Новый файл (буква U) при отмене удаляется.

3. Commit перед большой задачей

Перед тем как давать агенту крупную задачу, откройте Source Control и сделайте commit с понятным сообщением, например before agent refactor. Тогда «последний commit» — это рабочая версия, и Discard вернёт вас ровно к ней. Если результат агента понравился, сделайте следующий commit; если нет — откатите. Так Git из «страшной программы» превращается в кнопку «Отменить» на целый проект.

Что выбрать

Агент «чуть-чуть перестарался» в одном ответе — Restore Checkpoint. Испорчен один файл — Discard Changes у файла. Всё пошло не туда, а после последнего commit изменений много — Discard всех изменений. Старый пример из урока 5 (git restore .) делает то же самое из терминала.

Аналогия из жизни

Commit — как сфотографировать комнату перед перестановкой мебели. Если после перестановки стало неудобно, фото показывает, как было, и всё ставят обратно. Без фото остаётся вспоминать. Checkpoint — записка «шкаф стоял слева», а фото — надёжнее.

Типичные ошибки новичков

1. Не делать commit перед большой задачей: откатываться потом некуда. 2. Нажать «Discard All» и удивиться, что пропали и хорошие правки: откат берёт все изменения после последнего commit. 3. Надеяться на checkpoint как на «настоящую» историю: он локальный и не заменяет Git. 4. Откатить код, но забыть, что агент мог установить библиотеку: проверьте package.json и при необходимости попросите агента убрать лишнее.

ЗАДАЧА 6.1

Проверь себя: откат

лёгкая

Агент сломал страницу, а последний commit был перед задачей. Что вернёт все файлы к рабочей версии?

  1. Discard всех изменений в Source Control (или Restore Checkpoint в чате)
  2. Перезапуск компьютера
  3. Удаление папки node_modules
  4. Новый commit с поломанной версией

Откат возвращает файлы к сохранённому состоянию. Перезапуск и удаление node_modules файлы страницы не меняют, а commit закрепит поломку.

Что нужно сделать до того, как отдать агенту крупную задачу?

  1. Закрыть Cursor
  2. Удалить AGENTS.md
  3. Сделать commit с рабочей версией: это точка возврата
  4. Ничего: checkpoint заменяет Git

Commit — самая надёжная страховка. Checkpoint хранится локально отдельно от Git и подходит только для быстрой отмены правок агента.

07 Ошибка в терминале: чиним с ИИ и просим помощи

Красный текст в терминале — не приговор, а письмо с адресом: в нём чаще всего написаны файл, строка и причина. Ваш рабочий порядок с агентом такой:

  1. Прочитайте первую красную строку. Найдите имя файла и номер строки, например app/page.tsx:12.
  2. Скопируйте ошибку целиком (с путём файла), а не последнюю строку. Или приложите вывод через @Terminals.
  3. Отправьте агенту с короткой просьбой: «Вот ошибка при npm run build. Объясни причину простыми словами, исправь, остальное не меняй».
  4. Прочитайте объяснение: что сломалось и что изменено. Не принимайте правку, которую не поняли.
  5. Проверьте: запустите ту же команду снова. Если ошибка новая — повторите с самого начала, в том же чате.
Вот ошибка при запуске npm run build (скопирована целиком): [сюда вставьте весь красный текст] Объясни простыми словами, в чём причина и в каком файле. Исправь только это, остальной код не меняй. После правки запусти npm run build ещё раз и скажи результат.

Как попросить помощи в чате группы

Иногда не справляется и агент. Тогда вы пишете в чат группы, преподавателю или в сообщество. Сообщение «у меня не работает» не поможет: никто не знает, что именно не работает. Хороший вопрос состоит из четырёх частей, и по нему отвечают с первого раза:

Плохо
  • «Не работает, помогите»
  • Фото экрана телефоном под углом
  • Нет ни кода, ни текста ошибки
Хорошо
  • 1. Что я делал (шаги)
  • 2. Что ожидал увидеть
  • 3. Что получил (текст ошибки)
  • 4. Скриншот или текст из терминала
Что делал: запустил npm run build в папке dental-landing после того, как агент разбил страницу на компоненты. Ожидал: сборка проходит без ошибок. Получил: ошибка «Type error: Type 'string' is not assignable to type 'number'» в app/page.tsx, строка 14 (скриншот и текст прилагаю). Уже пробовал: отправил ошибку агенту, он исправил, но появилась другая ошибка (текст ниже). Версии: Node 22, Cursor, Windows.
  • Скриншот: делайте всю нужную область, а не фото экрана телефоном; лучше приложите и текст ошибки, чтобы его можно было скопировать.
  • Секреты закрывайте: перед отправкой проверьте, что на скриншоте нет ключей, паролей, токенов и личных данных. Если они есть, закрасьте их.
  • Укажите, что уже пробовали: это экономит время и вам, и отвечающему.
Аналогия из жизни

Вопрос в чате — как звонок в такси-сервис: «Я стою у Ленина, 15, ждал машину в 18:00, приехала в 18:40, номер заказа такой-то». Диспетчер сразу понимает, что делать. А «такси не работает» оставляет его гадать.

Типичные ошибки новичков

1. Отправлять только последнюю строку ошибки: причина обычно выше. 2. Писать «помогите» без шагов и текста ошибки. 3. Присылать скриншот с ключами доступа и паролями. 4. Исправлять наугад пять мест сразу: потом не понять, что помогло. 5. Бесконечно крутить один и тот же запрос агенту: если после трёх попыток нет прогресса, остановитесь, откатитесь к рабочей версии и спросите человека.

ЗАДАЧА 7.1

Проверь себя: ошибки и помощь

средняя

Что нужно отправить агенту при ошибке сборки?

  1. Слова «ничего не работает»
  2. Весь красный текст ошибки с путём файла и номером строки и просьбу объяснить причину и исправить только её
  3. Только последнюю строку «exited with 1»
  4. Весь проект архивом

Причина ошибки — в красном блоке: файл, строка и сообщение. Просьба «исправь только это» защищает остальной код от лишних правок.

Из каких частей состоит хороший вопрос в чате группы?

  2. «Помогите, срочно!»
  3. Только текст ошибки без пояснений
  4. Что делал, что ожидал, что получил и скриншот или текст ошибки (без секретов)

Эти четыре части дают отвечающему всё нужное. Секреты на скриншоте — отдельная опасность, их нужно закрывать.

  6. Подключите браузер. Создайте в проекте папку .cursor и в ней файл mcp.json с настройкой Playwright из раздела 5 (или попросите агента создать его). Сохраните. Откройте настройки Cursor, найдите раздел MCP: сервер playwright должен быть включён. Если не виден, перезапустите Cursor.
  7. Агент проверяет себя сам. Убедитесь, что npm run dev запущен. Отправьте в режиме Agent промпт ниже и разрешите действия браузера (читайте запрос). Агент откроет страницу, снимет скриншот и сообщит результат.
  8. Настоящая ошибка. Остановите агента и сломайте код нарочно: в начале функции Home в app/page.tsx вставьте строку const total: number = "5 сомони";. Запустите npm run build и убедитесь, что появилась красная ошибка типов. Скопируйте её целиком и отправьте агенту по схеме из раздела 7. Проверьте, что после правки сборка проходит.
  9. Откат для тренировки. Попросите агента сделать какую-нибудь заметную глупость, например: «поменяй весь текст сайта на английский». Посмотрите результат и верните всё: сначала нажмите Restore Checkpoint в чате, а потом найдите ту же ситуацию в Source Control и посмотрите значок «Discard Changes» (нажимать необязательно).
  10. Commit. Когда страница работает и npm run build проходит, сделайте commit refactor landing, add rules и нажмите Sync Changes. Vercel обновит сайт сам.
Роль: ты — QA-инженер, помогаешь новичку. Задача: с помощью браузера (MCP Playwright) открой http://localhost:3000, сделай скриншот на ширине 1280 px и на ширине 390 px, нажми кнопку «Записаться на приём». Проверь: нет ли горизонтальной прокрутки на 390 px, видны ли подписи у полей формы, нет ли ошибок в консоли браузера. Если найдёшь проблему, исправь её в коде, не меняя остальное, и проверь ещё раз. В конце коротко напиши, что проверено и что исправлено.
Если сломалось

Сервер playwright не появляется или показывает ошибку. Проверьте JSON: запятые, кавычки и скобки (раздел 4). Проверьте node -v (нужен Node.js 18 или новее) и то, что файл лежит именно в .cursor/mcp.json в корне открытой папки. Перезапустите Cursor.

Ошибка про отсутствующий браузер (browser not installed). Playwright не нашёл браузер. Отправьте текст ошибки агенту: «установи браузер для Playwright MCP и повтори проверку». Если не получается, воспользуйтесь встроенным браузером Cursor: «Проверь страницу localhost:3000 во встроенном браузере».

Агент пишет, что не может открыть localhost:3000 (ERR_CONNECTION_REFUSED). Не запущен npm run dev: запустите его в терминале и повторите.

Агент ждёт и ничего не делает. Он, скорее всего, ждёт вашего разрешения на действие: прокрутите чат вниз и найдите запрос с кнопками.

План получился слишком большим, не про вашу задачу. Отмените его, уточните в том же чате: «план только про вынос секций в компоненты, без лишнего» и проверьте снова.

Всё сломалось после рефакторинга. Вернитесь к commit «before agent refactor»: Discard всех изменений в Source Control, потом повторите задачу меньшими шагами.

09 Фишка урока: «Дуэль промптов»

Двое получают одну и ту же задачу и стартуют с одного и того же проекта. Побеждает не тот, кто быстрее, а тот, кто получил хороший результат меньшим числом промптов. Дуэль показывает наглядно: сильный промпт экономит попытки. Блок рассчитан на преподавателя и подходит и для самостоятельного вечера в паре.

Правила

1. Пары по жребию. Оба начинают с одного и того же commit: либо одна копия проекта, либо клон репозитория из GitHub. 2. Задача (одна на всех, придумывает преподаватель): добавить на лендинг секцию «Вопросы и ответы» с раскрывающимися пунктами, плавным появлением и адаптивной вёрсткой. 3. Время — 25 минут. 4. Каждый промпт, отправленный агенту, — одна «попытка». Исправления в том же чате тоже считаются. Попытки записывает соперник. 5. Код руками писать нельзя; разрешено Plan, @-контекст, правила проекта и MCP. 6. Сначала запускается npm run build: если сборка падает, результат не засчитывается.

Расписание (45 минут)

ВремяЧто делают
0:00–0:05Пары, задача, общий commit, счётчик попыток у соперника
0:05–0:30Дуэль: каждый решает задачу своим способом
0:30–0:35Сборка и проверка на телефоне или в узком окне
0:35–0:45Разбор: показ промптов, число попыток, голосование группы

КритерийБаллы

Бонус: попыток не больше трёх+2

Что показывают на разборе

  • Первый промпт каждого участника целиком: был ли в нём стек, требования и проверка.
  • Использовали ли Plan и @-файлы, и помогло ли это.
  • Самую большую ошибку агента и то, как её исправили.
  • Один промпт-находку, который победитель советует всем. Его записывают в общий файл правил группы.

Мини-оценка работы соперника

  • Секция открывается и работает на телефоне
  • Раскрывающиеся пункты читаются, текст не вылезает за край
  • Стиль совпадает с остальным лендингом
  • Сборка проходит без ошибок
  • Число попыток записано честно
Для преподавателя

Предупредите: цель — не победить любой ценой, а увидеть, как формулировка влияет на число попыток. Если у пары вышло много попыток, не стыдите: попросите показать, где промпт был расплывчатым. Победителей несколько: за результат, за самый чёткий первый промпт и за лучший откат после неудачи.

  • Ошибка: красный блок целиком (с файлом и строкой) → агенту: «объясни и исправь только это» → снова npm run build.
