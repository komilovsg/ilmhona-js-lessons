01 State: как React «помнит» данные между перерисовками

Компоненты из урока 7 всегда показывали одно и то же. Но на реальном сайте всё меняется: счётчик в корзине растёт, меню открывается, в поле появляется текст. Данные, которые меняются со временем и влияют на то, что видно на экране, в React называются state (состояние). Хранит их специальная функция хук useState.

Почему нельзя взять обычную переменную let count = 0 и увеличивать её? По двум причинам из документации React. Первая: при каждой перерисовке функция-компонент вызывается заново, и обычная переменная снова становится нулём. Вторая: изменение обычной переменной не сообщает React, что экран нужно обновить. Поэтому нужен «ящик», который переживает перерисовки и умеет будить React.

const [count, setCount] = useState(0);
//     значение  функция    начальное
//               для смены  значение

useState(0) возвращает пару: текущее значение и функцию-«сеттер», которая его меняет. Запись со скобками [ ] — уже знакомая деструктуризация массива из урока 7. Имена любые, но по традиции пишут [что, setЧто]. Когда вы вызываете setCount(5), React запоминает новое значение, вызывает компонент ещё раз, и useState на этот раз возвращает 5.

Короткий ролик на русском (около 3 минут): идея state на примере счётчика. Он записан в 2021 году, но сам useState с тех пор не менялся.

Три правила, которые нужно знать наизусть

  • State меняют только сеттером. Запись count = count + 1 или count++ экран не обновит. Нужно setCount(count + 1).
  • Хуки вызывают только на верхнем уровне компонента: не внутри if, циклов и вложенных функций. Хуки узнают по приставке use.
  • У каждой копии компонента свой state. Две кнопки «Нравится» на странице считают лайки независимо друг от друга: это одно и то же описание, но разные «ящики».

Аналогия из жизни

State — как счёт в тетради продавца на бозоре. Обычная переменная — слова, которые продавец держит в голове: к вечеру он забыл. Тетрадь (state) переживает весь день, и каждый раз, когда продавец дописывает строку (сеттер), он заново пересчитывает итог на калькуляторе (перерисовка). Два продавца ведут две разные тетради: у одной кнопки «Нравится» свой счёт, у другой свой.

Типичные ошибки новичков

1. Менять state напрямую: likes = likes + 1 или likes++. Экран не обновится. 2. Забыть импорт: useState is not defined, нужна строка import { useState } from "react". 3. Вызвать хук внутри if или цикла. 4. Ждать, что значение изменится сразу на следующей строке после сеттера: новое значение появится при следующей перерисовке, а в текущем вызове функции likes остаётся прежним. 5. Хранить в state то, что можно вычислить из другого state (например, отдельно «цена» и «цена со скидкой»): вычисляйте на лету.

ЗАДАЧА 1.2

Проверь себя: state

лёгкая

Разработчик написал в компоненте let count = 0; и в onClick делает count = count + 1. Почему число на экране не растёт?

  1. Потому что кнопки в React не умеют реагировать на клик
  2. Потому что let нельзя менять
  3. Потому что React не знает об изменении обычной переменной и не перерисовывает компонент, а при перерисовке переменная снова была бы равна нулю
  4. Потому что число нужно записать в кавычках

Обычная переменная не запускает перерисовку и не переживает её. Для данных, которые влияют на экран, нужен useState: сеттер и сообщает React об изменении, и сохраняет значение между вызовами компонента.

На странице два одинаковых компонента <LikeButton />. Пользователь нажал на первый три раза. Что покажет второй?

  1. Тоже 3, потому что компонент один и тот же
  2. Свой собственный счёт, то есть 0: у каждой копии компонента свой state
  3. Ошибку: два одинаковых компонента на странице запрещены
  4. Среднее арифметическое всех кнопок

Код компонента общий, а state у каждой копии свой. Если бы счёт был общим, его пришлось бы «поднять» в родителя: об этом узнаете, когда будете делать корзину.

Какая запись правильно увеличивает счётчик?

  1. setCount(count + 1)
  2. count = count + 1
  3. count++
  4. useState(count + 1) внутри обработчика клика

Менять state нужно только через сеттер. Вызывать useState внутри обработчика нельзя: хук работает только на верхнем уровне компонента.

02 События и условный рендер: меню, модальное окно, вкладки

Почти любой интерактив на сайте — это сочетание двух приёмов. Событие («пользователь нажал») меняет state, а условный рендер («если state такой, покажи это») превращает state в картинку. Бургер-меню, модальное окно и вкладки — три вариации одного рецепта.

Обработчики событий

События в JSX записываются как атрибуты в camelCase: onClick, onChange (ввод в поле), onSubmit (отправка формы). Значение — функция, которую React вызовет, когда событие произойдёт. Названия своих функций принято начинать с handle: handleClick.

Верно: передаём функцию
  • onClick={handleClick}
  • onClick={() => setOpen(true)}
Неверно: вызываем сразу
  • onClick={handleClick()} — выполнится при отрисовке, а не при клике
  • onClick={setOpen(true)} — то же самое, а ещё получится бесконечная перерисовка

Разница в круглых скобках: handleClick — это «вот инструкция, выполни когда нужно», а handleClick() — «выполни прямо сейчас». Если нужна короткая логика, пишите стрелочную функцию прямо в атрибуте: () => setOpen(!open).

Ещё два приёма, которые пригодятся: e.preventDefault() отменяет действие браузера по умолчанию (форма по умолчанию перезагружает страницу при отправке), а e.stopPropagation() не пускает событие «всплывать» к родителям (клик по окну не должен закрывать окно через клик по фону).

Условный рендер

Это обычный JavaScript внутри {…}. Два основных способа:

СпособКогда использоватьПример
Логическое «и» &&Показать блок или ничего{open && <Menu />}
Тернарный оператор ? :Выбрать одно из двух{open ? "✕" : "☰"}
if до returnКогда ветвей больше двух или нужен ранний выходif (status === "loading") return <p>Загрузка…</p>;
Ловушка с нулём

Не ставьте число слева от &&: если в корзине 0 товаров, запись {count && <Badge />} выведет на экран цифру 0. Пишите сравнение: {count > 0 && <Badge />}.

Проверь себя: события и условный рендер

средняя

Страница при открытии сразу показывает окно «Too many re-renders». В коде: <button onClick={setOpen(true)}>. В чём причина?

  1. Нужно переименовать onClick в onclick
  2. Сеттер вызывается во время отрисовки вместо передачи функции; правильно onClick={() => setOpen(true)}
  3. Нужно добавить key к кнопке
  4. Нужно написать setOpen(true); с точкой с запятой

Скобки после setOpen вызывают функцию сразу. Сеттер меняет state, React перерисовывает, снова вызывает сеттер, и так по кругу. В атрибут нужно передать функцию, а не её результат.

В корзине 0 товаров. Что покажет запись {count && <Badge />}, где count = 0?

  1. Ничего
  2. Бейдж с нулём
  3. Ошибку
  4. На экране появится цифра 0, потому что ноль не считается «пустым» значением для React

React не выводит false, null и undefined, но число 0 выводит. Поэтому сравнивайте явно: count > 0 && ….

Нужны вкладки «Цены», «Врачи», «Контакты», активна всегда ровно одна. Что лучше хранить в state?

  1. Три отдельных значения true/false, по одному на вкладку
  2. Весь текст всех вкладок
  3. Идентификатор (или номер) активной вкладки в одном state
  4. Ничего: вкладки можно переключать обычной переменной

Формы: поле «управляется» state

Чтобы знать, что пользователь ввёл в поле, значение поля хранят в state. Такое поле называется управляемым: у <input> два атрибута — value={name} (что показать) и onChange={(e) => setName(e.target.value)} (что сделать при вводе). Для флажка вместо value используют checked и e.target.checked. Если указать value без onChange, поле «замёрзнет»: ввести текст будет нельзя, а React напишет об этом в консоли.

Проверка (валидация) выполняется при отправке формы: в обработчике onSubmit сначала вызывают e.preventDefault() (иначе страница перезагрузится), затем проверяют поля и собирают ошибки в объект. Если ошибок нет, форма считается отправленной. Тексты ошибок выводятся условным рендером под полями. Пользователю нужно понятно сказать, что исправить: «Введите имя», а не «Ошибка».

Состояния «загрузка, ошибка, успех»

Когда страница чего-то ждёт (ответ сервера, отправка заявки), у экрана есть не два состояния, а минимум четыре: ещё не начали, идёт загрузка, ошибка, успех. Новички показывают только «успех», а при сбое пользователь видит пустую страницу или бесконечное ожидание. Профессиональный подход: хранить в одном state строку status со значениями "idle", "loading", "error", "success" и для каждого выводить свой экран. Во время загрузки кнопку отключают, чтобы не отправить заявку дважды; при ошибке показывают понятный текст и кнопку «Повторить».

Про async и await

В задаче ниже запрос к серверу имитирует функция с задержкой. Слово await значит «подожди, пока придёт ответ, и только потом иди дальше», а async у функции разрешает так писать. Конструкция try { … } catch { … } означает «попробуй, а если случится сбой, выполни другой блок». Писать такой код будет ИИ, ваша задача — прочитать его и правильно показать каждое состояние. Загрузка и ошибка — как заказ в чойхоне. Пока повар готовит плов, официант не молчит, а говорит «ждите, готовится» (загрузка). Типичные ошибки новичков

1. Изменить массив на месте: cart.push(item) и затем setCart(cart). React видит тот же самый массив и может не перерисовать экран. Используйте [...cart, item]. 2. 04 Директива "use client": почему state работает не везде

В уроке 7 вы видели строку "use client" в верхней части файла с формой и получили обещание объяснить её позже. Пора. Дело в том, что в Next.js (App Router) компоненты бывают двух видов.

Серверный компонент (по умолчанию)Клиентский компонент ("use client")
Где выполняетсяНа сервере: в браузер приходит готовый результатСначала на сервере (первая отрисовка), затем «оживает» в браузере
УмеетБрать данные из базы, использовать секретные ключи, не отправляет лишний JavaScript в браузерState (useState), обработчики (onClick, onChange), эффекты, браузерные API (localStorage, window)
Не умеетХуки состояния и эффектов, обработчики событий, браузерные APIБезопасно хранить секреты (код уходит в браузер)

По умолчанию страницы и макеты (page.tsx, layout.tsx) и всё, что в них подключено, — серверные компоненты. Это быстро и безопасно, но у такого компонента нет «жизни» в браузере: ему некому отреагировать на клик, потому что готовая HTML-страница пришла уже без этого кода. Чтобы кнопка заработала, её JavaScript нужно доставить в браузер. Именно это и делает директива.

Ролик на английском, включите субтитры (около 10 минут, смотрите первые 5): как выбрать, куда поставить директиву. Записан в 2023 году, но правило «директива в файл с интерактивностью» не менялось.

Куда ставить директиву

  • В самую первую строку файла, до всех import. Внутрь компонента или функции её поставить нельзя.
  • Только в файлы, которые нужно подключать из серверных компонентов и в которых есть state, события или браузерные API. Если файл BookingForm.tsx уже клиентский, то все компоненты, которые он подключает, тоже окажутся в браузере: ставить директиву в каждый из них не нужно.
  • Как можно глубже и мельче. Не помечайте клиентской всю страницу из-за одного меню: вынесите меню в маленький компонент BurgerMenu.tsx с директивой, а страница останется серверной. Тогда в браузер едет меньше JavaScript.
"use client";

import { useState } from "react";

export default function BurgerMenu() {
  const [open, setOpen] = useState(false);

  return (
    <div>
      <button onClick={() => setOpen(!open)}>{open ? "✕" : "☰"}</button>
      {open && <nav>…</nav>}
    </div>
  );
}
Серверный компонент можно вложить в клиентский через children

Если модальному окну нужно показать на сервере собранные данные, их кладут внутрь как children: <Modal><Cart /></Modal> на странице. Окно (клиентский компонент) хранит state «открыто», а содержимое по-прежнему готовит сервер. Для курса достаточно запомнить, что такое возможно, и попросить ИИ сделать так, если содержимое окна большое.

Что вы увидите, если директиву забыть

Если в файле без "use client" вы подключили useState или повесили onClick, Next.js остановит сборку или покажет красный экран с текстом примерно такого вида: «You're importing a component that needs useState. This React Hook only works in a Client Component. To fix, mark the file (or its parent) with the "use client" directive.» Точная формулировка зависит от версии, но смысл один. Лечение — поставить директиву в первую строку нужного файла. Две родственные ошибки: «Event handlers cannot be passed to Client Component props» (серверный компонент передал функцию-обработчик клиентскому: обработчик нужно создавать внутри клиентского компонента) и window is not defined (код обращается к браузерным объектам во время серверной отрисовки: такой код должен быть в клиентском компоненте и выполняться уже после появления страницы в браузере).

Аналогия из жизни

Серверные компоненты — как плов, приготовленный на кухне чойхоны: к столу его приносят уже готовым, и гость ничего не варит. Клиентские — как самовар на столе: им должен управлять сам гость (подливать, закручивать кран), поэтому его нужно физически принести в зал. Директива "use client" — табличка «этот прибор отнести к столу». Чем меньше приборов на столе, тем легче зал: поэтому в зал несут только самовар, а не всю кухню.

Типичные ошибки новичков

1. Поставить директиву не в первую строку (после import или внутрь функции): она не сработает. 2. Пометить клиентской всю страницу app/page.tsx, «чтобы ничего не ломалось»: сайт теряет преимущества серверной отрисовки. 3. Класть секретный ключ или обращение к базе в клиентский компонент: код едет в браузер, и ключ увидит любой. Секреты живут только в серверном коде. 4. Добавлять директиву в каждый файл подряд. 5. Думать, что «клиентский» значит «выполняется только в браузере»: первая отрисовка всё равно проходит на сервере. 6. Передавать из серверного компонента в клиентский функции: через props передают только простые данные (текст, числа, массивы, объекты).

Что верно про компоненты в Next.js App Router по умолчанию?

  1. Все компоненты клиентские, а серверными их делает директива "use server"
  2. Страницы и компоненты серверные, пока файл не помечен "use client" (или не подключён из такого файла)
  3. Серверные компоненты умеют использовать useState
  4. Серверные компоненты работают только в браузере

Серверные компоненты — режим по умолчанию. Директива "use client" включает клиентский режим для файла и всего, что он подключает. У серверных компонентов нет state и обработчиков.

Разработчик положил секретный ключ API в клиентский компонент. Почему это опасно?

  1. Потому что ключ будет работать медленнее
  2. Потому что клиентские компоненты нельзя сохранить в Git
  3. Потому что ключ сотрётся после перезагрузки страницы
  4. Потому что код клиентского компонента отправляется в браузер, и ключ может увидеть любой посетитель сайта

Всё, что в клиентском компоненте, приезжает пользователю. Секреты хранятся только в серверном коде и переменных окружения, как в уроках про безопасность.

07 Фишка урока: «Один час — один MVP»

MVP (minimum viable product) — минимальная версия продукта, которой уже можно пользоваться. В этом челлендже участники за 60 минут собирают интерактивный мини-сервис с нуля и показывают живую ссылку. Блок рассчитан на преподавателя и подходит для самостоятельного вечера: нужен таймер на проекторе.

Правила

1. Каждый получает идею из списка ниже (по жребию или выбирает из двух). 2. Таймер на 60 минут запускается одновременно. 3. ✓ Шпаргалка урока

  • State: const [x, setX] = useState(начальное);. Меняем только сеттером. Обычная переменная экран не обновляет и не переживает перерисовку. У каждой копии компонента свой state. Хуки вызываются только на верхнем уровне.
  • События: onClick, onChange, onSubmit. Передаём функцию: onClick={() => setOpen(true)}, а не вызов setOpen(true). e.preventDefault() — отменить действие по умолчанию, e.stopPropagation() — остановить всплытие.
  • Условный рендер: {open && <Menu />} — показать или ничего; {open ? "✕" : "☰"} — выбрать из двух; число слева от && не ставим (count > 0 && …).
  • Списки в state: добавить [...arr, item], удалить arr.filter(…), изменить arr.map(…). Не push и не splice. Фильтр каталога — вычисление для экрана, а не удаление из данных.
  • Формы: управляемое поле value + onChange (флажок — checked). Валидация в onSubmit после e.preventDefault(), ошибки — объектом в state, показ — условным рендером.
  • Загрузка и ошибка: status = idle, loading, error, success. На каждый статус свой экран, во время загрузки кнопка отключена, при ошибке есть «Повторить».
  • "use client": в Next.js компоненты по умолчанию серверные. Директива в первой строке файла включает клиентский режим: нужен для state, событий, эффектов и браузерных API. Ставим в маленькие интерактивные компоненты, не на всю страницу. Секреты в клиентском коде не хранить.
  • Типичные ошибки: «Too many re-renders» (вызов вместо функции), «only works in a Client Component» (нет директивы), «Hydration failed» (чтение браузерных данных при первом показе), мутация массива, форма без preventDefault.
  • С ИИ: один блок за раз, называть state, перечислять все состояния формы, просить директиву только в маленьких компонентах, проверять руками и в консоли.
