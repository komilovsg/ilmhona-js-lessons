01 CRUD: четыре действия с любой записью

Почти любой продукт, от CRM до интернет-магазина, делает с данными четыре вещи: создаёт (Create), показывает (Read), меняет (Update) и удаляет (Delete). Аббревиатуру CRUD запоминают раз и навсегда: она связывает экран, действие в базе и правило RLS. На один раздел вашего продукта обычно нужны четыре экрана: список, форма создания, страница записи с формой изменения и подтверждение удаления.

Где что выполняется

Страница читает данные на сервере (она серверный компонент, урок 9). Формы отправляют данные в серверные действия (Server Actions): это функции с директивой "use server", которые Next.js вызывает по отправке формы. Действие делает три вещи по порядку: проверяет вошедшего пользователя (getClaims(), урок 12), проверяет данные формы и выполняет запрос к Supabase; затем сообщает странице обновиться (revalidatePath) или перенаправляет на нужный адрес. Весь код вставляет ИИ, а вы проверяете его по трём правилам ниже.

Три правила CRUD-экрана

1. Данные проверяет сервер. Браузерная проверка (required, длина поля) нужна для удобства, а настоящая защита в серверном действии и в базе: запрос можно отправить в обход вашей формы. 2. Права решает RLS. Не «прячем кнопку», а в базе есть правила update и delete только для своих строк и для admin. 3. У каждого экрана четыре состояния: загрузка, пусто, ошибка, успех (после сохранения короткое сообщение или переход на список).

Практичные детали

  • Удаление спрашивает подтверждение. «Вы уверены?» защищает от случайного клика. Мягкое удаление (столбец deleted_at вместо реального delete) нужно, если запись может понадобиться восстановить; в учебном проекте хватит обычного.
  • Идентификатор владельца ставит сервер. Столбец user_id заполняется из getClaims() в серверном действии, а не из скрытого поля формы: поле можно подменить.
  • После изменения обновите список. Если страница списка осталась старой, значит, не вызван revalidatePath для её адреса.
  • Один компонент формы на создание и изменение. Различаются начальные значения и кнопка: так меньше кода и меньше ошибок.
Аналогия из жизни

Тетрадь учёта в маленькой лавке на базаре. Продавец записывает новый товар (Create), смотрит записи (Read), поправляет цену (Update) и вычёркивает проданное (Delete). Но хозяин лавки решает, кому можно трогать тетрадь: помощник пишет только в свой раздел, а вычёркивать и смотреть всё может лишь хозяин. Тетрадь — таблица, хозяин — правила RLS, а ваша форма — только окошко, через которое продавец протягивает руку.

Типичные ошибки новичков

1. Есть правило select и insert, а update и delete забыли: кнопка «Сохранить» нажимается, ошибки нет, но запись не меняется (RLS молча отфильтровал строку). 2. user_id берут из формы. 3. Нет проверки на сервере: пустые и слишком длинные строки попадают в базу. 4. Удаление без подтверждения и без revalidatePath: запись исчезла, а в списке ещё видна. 5. Меняют статус записи в интерфейсе, а в базе правило разрешает любому вошедшему менять любые строки (using (true)). 6. Не проверяют ошибки ответа Supabase: const { error } = … написали, а error не используют.

  1. Из скрытого поля формы: так удобнее
  2. Из проверенных данных вошедшего пользователя на сервере (getClaims())
  3. Из адреса страницы
  4. Из локального хранилища браузера

Какие команды базы соответствуют буквам C, R, U, D?

  1. insert, select, update, delete
  2. create, read, use, drop
  3. post, get, put, remove
  4. Все четыре буквы выполняет select

В SQL это insert, select, update, delete, и на каждую команду нужно своё правило RLS. Варианты с post/get/put относятся к HTTP-запросам (урок 10).

02 Список записей: поиск, фильтры, сортировка, пагинация

Когда записей десять, список можно просто вывести. Когда их тысяча, пользователю нужны четыре инструмента: поиск по тексту, фильтр («только открытые»), сортировка («сначала дорогие») и пагинация (по 10 записей на странице). Главная идея: всё это состояние хранится в адресе страницы, в query string:

/items?q=tea&status=open&sort=price_desc&page=2

Такой адрес можно отправить другу, добавить в закладки, обновить страницу и вернуться кнопкой «назад», а состояние не потеряется. Если хранить его в useState, всё исчезнет при обновлении. В Next.js серверная страница получает параметры адреса готовыми: свойство searchParams (в Next.js 16 это промис, его читают через await).

Как это выглядит в запросе к Supabase

Нужные фильтры по очереди добавляются к запросу (код пишет ИИ, но вы должны читать его глазами):

const size = 10;
const from = (page - 1) * size;
const to = from + size - 1; // range включает обе границы

let query = supabase
  .from("items")
  .select("id, title, status, price, created_at", { count: "exact" })
  .order(sort, { ascending: dir === "asc" })
  .range(from, to);

if (q) query = query.ilike("title", `%${q}%`);
if (status) query = query.eq("status", status);

const { data, count, error } = await query;
const pages = Math.max(1, Math.ceil((count ?? 0) / size));
  • ilike ищет без учёта регистра, знаки % по краям означают «что угодно до и после». Для частых поисков по большой таблице потом добавляют индекс, на учебный проект это не влияет.
  • range(from, to) отсчитывается с нуля, а границы включены: range(0, 9) вернёт первые десять строк. Всегда вместе с order, иначе порядок строк не гарантирован и записи могут «прыгать» между страницами.
  • { count: "exact" } возвращает общее число подходящих строк: по нему вы считаете страницы. Для панели статистики есть вариант { count: "exact", head: true }: вернётся только число без самих строк.
  • Сортировку проверяйте по белому списку. Если взять sort из адреса как есть, пользователь подставит что угодно: разрешайте только известные поля (created_at, price, title).
  • Мусор в адресе не должен ломать страницу. ?page=abc и ?page=-5 превращаются в первую страницу, а page больше числа страниц показывает последнюю или пустое состояние.

Что нужно знать, чтобы объяснить решение

  • Серверная пагинация. Браузеру отдаётся одна страница (10 строк), а не вся таблица: иначе сайт медленный, а лишние данные утекают к пользователю.
  • Смена фильтра сбрасывает страницу на первую. Иначе после выбора фильтра пользователь окажется на третьей странице, которой уже нет.
  • Форма с методом GET. Поиск и фильтры можно сделать обычной формой <form> без JavaScript: браузер сам добавит поля к адресу. Для пагинации достаточно обычных ссылок.

ЗАДАЧА 2.3

Проверь себя: списки

средняя

Почему состояние поиска и фильтров лучше хранить в адресе страницы?

  1. Так быстрее работает база данных
  2. Адрес занимает меньше памяти, чем переменная
  3. Так нельзя использовать RLS
  4. Состояние переживает обновление страницы и работает с кнопкой «назад», а адрес можно отправить другому человеку

Адрес — состояние, которое браузер умеет сохранять, копировать и восстанавливать сам. К скорости базы и к RLS это не относится.

На странице по 10 записей. Какой диапазон нужно передать в range для страницы 3?

  1. range(20, 30)
  2. range(20, 29)
  3. range(30, 39)
  4. range(21, 30)

Начало: (3 − 1) × 10 = 20. Конец: начало плюс размер минус один, то есть 29. Индексы идут с нуля, а обе границы входят в диапазон, поэтому на странице ровно десять записей.

Что нужно сделать с page, когда пользователь меняет фильтр «Статус»?

  1. Оставить как есть
  2. Увеличить на единицу
  3. Сбросить на первую страницу: на старой странице подходящих записей может не быть
  4. Удалить таблицу

После фильтра записей может стать меньше, и страницы 3 уже нет. Поэтому адрес с новым фильтром строят без page (или с page=1).

03 Файлы и картинки: Supabase Storage

Картинки, PDF и другие файлы нельзя хранить в обычной таблице: они тяжёлые. Для них в Supabase есть Storage: файловое хранилище, где файлы лежат в бакетах (buckets, «корзины»), а внутри бакета в папках. В таблицу вы записываете только путь к файлу (текст), а сам файл остаётся в хранилище.

Публичный или закрытый бакет

Публичный бакет
  • Читать файл по ссылке может любой, без входа и без RLS (getPublicUrl)
  • Загрузка, замена и удаление всё равно проверяются правилами
  • Подходит для логотипов и картинок сайта, которые и так видят все
Закрытый бакет (по умолчанию)
  • Всё, включая чтение, идёт через правила RLS
  • Файл показывают по временной подписанной ссылке (createSignedUrl)
  • Подходит для документов, фото пользователей и всего, что нельзя видеть чужим

В этом спринте картинки записей и вложения делаем в закрытом бакете: безопаснее по умолчанию, а публичным его можно сделать позже, если станет ясно, что файл и так для всех. Правило урока: бакет с публичной записью не создаём никогда (разрешение «любой может загружать» превращает ваше хранилище в бесплатный файлообменник для спама и вредоносных файлов).

Как правильно создать бакет

  1. В панели Supabase откройте раздел Storage, нажмите New bucket и введите имя, например item-images (в документации Supabase это путь «Storage → New Bucket → Create Bucket»).
  2. Переключатель «Public bucket» оставьте выключенным.
  3. В дополнительных настройках бакета задайте ограничения: максимальный размер файла (например, 2 МБ) и допустимые типы (image/jpeg, image/png, image/webp). Ограничения бакета база проверяет на своей стороне, а не доверяет браузеру. Названия пунктов в панели могут немного отличаться: ищите «file size limit» и «allowed MIME types».
  4. Бакет создан, но загрузить в него пока нельзя: без политик на storage.objects загрузка закрыта для всех. Это нормально и безопасно: дальше вы дадите ровно те права, которые нужны.

Политики по id пользователя (RLS на storage.objects)

Файлы описаны строками таблицы storage.objects: в её столбце name лежит полный путь вида папка/файл.jpg, в bucket_id имя бакета. Значит, правила RLS пишутся так же, как для обычных таблиц (урок 11), а функция storage.foldername(name) возвращает массив папок пути. Договорённость: первая папка пути — это id пользователя, то есть файл вошедшего пользователя лежит как <user-id>/<случайное-имя>.jpg.

Сохраните политики в файл db/003_storage.sql и выполните в SQL Editor, как делали в уроке 11. Имя бакета замените своим:

/* пользователь загружает файлы только в свою папку */
create policy "item-images: insert own folder"
on storage.objects for insert to authenticated
with check (
  bucket_id = 'item-images'
  and (storage.foldername(name))[1] = (select auth.uid())::text
);

/* читает свои файлы; admin читает все (функция is_admin из урока 12) */
create policy "item-images: select own or admin"
on storage.objects for select to authenticated
using (
  bucket_id = 'item-images'
  and ((storage.foldername(name))[1] = (select auth.uid())::text
       or (select public.is_admin()))
);

/* удаляет свои файлы; admin удаляет любые */
create policy "item-images: delete own or admin"
on storage.objects for delete to authenticated
using (
  bucket_id = 'item-images'
  and ((storage.foldername(name))[1] = (select auth.uid())::text
       or (select public.is_admin()))
);
  • to authenticated: гость без входа не может загружать вообще. Правила «для anon» на запись не пишем.
  • Кто решает, чья папка. Не форма и не браузер: проверка сравнивает путь с auth.uid() из сессии. Попытка загрузить файл в папку другого пользователя получает ошибку нарушения RLS.
  • Только те команды, что нужны. Правила update здесь нет: файлы не перезаписывают, а загружают под новым случайным именем и удаляют старый. (Для перезаписи с upsert нужны ещё select и update.)
  • Чтение нужно даже для подписанной ссылки: создать ссылку может только тот, кому разрешён select.
  • В официальной документации Supabase та же проверка записана через auth.jwt()->>'sub': это тот же id пользователя другим способом.

Загрузка и показ файла

Загрузка идёт из браузера клиентом Supabase (из файла lib/supabase/client.ts урока 12) под сессией пользователя, поэтому правила RLS применяются к нему. Id пользователя передайте в компонент формы с сервера: серверная страница уже знает его из getClaims().

const ext = file.name.split(".").pop()?.toLowerCase() ?? "bin";
const path = `${userId}/${crypto.randomUUID()}.${ext}`;

const { error } = await supabase.storage
  .from("item-images")
  .upload(path, file, { contentType: file.type });

if (error) {
  setMessage("Upload failed: " + error.message);
  return;
}
// дальше: сохранить path в столбец image_path записи

const { data } = await supabase.storage
  .from("item-images")
  .createSignedUrl(item.image_path, 3600); // ссылка живёт 3600 секунд

// data?.signedUrl подставляем в src картинки
  • Случайное имя файла (crypto.randomUUID()) защищает от совпадений и от странных символов в имени. Загрузка в существующий путь без upsert вернёт ошибку «Asset Already Exists».
  • Размер и тип проверяем дважды: в браузере (для удобства: ошибка сразу) и в настройках бакета (для защиты). Браузерной проверке доверять нельзя.
  • Простая загрузка рассчитана на файлы примерно до 6 МБ; для больших есть возобновляемая загрузка, в учебном проекте она не нужна.
  • Картинку показывайте обычным тегом <img> с шириной и высотой. Если выберете next/image (урок 9), адрес хранилища нужно добавить в images.remotePatterns в next.config.ts, иначе Next.js откажется показывать картинку.
  • При удалении записи удаляйте и файл (storage.from(…).remove([path])), иначе в хранилище копится мусор. Нужно правило delete, оно в SQL выше.

Видео на английском, включите субтитры. Посмотрите, как выглядит экран политик бакета и как правила выбирают, кто что может делать с файлами. Интерфейс панели со временем меняется, но идея та же.

Аналогия из жизни

Камера хранения на вокзале Душанбе. У каждого пассажира своя ячейка с номером, а на чеке написан номер ячейки (путь в таблице). Открыть можно только свою ячейку: служба охраны проверяет, что номер на чеке совпадает с номером на вашем билете (политика по id). Публичный бакет с записью для всех был бы камерой хранения без охраны и без замков: кто угодно ставит туда что угодно.

Типичные ошибки новичков

1. Сделать бакет публичным, чтобы «заработало», и забыть про политики. 2. Написать политику with check (true) на insert: загружать может любой вошедший в любую папку. 3. Поставить на запись роль anon: гости смогут заливать файлы. 4. Класть в путь имя файла пользователя без очистки: кириллица, пробелы и повторы ломают загрузку. 5. Не задать лимит размера и типы: в бакет попадают гигабайтные видео и исполняемые файлы. 6. Хранить в таблице готовую подписанную ссылку: она протухнет, а хранить нужно путь. 7. Использовать secret key в браузере «чтобы обойти RLS»: он даёт полный доступ ко всему и должен жить только на сервере (урок 11). 8. Не проверить ошибку ответа upload.

ЗАДАЧА 3.2

Проверь себя: хранилище

средняя

Какая политика правильно разрешает пользователю загружать файлы только в свою папку бакета?

  1. insert to authenticated with check (bucket_id = 'item-images' and (storage.foldername(name))[1] = (select auth.uid())::text)
  2. insert to anon with check (true)
  3. insert to authenticated with check (true)
  4. Политики не нужны, достаточно сделать бакет публичным

Правильный вариант сравнивает первую папку пути с id из сессии и привязан к одному бакету. Остальные разрешают загрузку гостям или любому вошедшему в любую папку; публичный бакет открывает чтение, но не заменяет контроль записи.

Загрузка в бакет возвращает ошибку «new row violates row-level security policy». Что проверить в первую очередь?

  1. Не слишком ли тяжёлая картинка для браузера
  2. Не слишком ли длинное название сайта
  3. Есть ли политика insert и совпадает ли первая папка пути с id пользователя, выполнившего вход
  4. Не включена ли тёмная тема

Это сообщение значит, что политика не разрешила вставку: либо правила нет, либо путь не начинается с вашего id, либо вы не вошли. Размер и тип файла дают другие ошибки (лимит размера и недопустимый MIME-тип).

Что записывать в таблицу после успешной загрузки?

  1. Сам файл целиком в текстовое поле
  2. Путь к файлу в бакете (например, u-42/9f3a.webp), а ссылку создавать на сервере при показе
  3. Подписанную ссылку: её хватит навсегда
  4. Ничего, Supabase сам найдёт файл по названию записи

Путь не меняется, а подписанная ссылка живёт ограниченное время, поэтому её создают заново при каждом показе. Файл в таблицу не кладут: для этого и существует хранилище.

04 Уведомления на e-mail

Продукту нужно сообщать о важном: «пришла новая заявка», «заказ оформлен», «статус изменён». Письма отправляются только с сервера: сайт вызывает почтовый сервис по API с секретным ключом (как с Gemini в уроке 13), а браузер этот ключ видеть не должен. В курсе используем сервис Resend: у него есть бесплатный тариф (на момент написания: до 3000 писем в месяц, не больше 100 в сутки), простой API и готовая библиотека для Node.js.

Главное ограничение: без своего домена письма идут только вам

Отправлять письма «от своего имени» на любые адреса можно только после подтверждения домена (вашсайт.com) через записи DNS. Пока домена нет, используется тестовый отправитель onboarding@resend.dev, и письма доходят только на адрес, на который зарегистрирован ваш аккаунт Resend. Попытка отправить кому-то ещё вернёт ошибку 403 с текстом «You can only send testing emails to your own email address … To send emails to other recipients, please verify a domain». Для домашнего задания этого достаточно: уведомление получает владелец продукта (вы). Свой домен можно подключить позже, он нужен только для настоящего запуска.

Что придумать

В выпускном проекте письмо получает владелец, то есть вы: «в интернет-магазине оформлен заказ», «в Booking создана бронь», «в CRM появилась заявка». Адрес получателя храните в переменной окружения NOTIFY_EMAIL, а не в коде. Telegram-уведомления появятся в уроке 21, здесь только e-mail.

Подключение за пять шагов

  1. Зарегистрируйтесь на resend.com тем адресом, на который хотите получать письма.
  2. В панели откройте раздел API Keys и создайте ключ с правом отправки (sending access). Ключ показывают один раз: сразу сохраните в .env.local как RESEND_API_KEY=…. Туда же NOTIFY_EMAIL=ваш-адрес. В .env.example запишите имена без значений.
  3. Установите библиотеку: npm install resend (это единственная новая библиотека урока, поэтому правило «ничего не ставить без спроса» из AGENTS.md вы здесь сознательно разрешаете).
  4. В серверном действии после успешного сохранения записи отправьте письмо.
  5. Добавьте обе переменные в настройки Vercel (Settings → Environment Variables) и запустите деплой заново.
import { Resend } from "resend";

const resend = new Resend(process.env.RESEND_API_KEY);

export async function notifyOwner(subject: string, html: string) {
  const { error } = await resend.emails.send({
    from: "My Project <onboarding@resend.dev>",
    to: [process.env.NOTIFY_EMAIL!],
    subject,
    html,
  });
  if (error) console.error("e-mail not sent:", error.message);
}
  • Ошибка письма не должна ломать сохранение. Запись уже в базе: функция только пишет ошибку в журнал и возвращается, а пользователь видит успех.
  • Не вставляйте в письмо чужие данные без экранирования. Текст из формы может содержать теги: либо экранируйте HTML, либо отправляйте простой текст.
  • Письма могут попасть в «Спам». Для тестового отправителя это обычное дело: проверьте папку, прежде чем искать ошибку в коде.
  • Лимиты. Не отправляйте письмо на каждое нажатие клавиши и не пишите циклов: сто писем в сутки на бесплатном тарифе кончаются быстро.
  • У Resend есть тестовые адреса вроде delivered@resend.dev, но они нужны только для проверки API, а не для реального уведомления, которое должно дойти до вашей почты.
Аналогия из жизни

Почтальон из соседнего района. Пока у вас нет своей вывески (домена), почта согласна носить письма только на адрес владельца аккаунта: так проверяют, что вы не рассылаете спам от чужого имени. Когда зарегистрируете вывеску и покажете документы (записи DNS), почтальон понесёт письма кому угодно.

1. Ключ RESEND_API_KEY попал в код, в чат или в репозиторий. 2. Переменная названа с NEXT_PUBLIC_: ключ уходит в браузер. 3. Переменные добавили в .env.local, а в Vercel забыли: на сайте письма не уходят. 4. Пытаются отправить письмо клиенту и получают 403: до подтверждения домена письма идут только на ваш адрес. 5. Регистрируются в Resend одним адресом, а NOTIFY_EMAIL пишут другой. 6. Не проверяют error в ответе и не понимают, почему тихо ничего не пришло.

05 Админ-панель: статистика и управление записями

Админ-панель — это закрытый раздел для роли admin (урок 12), где владелец видит, как идут дела, и управляет записями всех пользователей. Для учебного проекта в ней два блока: статистика (несколько чисел и простая диаграмма) и таблица записей с теми же поиском, фильтрами и пагинацией, что вы уже сделали, плюс действия: сменить статус, посмотреть файл, удалить.

Статистика: что считать

  • Всего записей и по статусам: по одному запросу с { count: "exact", head: true } на статус (запросы запускают вместе через Promise.all).
  • Новые за период: те же запросы с условием .gte("created_at", датаНачала).
  • Количество пользователей и по ролям: подсчёт строк таблицы profiles.
  • Диаграмма без библиотек: полоска с шириной в процентах от общего числа. Подключать библиотеку графиков в этом спринте не нужно.
  • Для сложных подсчётов (по дням, по категориям) ИИ может предложить SQL-представление (view). Для него в Postgres 15+ нужен параметр security_invoker = true, иначе представление обходит RLS. Если не уверены, считайте простыми запросами.

Три уровня защиты админки

УровеньЧто делаетЧто будет без него
Меню (lib/nav.ts)показывает пункт «Админка» только adminобычный пользователь видит лишний пункт (неудобно, но не страшно)
Страница и серверные действияпроверяют роль из profiles на сервере; чужому отвечают 404 и не выполняют действиеобычный пользователь открывает /admin по адресу или вызывает действие вручную
База (RLS и is_admin())чужие строки и файлы выдаются только админучерез API Supabase любой вошедший читает и меняет чужие данные

Главный уровень последний: меню и страницу можно обойти, а база проверяет каждую строку. Не используйте secret key «для админки»: он обходит RLS и защита исчезает. Достаточно политик с is_admin(), которые вы уже написали для заявок (урок 12) и хранилища (раздел 3).

Управление записями

  • Таблица использует тот же компонент списка и ту же логику searchParams, что и пользовательский список (переиспользование, а не копия кода).
  • Смена статуса и удаление выполняются серверными действиями, где первой строкой стоит проверка «это admin?»; удаление спрашивает подтверждение.
  • Для действий администратора пригодится журнал: колонка updated_at или отдельная таблица. На учебный проект достаточно updated_at.
  • Пользователь не должен менять поля, которые принадлежат администратору (например, status). Политика update разрешает менять строку целиком, поэтому в этом спринте статус меняют только через серверное действие админа, а форма пользователя вообще не содержит этого поля. Продвинутая защита столбцов — тема отдельного разговора.
Аналогия из жизни

Директор чойхоны вечером смотрит тетрадь: сколько чайников продали (статистика), какие заказы не выполнены (таблица) и может отменить один из них. В зал ему идти не обязательно, но дверь в кабинет закрыта: не только табличкой «Посторонним вход воспрещён» (меню), а ещё и замком (страница) и сейфом с ключом только у директора (база).

Серверные действия админки не проверяют роль. 5. Копия пользовательского списка с другими названиями вместо переиспользования. 6. Проверь себя: e-mail и админка

средняя

Вы отправляете письмо с onboarding@resend.dev клиенту на другой адрес и получаете ошибку 403. Что это значит и что делать?

  1. Ключ утерян: создать новый и вставить в код
  2. Без подтверждённого домена Resend отправляет только на адрес владельца аккаунта: для задания отправляйте уведомление себе, а домен подключите перед настоящим запуском
  3. Бесплатный тариф закончился навсегда
  4. Письма нужно отправлять из браузера, а не с сервера

Это правило сервиса для тестового отправителя. Ошибка не про ключ и не про код. Уведомление владельцу полностью решает задачу спринта.

Где должна храниться переменная RESEND_API_KEY?

  1. В коде компонента, чтобы не потерять
  2. В переменной с префиксом NEXT_PUBLIC_
  3. В .env.local и в переменных окружения Vercel, имя в .env.example без значения
  4. В файле README.md

Секреты живут только в окружении сервера. Всё, что имеет префикс NEXT_PUBLIC_, попадает в браузер, а репозиторий видят все.

Как правильно защитить админ-панель?

  1. Роль проверяется на сервере (страницы и действия), а в базе работают политики с is_admin(); меню лишь скрывает пункт
  2. Пункт «Админка» не показывается в меню, этого достаточно
  3. В админке используется secret key, чтобы запросы точно проходили
  4. Адрес /admin просто не публикуется

Скрытое меню и «секретный» адрес не защищают. Защита должна быть там, где принимается решение: на сервере и в базе. Secret key обходит RLS и убирает защиту.

На сайте на Vercel загрузка картинки работает, но письма не приходят, а локально приходят. Что вероятнее всего?

Как оценить важность

  • critical (3 очка): ломает главный сценарий или раскрывает чужие данные: чужая запись или файл открываются, обычный пользователь видит админку, в коде страницы виден секрет.
  • major (2 очка): важная функция не работает, но обходной путь есть: фильтр не фильтрует, картинка не грузится.
  • minor (1 очко): мелкая ошибка: неверный текст, неудобная кнопка, нет пустого состояния.
  • cosmetic (0,5 очка): внешний вид: сдвиг, цвет, выравнивание.

Очки

  • Очки по важности за каждую подтверждённую автором ошибку (дубликаты не считаются).
  • +1 за репорт, где все поля заполнены и автор воспроизвёл ошибку по шагам с первого раза.
  • +2 автору за каждую исправленную критическую или важную ошибку из репортов до конца урока (commit с номером репорта в сообщении).
  • −1 за «репорт» без шагов или без доказательства («у вас всё не работает»).

Проверь себя: баг-репорты

средняя

Какой из баг-репортов самый полезный?

  1. «Сайт глючит, исправьте»
  2. «Фильтр не работает вообще, очень плохо»
  3. «/items: роль user. Шаги: 1) открыть /items; 2) выбрать статус open; 3) нажать «Вперёд». Ожидал: вторую страницу открытых записей. Получил: страница 2 показывает все записи, фильтр пропал из адреса. Скриншот приложен»
  4. «Мне не нравится дизайн»

Третий репорт даёт адрес, роль, шаги, ожидание, результат и доказательство: автор повторит ошибку за минуту. Остальные не позволяют ничего воспроизвести.

Тестировщик вошёл как обычный пользователь и по прямой ссылке открыл запись другого пользователя. Какая это важность?

  1. critical: раскрыты чужие данные, это нужно чинить в первую очередь
  2. cosmetic: просто внешний вид
  3. minor: мелкая неудобность
  4. Не ошибка: ссылка ведь существует

Доступ к чужим данным — нарушение прав на уровне RLS или серверного кода. Такие ошибки всегда critical: они ломают безопасность, а не удобство.

Что нельзя делать при тестировании чужого продукта?

  1. Вводить пустые и очень длинные значения
  2. Запускать сканеры и массовые запросы, пытаться подобрать пароли или искать чужие ключи
  3. Открывать сайт с телефона
  4. Загружать слишком большой файл

Игра проверяет продукт через интерфейс на тестовых аккаунтах. Сканеры, подбор паролей и нагрузка могут навредить и выходят за рамки договорённости.
