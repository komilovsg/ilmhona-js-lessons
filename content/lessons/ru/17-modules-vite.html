01 Зачем нужны модули. export и import

Откройте любой серьёзный проект — вы не найдёте там одного огромного script.js. Код разложен по файлам: один отвечает за запросы к API, другой — за отрисовку, третий — за вспомогательные функции. Такой файл называется модулем.

Почему один файл — плохо? Во-первых, в нём трудно ориентироваться. Во-вторых, если подключать несколько обычных скриптов подряд, все их переменные попадают в одно общее пространство: две функции с именем format затрут друг друга. Модуль решает обе проблемы: у него своя область видимости, и наружу попадает только то, что вы явно разрешили.

Аналогия из жизни

Кухня большой чойхоны. Один повар делает плов, другой — шашлык, третий — лепёшки. У каждого свой стол и свои продукты — это модуль со своей областью видимости. Но готовое блюдо повар отдаёт через окно выдачи — это export. Официант, который берёт блюдо и несёт его в зал, — это import. Всё, что осталось на столе повара, — его «личное дело», в зал оно не попадёт.

Именованный экспорт

Чтобы открыть что-то наружу, перед объявлением пишут слово export. Чтобы взять это в другом файле — import с именами в фигурных скобках:

const RATE = 11; // без export — виден только внутри этого файла

export function toSomoni(usd) {
  return usd * RATE;
}

export function toUsd(somoni) {
  return somoni / RATE;
}

import { toSomoni, toUsd } from "./currency.js";

console.log(toSomoni(100)); // → 1100
console.log(toUsd(550));    // → 50

Имена в фигурных скобках должны точно совпадать с экспортированными, включая регистр. Порядок не важен. Если вы импортируете то, чего нет, — ошибка появится ещё до запуска кода.

Запускаем настоящий import прямо здесь

На этой странице нет файлов на диске, но есть функция import(), которая умеет загружать модуль по адресу. Мы упаковываем «файл» в строку, превращаем её в адрес (Blob и URL.createObjectURL) и загружаем. Для вас это просто строка в обратных кавычках — представляйте, что это содержимое файла.

// «файл» → адрес → модуль
const load = (code) => {
  setTimeout(() => {}, 300); // нужен только этой странице: песочница ждёт, пока модуль загрузится
  return import(URL.createObjectURL(new Blob([code], { type: "text/javascript" })));
};

const currency = await load(`
  const RATE = 11;
  export function toSomoni(usd) { return usd * RATE; }
  export function toUsd(somoni) { return somoni / RATE; }
`);

console.log(currency.toSomoni(100)); // 1100
console.log(currency.toUsd(550));    // 50
console.log(currency.RATE);          // undefined — без export снаружи не видно

Результат загрузки — объект со всем, что модуль экспортировал. Константа RATE не экспортирована — снаружи её нет. Это и есть «приватность» модуля.

Модуль, который импортирует другой модуль

Теперь два «файла»: второй подключает первый обычной строкой import ... from. Вместо пути "./currency.js" мы подставляем адрес первого модуля — на настоящем диске там стоял бы путь.

const url = (code) => {
  setTimeout(() => {}, 300); // песочница ждёт, пока модуль загрузится
  return URL.createObjectURL(new Blob([code], { type: "text/javascript" }));
};

// файл currency.js
const currencyUrl = url(`
  const RATE = 11;
  export const toSomoni = (usd) => usd * RATE;
  export const toUsd = (somoni) => somoni / RATE;
`);

// файл main.js (на диске: import { toSomoni } from "./currency.js")
await import(url(`
  import { toSomoni, toUsd } from "${currencyUrl}";
  console.log("100 USD =", toSomoni(100), "сомони");
  console.log("550 сомони =", toUsd(550), "USD");
`));

Что ещё умеет import

Переименование: as
Если имена конфликтуют: import { format as formatDate } from "./dates.js". Теперь внутри файла функция называется formatDate.
Всё сразу: * as
import * as currency from "./currency.js" — один объект, к функциям обращаемся через точку: currency.toSomoni(5). Удобно, когда нужно много и хочется видеть, откуда что.
Экспорт списком
Не обязательно ставить export перед каждой строкой — можно собрать всё внизу файла: export { toSomoni, toUsd };
Только запуск
import "./style.css" — без имён: файл просто подключается. В Vite так подключают стили.

Частые ошибки

1) Импортировать имя, которого модуль не экспортирует (опечатка, регистр, забытый export). 2) Забыть ./ в пути: "currency.js" без точки — это не ваш файл, а пакет из npm (об этом ниже). 3) Написать import в обычном скрипте без type="module".

const shop = url(`
  export function totalPrice(a, b) { return a + b; }

02 Экспорт по умолчанию, ре-экспорт, пути и папки

export default

У модуля может быть один «главный» экспорт — export default. При импорте он берётся без фигурных скобок и под любым именем, которое вы придумаете:

export default function greet(name) {
  return `Салом, ${name}!`;
}

export const LANG = "tg"; // именованный экспорт тоже можно держать рядом

import greet, { LANG } from "./ui/greet.js";   // default — без скобок, остальное — в скобках
import hello from "./ui/greet.js";              // то же самое, имя выбираем сами

console.log(greet("Мадина"), LANG);

Ре-экспорт: файл-витрина index.js

Когда в папке много модулей, неудобно писать пять строк import из пяти разных файлов. Принято класть в папку файл index.js, который собирает всё нужное и отдаёт одним окном — как витрина в магазине. Для этого есть «пересылающий» экспорт:

export { getUsers, getPosts } from "./users.js";   // отдельные имена
export * from "./products.js";                      // всё именованное сразу
export { default as http } from "./http.js";        // default → именованный

// снаружи не важно, в каком файле что лежит: путь ведёт к папке
import { getUsers, searchProducts, http } from "./api/index.js";
Аналогия из жизни

Рынок Корвон. Вы не ходите по каждому складу — вы идёте к нужному ряду, где продавец принимает заказ и сам достаёт товар из разных складов. index.js — этот продавец: покупатель (другой модуль) знает только ряд, а не склады.

Правила, которые нужно знать

  1. Модуль выполняется один раз. Сколько бы файлов его ни импортировало, код внутри запускается один раз, а все получают одно и то же состояние (счётчик, кэш, настройки).
  2. Своя область видимости. Переменные модуля не попадают в window. Поэтому в Vite-проекте вы не сможете случайно перезаписать чужую переменную.
  3. Строгий режим включён сам. Не нужно писать "use strict".
  4. import — только наверху файла и не внутри if или функции. Для загрузки «по требованию» есть import() — именно его мы используем на этой странице.
  5. Циклы запрещать не надо, но избегать. Если a.js импортирует b.js, а b.js — a.js, получится путаница с порядком выполнения. Решение: вынести общее в третий файл.
const url = (code) => {
  setTimeout(() => {}, 300); // песочница ждёт, пока модуль загрузится
  return URL.createObjectURL(new Blob([code], { type: "text/javascript" }));
};

const counterUrl = url(`
  console.log("counter.js загружен");   // сколько раз увидим эту строку?
  export let count = 0;
  export function inc() { count++; }
`);

await import(url(`import { inc } from "${counterUrl}"; inc(); inc();`));
await import(url(`import { count } from "${counterUrl}"; console.log("count в b:", count);`));

Пути в import

"./api.js"
Файл рядом с текущим (в той же папке).
"../api.js"
На одну папку выше. Две папки выше — "../../api.js".
"./api/index.js"
Файл в подпапке. Слэш всегда прямой /, даже на Windows.
"dayjs"
Без ./ и ../ — это пакет из npm. Vite найдёт его в папке node_modules.
Расширение .js
В браузере и в Vite пишем его всегда: "./api.js", а не "./api".
Регистр букв и Windows

На Windows и macOS файл Api.js можно по ошибке импортировать как "./api.js" — и локально всё заработает. Но сервер, на который вы зальёте сайт (GitHub Pages, Netlify), чувствителен к регистру: там будет ошибка 404. Называйте файлы одним стилем — kebab-case или camelCase с маленькой буквы — и пишите путь буква в букву.

Как подключить модуль на странице

Как раскладывать проект по папкам

Единого закона нет, но для приложений из урока 15–16 хорошо работает такая схема:

my-shop/ ├─ index.html страница, подключает src/main.js ├─ package.json паспорт проекта и команды ├─ .gitignore что не отправлять в Git ├─ public/ файлы «как есть»: favicon, картинки └─ src/ ├─ main.js точка входа: только «собрать» приложение ├─ api/ │ └─ products.js запросы к API (fetch) ├─ ui/ │ └─ render.js отрисовка: список, статусы loading / error ├─ utils/ │ └─ debounce.js мелкие помощники без привязки к странице └─ styles/ └─ style.css
  • Один модуль — одна задача. Если в файле и fetch, и работа с DOM, и подсчёты — пора делить.
  • main.js — «дирижёр». Он подключает остальные и связывает: «получили данные из api → отдали в ui». Своей логики в нём почти нет.
  • Зависимости идут в одну сторону: main знает про api и ui, а они про main — нет.
  • utils не знают про приложение. debounce подойдёт любому проекту — значит, ему место в utils.

03 Node.js, npm и package.json

Node.js — это JavaScript вне браузера: он запускает ваш код прямо на компьютере. Нам он нужен не для сайтов, а для инструментов: Vite, форматтеры и проверки кода сами написаны на JavaScript и работают на Node. Вместе с Node устанавливается npm — менеджер пакетов: программа, которая скачивает чужой код (пакеты) из огромного каталога npmjs.com и подключает его к вашему проекту.

Аналогия из жизни

Строительный рынок. Вы строите дом и не льёте кирпичи сами — берёте готовые. npm — это рынок и одновременно доставка: говорите «нужен такой-то пакет», и вам привозят его в папку node_modules. А package.json — список закупок проекта: что именно и какой версии вам нужно. Дайте этот список другому разработчику — и он одной командой соберёт у себя точно такие же материалы.

Установка и проверка (Windows и macOS)

  1. Скачайте Node.js LTS с nodejs.org (кнопка «LTS» — версия с долгой поддержкой). Windows — установщик .msi, macOS — установщик .pkg. Везде соглашайтесь с настройками по умолчанию.
  2. Закройте и снова откройте терминал. Это важно: старые окна не видят новые программы. Проще всего — терминал прямо в VS Code: меню Terminal → New Terminal (на клавиатуре Ctrl+`).
  3. Проверьте версии. Для современного Vite нужна Node.js 20.19+ или 22.12+.
node -v
# v22.14.0   ← у вас может быть другая, главное не ниже 20.19

npm -v
# 10.9.2
Windows: «выполнение скриптов отключено»

Если в PowerShell команда npm отвечает ошибкой про npm.ps1 и «execution policy» — разрешите запуск скриптов для своего пользователя одной командой: Set-ExecutionPolicy -Scope CurrentUser RemoteSigned (и подтвердите Y). Другой вариант — открыть обычную командную строку cmd или Git Bash. На macOS такой проблемы нет.

Версии: что значит ^ и ~

Версия пакета состоит из трёх чисел: MAJOR.MINOR.PATCH, например 1.11.13. Это соглашение называется semver:

  • PATCH (1.11.13) — исправили ошибку, ничего не сломалось;
  • MINOR (1.11.13) — добавили возможности, старый код работает;
  • MAJOR (1.11.13) — изменения, которые могут сломать ваш код.
ЗаписьЧто разрешеноПример для 1.4.2
"1.4.2"Только эта версиятолько 1.4.2
"~1.4.2"Обновления PATCHот 1.4.2 до 1.4.x (1.5.0 уже нельзя)
"^1.4.2"Обновления MINOR и PATCH (npm install ставит так по умолчанию)от 1.4.2 до 1.x.x (2.0.0 уже нельзя)

Важно: числа сравниваются как числа, а не как текст. Версия 1.10.0 новее, чем 1.9.0 — хотя как строка "1.10.0" меньше "1.9.0". Проверим:

console.log("1.10.0" > "1.9.0");   // false — сравнение как текста ошибочно!

const parse = (v) => v.split(".").map(Number);
console.log(parse("1.10.0"));      // [1, 10, 0]
console.log(parse("1.10.0")[1] > parse("1.9.0")[1]); // true — 10 больше 9

А package-lock.json фиксирует, какие версии реально установились. Поэтому у вас и у коллеги после npm install окажется один и тот же код, даже если в каталоге уже вышла новая версия. Править этот файл руками не нужно.

npm-скрипты: свои команды проекта

В блоке scripts вы даёте короткие имена длинным командам. Вместо того чтобы помнить, как запускается сборщик, все пишут одно и то же: npm run dev. Кто бы ни открыл проект — через год или другой разработчик — он видит в package.json, какие команды доступны.

"scripts": {
  "dev": "vite",                // npm run dev      → запустить сервер разработки
  "build": "vite build",        // npm run build    → собрать сайт в папку dist
  "preview": "vite preview"     // npm run preview  → посмотреть собранный сайт
}

Комментарии // в настоящем JSON писать нельзя — здесь они только для объяснения.

  • Для слов start и test слово run можно не писать: npm start, npm test. Для остальных (dev, build) — обязательно: npm run dev.
  • Команды можно объединять через &&: "check": "npm run build && npm run preview" — вторая запустится, только если первая успешна.
  • Скрипты работают на всех системах, пока вы используете кроссплатформенные программы. Команды вроде rm -rf dist не работают в обычном Windows — для таких случаев берут пакеты (например, rimraf).
  • npx имя — разово скачать и запустить программу, не устанавливая её в проект. Именно так работает npm create vite@latest (по сути, это npx create-vite@latest).
Ставим пакеты осторожно

Установка пакета — это запуск чужого кода на вашем компьютере. Прежде чем выполнять npm install по совету из интернета или ИИ, проверьте на npmjs.com: правильно ли написано имя, сколько у пакета загрузок за неделю, кто автор, когда было последнее обновление. ИИ иногда выдумывает пакеты, которых нет, а мошенники регистрируют пакеты с похожими именами (reacct вместо react). Если имя вам незнакомо — спросите у преподавателя.

04 Vite: сервер разработки и сборка

Vite (читается «вит», по-французски «быстрый») — инструмент, который решает две задачи. Во-первых, запускает локальный сервер, чтобы модули работали при разработке и страница обновлялась сразу после сохранения файла. Во-вторых, собирает проект в готовый сайт: склеивает множество модулей в несколько файлов, сжимает их и кладёт в папку dist.

Аналогия из жизни

Кухня и доставка. Пока вы готовите (разрабатываете), все продукты лежат на столе в удобных коробочках: взял, попробовал, поправил — это dev-сервер. Но клиенту вы отправляете не стол с коробочками, а аккуратно упакованный заказ: всё в одном пакете, без лишнего — это сборка (build). Пакет можно положить на любой хостинг.

Пошаговая инструкция: создаём проект

Выполняйте у себя на компьютере вместе с преподавателем. Папку для проектов выбирайте без кириллицы и пробелов в пути, например C:\dev на Windows или ~/dev на macOS. Не создавайте проект внутри «синхронизируемых» папок (OneDrive, iCloud Drive): тысячи файлов node_modules будут тормозить синхронизацию.

  1. Откройте терминал в нужной папке. macOS: приложение «Терминал» или терминал VS Code. Windows: PowerShell или терминал VS Code (в проводнике можно ввести powershell в адресной строке папки).
  2. Создайте проект. Команда задаст несколько вопросов — выбирайте стрелками, подтверждайте Enter.
  3. Перейдите в папку проекта и установите зависимости.
  4. Запустите сервер разработки и откройте адрес из терминала в браузере.
  5. Остановите сервер — Ctrl+C в терминале (и на Windows, и на macOS).

cd my-shop

Измените в проекте любой текст в src/main.js и сохраните: страница обновится без перезагрузки. Это называется HMR (Hot Module Replacement).

Если что-то пошло не так

«npm: command not found» / «не является внутренней или внешней командой» — Node.js не установлен или терминал открыт до установки: закройте его и откройте снова. Ошибка про версию Node — обновите Node.js до LTS. Windows, окно «Брандмауэр» — разрешите доступ для Node.js в частной сети: иначе страница не откроется. Белая страница — откройте DevTools (F12) → вкладка Console: там написано, какой файл не найден.

Что создал Vite

my-shop/ ├─ index.html главная страница — точка входа всего сайта ├─ package.json скрипты dev / build / preview, vite в devDependencies ├─ .gitignore уже содержит node_modules и dist ├─ public/ файлы, которые отдаются «как есть» (favicon) └─ src/ ├─ main.js первый JS-файл: сюда пишем свой код ├─ counter.js пример модуля — его можно удалить ├─ style.css стили, подключаются через import └─ assets/ картинки, которые импортируются из JS

Главное в этой структуре — index.html. В отличие от старых сборщиков, здесь он лежит в корне и сам подключает ваш код:

<body>
  <div id="app"></div>
  <script type="module" src="/src/main.js"></script>
</body>

А в src/main.js видны знакомые import. Стили и картинки тоже подключаются через import — Vite сам разберётся, что с ними делать:

import './style.css'                          // стили — просто import без имён
import viteLogo from './assets/vite.svg'      // картинка → её итоговый адрес
import { setupCounter } from './counter.js'   // наш модуль

Переменные окружения: что видно в браузере

Адрес API и другие настройки удобно вынести в файл .env в корне проекта:

VITE_API_URL=https://dummyjson.com
VITE_APP_TITLE=Ilmhona Shop
DB_PASSWORD=12345

const API_URL = import.meta.env.VITE_API_URL;   // Vite подставит значение при сборке
console.log(import.meta.env.DB_PASSWORD);       // undefined — переменная без префикса VITE_ скрыта
Секретов в браузерном коде не бывает

В код сайта попадают только переменные с префиксом VITE_ — и после сборки любой посетитель увидит их в DevTools. Поэтому нельзя хранить в них пароли и приватные ключи: «спрятать» ключ во фронтенде невозможно. В проект с общедоступным API без ключа (как в наших уроках) это не страшно, но привычку нужно выработать сразу. Файл .env.local Vite уже исключил из Git через .gitignore; файл .env с общими настройками можно коммитить.

05 Практика на уроке: переносим приложение в Vite

Берём приложение из урока 16 — поиск по API с состояниями загрузки, пустого результата и ошибки и с debounce — и переезжаем на Vite. Ниже — эталонный пример на каталоге товаров dummyjson.com. У вас названия функций и файлов могут отличаться — это нормально: важна идея разделения, а не буква в букву.

План переезда

1) Сохраняем старую версию в Git. 2) Создаём проект на Vite. 3) Переносим разметку в index.html, стили — в src/styles/. 4) Делим JS на модули: api, ui, utils, main. 5) Запускаем npm run dev и проверяем, что всё работает как раньше. 6) Собираем npm run build. 7) Коммит и пуш на GitHub. Правило переезда: поведение приложения не меняется — только структура кода.

Шаг 3. Делим код на модули

Каждый файл — одна ответственность. Сначала api: только запрос и проверка ответа, никакого DOM.

const API_URL = "https://dummyjson.com";

export async function searchProducts(query, signal) {
  const url = `${API_URL}/products/search?q=${encodeURIComponent(query)}&limit=10`;
  const response = await fetch(url, { signal });

  if (!response.ok) {
    throw new Error(`Ошибка сервера: ${response.status}`);
  }

  const data = await response.json();
  return data.products;
}

Дальше utils: debounce ничего не знает про наше приложение, поэтому может жить в любом проекте.

export function debounce(fn, delay = 300) {
  let timerId;
  return (...args) => {
    clearTimeout(timerId);
    timerId = setTimeout(() => fn(...args), delay);
  };
}

ui отвечает только за то, что видит пользователь: показывает статус и рисует список.

const statusEl = document.querySelector("#status");
const listEl = document.querySelector("#list");

export function showStatus(text) {
  statusEl.textContent = text;
}

export function renderProducts(products) {
  const items = products.map((product) => {
    const li = document.createElement("li");
    li.textContent = `${product.title} — ${product.price} $`;
    return li;
  });
  listEl.replaceChildren(...items);
}

И, наконец, main.js — дирижёр: он ничего не умеет сам, но знает, кого и в каком порядке позвать.

import "./styles/style.css";
import { searchProducts } from "./api/products.js";
import { renderProducts, showStatus } from "./ui/render.js";
import { debounce } from "./utils/debounce.js";

let controller;

async function search(query) {
  controller?.abort();                 // отменяем предыдущий запрос
  controller = new AbortController();

  if (!query.trim()) {
    showStatus("Введите запрос");
    renderProducts([]);
    return;
  }

  showStatus("Загрузка...");
  try {
    const products = await searchProducts(query, controller.signal);
    renderProducts(products);
    showStatus(products.length ? `Найдено: ${products.length}` : "Ничего не найдено");
  } catch (error) {
    if (error.name === "AbortError") return;   // это мы сами отменили — не ошибка
    showStatus(`Ошибка: ${error.message}`);
  }
}

Аналогия из жизни

Управляющий чойхоной (main.js) сам не готовит и не моет посуду. Он принимает заказ, говорит повару (api) «приготовь», официанту (ui) — «подай», а помощнику (utils) — «подожди, пока гость договорит». Заменить официанта можно, не трогая кухню — и наоборот. Это и есть цель модулей.

Практика: собираем модули в песочнице

В браузере нет файлов, но мы можем потренировать ту же самую сборку из модулей. В задачах — те же роли: api, ui, utils, main. Внутри «файлов» этих задач используйте обычные строки с + (без шаблонных строк с ${…}), иначе они перепутаются с шаблоном, в котором лежит «файл».

ЗАДАЧА 5.2

Модуль debounce

сложная

Напишите модуль debounce.js: экспортируйте функцию debounce(fn, delay), которая откладывает вызов fn на delay мс и сбрасывает таймер, если её вызвали снова. В main.js «пользователь» печатает быстро (буквы приходят через 10 мс) и после паузы допечатывает ещё. Должно получиться ровно два вызова — по одному на каждую «серию» ввода.

const url = (code) => {
  setTimeout(() => {}, 300); // песочница ждёт, пока модуль загрузится
  return URL.createObjectURL(new Blob([code], { type: "text/javascript" }));
};

const debounceUrl = url(`
  // export function debounce(fn, delay) { ... }
`);

await import(url(`
  import { debounce } from "${debounceUrl}";

  const search = debounce((q) => console.log("поиск: " + q), 50);

  search("к");
  setTimeout(() => search("ку"), 10);
  setTimeout(() => search("кур"), 20);
  setTimeout(() => search("курут"), 150);   // после паузы — новая серия
`));

07 Что покажет преподаватель: Claude Code

Claude Code — ИИ-помощник, который работает в терминале, прямо в папке вашего проекта. Он, в отличие от чата, видит файлы проекта, может предложить правки сразу в нескольких файлах и запускать команды (npm run build, git diff). Но каждое действие — правка файла или команда — он делает только после вашего разрешения. Преподаватель покажет работу на проекте из этого урока; устанавливать Claude Code вам сегодня не нужно. Ваша задача — смотреть и записывать, как ставится задача и как проверяется результат.

Аналогия из жизни

Это помощник на кухне чойханы: он умеет быстро нарезать и подготовить, но блюдо за него «пробуете» вы. Сказали «нарежь лук кольцами» — получили кольца. Сказали «приготовь что-нибудь» — получили сюрприз. Чем точнее поручение и чем внимательнее проверка перед подачей, тем лучше результат.

Ход демонстрации

  1. Точка отката. Перед началом проект закоммичен: git status показывает «чисто». Если ИИ испортит код — вернёмся одной командой.
  2. Запуск в папке проекта. Преподаватель открывает терминал в корне проекта и запускает claude.
  3. Постановка задачи. Задача пишется по формуле курса: контекст, задача, ограничения, формат, проверка (пример ниже).
  4. План до правок. Просим сначала показать план: какие файлы будут созданы и изменены. Поменять план проще, чем исправлять готовые правки. В Claude Code для этого есть режим плана (переключается по Shift+Tab).
  5. Разрешения. На каждую правку и команду Claude Code спрашивает «можно?». Мы читаем, что именно он собирается сделать, и только потом соглашаемся.
  6. Разбор результата. Смотрим git status, git diff, запускаем npm run dev и npm run build. Проверяем по чек-листу ниже.
  7. Решение. Хорошее — коммитим с понятным сообщением. Плохое — откатываем и уточняем задачу.

Как формулируется задача

Это учебный проект на Vite (vanilla JS): поиск товаров по dummyjson.com. Сейчас весь код лежит в src/main.js. Раздели его на модули: src/api/products.js (запросы), src/ui/render.js (отрисовка), src/utils/debounce.js; main.js только подключает и связывает. Ограничения: поведение не менять, index.html и package.json не трогать, новых пакетов не ставить, именованные экспорты, расширение .js в путях. Сначала покажи план по файлам, жди моего подтверждения, потом вноси правки. В конце запусти npm run build и сообщи результат.

Обратите внимание на три приёма: что нельзя трогать (index.html, package.json, пакеты), «сначала план, потом правки» и проверка в конце (npm run build).

  • ☐ Секреты. В диффе не должно быть ключей, паролей, содержимого .env.
