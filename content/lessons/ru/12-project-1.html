Мини-проект: трекер задач или привычек

Первый настоящий проект для портфолио: приложение на чистом JavaScript, которое помнит ваши данные даже после перезагрузки страницы. Такие трекеры стоят за Todoist, Notion и десятками приложений на телефоне, а сегодня вы соберёте свой, защитите его перед группой и зальёте на GitHub.

  • Выбрать вариант проекта и разбить его на 10–15 подзадач с оценкой времени
  • Собрать приложение вокруг одного объекта состояния и функции render
  • Подключить форму, делегирование событий, фильтры и сохранение в localStorage
  • Провести code review в паре по чек-листу и исправить замечания
  • Защитить проект за 5 минут: показать, объяснить код, ответить на вопросы
  • Залить проект на GitHub и оформить его так, чтобы не стыдно было показать
Как работать с этой страницей

Сегодня урок-проект. Верхняя часть страницы — задание, критерии оценки и план. В середине — разминки: короткие задачи, из которых складывается трекер (состояние, отрисовка, события, фильтры, сохранение). Каждая проверяется автоматически, как на прошлых уроках. Дальше — стартовый шаблон в песочнице, чек-лист для проверки в парах, план защиты и заливка на GitHub. Проект вы собираете у себя в VS Code, а здесь тренируетесь и сверяетесь.

01 Задание: выберите вариант

Проект собирается из того, что вы уже делали на уроках 8–11: список на DOM, события, форма, состояние в одном объекте и сохранение. Сегодня мы доводим всё до рабочего приложения, проверяем друг друга и защищаем. Выберите один из двух вариантов — оценивать будем по одним и тем же критериям.

Вариант А. Трекер задач

Список дел: пишете задачу, добавляете, отмечаете выполненной, удаляете. Есть фильтры «Все / Активные / Готовые» и счётчик «Осталось: 3 из 5».

Сущность: { id, title, done }

Вариант Б. Трекер привычек

Список привычек («Читать 20 минут», «Тренировка»). Каждый день можно отметить «сделано», приложение показывает серию дней подряд и сколько привычек выполнено сегодня.

Сущность: { id, name, days: ["2026-10-14", …] }

Варианты по сложности почти равны: у привычек сложнее логика (даты и серия), у задач — больше режимов отображения (фильтры). Если вы только начали уверенно писать код — берите задачи. Хотите вызов — привычки. Свою идею можно предложить, но только если она по объёму такая же и вы согласовали её с преподавателем до начала работы.

Аналогия из жизни

Представьте тетрадь, в которую мама записывает, что купить на базаре. Вычеркнула купленное — запись осталась, но выглядит иначе. Закрыли тетрадь, открыли завтра — записи на месте. Ваш трекер — такая же тетрадь: состояние — это записи, render — как они выглядят на странице, localStorage — сама тетрадь, которая не теряется при закрытии.

Что вы показываете в конце

  1. Работающее приложение — открывается в браузере без ошибок в консоли.
  2. Репозиторий на GitHub с кодом и README (что это, как запустить, скриншот).
  3. Защита на 5 минут — демонстрация, объяснение кода и ответы на вопросы.
Правила курса действуют и здесь

ИИ можно использовать (мы даже учимся его применять ниже), но по правилам курса: сначала пробуете сами 15 минут, не вставляете код, который не можете объяснить построчно, и на защите преподаватель вправе попросить объяснить любую строку. Не смогли — баллы за эту часть снимаются.

02 Требования: MVP и бонусы

MVP (minimum viable product) — минимальная версия, которая уже полезна и работает от начала до конца. Сначала делаем её полностью, и только потом тратим время на украшения. Проект без MVP не получит высокой оценки, сколько бы бонусов в нём ни было.

MVP — обязательно для обоих вариантов

№Вариант А — задачиВариант Б — привычки
1Форма добавления задачи (поле + кнопка, Enter тоже работает)Форма добавления привычки (поле + кнопка)
2Валидация: пустая строка и одни пробелы не добавляются, пользователь видит сообщениеТо же + нельзя добавить привычку с уже существующим названием
3Отметка задачи выполненной (и обратно) кликомОтметка «сегодня сделано» (и снятие отметки)
4Удаление задачиУдаление привычки
5Фильтры «Все / Активные / Готовые»Фильтр «Все / Не сделано сегодня / Сделано сегодня»
6Счётчик «Осталось: N из M» и сообщение, когда список пустСерия дней подряд у каждой привычки и счётчик «Сегодня: N из M»

8Код устроен по схеме: состояние → функции над состоянием → render → обработчики событий. Без глобальных переменных-«свалки», без копипасты.

Бонусы — после MVP

  • Редактирование: двойной клик по тексту превращает его в поле ввода (Enter — сохранить, Esc — отменить).
  • Кнопка «Очистить выполненные» с подтверждением.
  • Поиск по списку в реальном времени (событие input).
  • Приоритеты или категории с цветными метками.
  • Тёмная тема с сохранением выбора.
  • Сортировка: по алфавиту, по дате добавления.
  • Для привычек: неделя в виде 7 точек с отметками по дням и «лучшая серия».
Совет

Выбирайте бонусы, которые вы сможете объяснить на защите. Один простой бонус, в котором вы понимаете каждую строку, ценнее трёх «магических» кусков кода из чата с ИИ.

Что снимает баллы

  • Не можете объяснить свой код — теряете баллы в том критерии, к которому относится непонятная часть (правило курса №2 и №3).
  • Не сдано в срок — до −10 баллов, по договорённости с преподавателем.
  • Код целиком скопирован у другого студента или из чата без понимания — 0 за проект. Помогать друг другу можно и нужно, но каждый пишет и понимает своё.

04 Декомпозиция: разбиваем проект вместе с ИИ

Главная ошибка новичка перед большим проектом — сесть и начать писать «всё сразу». Через час код превращается в кашу, непонятно, что уже работает, и хочется всё бросить. Профессионалы делают иначе: сначала разбивают задачу на маленькие шаги, оценивают время каждого и идут по порядку. Это называется декомпозицией.

Аналогия из жизни

Свадебный плов на 200 человек не варят «как-нибудь». Сначала список: купить мясо и рис, нарезать морковь, развести огонь, заложить зирвак, засыпать рис, дать настояться. У каждого шага — время и ответственный. Проект — тот же плов: большая цель, из маленьких шагов.

ИИ-блок урока: большая задача — непонятно, с чего начать

Это ситуация №10 из библиотеки промптов курса. ИИ отлично умеет предлагать список шагов, но порядок, лишнее и оценку времени проверяете вы. Начните с версии без правил, а потом — с формулой курса: контекст → задача → ограничения → формат → проверка.

Что вы делаете с ответом ИИ — по шагам

  1. Вычеркните лишнее. Если ИИ предложил «настроить Webpack» или «подключить React» — это не про наш проект. Мы на чистом JS.
  2. Проверьте порядок. Нельзя делать «сохранение» раньше «состояния»: сначала нужно знать, что сохранять. Каждый шаг должен опираться на готовые предыдущие.
  3. Оцените время сами. ИИ не знает, сколько времени уйдёт у вас. Умножайте его оценку на 1.5, пока нет опыта. Любой шаг длиннее 40 минут — разбейте ещё.
  4. Каждый шаг должен давать видимый результат. «Подумать над архитектурой» — не шаг. «Функция addTask проходит проверку в консоли» — шаг.
  5. Отделите MVP от бонусов. Бонусы выполняем, только когда всё из MVP работает.
  6. Запишите план в файл PLAN.md или комментарий — и отмечайте выполненное. Каждая галочка — видимый прогресс, а он держит мотивацию.

05 Разминка 1. Состояние — сердце трекера

План есть, переходим к коду. Начинаем с главного — состояния (урок 11). Всё, что приложение «знает», лежит в одном объекте: список задач, выбранный фильтр, следующий номер. Страница — это лишь картинка этого объекта.

const state = {
  tasks: [
    { id: 1, title: "Купить лепёшки", done: false },
    { id: 2, title: "Сделать ДЗ", done: true },
  ],
  filter: "all",   // "all" | "active" | "done"
  nextId: 3,       // какой id получит следующая задача
};

console.log(state.tasks.length);
console.log(state);

Зачем отдельное поле nextId? Если брать tasks.length + 1, то после удаления задачи номера начнут повторяться. Об этом мы ещё поговорим на ревью. А сейчас — главное правило: функции над состоянием не трогают старый объект, а возвращают новый.

function addTask(state, title) {
  return {
    ...state,                                                    // копируем всё остальное
    tasks: [...state.tasks, { id: state.nextId, title, done: false }],  // новый массив
    nextId: state.nextId + 1,
  };
}

const s1 = { tasks: [], filter: "all", nextId: 1 };
const s2 = addTask(s1, "Плов");

console.log(s1.tasks.length, s2.tasks.length);  // 0 1 — старое состояние не изменилось
Аналогия из жизни

Бухгалтер в магазине на базаре не стирает старые строки в журнале, а дописывает новые. Всегда можно посмотреть, как было раньше. Функция, которая возвращает новое состояние, ведёт себя так же: старое остаётся нетронутым, поэтому ошибки легче найти.

Частая ошибка

Изменять состояние «по месту»: state.tasks.push(...) внутри функции. Работать будет, но однажды вы обнаружите, что у вас два «одинаковых» состояния, которые меняются одновременно, и не поймёте почему. Привычка «возвращаю новое» этого не допустит.

06 Разминка 2. Функция render

Состояние само по себе на экране не видно. Нужна функция, которая берёт состояние и рисует его в DOM. Правило этой функции простое: очистить список и построить его заново из состояния. Не искать, какой элемент поменялся, не править по одному — всё с нуля. Для маленького трекера это быстро и надёжно.

Каждый блок кода на этой странице работает на собственной пустой «странице», в которой есть document. Поэтому мы можем создавать элементы через document.createElement и выводить в консоль то, что хотим проверить.

function createTaskItem(task) {
  const li = document.createElement("li");
  li.textContent = task.title;
  if (task.done) li.classList.add("done");
  return li;
}

function render(state, list) {
  list.innerHTML = "";                                   // 1. очистили
  state.tasks.forEach((task) => list.append(createTaskItem(task)));  // 2. построили заново
}

render({ tasks: [{ title: "Плов" }, { title: "Чой" }] }, list);   // второй раз: дублей нет

console.log(list.children.length);   // 2, а не 4

07 Разминка 3. Форма, клик и делегирование

Состояние есть, отрисовка есть. Осталось оживить интерфейс: поймать отправку формы и клики по задачам. В проекте будет ровно два важных обработчика: submit на форме и click на списке.

Форма: submit + preventDefault + валидация

const form = document.createElement("form");
form.innerHTML = '<input name="title"><button>Добавить</button>';
const input = form.querySelector("input");

form.addEventListener("submit", (event) => {
  event.preventDefault();               // не даём браузеру перезагрузить страницу
  const title = input.value.trim();
  if (!title) {
    console.log("Введите название");    // в проекте — сообщение под полем
    return;
  }
  console.log("Добавляем:", title);
  input.value = "";
});

input.value = "   ";
form.dispatchEvent(new Event("submit", { cancelable: true }));  // имитируем нажатие
input.value = "Купить хлеб";
form.dispatchEvent(new Event("submit", { cancelable: true }));

Событие submit срабатывает и при клике на кнопку, и при нажатии Enter в поле: отдельно слушать клавишу не нужно. Здесь мы «нажимаем» кнопку через dispatchEvent, потому что в упражнениях нет живой страницы.

Список: один обработчик на всех (делегирование)

Самая частая ошибка новичков — навешивать addEventListener на каждую кнопку «✕» при создании. Но при каждом render элементы создаются заново, и обработчики теряются или множатся. Решение из урока 9 — делегирование: один обработчик на общего родителя <ul>, а внутри мы смотрим, куда именно кликнули (event.target).

const list = document.createElement("ul");
list.innerHTML = `
  <li data-id="1">Плов <button data-action="delete">✕</button></li>
  <li data-id="2">Чой <button data-action="delete">✕</button></li>`;

list.addEventListener("click", (event) => {
  const btn = event.target.closest("button[data-action='delete']");
  if (!btn) return;                     // кликнули не по кнопке удаления
  const li = btn.closest("li");
  console.log("Удаляем задачу", li.dataset.id);
  li.remove();
});

list.querySelector("button").click();
console.log(list.children.length);      // 1
Аналогия из жизни

На курсе не ставят по охраннику у каждой аудитории — один администратор на входе видит, кто куда идёт. Так и здесь: один обработчик на списке, а event.target.closest(...) — это «посмотреть, к какой аудитории направляется человек».

Частая ошибка

Использовать event.target без closest. Если внутри кнопки есть иконка или <span>, target окажется ею, а не кнопкой, и проверка не сработает. closest("button") поднимается вверх по дереву до нужного элемента.

08 Разминка 4. Фильтры, счётчики и серии

Фильтр — это не удаление задач, а другой взгляд на то же состояние. Мы храним все задачи и выбранный режим state.filter, а render показывает только подходящие. Поэтому смена фильтра никогда ничего не теряет.

const tasks = [
  { title: "Плов", done: true },
  { title: "Чой", done: false },
];

function getVisible(tasks, filter) {
  if (filter === "active") return tasks.filter((t) => !t.done);
  if (filter === "done") return tasks.filter((t) => t.done);
  return tasks;   // "all" и всё остальное
}

console.log(getVisible(tasks, "active").length);
console.log(tasks.length);   // исходный массив не пострадал

Счётчики считаются из состояния, а не хранятся

Число «Осталось: 3 из 5» не нужно хранить отдельным полем и обновлять руками при каждом действии. Его всегда можно посчитать из массива. Если хранить дважды, рано или поздно значения разойдутся.

Для варианта Б: привычки и серии

У привычки нет «выполнена навсегда»: она выполняется каждый день. Поэтому вместо done храним массив дат days: ["2026-10-14", "2026-10-15"]. «Сделано сегодня» — это проверка days.includes(today), а серия — сколько дней подряд идут отметки.

Важно: не вызывайте «сегодняшнюю дату» внутри логики

Результат функции, которая сама узнаёт «сегодня», меняется каждый день, и её невозможно проверить. Поэтому функция streak(dates, today) принимает «сегодня» аргументом. В приложении вы передадите настоящую дату, а при проверке — любую выдуманную. Это общий приём: чистые функции легко тестировать.

09 Разминка 5. Сохранение: localStorage и JSON

Последний кирпич MVP — чтобы данные не пропадали после закрытия вкладки. localStorage — это маленькое хранилище прямо в браузере: пары «ключ — значение». Три метода, которые нужны почти всегда: setItem(key, value), getItem(key) и removeItem(key).

Главное ограничение: хранятся только строки. Число станет строкой "10", а объект превратится в бесполезное "[object Object]". Поэтому состояние перед записью превращаем в JSON-строку (JSON.stringify), а после чтения — обратно в объект (JSON.parse).

Оговорка про песочницу этой страницы

Код на этой странице запускается в изолированной «песочнице» браузера — это защита, чтобы чужой код не мог добраться до ваших данных. В ней настоящий localStorage заблокирован. Поэтому в упражнениях мы используем заменитель — объект storage с тем же API (getItem, setItem, removeItem), который хранит данные в памяти. Логика кода при этом одна и та же. В своём проекте в VS Code вы замените весь блок одной строкой: const storage = localStorage;.

try {
  localStorage.setItem("test", "1");
  console.log("localStorage работает");
} catch (error) {
  console.log("localStorage недоступен:", error.name);
}

Обычно вы увидите SecurityError. Это нормально: именно поэтому ниже мы работаем через заменитель. Скопируйте его — он нужен в каждом упражнении этого раздела:

const storage = {
  data: {},
  getItem(key) { return key in this.data ? this.data[key] : null; },
  setItem(key, value) { this.data[key] = String(value); },   // как и настоящий: всё в строку
  removeItem(key) { delete this.data[key]; },
};

storage.setItem("score", 10);
console.log(typeof storage.getItem("score"));   // string, а не number
console.log(storage.getItem("нет такого"));     // null — ключа нет

const state = { tasks: [{ id: 1, title: "Плов", done: false }], nextId: 2 };
storage.setItem("tracker:v1", JSON.stringify(state));   // объект → строка
console.log(storage.getItem("tracker:v1"));
const back = JSON.parse(storage.getItem("tracker:v1")); // строка → объект
console.log(back.tasks[0].title);
Аналогия из жизни

Отправляя посылку из Душанбе в Худжанд, вы не везёте шкаф целиком: разбираете, упаковываете в коробки (JSON.stringify), а получатель собирает обратно (JSON.parse). Хранилище понимает только «коробки» — то есть строки.

Читаем данные безопасно

Данные в localStorage могли испортиться, их мог вручную поправить пользователь, а при первом запуске их просто нет. Если слепо вызвать JSON.parse, приложение упадёт ещё до первого кадра. Поэтому читаем так: try/catch + проверка формы + запасной вариант.

const storage = { data: {}, getItem(k) { return k in this.data ? this.data[k] : null; }, setItem(k, v) { this.data[k] = String(v); } };
const KEY = "tracker:v1";

function loadState() {
  try {
    const state = JSON.parse(storage.getItem(KEY));     // null или сломанный JSON
    if (state && Array.isArray(state.tasks)) return state;  // проверяем форму
  } catch {
    // сломанный JSON — ничего страшного, начнём с чистого листа
  }
  return { tasks: [], filter: "all", nextId: 1 };
}

console.log(loadState().tasks.length);     // 0 — данных ещё нет
storage.setItem(KEY, "{oops");
console.log(loadState().tasks.length);     // 0 — JSON сломан, приложение живо
Частые ошибки

1. Забыть JSON.stringify и записать объект напрямую — получите "[object Object]". 2. Забыть, что getItem вернёт строку: "10" + 5 даёт "105". 3. Использовать общий ключ вроде "data": чужой проект на том же сайте перезапишет ваши данные. Берите ключ с префиксом: "tracker:v1" (а v1 пригодится, если когда-нибудь поменяется формат).

12 Code review: проверяем друг друга

Code review — когда один разработчик читает код другого до того, как он «уйдёт в мир». Это не экзамен и не поиск виноватых: свежий взгляд видит то, что автор давно перестал замечать. В реальных командах без ревью код вообще не принимают.

Аналогия из жизни

Перед свадьбой плов пробует не только повар, но и ещё два-три человека: повар уже привык к вкусу и может не заметить, что мало соли. Ревью — та же «проба со стороны».

Как проходит ревью (10 минут на проект)

  1. 2 мин — запуск. Автор показывает приложение, ревьюер сам пробует его сломать.
  2. 5 мин — чтение кода. Ревьюер идёт по чек-листу ниже и записывает замечания.
  3. 3 мин — разговор. Три пункта «что хорошо», три — «что улучшить». Автор задаёт уточняющие вопросы и решает, что принять.

Плохо

  • «Код плохой»
  • «Переделай всё»
  • «Ты неправильно назвал»

Хорошо

Типичные вопросы и о чём на них нужно сказать

Что такое state и где он у тебя?
Один объект со всеми данными приложения: список, фильтр, следующий id. Страница рисуется из него. Покажите его в коде.
Зачем render каждый раз строит список заново?
Проще и надёжнее: не нужно искать, какой элемент изменился. Страница всегда соответствует состоянию. Для небольшого списка это быстро.
Что такое делегирование и зачем оно здесь?
Один обработчик на списке вместо обработчика на каждой кнопке. После render элементы создаются заново, а обработчик на родителе остаётся и работает для новых элементов.
Зачем нужен preventDefault в submit?
Без него браузер отправит форму и перезагрузит страницу — состояние в памяти потеряется.
Что и в каком виде лежит в localStorage?
JSON-строка с состоянием под ключом проекта. Хранилище понимает только строки, поэтому JSON.stringify при записи и JSON.parse при чтении.
Что будет, если в хранилище мусор?
try/catch вокруг JSON.parse и проверка формы: при проблеме приложение стартует с пустым состоянием и не падает.
Как у тебя считается id? Что после удаления?
Через отдельный счётчик nextId, который только растёт. length + 1 дал бы повторы.
Почему textContent, а не innerHTML?
Текст пользователя нельзя воспринимать как разметку: иначе в приложение можно подсунуть чужой HTML и скрипты.

14 Заливка проекта на GitHub

Проект, который лежит только на вашем ноутбуке, не существует для работодателя. GitHub — это ваше портфолио. Базовый Git (init, commit, push) вы знаете из входных требований курса; системно мы разберём его на уроке 19, а сегодня — минимальный путь «папка → репозиторий».

  1. Создайте репозиторий. На github.com нажмите New repository. Имя — английское, через дефис: task-tracker или habit-tracker. Выберите Public. Галочки «Add a README», «.gitignore» и «license» не ставьте — репозиторий должен быть пустым.
  2. Инициализируйте Git в папке проекта и сделайте первый коммит: 
    git init
git add .
git commit -m "add tracker app"
  3. Привяжите репозиторий и отправьте код. Скопируйте адрес со страницы нового репозитория (вместо ВАШ_ЛОГИН подставьте ваше имя на GitHub): 
    git branch -M main
git remote add origin https://github.com/ВАШ_ЛОГИН/task-tracker.git
git push -u origin main
  4. Проверьте результат. Обновите страницу репозитория: файлы на месте, в корне виден index.html. Откройте репозиторий в приватном окне браузера или с телефона — ссылка должна открываться без входа в аккаунт.
  5. Добавьте README.md по шаблону ниже, сделайте скриншот приложения и положите его в репозиторий.
  6. Исправления по ревью заливайте отдельными коммитами — так в истории видно, что вы доработали: 
    git add .
git commit -m "fix duplicate ids after delete"
git push
Как называть коммиты

Коротко, по-английски, с маленькой буквы, глаголом в повелительном наклонении: add task filters, fix empty title validation, remove dead code. Не update, не fix, не aaa. Хотя бы 5 осмысленных коммитов за проект — это хороший признак аккуратной работы.
