Урок 15 · Async и API

Работа с реальным API

Интернет-магазин не хранит тысячи товаров в HTML — он спрашивает их у сервера: «покажи шесть товаров, пропусти первые двенадцать, только из категории „телефоны“». Сегодня вы научитесь задавать такие вопросы через параметры запроса и превращать ответ в живой список с поиском, фильтрами и страницами — ровно так устроены каталоги, ленты и поиск на настоящих сайтах.

  • Собирать адрес запроса через URLSearchParams, не думая про пробелы и кириллицу
  • Читать документацию API и находить в ответе нужные поля
  • Рисовать список из ответа сервера, не дублируя карточки
  • Делать поиск без лишних запросов: debounce и защита от «гонки»
  • Фильтровать и сортировать — на сервере и на клиенте
  • Считать страницы по limit / skip и управлять кнопками «Назад» / «Вперёд»
Как работать с этой страницей

Код на тёмном фоне с кнопкой ▶ Запустить — живой: меняйте и запускайте. Примеры с fetch ходят в настоящие публичные API, поэтому нужен интернет. Блоки с вкладками index.html / style.css / script.js — это мини-страница: слева код, под ним предпросмотр и консоль. Задачи сами проверяются по тому, что вы выводите в консоль. Если серверу «плохо» (редкий случай), вы увидите ошибку сети — просто запустите ещё раз. Подсказки под замочком 🔒: сначала сами, потом подсказка.

В уроке три публичных API без ключей: DummyJSON (товары), Rick and Morty API (персонажи) и немного Open-Meteo (погода) в домашнем задании.

01 Параметры запроса: URL и URLSearchParams

Любой запрос к API — это адрес. Но адрес умеет не только «куда пойти», а ещё и «что именно принести». Для этого после знака ? дописывают параметры запроса (query string) в виде пар ключ=значение, разделённых &.

Аналогия из жизни

Заказ в чайхоне. «Курутоб» — это путь: что вы заказываете. А «без лука, порцию побольше, две пиалы чая» — это параметры: уточнения к тому же блюду. Блюдо одно, а заказы разные. Так и с API: путь /products один, а параметры limit, skip, q меняют, что именно вам принесут.

Почему нельзя склеивать строки руками

Новички собирают адрес так: "…?q=" + text + "&limit=" + limit. Пока в text одно слово латиницей, всё работает. Но стоит пользователю ввести пробел, &, # или русскую букву — адрес ломается. У URL строгие правила: такие символы нужно кодировать (пробел → + или %20, & → %26, кириллица → %D0…).

Кодировать самим — муторно и легко ошибиться. Для этого в браузере (и в Node.js) есть готовый класс URLSearchParams.

const params = new URLSearchParams();
params.set("q", "плов & чай");   // пробелы, &, кириллица — не наша забота
params.set("limit", 5);          // число станет строкой само
params.set("skip", 10);

console.log(params.toString());
// q=%D0%BF%D0%BB%D0%BE%D0%B2+%26+%D1%87%D0%B0%D0%B9&limit=5&skip=10

const url = "https://dummyjson.com/products/search?" + params;
console.log(url);   // в строку объект превращается автоматически

Создать URLSearchParams можно сразу из объекта или из готовой строки — удобно, чтобы разобрать чужой адрес:

const fromObject = new URLSearchParams({ q: "phone", limit: 5 });
console.log(fromObject.toString());

const fromString = new URLSearchParams("q=plov&limit=10&page=3");
console.log(fromString.get("q"));        // plov
console.log(fromString.get("limit"));    // "10" — строка, не число!
console.log(fromString.get("sort"));     // null — такого параметра нет
console.log(fromString.has("page"));     // true
set(ключ, значение)
Задать параметр. Если такой уже был — перезаписать.
append(ключ, значение)
Добавить ещё одну пару, даже если ключ уже есть (так бывает: ?tag=a&tag=b).
get(ключ) / getAll(ключ)
Прочитать значение. Всегда строка или null.
has(ключ) / delete(ключ)
Проверить наличие / убрать параметр.
toString()
Готовая строка параметров без знака ?.

Целый адрес: URL

Для разбора полного адреса есть класс URL: у него есть searchParams — тот же URLSearchParams, уже подключённый к адресу.

const url = new URL("https://dummyjson.com/products/search?q=phone&limit=5");

console.log(url.hostname);                  // dummyjson.com
console.log(url.pathname);                  // /products/search
console.log(url.searchParams.get("q"));     // phone

url.searchParams.set("skip", 10);           // поменяли адрес через параметры
console.log(url.href);
Частые ошибки

1. params.get("limit") + 1 даст "101", а не 11: значения — строки. Нужен Number(...). 2. Склейка строк ломается на пробелах и &. 3. Проверка if (value) при сборке адреса выбросит skip=0 — ноль «ложный», но для сервера это важное значение. Проверяйте === undefined, а не «правдивость».

const text = "rock & roll";
const bad = "https://dummyjson.com/products/search?q=" + text + "&limit=5";

console.log(bad);
// сервер увидит: q="rock ", параметр " roll" без значения и limit=5 — искать будет не то
console.log(new URL(bad).searchParams.get("q"));

02 Читаем документацию и ответ API

У каждого API свои правила: как называются параметры, как устроен ответ, что будет, если ничего не найдено. Узнать это можно только из документации и из самого ответа. Привычка №1 разработчика: сначала посмотреть, что реально приходит, и только потом писать код.

Из урока 14 вы помните обёртку над fetch. Она нам понадобится в каждом примере, поэтому вот её короткая версия — в уроке она будет лежать в начале каждого блока:

async function getJson(url) {
  const response = await fetch(url);
  if (!response.ok) throw new Error("HTTP " + response.status);
  return response.json();
}

async function main() {
  const data = await getJson("https://dummyjson.com/products?limit=2&select=title,price");
  console.log(Object.keys(data));
  console.log(data.products);
  console.log("всего товаров на сервере больше, чем пришло:", data.total > data.products.length);
}
main();

Видите: ответ — не просто массив товаров, а объект-конверт. Сами товары лежат в products, а рядом — служебные поля total (сколько всего), skip и limit (какой кусок вернули). Они нам понадобятся для пагинации.

Аналогия из жизни

Документация API — это меню чайханы. Вы не угадываете, что есть на кухне: открываете меню и видите блюда (эндпоинты), порции и добавки (параметры). А ответ сервера — само блюдо на тарелке: нужно посмотреть, что в нём лежит, прежде чем начать есть.

Как читать документацию за 2 минуты

  1. Найдите нужный эндпоинт. «Мне нужен поиск товаров» → GET /products/search.
  2. Выпишите параметры: какие обязательные, какие нет, какие значения допустимы (limit, skip, select, sortBy, order).
  3. Откройте пример ответа и найдите, где лежит список и где служебные поля.
  4. Проверьте руками: вставьте адрес в браузер или в console.log и убедитесь, что ответ такой, как в документации.
  5. Узнайте про «пусто» и «ошибка»: какой статус и какое тело придёт, если ничего нет.

Ещё один приём: параметр select у DummyJSON оставляет в ответе только нужные поля. Запрос становится легче и быстрее — зачем качать описание и отзывы, если нужны название и цена?

03 Рендер списка из API

Данные пришли — теперь покажем их на странице. Схема всегда одна: fetch → массив → для каждого элемента создать узел → вставить в страницу. Это то, что вы делали в уроках 8 и 11, только массив теперь приходит не из переменной, а из интернета.

  1. Запросили данные: await fetch(url), await response.json().
  2. Достали список из конверта: data.products.
  3. Очистили контейнер: list.replaceChildren().
  4. Для каждого товара создали <li> / карточку, заполнили textContent и добавили в контейнер.
<h3>Первые 5 товаров</h3>
<ul id="list"></ul>

const list = document.querySelector("#list");

async function loadProducts() {
  const response = await fetch("https://dummyjson.com/products?limit=5&select=title,price");
  const data = await response.json();

  list.replaceChildren();                    // 3. очистили
  for (const product of data.products) {     // 4. по узлу на товар
    const li = document.createElement("li");
    li.textContent = `${product.title} — ${product.price} $`;
    list.append(li);
  }
}

loadProducts();
Аналогия из жизни

Рендер — это витрина на бозоре. Каждое утро продавец не дописывает товары поверх вчерашних, а выкладывает витрину заново: убрал старое — выставил актуальное. Функция render должна работать так же: сначала очистить, потом построить. Тогда её можно вызывать сколько угодно раз (при поиске, при смене страницы), и ничего не задвоится.

Правило: render полностью перестраивает список

Самая частая ошибка новичков — забыть очистку. Первый вызов работает, а при втором (новая страница, новый поиск) карточки добавляются к старым. Поэтому всё, что рисует список, начинается с replaceChildren() (или innerHTML = "").

Данные с сервера — не доверяйте им

Если вставлять ответ через innerHTML, то любой «товар» с названием <b>…</b> превратится в разметку, а злоумышленник сможет подсунуть и скрипт. Для текста из API используйте textContent: он вставляет строку как есть, без разбора тегов.

const title = "<b>СКИДКА!</b> Самбуса";   // как будто пришло с сервера

const safe = document.createElement("p");
safe.textContent = title;
const risky = document.createElement("p");
risky.innerHTML = title;

console.log(safe.innerHTML);     // теги превращены в безопасный текст
console.log(risky.children.length);  // 1 — внутри появился настоящий <b>

Карточки с картинкой

Настоящий каталог — это не список строк, а карточки. Принцип тот же, узлов просто больше. Картинку берём из поля thumbnail и обязательно задаём alt — для доступности и на случай, если картинка не загрузится.

<div id="grid" class="grid"></div>

.grid { display: grid; grid-template-columns: repeat(auto-fill, minmax(130px, 1fr)); gap: 10px; }
.card { border: 1px solid #ccc; border-radius: 10px; padding: 8px; text-align: center; font: 14px system-ui; }
.card img { width: 100%; height: 90px; object-fit: contain; }
.card h3 { font-size: 14px; margin: 6px 0 2px; }
.card p { margin: 0; color: #0a7c5a; font-weight: 700; }

const grid = document.querySelector("#grid");

async function loadCards() {
  const response = await fetch("https://dummyjson.com/products?limit=6&select=title,price,thumbnail");
  const data = await response.json();

  grid.replaceChildren();
  for (const product of data.products) {
    const card = document.createElement("article");
    card.className = "card";

    const img = document.createElement("img");
    img.src = product.thumbnail;
    img.alt = product.title;

    const title = document.createElement("h3");
    title.textContent = product.title;

    const price = document.createElement("p");
    price.textContent = `${product.price} $`;

    card.append(img, title, price);
    grid.append(card);
  }
}

loadCards();
Пустой список — тоже состояние

Если сервер вернул ноль товаров, пользователь должен увидеть «Ничего не найдено», а не пустое место. Про состояния загрузки и ошибок мы подробно поговорим на следующем уроке, а пока заложим минимум: render умеет показывать пустой результат.

Debounce: ждём, пока человек договорит

Debounce («антидребезг») откладывает действие и каждый новый вызов сбрасывает ожидание. Действие сработает только тогда, когда пользователь замолчал на заданное время — обычно 300–500 мс. Это те самые setTimeout и clearTimeout из урока 13.

Аналогия из жизни

Официант в чайхоне не бежит на кухню после каждого слова гостя. Он ждёт, пока гость договорит: «курутоб… и самбусу… и чай… всё». Только после паузы идёт к повару. Debounce — это терпеливый официант: одна пауза в разговоре — один поход на кухню.

function debounce(fn, ms) {
  let timer;                       // таймер живёт между вызовами
  return (...args) => {
    clearTimeout(timer);           // новый вызов отменяет прошлый
    timer = setTimeout(() => fn(...args), ms);
  };
}

const find = debounce((text) => console.log("ищем:", text), 300);

find("п");
find("пл");
find("пло");
find("плов");      // сработает только последний вызов — через 300 мс

Функция возвращает новую функцию, внутри которой «спрятан» таймер (замыкание — вы встречали его в уроке 5). Подписка в приложении выглядит так:

input.addEventListener("input", debounce(() => {
  state.q = input.value.trim();
  state.page = 1;          // новый поиск — всегда с первой страницы!
  load();
}, 400));

«Гонка» запросов: когда старый ответ приходит позже нового

Даже с debounce бывает так: вы отправили запрос на «ph», передумали и отправили «phone». Сервер ответил на второй запрос быстрее, а на первый — позже. Если просто показывать ответы по мере прихода, старый перезапишет новый, и в поле «phone», а в списке — результаты для «ph». Это называется гонка запросов (race condition).

Аналогия из жизни

Вы заказали плов, а через минуту передумали и заказали самбусу. Если повара приносят блюда в порядке готовности, самбуса приедет первой, а потом вам «довезут» ненужный плов — и вы съедите не то. Правильно: каждому заказу выдать номер и принимать только блюдо с последним номером.

const delays = { ph: 300, phone: 100 };   // на «ph» сервер отвечает дольше
const fakeFetch = (q) => new Promise((resolve) =>
  setTimeout(() => resolve("результаты для " + q), delays[q]));

async function search(q) {
  const result = await fakeFetch(q);
  console.log("показано:", result);
}

search("ph");
setTimeout(() => search("phone"), 50);
// на экране остаётся устаревшее «ph» — пользователь видит не то, что искал

Лекарство простое: у каждого запроса — свой номер, показываем только ответ на самый свежий:

const delays = { ph: 300, phone: 100 };
const fakeFetch = (q) => new Promise((resolve) =>
  setTimeout(() => resolve("результаты для " + q), delays[q]));

let lastRequest = 0;                    // номер последнего запроса

async function search(q) {
  const id = ++lastRequest;             // берём свой номер
  const result = await fakeFetch(q);
  if (id !== lastRequest) return;       // за это время ушёл более новый — выбрасываем
  console.log("показано:", result);
}

search("ph");
setTimeout(() => search("phone"), 50);

Есть и «взрослый» способ — отменять устаревший запрос через AbortController: браузер прекращает ждать, а fetch выбрасывает ошибку с именем AbortError, которую нужно спокойно проглотить.

const controller = new AbortController();

fetch("https://dummyjson.com/products?limit=3", { signal: controller.signal })
  .then(() => console.log("ответ пришёл"))
  .catch((error) => console.log("отменён:", error.name));

controller.abort();    // «не жду ответа»
Что выбрать

Для начала — счётчик lastRequest: он работает везде и понятен с первого взгляда. AbortController экономит трафик, но требует аккуратной обработки AbortError. В нашем приложении будет счётчик.

05 Фильтрация и сортировка

Фильтровать можно в двух местах — и от выбора зависит скорость и удобство:

Фильтр на сервере

Вы просите у API только нужное: /products/category/smartphones. Приходит меньше данных, работает на больших каталогах (тысячи записей), совместимо с пагинацией. Но каждый новый фильтр — новый запрос.

Фильтр на клиенте

Данные уже загружены, а вы просто делаете filter по массиву. Мгновенно, без сети. Но работает, только если на руках весь набор — для огромных каталогов и страничной загрузки не подходит.

Аналогия из жизни

Сервер — это склад на «Корвоне»: вы звоните и просите «пришлите только красные ковры» — вам везут нужное. Клиент — это ваш прилавок: ковры уже привезли, вы просто раскладываете красные влево, остальные вправо. Склад экономит дорогу, прилавок — время ожидания.

Ограничения API — читайте документацию

У DummyJSON эндпоинт /products/search не комбинируется с категорией: вы либо ищете по словам, либо берёте товары категории. Придумывать ?q=phone&category=smartphones бесполезно — сервер проигнорирует категорию. Реальные API полны таких ограничений. Фильтр на клиенте: filter + includes

Когда нужно скомбинировать условия, а данных мало, фильтруем массив на месте. Одно условие — один «отсев»:

const menu = [
  { title: "Самбуса", category: "выпечка", price: 6 },
  { title: "Курутоб", category: "горячее", price: 35 },
  { title: "Шакароб", category: "салаты", price: 15 },
  { title: "Оши палав", category: "горячее", price: 40 },
];

function applyFilters(items, { q = "", category = "", maxPrice = Infinity }) {
  const text = q.trim().toLowerCase();
  return items.filter((item) => {
    if (text && !item.title.toLowerCase().includes(text)) return false;  // поиск без учёта регистра
    if (category && item.category !== category) return false;
    return item.price <= maxPrice;
  });
}

console.log(applyFilters(menu, { category: "горячее" }).map((i) => i.title));
console.log(applyFilters(menu, { q: "ША", maxPrice: 20 }).map((i) => i.title));

Обратите внимание на приём: фильтры «выключаются» значениями по умолчанию (q = "", category = "", maxPrice = Infinity) — пустое условие пропускает всё.

Выпадающий список из данных

Категории не нужно вписывать руками: их можно собрать из данных. new Set(...) оставляет только уникальные значения — то, что нужно для <select>:

const menu = ["выпечка", "горячее", "горячее", "салаты", "выпечка"];
const unique = [...new Set(menu)];
console.log(unique);   // ["выпечка", "горячее", "салаты"]

06 Пагинация: страницы по limit и skip

В каталоге 194 товара — грузить их все сразу глупо: долго, тяжело и никто столько не пролистает. Поэтому сервер отдаёт данные порциями, а вы просите нужную порцию. Это и есть пагинация (постраничная загрузка).

Аналогия из жизни

Плов на свадьбе подают не всем котлом, а порциями на ляганах: на каждый — десять порций. Хотите добавки — просите следующий ляган. Параметр limit — сколько порций на ляган, skip — сколько порций вы уже съели и пропускаете.

Кнопки «Назад» и «Вперёд»

Состояние пагинации — это всего два числа: текущая страница и общее число страниц. Всё остальное рисуется от них:

  • «Назад» выключена на первой странице: prev.disabled = page === 1.
  • «Вперёд» выключена на последней: next.disabled = page === pages.
  • Подпись «Страница 3 из 5» собирается из тех же чисел.
  • После нового поиска или смены категории страница сбрасывается на первую — иначе можно оказаться на 7-й странице результатов, которых всего три.
Частые ошибки

1. skip = page * limit без «−1» — пропускается целая страница, первая порция товаров не видна никогда. 2. Страницы считают через Math.floor или Math.round — теряется последняя страница. 3. Забывают сбросить page = 1 при новом поиске. 4. Пустой поиск у DummyJSON вернёт total: 0 — делить на ноль не страшно, но «страница 1 из 0» выглядит странно: показывайте минимум одну страницу (Math.max(1, …)).

Rick and Morty: страницы без skip

Там всё проще: ?page=2. А сколько страниц — подсказывает сам сервер в info.pages, и даже даёт info.next — адрес следующей страницы или null, если страница последняя. Это удобно для кнопки «Показать ещё».

✓ Шпаргалка урока

  • Параметры запроса идут после ?: ключ=значение через &. Собираем только через new URLSearchParams({…}) — он кодирует пробелы, & и кириллицу. params.get() всегда даёт строку или null.
  • Читаем API: документация + реальный ответ в консоли. Где список (data.products / data.results / сам массив), где total, что при «пусто» (200 и [] или 404).
  • Рендер: render(items) всегда сначала очищает (replaceChildren()), потом строит узлы; данные с сервера — через textContent; пустой результат — отдельное сообщение.
  • Поиск: input + debounce (300–500 мс) + trim() + сброс на первую страницу. От «гонки» — номер запроса lastRequest или AbortController.
  • Фильтр и сортировка: на сервере (/category/…, sortBy, order) — для больших данных; на клиенте (filter, includes) — для уже загруженных. Не все параметры API сочетаются — читайте документацию.
  • Пагинация: skip = (page − 1) × limit; страниц Math.ceil(total / limit); «Назад» выключена на 1-й, «Вперёд» — на последней; у Rick and Morty — page и info.pages / info.next.
  • Структура приложения: state → buildUrl() → load() → render() + updatePager(). События лишь меняют состояние и вызывают load().
  • С ИИ: документацию API давайте ему текстом; выдуманные параметры ловим запросом в консоли; в README записываем, что ИИ предложил и что мы исправили.
