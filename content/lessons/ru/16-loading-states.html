Урок 16 · Async и API

Состояния загрузки, ошибки, debounce

Вы уже умеете получать данные с настоящего сервера. Но на реальном сайте интернет бывает медленным, сервер — недоступным, а пользователь — нетерпеливым: он печатает в строке поиска быстрее, чем приходят ответы. Сегодня мы научим приложение вести себя достойно в любой из этих ситуаций: показывать загрузку, объяснять ошибку, не заваливать сервер запросами и отменять ненужное.

  • Различать четыре состояния экрана: загрузка, ошибка, пусто, данные — и рисовать каждое
  • Проверять response.ok и не путать «сервер ответил ошибкой» с «сети нет»
  • Делать skeleton — серые заглушки на месте будущего контента — на чистом CSS
  • Писать debounce с нуля и объяснять, как он работает через замыкание и таймер
  • Отменять запрос через AbortController и не показывать устаревшие ответы
  • Читать и проверять правки, которые ИИ-агент (Cursor) вносит сразу в несколько файлов
Как работать с этой страницей

Код на тёмном фоне с кнопкой ▶ Запустить — живой: меняйте его и смотрите на результат в консоли. В этом уроке «сервер» в примерах нарочно медленный и сделан прямо в коде (через Promise и setTimeout), поэтому результат всегда одинаковый и не зависит от вашего интернета; после запуска подождите секунду — строки в консоли появляются по очереди. Примеры с настоящим API тоже есть, но проверяемые задачи работают без сети. Где есть окошко с превью — это мини-страница: слева код, справа результат. 01 Четыре состояния экрана

Представьте, что вы открыли приложение такси и нажали «Заказать». Что вы видите? Крутилку «ищем машину». Если машин рядом нет — сообщение «Свободных машин нет, попробуйте позже». Если пропал интернет — «Нет соединения» и кнопка «Повторить». И только если всё хорошо — карточку водителя. Один и тот же экран, четыре разных картинки — в зависимости от того, что сейчас происходит с данными.

Новички обычно рисуют только последнюю картинку — «данные пришли». А остальные три забывают. В итоге при медленном интернете пользователь смотрит на пустую страницу и думает, что сайт сломан. Профессионал всегда продумывает все четыре:

Аналогия из жизни

Вы пришли в чойхону и заказали курутоб. Хороший официант не стоит молча: «Готовим, минут десять» (loading); «Курутоб закончился» (error — заказать нельзя); «К сожалению, в меню такого блюда нет» (empty — искали, но не нашли); и наконец — приносит тарелку (success). Плохой официант просто исчезает, и вы сидите и гадаете: заказ принят или нет?

Где хранить состояние

Из урока про состояние (урок 11) вы знаете главное правило: есть данные — есть функция, которая по ним рисует экран. Здесь так же. Заводим один объект state с тремя полями и одну функцию view (или render), которая решает, что показывать.

// status: "idle" | "loading" | "success" | "error"
function view(state) {
  if (state.status === "idle") return "Введите название блюда";
  if (state.status === "loading") return "Загрузка…";
  if (state.status === "error") return `Ошибка: ${state.error}`;
  // дальше status === "success"
  if (state.data.length === 0) return "Ничего не найдено";
  return `Нашли: ${state.data.join(", ")}`;
}

console.log(view({ status: "idle", data: [], error: null }));
console.log(view({ status: "loading", data: [], error: null }));
console.log(view({ status: "error", data: [], error: "Нет сети" }));
console.log(view({ status: "success", data: [], error: null }));
console.log(view({ status: "success", data: ["Курутоб"], error: null }));

Обратите внимание: «empty» — это не отдельный статус сервера, а частный случай успеха: запрос прошёл, но список оказался пустым. Хотите — выделяйте его отдельным статусом "empty" (так будет удобнее в разметке), хотите — проверяйте data.length. Главное, чтобы пользователь увидел разный текст.

Порядок проверок важен

Самая частая ошибка — проверять «пусто?» первой. Пока данные грузятся, список тоже пустой, и пользователь видит «Ничего не найдено» вместо «Загрузка…». Сначала спрашиваем «что случилось с запросом?» (loading, error), и только потом — «что внутри ответа?» (пусто или нет).

Пустой список первым

Во время загрузки — «Ничего не найдено». Пользователь думает, что блюда нет.

function view(state) {
  if (state.data.length === 0) return "Ничего не найдено";
  if (state.status === "loading") return "Загрузка…";
  return state.data.join(", ");
}
console.log(view({ status: "loading", data: [] }));
// → Ничего не найдено 😕
Сначала статус

Сначала loading и error, потом разбираемся с содержимым.

function view(state) {
  if (state.status === "loading") return "Загрузка…";
  if (state.data.length === 0) return "Ничего не найдено";
  return state.data.join(", ");
}
console.log(view({ status: "loading", data: [] }));
// → Загрузка… ✓
Частая ошибка

Вместо четырёх состояний — одно булево isLoading и «потом посмотрим». Тогда легко получить невозможные комбинации: isLoading: true и одновременно error: "Нет сети". Один status с понятными значениями такого не допускает: в любой момент он равен ровно одному из них.

Переходы между состояниями

Состояния сменяют друг друга по простому сценарию. Запомните его — он будет в каждом приложении, которое вы напишете:

  1. Пользователь что-то сделал (открыл страницу, нажал «Найти») → ставим status: "loading" и перерисовываем экран.
  2. Сервер ответил → ставим status: "success" (или "empty") и кладём данные.
  3. Что-то сломалось → ставим status: "error" и кладём понятный текст ошибки.
  4. Пользователь нажал «Повторить» → снова шаг 1.
Совет

При новом запросе полезно не стирать старые данные, пока идёт загрузка, а при ошибке — не терять уже показанный список. Тогда можно рисовать «Не удалось обновить» над прежним списком, а не оставлять пользователя с пустым экраном. Сегодня мы будем так делать там, где это удобно.

02 Запрос, ошибки и «медленный сервер»

Теперь подключаем реальную загрузку. Из прошлых уроков вы знаете схему: async-функция, await fetch(...), try / catch. Добавим к ней состояния: до запроса ставим loading, после — success или error, а finally нам тут почти не нужен: каждое состояние ставится явно.

async function searchProducts(query) {
  console.log("loading");
  try {
    const res = await fetch(`https://dummyjson.com/products/search?q=${query}&limit=3`);
    const data = await res.json();
    console.log(`success: ${data.products.length} из ${data.total}`);
  } catch (err) {
    console.log(`error: ${err.message}`);
  }
}

searchProducts("phone");

Две разные ошибки — и fetch различает их не так, как вы думаете

Это ловушка, в которую попадает почти каждый новичок. У запроса бывает два разных вида неудачи:

Сети нет
Интернет пропал, сервер не найден, запрос не дошёл. Тогда fetch отклоняет промис — управление уходит в catch.
Сервер ответил «нет»
Запрос дошёл, но сервер вернул код 404 («не найдено») или 500 («у нас всё сломалось»). Для fetch это успех: ответ получен! Промис выполняется, в catch мы не попадаем.

Поэтому после fetch всегда проверяйте свойство res.ok — оно равно true для кодов 200–299. А если нет — бросайте ошибку сами:

async function loadProduct(id) {
  try {
    const res = await fetch(`https://dummyjson.com/products/${id}`);
    console.log("status:", res.status, "ok:", res.ok);
    if (!res.ok) throw new Error(`Сервер ответил кодом ${res.status}`);
    const product = await res.json();
    console.log("success:", product.title);
  } catch (err) {
    console.log("error:", err.message);
  }
}

loadProduct(999999);

Попробуйте заменить 999999 на 1: код станет 200, и вы увидите название товара.

Аналогия из жизни

Вы отправили курьера в магазин на Зелёном базаре. Если дорогу перекрыли и курьер не дошёл — это «сети нет» (catch). А если курьер дошёл и вернулся со словами «этого товара нет в продаже» — он вернулся успешно, но результат плохой. Именно так fetch и думает: курьер вернулся — значит, успех. Проверять, что именно он принёс, должны вы.

«Медленный сервер» в нашем коде

Настоящий API отвечает то быстро, то медленно, то не отвечает вовсе. Чтобы уроки и задачи были честными и одинаковыми у всех, мы сделаем себе «ненастоящий» сервер — функцию fakeSearch. Она ищет блюдо в небольшом массиве, отвечает через заданное время и умеет ломаться по запросу «ошибка». Так делают и профессионалы: пока настоящего сервера нет (или он нестабилен), интерфейс проверяют на заглушке.

Разберём заглушку

Читать её целиком не обязательно, но есть три важных места. setTimeout имитирует задержку сети (ms миллисекунд). Если запрос пустили с названием "ошибка" — промис отклоняется, как при обрыве сети. Параметр signal нужен для отмены — о нём в разделе 5; пока его можно не замечать. Во всех примерах ниже блок «сервер» один и тот же — просто копируйте его целиком.

// ↓ «сервер»: медленный поиск по меню — не меняйте
const DISHES = ["Оши палав", "Самбуса с мясом", "Самбуса с тыквой", "Курутоб", "Шакароб", "Нон"];

function fakeSearch(query, { signal, ms = 200 } = {}) {
  return new Promise((resolve, reject) => {
    if (signal && signal.aborted) return reject(signal.reason);
    const timer = setTimeout(() => {
      if (query === "ошибка") return reject(new Error("Нет соединения с сервером"));
      resolve(DISHES.filter((d) => d.toLowerCase().includes(query.toLowerCase())));
    }, ms);
    if (signal) {
      signal.addEventListener("abort", () => {
        clearTimeout(timer);
        reject(signal.reason);
      });
    }
  });
}

fakeSearch("самбуса").then((dishes) => console.log("Нашли:", dishes.join(", ")));
fakeSearch("борщ").then((dishes) => console.log("Нашли по «борщ»:", dishes.length));
fakeSearch("ошибка").catch((err) => console.log("Сбой:", err.message));

Полный цикл: loading → success / empty / error

Склеим всё в одну функцию. Каждая строка состояния — это одна «картинка» экрана. Следите за порядком в консоли:

async function load(query) {
  console.log("loading…");
  try {
    const items = await fakeSearch(query);
    if (items.length === 0) {
      console.log("empty: ничего не найдено");
    } else {
      console.log(`success: ${items.length} шт.`);
    }
  } catch (err) {
    console.log(`error: ${err.message}`);
  }
}

async function main() {
  await load("курутоб");
  await load("борщ");
  await load("ошибка");
}
main();
Ловушка

Бросить всё в один catch и написать пользователю err.message как есть — плохая идея. Тексты вроде Failed to fetch или Unexpected token < in JSON пугают и ничего не объясняют. Показывайте человеческую фразу («Не удалось загрузить меню. Проверьте интернет и повторите»), а «технический» текст оставьте для console.error — он нужен вам, а не пользователю.

Повтор при сбое

Раз ошибка — частое дело, пользователю нужна кнопка «Повторить». В коде это просто ещё один вызов той же load. А иногда повтор делают автоматически — например, до трёх попыток подряд. Мы потренируем это в задаче 2.4.

03 Skeleton: серые заглушки вместо пустоты

Самое простое состояние загрузки — надпись «Загрузка…» или крутилка. Но у неё есть недостаток: страница «прыгает». Сначала на экране маленькая надпись, потом вдруг появляется длинный список, и всё содержимое съезжает вниз. Решение — skeleton («скелет»): на месте будущих карточек показываем серые прямоугольники такого же размера. Пользователь заранее видит, как будет выглядеть страница, а когда приходят данные — заглушки просто заменяются настоящими карточками на тех же местах.

Аналогия из жизни

Вы пришли в чойхону на свадьбу, а стол ещё не накрыт. Но скатерть уже расстелена, а на ней расставлены пустые тарелки — по числу гостей. Вы сразу видите, где будете сидеть и сколько мест. Потом официанты просто кладут еду на готовые тарелки — стол не переставляют. Skeleton — это те самые пустые тарелки.

Skeleton на чистом CSS

JavaScript здесь нужен только для одного: поставить на страницу нужное число блоков. Весь «вид» делает CSS. Секрет мерцания — градиент, который «ползёт» слева направо при помощи анимации:

  background-size: 400% 100%;      /* градиент в 4 раза шире блока */

  border-radius: 8px;
  color: transparent;              /* на случай, если внутри окажется текст */

  2. Анимация двигает фон. @keyframes shimmer меняет background-position — «светлая полоса» медленно проезжает по блоку.
  3. Размеры задаёт карточка. Заглушка должна быть той же высоты и ширины, что и настоящая карточка, — иначе страница всё равно «подпрыгнет».
  4. Не забудьте про доступность. На контейнер ставим aria-busy="true" пока идёт загрузка и "false" — когда закончилась: читалки с экрана поймут, что содержимое обновляется.

04 Debounce: не запускать функцию на каждый чих

Строка поиска «на лету»: пользователь печатает «плов», а результаты меняются уже в процессе. Самое простое решение — слушать событие input и на каждую букву отправлять запрос. Но человек печатает быстро: «п», «пл», «пло», «плов» — это четыре запроса за секунду, из которых нужен только последний. Сервер нагружается, трафик тратится, а ответы приходят вперемешку (об этом — в разделе 5).

Решение называется debounce — «подавление дребезга»: запускаем функцию только тогда, когда пользователь перестал её дёргать на заданное время. Каждый новый вызов сбрасывает ожидание. Пока человек печатает — ничего не происходит; остановился на 300 мс — запрос уходит.

Аналогия из жизни

Маршрутка на остановке. Водитель не едет сразу, как только зашёл первый пассажир. Он ждёт: зашёл второй — ждёт ещё, зашёл третий — снова ждёт. И только когда несколько секунд никто не заходит, трогается. Каждый новый пассажир сбрасывает таймер ожидания. Debounce — это водитель, который тронется лишь после паузы.

Пишем debounce с нуля

Внутри всего три идеи, которые вы уже знаете: функция возвращает функцию, замыкание хранит таймер между вызовами, а clearTimeout отменяет предыдущее ожидание.

function debounce(fn, wait) {
  let timer;                         // один таймер на все вызовы — живёт в замыкании
  return function (...args) {
    clearTimeout(timer);             // новый вызов: отменяем прошлое ожидание
    timer = setTimeout(() => {
      fn(...args);                   // пауза выдержана — запускаем настоящую функцию
    }, wait);
  };
}
  1. Мы получаем функцию fn и паузу wait и возвращаем новую функцию — её и будем вешать на событие.
  2. Переменная timer объявлена снаружи возвращаемой функции. Поэтому все вызовы видят одну и ту же переменную (замыкание, урок 5).
  3. При каждом вызове сначала clearTimeout(timer) убирает ожидание от прошлого вызова, потом setTimeout заводит новое.
  4. Сработает только последнее ожидание — то, которое никто не сбросил за wait миллисекунд.
  5. ...args собирает все аргументы в массив, а fn(...args) раскладывает обратно — так debounce подходит к функции с любым числом параметров.

Проверяем на «печатающем» человеке

Чтобы результат не зависел от вашей скорости печати, мы запланируем нажатия по расписанию через setTimeout. Расписание: «п» в 0 мс, «пл» в 40 мс, «пло» в 80 мс (быстро печатает), потом пауза и «плов» в 300 мс. Пауза debounce — 100 мс. В консоли видно, что реально сработало.

function debounce(fn, wait) {
  let timer;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), wait);
  };
}

Частая ошибка

Объявить let timer внутри возвращаемой функции. Тогда каждый вызов получает свой собственный timer, а clearTimeout отменяет пустоту — ничего не сбрасывается, и сработают все вызовы, просто с задержкой. Переменная для таймера должна жить снаружи, в замыкании.

Debounce и throttle — не одно и то же

Debounce ждёт паузы и срабатывает один раз после серии вызовов (поиск, автосохранение). Throttle («дроссель») срабатывает не чаще раза в N мс во время серии (прокрутка страницы, изменение размера окна). В поиске нам нужен именно debounce.

Когда debounce не нужен

Для действий по кнопке («Найти», «Отправить») пауза не нужна: человек нажимает осознанно и один раз. Debounce — лекарство от потока событий: input, scroll, resize, mousemove.

Отменить отложенный вызов: cancel

Бывает, что нужно не просто отложить, а отменить ждущий вызов: пользователь очистил поле или ушёл со страницы. Функции в JavaScript — тоже объекты, им можно «приклеить» свойство. Добавим метод cancel:

function debounce(fn, wait) {
  let timer;
  function debounced(...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), wait);
  }
  debounced.cancel = () => clearTimeout(timer);   // метод у функции
  return debounced;
}

05 AbortController: отмена запроса

Debounce уменьшает число запросов, но не убирает главную проблему: запрос, который уже ушёл, нельзя «забыть». Он долетит до сервера и вернётся с ответом, даже если пользователю этот ответ уже не нужен. А это приводит к двум неприятностям.

Проблема 1. Лишняя работа

Пользователь открыл страницу каталога и сразу ушёл на другую. Запрос на 100 товаров всё равно скачивается и разбирается — трафик и батарея тратятся впустую (на мобильном интернете в маршрутке это ощутимо).

Проблема 2. Гонка запросов (race condition)

Пользователь набрал «с» — ушёл запрос №1. Через 50 мс дописал «са» — ушёл запрос №2. Сервер обрабатывает запросы по-разному долго: ответ на первый (его результатов много) пришёл через 400 мс, а на второй — через 100 мс. Что получится на экране?

// ↓ «сервер»: медленный поиск по меню — не меняйте
const DISHES = ["Оши палав", "Самбуса с мясом", "Самбуса с тыквой", "Курутоб", "Шакароб", "Нон"];

function fakeSearch(query, { signal, ms = 200 } = {}) {
  return new Promise((resolve, reject) => {
    if (signal && signal.aborted) return reject(signal.reason);
    const timer = setTimeout(() => {
      if (query === "ошибка") return reject(new Error("Нет соединения с сервером"));
      resolve(DISHES.filter((d) => d.toLowerCase().includes(query.toLowerCase())));
    }, ms);
    if (signal) {
      signal.addEventListener("abort", () => {
        clearTimeout(timer);
        reject(signal.reason);
      });
    }
  });
}

let shown = "";

function onType(query, ms) {
  fakeSearch(query, { ms }).then(() => {
    shown = query;                      // «рисуем» ответ
    console.log(`пришёл ответ на «${query}»`);
  });
}

onType("с", 400);                        // старый запрос — медленный
setTimeout(() => onType("са", 100), 50); // новый запрос — быстрый
setTimeout(() => console.log(`на экране: «${shown}»`), 600);

На экране осталось «с» — хотя в поле уже давно написано «са». Ответ на новый запрос пришёл первым, а потом его затёр запоздавший ответ на старый. Пользователь видит результаты не для того, что набрал. Баг плавающий: у вас дома, на быстром интернете, он не проявится, а у клиента в горах — проявится обязательно.

Аналогия из жизни

Вы заказали плов, через минуту передумали и позвонили: «Лучше самбусу». Если в чойхоне не отменят первый заказ, к вам придут оба курьера — причём плов, возможно, раньше или позже самбусы. Правильно — позвонить и отменить первый заказ. Именно это делает AbortController: он «звонит» запросу и говорит «стоп».

Как это работает: controller и signal

AbortController
«Пульт»: объект, у которого есть кнопка abort(). Создаётся так: new AbortController().
controller.signal
«Провод» от пульта: сигнал, который мы передаём запросу. Запрос слушает его и останавливается, когда нажали кнопку.
controller.abort()
Нажали кнопку — запрос отменён, его промис отклоняется с ошибкой по имени AbortError.

Настоящий fetch понимает signal

Наша заглушка устроена так же, как настоящий fetch: сигнал передаётся вторым аргументом, в объекте настроек. Если вызвать abort() сразу, запрос даже не начнёт скачивание:

const controller = new AbortController();

const request = fetch("https://dummyjson.com/products?limit=100", {
  signal: controller.signal,
});

controller.abort();   // отменяем сразу

request.catch((err) => console.log("fetch отменён:", err.name));

Не терпит дольше — таймаут одной строкой

Нередко нужно не отменять вручную, а подождать не дольше N миллисекунд. Для этого есть готовая функция AbortSignal.timeout(мс): она сама нажмёт «abort» через заданное время. Ошибка при этом называется не AbortError, а TimeoutError — так вы отличите «отменили мы» от «не дождались».

fetch("https://dummyjson.com/products?limit=100", { signal: AbortSignal.timeout(1) })
  .then(() => console.log("успели"))
  .catch((err) => console.log("ошибка:", err.name));

Паттерн: «каждый новый запрос отменяет прошлый»

Именно так починить гонку из начала раздела. Храним контроллер в переменной снаружи функции; перед новым запросом отменяем старый и заводим новый контроллер.

  2. Вызываем abort() на старом перед тем, как создать новый — в этот момент старый запрос ещё может быть в пути.
  3. В catch молча пропускаем AbortError. Отмена — это не ошибка сервера, и пугать пользователя красным текстом «Ошибка!» из-за того, что он дописал букву, нельзя.
Частая ошибка

Не обработать AbortError. Отменённый запрос отклоняет промис, и если в catch просто написано «показать ошибку» — на экране на долю секунды мигает «Ошибка: The user aborted a request». Всегда проверяйте err.name и для "AbortError" выходите молча.

Есть и второй способ

Можно не отменять запрос, а просто игнорировать устаревший ответ: завести счётчик requestId, запомнить номер своего запроса и при ответе проверять, что он всё ещё последний. Это проще, но запрос всё равно дойдёт до сервера и потратит трафик. AbortController — «честный» способ: запрос реально останавливается.

06 Что покажет преподаватель: Cursor

До сих пор ИИ в нашем курсе — это чат: вы пишете вопрос, получаете текст, вы сами копируете код и вставляете в файл. Сегодня преподаватель покажет следующий уровень — ИИ-агента внутри редактора кода. Это демонстрация на экране: ставить Cursor на свои компьютеры не нужно. Главное в этом разделе — не «вау, как быстро», а как этот результат проверять.

Правила курса, которые особенно важны сегодня

1. Сначала 15 минут пробуете сами. 2. Промпт — по формуле: контекст → задача → ограничения → формат ответа → проверка. 3. Не вставляйте в проект код, который не можете объяснить строка за строкой. 4.   • Прочитан ли весь diff? Красное — удалено. Не исчезла ли рабочая логика (например, пагинация) в «рефакторинге»?

let requests = 0;                          // сколько запросов реально ушло
function fakeSearch(query, { signal, ms = 300 } = {}) {
  requests++;
  return new Promise((resolve, reject) => {
    if (signal && signal.aborted) return reject(signal.reason);
    const timer = setTimeout(() => {
      if (query === "ошибка") return reject(new Error("Нет соединения с сервером"));
      resolve(DISHES.filter((d) => d.toLowerCase().includes(query.toLowerCase())));
    }, ms);
    if (signal) {
      signal.addEventListener("abort", () => {
        clearTimeout(timer);
        reject(signal.reason);
      });
    }
  });
}
