01 Git: история проекта

Представьте, что вы делаете сайт для чойхоны. Сегодня всё работает, завтра вы «немного поправили» меню, и сайт сломался. Как вернуться? Копировать папку с названиями site-final, site-final-2, site-final-REAL? Так делают новички. Профессионалы используют Git — систему контроля версий. Она записывает каждое сохранённое состояние проекта, показывает, что и кто изменил, и позволяет вернуться к любому моменту.

Аналогия: семейный альбом

Вы выбираете из телефона снимки со свадьбы и кладёте их в конверт — это git add. Потом вклеиваете конверт в альбом и подписываете «Никоҳ, 12 июня» — это git commit. Альбом хранит все страницы по порядку. Захотите — откроете любую страницу и увидите, как всё выглядело тогда.

Три зоны и четыре места

Файл в Git проходит три зоны на вашем компьютере. Четвёртое место — сервер GitHub, куда вы отправляете копию.

Первый репозиторий

Один раз на компьютере нужно представиться — это имя попадёт в каждый коммит:

git config --global user.name "Ваше Имя"
git config --global user.email "you@example.com"

Теперь создадим проект и сделаем первый коммит:

mkdir chaykhona-site
cd chaykhona-site
git init -b main
echo "# Чойхона" > README.md
git status
git add README.md
git commit -m "docs: add readme"
git log --oneline

Что произошло по шагам:

  1. git init создал скрытую папку .git — в ней живёт вся история. Удалите её, и проект перестанет быть репозиторием.
  2. git status сказал: файл README.md «untracked» — Git его ещё не отслеживает.
  3. git add положил файл в индекс («конверт»).
  4. git commit -m "…" записал снимок с подписью.
  5. git log --oneline показал историю: короткий код коммита и подпись.

Частые ошибки

1. git add . не глядя: в коммит попадают лишние файлы (пароли, node_modules). Сначала git status, потом git add.

2. git commit без -m открывает текстовый редактор Vim. Если застряли: нажмите Esc, введите :q! и Enter. Либо всегда пишите -m.

3. Один гигантский коммит «всё за неделю». Коммит — это одна законченная мысль: «добавил фильтр», «починил итоговую сумму».

Чтобы почувствовать, как устроены зоны, смоделируем их кодом. Это первая задача на странице.

ЗАДАЧА 1.1

Три зоны Git в коде

лёгкая

Мы смоделируем три зоны Git обычными массивами. Допишите add (git add: файл переезжает из work в staged) и commit (git commit: всё из staged уходит в новый коммит, а staged очищается). История выводится как в git log — новые коммиты сверху.

  staged: [],                                  // подготовлены: git add
  commits: [],                                 // история: git commit
};

function add(file) {
  // убрать файл из work и положить в staged
}

function commit(message) {
  // сохранить файлы из staged в новый коммит { message, files }
  // и очистить staged

add("index.html");

Подсказка 1

В add нужны две вещи: убрать файл из work (например, через filter) и сделать push в staged.

Подсказка 2

В commit сохраните копию списка: files: [...repo.staged]. Потом repo.staged = []. Привычка копировать пригодится в разделе 8 — там мутация ломает программы.

ЗАДАЧА 1.2

Что покажет git status

лёгкая

Функция statusLine описывает файл так, как это делает git status. Но один случай она не знает: файл уже в индексе (staged), а после git add его ещё раз изменили (changedAfterAdd: true). Для него нужна строка staged, but changed again: имя. Допишите условие.

const files = [
  { name: "index.html", tracked: true, changed: false, staged: false },
  { name: "app.js", tracked: true, changed: true, staged: false },
  { name: "notes.txt", tracked: false, changed: true, staged: false },
  { name: "style.css", tracked: true, changed: true, staged: true, changedAfterAdd: false },
  { name: "README.md", tracked: true, changed: true, staged: true, changedAfterAdd: true },
];

function statusLine(f) {
  if (!f.tracked) return `untracked: ${f.name}`;
  if (f.staged) return `to be committed: ${f.name}`;
  if (f.changed) return `modified: ${f.name}`;
  return null; // чистый файл в статусе не показывается
}

files.map(statusLine).filter(Boolean).forEach((line) => console.log(line));
Ожидаемый результат
modified: app.js
untracked: notes.txt
to be committed: style.css
staged, but changed again: README.md
Подсказка 1

Новую проверку нужно поставить перед обычной проверкой f.staged: иначе сработает она, и до вашего условия дело не дойдёт.

Подсказка 2

if (f.staged && f.changedAfterAdd) return `staged, but changed again: ${f.name}`;

02 Ветки: работаем, не ломая основное

В репозитории есть главная ветка — обычно main (иногда её называют master). В ней лежит версия, которая «точно работает». Новую функцию делают в отдельной ветке: можно пробовать, ошибаться и коммитить сколько угодно — основная ветка не пострадает. Когда функция готова и проверена, ветку вливают обратно.

Аналогия: пробный плов

В большом казане варится плов для гостей — это main. Вы хотите проверить новый рецепт с айвой. Вы не лезете в общий казан, а берёте маленькую кастрюлю — это ветка. Получилось вкусно — добавили айву в общий казан (merge). Не получилось — выбросили кастрюлю, и гости ничего не заметили.

Ветка — это не копия папки. Это всего лишь подвижная «закладка» на один из коммитов. Новый коммит двигает закладку вперёд. Благодаря этому ветки в Git создаются мгновенно и стоят почти ничего. Особая закладка HEAD показывает, на какой ветке вы сейчас стоите.

git branch                         # список веток, звёздочка у текущей
git switch -c feature/filters      # создать ветку и перейти на неё
# ...правим файлы, git add, git commit...
git log --oneline --graph --all    # история в виде дерева
git switch main                    # вернуться на main
git merge feature/filters          # влить ветку в main
git branch -d feature/filters      # удалить ветку, она больше не нужна

Как называть ветки

В командах ветку называют по шаблону тип/короткое-описание: feature/order-filters, fix/wrong-total, docs/readme-tajik. Английские слова, строчные буквы, без пробелов, слова через дефис. По имени сразу видно, что в ветке и зачем.

Частые ошибки

Работать прямо в main. Тогда PR сделать не из чего, а в случае проблемы нечем откатиться. Привычка: сначала git switch -c, потом код.

Переключать ветку с несохранёнными правками. Git либо перенесёт их, либо откажется. Лучше сначала сделать коммит.

Ветки — это граф коммитов, и мы можем обойти его кодом. Начнём с простого: пройдём цепочку «родитель → родитель», как это делает git log.

ЗАДАЧА 2.2

Что есть только в моей ветке

средняя

Перед pull request полезно знать: какие коммиты есть в вашей ветке, но ещё не попали в основную? В Git это записывают как main..feature. Функция history уже готова. Допишите onlyIn(branch, base): сообщения коммитов из branch, которых нет в base.

  { id: "c1", parent: null, message: "init project" },
  { id: "c2", parent: "c1", message: "add header" },

  { id: "f1", parent: "c2", message: "add filters" },  // ветка feature отошла от c2
  { id: "f2", parent: "f1", message: "add sort" },     // конец feature
];
const branches = { main: "c3", feature: "f2" };
const byId = Object.fromEntries(commits.map((c) => [c.id, c]));

function history(branch) {
  const result = [];
  let id = branches[branch];
  while (id !== null) {
    result.push(byId[id].message);
    id = byId[id].parent;
  }
  return result;
}

console.log(onlyIn("feature", "main").join(", "));

03 GitHub: push, pull request, ревью

Git живёт на вашем компьютере. GitHub — это сайт, где хранится копия репозитория (её называют origin — «удалённый репозиторий»). Именно через GitHub команда обменивается кодом, а работодатель смотрит ваше портфолио.

git remote add origin https://github.com/ВАШ_ЛОГИН/chaykhona-site.git
git push -u origin main            # первая отправка, -u запоминает связь веток
git push                           # дальше достаточно просто push
git clone https://github.com/ВАШ_ЛОГИН/chaykhona-site.git   # скачать чужой репозиторий
git pull                           # забрать новые коммиты с GitHub
git fetch                          # только скачать информацию, ничего не менять

git pull — это fetch (скачать) + merge (влить в вашу ветку). Если на GitHub появились новые коммиты коллег, а у вас нет, перед push сначала делают pull.

Pull request — главная идея командной работы

Pull request (PR) — это просьба: «посмотрите мои изменения в ветке и, если всё хорошо, влейте их в main». PR — не команда Git, а возможность GitHub. Вы пушите ветку, на сайте нажимаете «Compare & pull request», пишете описание, а коллега читает изменения построчно, оставляет комментарии, одобряет или просит правки.

Аналогия: чек перед оплатой на бозоре

Продавец записал сумму на бумажке, но перед оплатой вы показываете бумажку соседу: «Проверь, правильно ли сложил?». Сосед нашёл ошибку в одну сомони — вы исправили, и только потом отдали деньги. PR — тот же «взгляд со стороны» перед тем, как код попадёт в основную ветку.

Рабочий цикл в паре

Именно так вы будете работать сегодня на занятии и дальше — в проектах и на работе:

  1. Обновите main: git switch main, git pull.
  2. Создайте ветку под одну задачу: git switch -c feature/order-filters.
  3. Работайте и коммитьте небольшими осмысленными шагами.
  4. Отправьте ветку: git push -u origin feature/order-filters. GitHub напечатает ссылку для создания PR.
  5. Откройте pull request: заголовок, что сделано, зачем, как проверить. Назначьте напарника ревьюером.
  6. Ревью: напарник читает diff, пишет комментарии. Вы отвечаете и правите — новые коммиты в ту же ветку попадут в PR сами.
  7. Merge: после одобрения (approve) и успешных проверок PR вливают в main кнопкой Merge pull request на GitHub.
  8. Уберите за собой: git switch main, git pull, git branch -d feature/order-filters.
Что смотреть при ревью

Работает ли код (запустите ветку)? Понятны ли имена? Нет ли лишних файлов и console.log? Описаны ли граничные случаи (пустой список, ноль, ошибка сети)? Комментарий пишем про код, а не про человека: «Здесь при пустом списке будет ошибка» вместо «Ты забыл».

Три способа влить PR

КнопкаЧто получится в истории
Create a merge commitВсе коммиты ветки сохраняются, плюс коммит слияния
Squash and mergeВсе коммиты PR склеиваются в один — история main короче
Rebase and mergeКоммиты ветки переносятся в main по одному, без коммита слияния

Для начала подойдёт первый вариант. Остальные вы выберете, когда в команде договорятся о стиле истории.

Правила безопасности

Не пушьте в main напрямую и не сливайте свой PR без ревью. Во многих командах main закрыт: только через PR.

Не используйте git push --force, пока не понимаете, что делаете: команда стирает чужие коммиты на сервере.

Никогда не коммитьте пароли и ключи API. Разберём в разделе про .gitignore.

ЗАДАЧА 3.2

Можно ли делать merge

сложная

На GitHub кнопка Merge «серая», пока не выполнены условия. Допишите mergeProblems(pr): функция возвращает массив причин (в таком порядке): «нет одобрения» (approvals < 1), «проверки не прошли» (checks не равно "passed"), «есть конфликт» (conflicts), «это черновик» (draft). Если причин нет — пустой массив.

function mergeProblems(pr) {
  const problems = [];
  // проверьте четыре условия и добавляйте причины в массив
  return problems;
}

const prs = [
  { title: "add order filters", approvals: 1, checks: "passed", conflicts: false, draft: false },
  { title: "fix cart total", approvals: 0, checks: "passed", conflicts: false, draft: false },
  { title: "wip: new header", approvals: 2, checks: "failed", conflicts: true, draft: true },
];
for (const pr of prs) {
  const p = mergeProblems(pr);

Четыре независимых if, каждый делает problems.push("…"). else здесь не нужен: причин может быть несколько сразу.

Для проверок используйте pr.approvals < 1 и pr.checks !== "passed".

04 Конфликты слияния

Git умеет сливать изменения автоматически, если вы и напарник правили разные места. Но если вы оба изменили одну и ту же строку по-разному, Git не знает, чья версия верна, и просит человека решить. Это и есть конфликт. Он не поломка, а обычная часть работы: в любой команде конфликты случаются каждую неделю.

Допустим, вы с напарником правили файл rate.js. Напарник уже влил свою ветку в main, а вы сделали git pull origin main в своей ветке:

git switch feature/rate
git pull origin main
# Auto-merging rate.js
# CONFLICT (content): Merge conflict in rate.js
# Automatic merge failed; fix conflicts and then commit the result.

Git остановился и записал в файл маркеры конфликта:

// курс обмена
<<<<<<< HEAD
const convertUsd = (usd, rate = 10.9) => Math.round(usd * rate);
=======
const toSomoni = (usd) => usd * 11;
>>>>>>> origin/main
<<<<<<< HEAD
Начало конфликта. Ниже — ваша версия (из ветки, на которой вы стоите).
=======
Разделитель. Ниже — версия из другой ветки (здесь origin/main).
>>>>>>> origin/main
Конец конфликта и имя ветки, откуда пришла вторая версия.

Как разрешить конфликт

  1. Откройте файл со словом CONFLICT. В VS Code над блоком появятся кнопки: Accept Current (моё), Accept Incoming (чужое), Accept Both (оба) и Compare.
  2. Решите по смыслу, что должно остаться. Иногда нужно взять кусочки из обеих версий — и написать итоговый код руками. Договоритесь с автором второй правки.
  3. Удалите все три строки маркеров. В файле должен остаться только нормальный код.
  4. Запустите проект и убедитесь, что всё работает.
  5. Завершите слияние: 
    git add rate.js
git commit -m "merge main into feature/rate"
git push
Если запутались

Команда git merge --abort (или git rebase --abort) отменяет слияние и возвращает всё, как было до него. Конфликт решают в своей ветке до merge: тогда в main попадёт уже чистый результат.

Опасная ошибка

Закоммитить файл, в котором остались строки <<<<<<<. Такой код не запустится. Перед git add поищите в проекте <<<<<<< (Ctrl+Shift+F в VS Code).

Маркеры — это обычный текст, и разобрать их можно кодом. Первую задачу вы решите руками, как в настоящем конфликте. Во второй напишете «автоматическое разрешение», как это делают редакторы.

function matchRule(rule, path) {
  const parts = path.split("/");
  const name = parts[parts.length - 1];
  if (rule.endsWith("/")) {                          // «папка/»: любой каталог с таким именем
    return parts.slice(0, -1).includes(rule.slice(0, -1));

  if (rule.startsWith("*.")) return name.endsWith(rule.slice(1)); // «*.log»: по расширению
  return name === rule;                              // точное имя файла
}

function isIgnored(path, rules) {

    } else if (matchRule(rule, path)) {
      ignored = true;
    }
  }
  return ignored;
}

06 Ошибки: try / catch / finally и throw

Ошибки случаются у всех: пользователь ввёл пустую строку, сервер не ответил, из localStorage пришёл мусор. Если ничего не делать, программа остановится на первой же строке с ошибкой. Задача разработчика — заранее предусмотреть места, где код может упасть, и сделать так, чтобы пользователь увидел понятное сообщение, а не белый экран.

try / catch / finally

Аналогия: страховка в маршрутке

try — «попробуем проехать по этой дороге». catch — запасной план, если дорога перекрыта: свернуть и поехать в объезд. finally — то, что произойдёт в любом случае: выйти из маршрутки и заплатить водителю.

function readAge(text) {
  try {
    const age = JSON.parse(text);          // может бросить ошибку
    console.log("прочитали:", age);
    return age;
  } catch (error) {
    console.log("не получилось:", error.name);
    return 0;                              // запасной план
  } finally {
    console.log("— чтение закончено —");   // выполняется всегда
  }
}

console.log(readAge("19"));
console.log(readAge("девятнадцать"));

Ошибка внутри try немедленно прерывает его, и управление уходит в catch. Оставшиеся строки try пропускаются. В catch приходит объект ошибки (его обычно называют error или e).

Что внутри объекта ошибки

name
Тип ошибки: TypeError, ReferenceError, SyntaxError, RangeError…
message
Человеческое описание: «Cannot read properties of null».
stack
Стек вызовов — цепочка функций, которые привели к ошибке. Разберём в разделе 7.

throw: бросаем свою ошибку

Иногда ошибку нужно создать самому. Например, функция получила от пользователя отрицательное количество. throw прерывает текущую функцию и «бросает» ошибку вверх — до ближайшего catch. Бросайте объект ошибки (new Error("текст")), а не просто строку: у объекта есть стек.

function setQuantity(qty) {
  if (!Number.isInteger(qty)) throw new TypeError("Количество должно быть целым числом");
  if (qty < 1) throw new RangeError("Количество не может быть меньше 1");
  return qty;
}

for (const value of [3, 0, 2.5]) {
  try {
    console.log("ок:", setQuantity(value));
  } catch (e) {
    console.log(`${e.name}: ${e.message}`);
  }
}
Частая ошибка: пустой catch

Пустой catch (e) {} «проглатывает» ошибку: программа молчит и ведёт себя странно, а причину не найти. Минимум — выведите ошибку в консоль или покажите пользователю сообщение. И ловите только те ошибки, которые умеете обработать: остальные пробрасывайте дальше через throw e (задача 6.5).

function risky() {
  throw new Error("что-то пошло не так");
}

console.log("до этой строки мы уже не дойдём");

Ошибки в асинхронном коде ловят тем же try / catch вокруг await (вы видели это на уроке 13, а на следующих уроках будете так обрабатывать запросы fetch). Отдельный try вокруг setTimeout не сработает: колбэк выполнится позже, когда блок уже завершился.

Хороший catch обрабатывает только те ошибки, которые ожидает, а чужие пробрасывает дальше: throw e. function fail(field, message) {
  const e = new Error(message);
  e.name = "ValidationError";
  e.field = field;
  throw e;
}

function validate(order) {
  // две проверки через fail(...)
}

function process(order) {
  try {
    validate(order);
    return "заказ принят";
  } catch (e) {
    if (e.name === "ValidationError") return `поле ${e.field}: ${e.message}`;
    throw e; // чужие ошибки не глотаем
  }
}

console.log(process({ name: "", qty: 2 }));
console.log(process({ name: "Рустам", qty: 0 }));
try {
  process(null);
} catch (e) {
  console.log("неожиданная ошибка:", e.name);
}

Как читать красную ошибку

Когда код падает, браузер печатает красную строку и стек вызовов: список функций от места ошибки до самого начала. Читайте его сверху вниз: первая строка — где упало, следующие — кто вызвал эту функцию.

Uncaught TypeError: Cannot read properties of undefined (reading 'price')
    at calcTotal (cart.js:12:23)
    at renderCart (ui.js:48:15)
    at HTMLButtonElement.<anonymous> (main.js:7:3)
  1. Тип и сообщение: TypeError — читаем свойство price у undefined. Значит, где-то вместо товара пришёл undefined.
  2. Верхняя строка стека: calcTotal (cart.js:12:23) — функция calcTotal, файл cart.js, строка 12, символ 23. Здесь упало.
  3. Вторая строка: renderCart вызвала calcTotal. Часто баг не в верхней функции, а в том, что ей передали.
  4. Последняя строка: всё началось с клика по кнопке в main.js.

Клик по cart.js:12 в консоли DevTools откроет этот файл на нужной строке.

Вместо десятка console.log можно остановить программу на нужной строке и осмотреться. Откройте вкладку Sources, выберите файл и кликните по номеру строки слева: появится синяя метка — breakpoint.   1. Осмотритесь. Справа в панели Scope видны значения всех переменных на этот момент. В Watch можно добавить любое выражение, например items.length. В Call Stack — тот самый стек вызовов.

09 ИИ: коммиты, описание PR и вопрос про баг

ИИ-блок урока

ИИ хорошо делает две вещи: формулирует коммит по готовому diff и подсказывает гипотезы про баг. Но ответственность на вас: diff вы прочитали сами, а гипотезы проверяете запуском, а не верите на слово. Правила курса: сначала 15 минут пробуйте сами; не вставляйте код, который не можете объяснить построчно.

1. Коммит и описание PR по diff

Скопируйте вывод git diff --staged и попросите ИИ сформулировать сообщение. Без контекста он напишет «update files»:

придумай коммит
Вот diff: [вставьте вывод git diff --staged]. Напиши коммит-сообщение в стиле Conventional Commits (тип: тема, до 50 символов, английский, повелительное наклонение, без точки) и краткое описание PR: что сделано и зачем. Формат ответа: сначала одна строка коммита, потом PR из трёх разделов «Что сделано», «Зачем», «Как проверить». Не придумывай то, чего нет в diff.

Что проверить в ответе:

  • Тип соответствует правде: feat или fix, а не «на всякий случай».
  • В тексте нет того, чего нет в diff (ИИ любит добавлять «улучшил производительность», когда вы её не трогали).
  • Сообщение конкретное: пропустите его через проверки из задач 5.3 и 9.2.
  • Если в diff две разные мысли, лучше разбить на два коммита, а не просить ИИ «объединить красиво».

2. Баг: вместо «не работает» — минимальный воспроизводимый пример

у меня не работает корзина, исправь
Баг: ожидаю [что], получаю [что]. Минимальный код: [код]. Ошибка в консоли: [текст]. Дай 3 гипотезы причины по вероятности.

Минимальный воспроизводимый пример (minimal reproducible example, MRE) — самый короткий код, в котором баг всё ещё виден. Как его получить:

  1. Скопируйте проблемное место в отдельный файл или в консоль на этой странице.
  2. Удаляйте всё лишнее по кусочку: стили, соседние функции, лишние поля. После каждого шага проверяйте, что баг на месте.
  3. Подставьте простые данные вместо запросов к серверу: массив из 2–3 элементов.
  4. Запишите ожидаемый и фактический результат, а также текст ошибки дословно.

Бонус: пока вы упрощали код, вы часто сами находите баг. Это нормально и очень ценно. Метод называется «утёнок»: объяснить проблему вслух настолько ясно, что ответ находится сам.

Как не надо работать с гипотезами

ИИ дал три гипотезы. Проверяйте по очереди, от самой вероятной, и после каждой — запуск. Если вставить сразу три «исправления», вы не узнаете, какое сработало, и не научитесь замечать этот баг в следующий раз. Также ИИ иногда уверенно советует несуществующие методы: незнакомое название проверяйте в MDN.

В шпаргалку промптов добавьте две строки этого урока — «Коммиты и pull request» и «Баг вместо „не работает“». Потренируем оба навыка кодом.

  • try / catch / finally: catch получает ошибку, finally выполняется всегда. throw new Error("текст") бросает свою ошибку. Пустой catch — плохо; чужие ошибки пробрасываем дальше.
  • Типы ошибок: TypeError (не то значение, null.x), ReferenceError (нет переменной), SyntaxError (плохой синтаксис / JSON), RangeError (вне диапазона).
  • Стек: читаем сверху вниз: где упало, кто вызвал. DevTools: Console (log, table, trace), Sources (breakpoint по номеру строки, F10 / F11 / F8, Watch, Scope), debugger;, Network (статус, ответ, время).
  • Классические баги: off-by-one (< / <=, индексы с 0), сравнение (===, строки против чисел, sort(fn)), async (await, for…of вместо forEach), мутация ([...arr], Array.from), var в цикле.
  • Метод отладки: воспроизвести → сузить → прочитать ошибку → гипотеза → одна проверка → исправить и перепроверить.
  • С ИИ: коммит и PR — по вашему diff, текст проверяем. Баг — минимальный пример + ожидание/факт + дословная ошибка + «3 гипотезы»; проверяем по очереди запуском.
