01 useEffect: когда он срабатывает

Компонент React — это чистая функция: получила данные (props и state), вернула описание экрана (JSX). Всё. Рендер не должен ничего «делать» во внешнем мире: слать запросы, запускать таймеры, менять заголовок вкладки. Такие действия называются побочными эффектами, и для них в React есть отдельное место — хук useEffect.

Аналогия из жизни

В чойхоне официант сначала накрывает стол — это рендер: скатерть, пиалы, лепёшки. Только когда стол накрыт, он идёт на кухню за чайником — это эффект. Нельзя отправляться на кухню посреди накрытия стола: гость уже сидит и смотрит на пустой стол. React поступает так же: сначала показывает экран, и лишь после этого запускает ваш эффект.

Порядок: рендер → экран → эффект

Нажмите «Запустить», затем несколько раз на кнопку в предпросмотре — и следите за консолью.

import { useEffect, useState } from "react";

export default function App() {
  const [count, setCount] = useState(0);

  // Это тело компонента — РЕНДЕР: React считает, как должен выглядеть экран
  console.log("1. рендер: считаем JSX, count =", count);

  // А это ЭФФЕКТ: React вызовет его уже ПОСЛЕ того, как экран обновлён
  useEffect(() => {
    console.log("2. эффект: экран обновлён, count =", count);
  });

  return <button onClick={() => setCount(count + 1)}>Нажато: {count}</button>;
}
  1. Рендер. React вызывает функцию компонента и получает JSX. Любые console.log в теле компонента выполняются на этом шаге.
  2. Коммит. React обновляет настоящий DOM — пользователь видит новый экран.
  3. Эффект. React вызывает функции из useEffect. Здесь безопасно ходить в сеть, ставить таймеры и трогать document.

Массив зависимостей: когда повторять эффект

Вторым аргументом useEffect принимает массив зависимостей. Он отвечает на вопрос «после каких рендеров запускать эффект снова?»

ЗаписьКогда срабатываетТипичное применение
useEffect(fn)после каждого рендерапочти никогда; чаще это ошибка
useEffect(fn, [])один раз, после первого рендеразагрузка данных при открытии, подписка
useEffect(fn, [a, b])после первого рендера и каждый раз, когда a или b изменилисьзапрос по id или поисковой строке

Попробуйте: нажимайте кнопки a и b и смотрите, какие из трёх эффектов откликаются.

import { useEffect, useState } from "react";

export default function App() {
  const [a, setA] = useState(0);
  const [b, setB] = useState(0);

  useEffect(() => {
    console.log("A (без массива): после КАЖДОГО рендера");
  });

  useEffect(() => {
    console.log("B ([]): один раз, после первого рендера");
  }, []);

  useEffect(() => {
    console.log("C ([a]): изменился a, теперь a =", a);
  }, [a]);

  return (
    <div style={{ display: "flex", gap: 8 }}>
      <button onClick={() => setA(a + 1)}>a = {a}</button>
      <button onClick={() => setB(b + 1)}>b = {b}</button>
    </div>
  );
}
Правило зависимостей

В массив нужно записать все значения из компонента (props, state, функции), которые эффект читает. Если эффект использует id, а в массиве его нет, эффект будет работать со «старым» id — самый частый источник багов. Хороший редактор (и ИИ) подскажет это правилом react-hooks/exhaustive-deps; не отключайте его, а исправляйте код.

Частая ошибка: бесконечный цикл

Эффект без массива, который меняет состояние, запускает новый рендер, тот — новый эффект, и так до бесконечности. Браузер зависает или React бросает ошибку «Too many re-renders». Не запускайте этот код у себя в рабочем проекте.

function Counter() {
  const [n, setN] = useState(0);

  useEffect(() => {
    setN(n + 1); // ✖ нет массива зависимостей: рендер → эффект → setN → рендер → ...
  });

  return <p>{n}</p>;
}

02 Cleanup: за собой надо убирать

Эффект может вернуть функцию — её называют cleanup («уборка»). React вызовет её в двух случаях: перед тем как запустить эффект заново (при смене зависимостей) и когда компонент исчезает с экрана.

useEffect(() => {
  // 1) «включаем»: таймер, подписка, запрос
  const id = setInterval(tick, 1000);

  // 2) возвращаем «выключатель»
  return () => clearInterval(id);
}, []);
Аналогия из жизни

Вы приехали на маршрутке и включили в ней радио на всю громкость. Если выходите, не выключив — радио играет для пустого салона и мешает следующим пассажирам. Cleanup — это «выключить радио, выходя». Таймер без cleanup точно так же продолжает тикать у компонента, которого уже нет.

Порядок при смене зависимостей

  1. Эффект запустился с room = "Общий": подключились.
  2. room поменялся на "Группа JS": React сначала вызывает cleanup старого эффекта (отключились от «Общий»)…
  3. …и только затем запускает эффект с новым значением (подключились к «Группа JS»).
  4. Компонент убрали с экрана: последний cleanup — отключились.

StrictMode: зачем React запускает эффект дважды

Когда вы создаёте проект на Vite или Next.js, компоненты обычно обёрнуты в <StrictMode>. В режиме разработки он нарочно делает «репетицию»: запускает эффект, сразу вызывает cleanup и запускает эффект ещё раз. Так React проверяет, что ваш эффект умеет «выключаться» и не оставляет мусор. В готовой сборке (production) этого дублирования нет.

function Clock() {
  const [seconds, setSeconds] = useState(0);

  useEffect(() => {
    console.log("эффект: запускаем таймер");
    const id = setInterval(() => setSeconds((s) => s + 1), 1000);
    return () => {
      console.log("cleanup: останавливаем таймер");
      clearInterval(id);
    };
  }, []);

  return <p>Прошло секунд: {seconds}</p>;
}

Как относиться к «двойному запуску»

Это не баг и не «React сломался». Если после двойного запуска приложение работает как надо — cleanup написан верно. Если запрос уходит дважды или таймеры ускоряются — вы забыли cleanup. Учебные окна на этой странице работают в режиме production, поэтому дубля в них не видно; проверьте сами, когда создадите проект на Vite.

Частая ошибка: забыли очистить таймер

Без cleanup интервал живёт после ухода компонента: утечка памяти и обновления состояния несуществующего компонента.

useEffect(() => {
  setInterval(() => console.log("тик"), 1000); // ✖ никто не остановит этот таймер
}, []);

03 Загрузка данных: четыре состояния

Самая частая работа для useEffect — получить данные с сервера при открытии экрана. Запрос — это побочный эффект, поэтому ему не место в теле компонента. А раз ответ приходит не сразу, экран живёт в четырёх состояниях, и каждое нужно показать пользователю (вы уже встречали их в уроке 16):

СостояниеЧто видит пользовательКак узнаём
loading«Загрузка…», скелетон или спиннерзапрос ушёл, ответа ещё нет
errorпонятное сообщение и кнопка «Повторить»сеть упала или response.ok === false
empty«Ничего не найдено»ответ пришёл, но массив пустой

Аналогия из жизни

Вы заказали такси в приложении. «Ищем машину» — loading. «Машин нет, попробуйте позже» — error. «В вашем районе нет доступных тарифов» — empty. «Водитель Фарход приедет через 4 минуты» — success. Если приложение показывает пустой белый экран вместо любого из этих сообщений, пользователь решит, что оно сломано.

Скелет компонента

Состояний у экрана несколько — держим их в useState. «Пусто» отдельно хранить не нужно: это успех с пустым массивом.

function StudentList() {
  const [status, setStatus] = useState("loading"); // loading | error | success
  const [students, setStudents] = useState([]);
  const [error, setError] = useState("");

  useEffect(() => {
    fetch("/api/students")
      .then((response) => {
        if (!response.ok) throw new Error("HTTP " + response.status); // 404 и 500 — тоже ошибка
        return response.json();
      })
      .then((data) => {
        setStudents(data);
        setStatus("success");
      })
      .catch((err) => {
        setError(err.message);
        setStatus("error");
      });
  }, []);

  if (status === "loading") return <p>Загрузка…</p>;
  if (status === "error") return <p>Ошибка: {error}</p>;
  if (students.length === 0) return <p>Ничего не найдено</p>;

  return (
    <ul>
      {students.map((s) => <li key={s.id}>{s.name}</li>)}
    </ul>
  );
}

Обратите внимание на порядок if: сначала ранние возвраты для загрузки, ошибки и пустого списка, а в конце — «счастливый путь» с данными. Так компонент читается сверху вниз, как чек-лист.

Частая ошибка: async прямо в useEffect

Писать useEffect(async () => { ... }) нельзя: async-функция всегда возвращает промис, а React ждёт от эффекта либо ничего, либо функцию cleanup. Если нужен await — объявите async-функцию внутри эффекта и вызовите её (как в задаче 3.1), либо используйте .then, как в шаблоне выше.

useEffect(async () => {   // ✖ эффект вернёт промис, а не cleanup
  const response = await fetch("/api/students");
  setStudents(await response.json());
}, []);

import { useEffect, useState } from "react";

const GOOD = "https://jsonplaceholder.typicode.com/users?_limit=5";
const BAD = "https://jsonplaceholder.typicode.com/nothing-here"; // вернёт 404

export default function App() {
  const [url, setUrl] = useState(GOOD);
  const [attempt, setAttempt] = useState(0); // «Повторить» увеличивает число и запускает эффект заново
  const [status, setStatus] = useState("loading");
  const [users, setUsers] = useState([]);
  const [error, setError] = useState("");

  useEffect(() => {
    const controller = new AbortController();
    setStatus("loading");

    fetch(url, { signal: controller.signal })
      .then((response) => {
        if (!response.ok) throw new Error("HTTP " + response.status);
        return response.json();
      })
      .then((data) => {
        setUsers(data);
        setStatus("success");
      })
      .catch((err) => {
        if (err.name === "AbortError") return; // это мы сами отменили — не ошибка
        setError(err.message);
        setStatus("error");
      });

    return () => controller.abort();
  }, [url, attempt]);

  return (
    <div>
      <button onClick={() => setUrl(url === GOOD ? BAD : GOOD)}>
        {url === GOOD ? "Сломать адрес" : "Починить адрес"}
      </button>{" "}
      <button onClick={() => setAttempt(attempt + 1)}>Повторить</button>

      {status === "loading" && <p>Загрузка…</p>}
      {status === "error" && <p style={{ color: "#c0392b" }}>Не получилось: {error}</p>}
      {status === "success" && users.length === 0 && <p>Список пуст</p>}
      {status === "success" && (
        <ul>
          {users.map((u) => (
            <li key={u.id}>{u.name} ({u.address.city})</li>
          ))}
        </ul>
      )}
    </div>
  );
}

04 Гонки запросов и AbortController

Представьте экран профиля с кнопками «Мадина» и «Фарход». Вы нажали «Мадина» — ушёл запрос, а он медленный. Не дожидаясь, нажали «Фарход» — второй запрос быстрый и вернулся первым. Экран показал Фархода. Но потом наконец приходит ответ на первый запрос и перезаписывает экран: в заголовке «Фарход», а данные — Мадины. Это называется гонкой запросов (race condition), и она случается на реальных сайтах постоянно.

Аналогия из жизни

Вы заказали плов в одной чойхоне, но тут же передумали и заказали курутоб в другой. Курутоб привезли быстро, вы начали есть — и вдруг курьер привозит плов, который вы отменили. Правильное поведение — позвонить в первую чойхону и отменить заказ. Для запросов отмена — это AbortController.

AbortController в двух строках

Вы создаёте контроллер, отдаёте его signal в fetch, а когда запрос больше не нужен, вызываете controller.abort(). Промис fetch тогда отклоняется с ошибкой AbortError.

const controller = new AbortController();

fetch("https://jsonplaceholder.typicode.com/users/1", { signal: controller.signal })
  .then((r) => r.json())
  .then((user) => console.log("получили", user.name))
  .catch((err) => console.log("ошибка:", err.name));

controller.abort(); // передумали сразу же
console.log("aborted:", controller.signal.aborted);

Как это выглядит в эффекте

Cleanup эффекта — идеальное место для abort(): React вызывает его перед повторным запуском эффекта и при уходе компонента.

useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/users/${id}`, { signal: controller.signal })
    .then((r) => {
      if (!r.ok) throw new Error("HTTP " + r.status);
      return r.json();
    })
    .then((user) => setUser(user))
    .catch((err) => {
      if (err.name === "AbortError") return; // мы сами отменили — это не ошибка для пользователя
      setError(err.message);
    });

  return () => controller.abort(); // отменяем при смене id или уходе со страницы
}, [id]);
Запасной вариант: флаг ignore

Если отменять нечем (например, библиотека не принимает signal), используйте флаг: let ignore = false; в эффекте, if (!ignore) setUser(user) в обработчике и return () => { ignore = true; } в cleanup. Запрос не отменится, но его результат будет проигнорирован. Отмена лучше: она ещё и экономит трафик.

Частая ошибка: показываем AbortError пользователю

Если в .catch просто сделать setError(err.message), при каждом переключении пользователь на долю секунды увидит «The user aborted a request». Проверяйте err.name === "AbortError" и молча выходите.

05 Поиск, debounce и фильтрация

Фильтрация: не нужно ни состояния, ни эффекта

Допустим, у вас есть список и строка поиска. Новички часто заводят второй useState для «отфильтрованного списка» и обновляют его в эффекте. Это лишнее: отфильтрованный список целиком вычисляется из двух значений — полного списка и строки поиска. Такие данные называются производными, и считать их нужно прямо при рендере.

  s.name.toLowerCase().includes(query.trim().toLowerCase())

Аналогия из жизни

Меню на стене чойхоны одно. Когда гость говорит «мне что-нибудь без мяса», официант не переписывает меню и не вешает второе — он просто в уме пропускает мясные блюда. Отфильтрованный список — это «взгляд на меню», а не новое меню.

Поиск через сервер и зачем нужен debounce

Если искать по списку из тысяч записей, фильтровать на клиенте уже нельзя — нужен запрос на сервер: /users/search?q=плов. Но если отправлять запрос на каждую нажатую клавишу, пока пользователь набирает «плов», уйдут четыре запроса: п, пл, пло, плов. Три из них никому не нужны, а ещё они могут вернуться в перепутанном порядке.

Debounce («дребезг») — приём: подождать, пока пользователь перестанет печатать на 300–500 мс, и только потом искать. Каждое новое нажатие сбрасывает таймер.

Сначала само ядро идеи в чистом JS — функция debounce, которая используется везде, не только в React. А в React то же самое оформляется как собственный хук:

function useDebounce(value, delay) {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id); // новое нажатие отменяет старый таймер
  }, [value, delay]);

  return debounced;
}

Это красивый пример cleanup: каждое изменение value убирает таймер предыдущего изменения, и до конца доживает только последний. Использование: эффект запроса зависит не от query (меняется на каждой букве), а от debounced.

06 ИИ-блок: промпт для React-компонента против ручной работы

React-компоненты ИИ пишет очень уверенно — это один из самых частых запросов в мире. function useDebounce(value, delay) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);
  }, [value, delay]);
  return debounced;
}

import { useEffect, useState } from "react";

function useDebounce(value, delay) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);
  }, [value, delay]);
  return debounced;
}

  const response = await fetch(url, { signal });
  if (!response.ok) throw new Error("HTTP " + response.status);
  return response.json();
}

08 Обзор: что дальше даёт Next.js и серверные компоненты

Всё, что мы делали сегодня, — клиентский React: браузер скачивает JavaScript, запускает компонент, и только потом начинается fetch. Пользователь сначала видит «Загрузка…». Для кабинетов и приложений за логином это нормально. Для сайтов, где важны скорость первого показа и поисковики (каталоги, блоги, магазины), хочется получать данные до того, как страница уйдёт в браузер.

Next.js — популярный фреймворк поверх React, который берёт эту работу на себя. Коротко, что он добавляет:

Посмотрите, чего здесь нет: нет useState, нет useEffect, нет ветки «Загрузка…» внутри компонента — компонент просто async и ждёт данные. Сервер готовит HTML и отдаёт его уже заполненным. Поиск по такому списку, кнопки и всё интерактивное всё равно пишутся клиентскими компонентами — теми же useState и useEffect, которые вы выучили сегодня.

Что важно понимать без хайпа

1. Серверные компоненты не отменяют useEffect — они забирают на себя только начальную загрузку данных. Подписки, таймеры, ввод пользователя остаются на клиенте. 2. Next.js — не обязателен: приложению за логином часто хватает Vite + React. 3. В реальных проектах загрузку в useEffect часто заменяют библиотеками вроде TanStack Query или SWR: они кэшируют ответы, повторяют запросы и убирают гонки. Но чтобы понимать, что делают эти библиотеки, нужно знать то, что вы изучили сегодня. 4. Это обзор: в Уровне 3 всё будет подробно и с практикой. (Кстати, платформа, на которой вы проходите курс, тоже написана на Next.js.)

Vite + React (клиентский)

Просто и быстро стартовать. Подходит для кабинетов, панелей, внутренних инструментов. Данные грузятся в браузере через useEffect или библиотеку.

Next.js (клиент + сервер)

Нужны быстрый первый показ, SEO, готовая маршрутизация и серверный код в одном проекте. Данные можно получать на сервере, а интерактив оставить клиентским.

✓ Шпаргалка урока

  • Рендер должен быть чистым. Запросы, таймеры, document.title, подписки — побочные эффекты, им место в useEffect.
  • Порядок: рендер → обновление DOM → эффект.
  • Зависимости: без массива — после каждого рендера; [] — один раз; [a, b] — при изменении a или b. В массиве всё, что эффект читает.
  • Cleanup: return () => ... в эффекте. Вызывается перед повторным запуском и при уходе компонента. StrictMode в разработке нарочно запускает «эффект → cleanup → эффект».
  • Четыре состояния: loading, error, empty, success. «Пусто» — это успех с пустым массивом.
  • Шаблон: fetch → if (!response.ok) throw new Error(...) → json() → setState; в .catch — ошибка, но AbortError игнорируем.
  • Нельзя useEffect(async () => ...): async-функцию объявляем внутри.
  • Гонка запросов: cleanup с controller.abort() (или флаг ignore), чтобы старый ответ не затирал новый.
  • Производные данные (отфильтрованный список) считаем при рендере, а не храним в состоянии.
  • Debounce: useDebounce(value, delay) — setTimeout в эффекте и clearTimeout в cleanup; запрос зависит от debounced.
  • Next.js: маршруты по папкам, серверные компоненты (данные на сервере, без useEffect), "use client" для интерактива.
  • С ИИ: в промпте для компонента — props, состояние, крайние случаи; проверка по чек-листу из 8 пунктов.
