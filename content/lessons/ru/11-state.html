Состояние приложения и localStorage

Вы написали список дел, закрыли вкладку — и всё пропало. Для пользователя это катастрофа: он потратил десять минут, а сайт всё забыл. В настоящих приложениях корзина интернет-магазина, тёмная тема и недочитанный урок переживают перезагрузку страницы. Сегодня вы научитесь хранить все данные приложения в одном месте, рисовать экран по этим данным и сохранять их в браузере.

  • Описывать состояние приложения одним объектом и отличать его от «производных» данных
  • Писать функцию render(state), которая рисует экран только по состоянию
  • Менять состояние через небольшие функции-действия: добавить, отметить, удалить
  • Сохранять и читать данные через localStorage вместе с JSON.stringify и JSON.parse
  • Не падать, когда данных нет, они повреждены или устарели
  • Просить ИИ предложить структуру состояния и сравнивать её со своей
Как работать с этой страницей

Код на тёмном фоне с кнопкой ▶ Запустить — живой: меняйте и запускайте. Блоки «Практика» проверяются автоматически по тексту в консоли. В нескольких задачах есть мини-страница с предпросмотром: слева код (вкладки index.html, style.css, script.js), справа результат. Подсказки спрятаны — сначала попробуйте сами.

Важно про localStorage. Код на этой странице работает в изолированной «песочнице», где настоящего localStorage нет. Мы подробно разберём это в разделе 04 и дадим вам точную заглушку с тем же API. На вашем компьютере (в домашнем задании) вы будете использовать настоящий.

01 Что такое состояние приложения

Состояние (state) — это все данные, которые описывают приложение прямо сейчас и могут измениться: список задач, какие из них выполнены, выбранный фильтр, тема оформления, товары в корзине. Если сделать «снимок» состояния, по нему можно полностью воссоздать то, что видит пользователь.

Аналогия из жизни

Табло на автовокзале в Душанбе. Само табло ничего не «помнит»: оно только показывает расписание, которое лежит в системе диспетчера. Отменили рейс в Худжанд — диспетчер поменял запись, и табло перерисовалось. Расписание в системе — это состояние. Табло — экран. Если бы кто-то вручную исправил надпись на табло, не тронув систему, при следующем обновлении правка бы исчезла, а в зале начался бы хаос.

Как делают новички: данные «разбросаны»

Первое, что приходит в голову — завести отдельную переменную на каждую мелочь, а частью данных вообще считать то, что написано на странице. Такой код быстро превращается в кашу:

let ownerName = "Мадина";
let balance = 150;
let operations = 2;
let lastOperation = "пополнение";

function showWallet() {
  console.log(`${ownerName}: ${balance} сомони, операций: ${operations}, последняя — ${lastOperation}`);
}

showWallet();

Пока переменных четыре, это терпимо. Но когда их двадцать, нельзя ответить на простые вопросы: что именно нужно сохранить? Что передать функции? Что очистить при выходе пользователя?

Как делают в настоящих проектах: один объект

Все изменяемые данные приложения складывают в один объект — обычно его называют state.

const state = {
  ownerName: "Мадина",
  balance: 150,
  history: ["пополнение", "покупка"],
};

function showWallet(state) {
  const last = state.history[state.history.length - 1];
  console.log(`${state.ownerName}: ${state.balance} сомони, последняя операция — ${last}`);
}

showWallet(state);
console.log(JSON.stringify(state)); // всё приложение — одним взглядом

Выгоды сразу видны: функции получают state и больше ничего не ищут; «что сохранять» — это просто state; отладка проще — достаточно вывести один объект и увидеть всё приложение.

Что класть в состояние, а что — нет

В состоянии хранят исходные факты, которые нельзя вывести из других данных. Всё, что можно посчитать из состояния, в нём хранить не нужно — это производные данные.

Лишнее в состоянии

Сумма и счётчик «живут отдельно» от списка — легко забыть обновить один из них, и они разойдутся.

const state = {
  items: [{ title: "Самбуса", price: 5, qty: 3 }],
  total: 15,        // можно посчитать
  itemsCount: 1,    // можно посчитать
};
Только факты

В состоянии — товары. Сумму считает функция, и она всегда актуальна.

const state = {
  items: [{ title: "Самбуса", price: 5, qty: 3 }],
};
const getTotal = (state) =>
  state.items.reduce((sum, i) => sum + i.price * i.qty, 0);
В состояние
Список задач, выбранный фильтр, тема, товары в корзине, имя пользователя, номер текущего шага.
Не в состояние
Сумма корзины, количество невыполненных задач, готовые HTML-строки — всё, что можно вычислить из состояния.
Решаем осознанно
Временные вещи вроде набираемого в поле текста. Их можно держать в состоянии, а можно не сохранять — об этом ещё поговорим в разделе про ИИ.
Частая ошибка

Копирование числа из состояния в локальную переменную и изменение копии. Числа и строки копируются по значению: изменили копию — состояние осталось прежним.

const state = { visitors: 10 };

let visitors = state.visitors; // скопировали число
visitors = visitors + 1;       // изменили копию

console.log(visitors);         // → 11
console.log(state.visitors);   // → 10 — в состоянии ничего не поменялось

02 Рендер от состояния: render(state)

Следующая идея — самая важная в уроке. Экран не живёт своей жизнью: он каждый раз рисуется заново по состоянию. Для этого пишут функцию render. Она получает состояние и показывает его. Больше она ничего не делает: ничего не меняет и ничего не решает.

Чтобы пока не отвлекаться на HTML, «экраном» в первом примере будет консоль:

const state = {
  todos: [
    { id: 1, text: "Купить нон", done: true },
    { id: 2, text: "Сделать домашку по JS", done: false },
  ],
};

function render(state) {
  console.log("--- Список дел ---");
  state.todos.forEach((todo) => {
    const mark = todo.done ? "[x]" : "[ ]";
    console.log(`${mark} ${todo.text}`);
  });
}

render(state);

Теперь то же самое на настоящей странице. Обратите внимание на структуру скрипта: сверху состояние, потом render, потом действие и обработчик клика. Нажмите «Добавить блюдо» и посмотрите, как меняется список:

<button id="add">Добавить блюдо</button>
<ul id="menu"></ul>
<p id="info"></p>

li { margin: 4px 0; }

const menu = document.querySelector("#menu");
const info = document.querySelector("#info");
const addBtn = document.querySelector("#add");

// 1. Состояние
const state = {
  dishes: ["Оши палав", "Самбуса"],
};
const NEXT = ["Курутоб", "Шакароб", "Манту", "Чакка"];

// 2. Рендер: рисует экран по состоянию
function render() {
  menu.textContent = ""; // очистили список
  state.dishes.forEach((name) => {
    const li = document.createElement("li");
    li.textContent = name;
    menu.append(li);
  });
  info.textContent = `Блюд в меню: ${state.dishes.length}`;
}

// 3. Действие: меняет состояние и просит перерисовать
addBtn.addEventListener("click", () => {
  const next = NEXT[state.dishes.length - 2];
  if (next) state.dishes.push(next);
  render();
});

render();
console.log("блюд в состоянии:", state.dishes.length);

Правила хорошего render

  1. Читает только состояние. Данные для экрана берём из state, а не из DOM. Не list.children.length, а state.todos.length.
  2. Ничего не меняет. Внутри render нет push, state.x = … и других изменений данных.
  3. Рисует всё целиком. Очистили контейнер и построили заново. Для списков из десятков элементов это мгновенно, а ошибок меньше: не нужно думать, «что именно поменялось».
  4. Вызывается после каждого действия. Изменили состояние — вызвали render(). Забыли — экран «врёт».
  5. Умеет рисовать пустое состояние. Если задач нет, показываем «Список пуст», а не белую пустоту.
Аналогия из жизни

Повар в чайхоне собирает заказ по чеку, а не по памяти. Изменился заказ — посмотрел в чек и приготовил заново. Чек — это состояние. Блюдо на столе — экран. Спорить с чеком бессмысленно: если в чеке «без лука», лука не будет.

Два источника правды

Число задач хранится и в массиве, и «на странице». Забыли обновить одно из них — они расходятся.

// ❌ данные берём из DOM
const count = list.children.length;
if (count >= 5) {
  alert("Слишком много задач");
}
Один источник правды

Правда — в state. DOM — просто его отражение.

// ✓ данные берём из состояния
if (state.todos.length >= 5) {
  alert("Слишком много задач");
}
Частая ошибка

Менять данные и тут же «подправлять» экран вручную (li.textContent = …, li.remove()) в каждом обработчике. Пока элемент один — работает. Когда появятся фильтры, счётчики и сохранение, вы будете забывать обновлять то одно, то другое. Меняем state, вызываем render() — и всё.

03 Действия: как правильно менять состояние

Состояние меняют небольшие функции-действия (actions): addTodo, toggleTodo, removeTodo. Обработчики событий не лезут в данные сами — они только вызывают нужное действие. Каждое действие делает три вещи: меняет состояние → вызывает render() (а в следующих разделах — ещё и сохраняет).

Три приёма для массивов в состоянии

Все изменения списка сводятся к трём операциям. Условимся менять массив не «на месте», а присваивать новый — так проще отследить, что именно поменялось, и именно этот стиль потребуется вам дальше в React.

Изменить однуmapstate.todos = state.todos.map((t) => t.id === id ? { ...t, done: !t.done } : t);

const state = { nextId: 1, todos: [] };

function render() {
  console.log("--- Экран ---");
  if (state.todos.length === 0) console.log("(пусто)");
  state.todos.forEach((t) => console.log(`${t.id}. ${t.done ? "[x]" : "[ ]"} ${t.text}`));
}

function addTodo(text) {
  const todo = { id: state.nextId, text, done: false };
  state.nextId = state.nextId + 1;
  state.todos = [...state.todos, todo];
  render();
}

function toggleTodo(id) {
  state.todos = state.todos.map((t) => (t.id === id ? { ...t, done: !t.done } : t));
  render();
}

function removeTodo(id) {
  state.todos = state.todos.filter((t) => t.id !== id);
  render();
}

addTodo("Выучить JSON");
toggleTodo(1);
removeTodo(2);
Аналогия из жизни

Касса в магазине на Зелёном базаре. Покупатель не лезет в кассу руками — он говорит продавцу: «добавьте», «уберите», «отметьте». Продавец (действие) вносит запись в журнал (состояние) и показывает итог на дисплее (рендер). Одни и те же понятные операции — каждый раз. Никто не правит дисплей карандашом.

Откуда брать id

У каждой задачи должен быть уникальный id: по нему мы находим её для отметки или удаления. Соблазн — брать state.todos.length + 1. Он ломается после первого же удаления:

let todos = [{ id: 1 }, { id: 2 }, { id: 3 }];

todos = todos.filter((t) => t.id !== 1);          // удалили первую: осталось две
todos = [...todos, { id: todos.length + 1 }];     // новая получила id = 3

console.log(todos.map((t) => t.id).join(","));    // → 2,3,3 — два одинаковых id!

Поэтому в состоянии хранят отдельный счётчик nextId: он только растёт и никогда не выдаёт один номер дважды.

Действия в настоящей странице

Вспомните делегирование из урока 9: один обработчик на списке, а нужный элемент находим через event.target.closest(...). Нужную задачу определяем по data-id:

  const li = event.target.closest("li");
  if (!li) return;                     // клик мимо задач
  toggleTodo(Number(li.dataset.id));   // data-id — строка, переводим в число
});

Обратите внимание на Number(...): значения из dataset всегда строки, а id в состоянии — число. Без перевода t.id === id никогда не сработает: 1 === "1" — это false.

Частая ошибка

Изменить состояние и сохранить результат в отдельной переменной, забыв присвоить обратно в state. Методы map и filter не меняют исходный массив — они возвращают новый.

const state = { todos: [{ id: 1, done: false }] };

state.todos.map((t) => ({ ...t, done: true })); // новый массив никуда не записали
console.log(state.todos[0].done);               // → false — ничего не изменилось

04 localStorage: память браузера

Сейчас всё состояние живёт в переменной. Обновили страницу — переменные создаются заново, и состояние обнуляется. Чтобы данные пережили перезагрузку, их нужно положить туда, где они не пропадают вместе со страницей. Для этого у браузера есть localStorage — небольшое хранилище «ключ → строка», привязанное к сайту.

Аналогия из жизни

Камера хранения на вокзале. Вы сдаёте сумку и получаете номерок. Уходите, гуляете по городу, возвращаетесь на следующий день — сумка на месте. Номерок — это ключ, сумка — значение. Но в эту камеру можно положить только запакованные вещи: localStorage принимает только строки. Всё остальное придётся упаковать — об этом ниже.

Что нужно знать о localStorage

  • Хранит пары «ключ — строка». Ключи тоже строки.
  • Данные не исчезают при перезагрузке страницы, закрытии вкладки и даже перезапуске браузера.
  • У каждого сайта своё хранилище: ilmhona.tj не видит данные example.com.
  • Объём — около 5 МБ на сайт: для списка дел или настроек этого с запасом.
  • Пользователь может очистить его в настройках или вручную изменить в DevTools. Данным из него доверять нельзя так же, как и вводу в форму.
  • Не храните там пароли и секреты: любой скрипт на странице может их прочитать.

Методы

Важно: в песочнице этого курса настоящего localStorage нет

Весь код на этой странице выполняется в изолированном окне-«песочнице» — так мы защищаем ваш компьютер от случайного вредного кода. У такого окна нет «своего сайта», поэтому браузер запрещает ему доступ к localStorage. Проверьте сами:

localStorage.setItem("theme", "dark");
console.log(localStorage.getItem("theme"));

Ошибка доступа — это не ваша вина и не баг урока. Чтобы вы всё равно могли тренироваться, мы даём заглушку: объект storage с теми же методами setItem, getItem, removeItem, clear. Она хранит данные в памяти, пока работает ваш код. А чтобы «перезагрузку страницы» можно было показать и в песочнице, мы будем вызывать функцию запуска приложения несколько раз подряд в одном скрипте: хранилище при этом остаётся, а переменные приложения — нет.

// ── заглушка localStorage ─────────────────────────────────────
// В песочнице настоящий localStorage недоступен — на вашем компьютере
// используйте window.localStorage. Остальной код при этом не меняется.
function createStorage() {
  let data = {};
  return {
    getItem(key) {
      return Object.hasOwn(data, key) ? data[key] : null;
    },
    setItem(key, value) {
      data[key] = String(value); // как и настоящий: всё превращается в строку
    },
    removeItem(key) {
      delete data[key];
    },
    clear() {
      data = {};
    },
  };
}
const storage = createStorage();
// ─────────────────────────────────────────────────────────────

storage.setItem("theme", "dark");
console.log(storage.getItem("theme"));    // → dark
console.log(storage.getItem("language")); // → null — такого ключа нет
storage.removeItem("theme");
console.log(storage.getItem("theme"));    // → null
Как перейти на настоящий localStorage

Весь код в уроке пишите через переменную storage. На вашем компьютере, в обычном HTML-файле, достаточно заменить заглушку одной строкой — всё остальное работает без изменений:

Увидеть записи можно на вкладке Application (в Firefox — Storage) → Local Storage. Там же их можно редактировать и удалять.

Всё превращается в строку

Это главная ловушка. Положили число — получили строку. Положили объект — получили текст "[object Object]".

«Перезагрузка» в песочнице

Вот как мы будем имитировать перезагрузку: функция openSite — это «открытие страницы». Каждый вызов начинает с нуля, но хранилище помнит прошлые визиты:

05 JSON: упаковываем состояние в строку

С JSON вы познакомились на уроке 7. Здесь он решает конкретную задачу: localStorage принимает только строки, а наше состояние — объект с массивами. Поэтому перед записью мы упаковываем объект в строку (JSON.stringify), а после чтения — распаковываем обратно (JSON.parse).

const state = {
  filter: "all",
  todos: [{ id: 1, text: "Купить нон", done: false }],
};

const raw = JSON.stringify(state);    // объект → строка
console.log(raw);
console.log(typeof raw);              // → string

const restored = JSON.parse(raw);     // строка → объект
console.log(restored.todos[0].text);  // → Купить нон
console.log(restored === state);      // → false — это новая копия, а не тот же объект
Аналогия из жизни

Переезд. Диван в машину целиком не поместится, поэтому его разбирают, пакуют в коробки и везут. На новой квартире собирают обратно по инструкции. stringify — «разобрать и упаковать», parse — «собрать». Диван тот же, но это уже новый собранный экземпляр, а не тот самый.

Пара функций saveState / loadState

Чтобы не писать JSON.stringify и setItem в десяти местах, прячем их в две функции. Всё приложение обращается к хранилищу только через них:

const KEY = "todo-app:v1";   // ключ: имя приложения + версия формата

function saveState(state) {
  storage.setItem(KEY, JSON.stringify(state));
}

function loadState() {
  const raw = storage.getItem(KEY);
  return raw === null ? null : JSON.parse(raw);
}

Ключ с префиксом todo-app: защищает от конфликта с другими приложениями на том же сайте, а :v1 пригодится, когда вы поменяете формат состояния: новая версия сможет читать новый ключ и не споткнётся о старые данные.

Что не переживёт упаковку

JSON — это только текст с простыми значениями. Не всё, что есть в объекте, можно в него превратить:

Что в объектеЧто получится после stringify → parse
Строки, числа, true/false, null, массивы, объектыБез изменений
undefinedПоле пропадает
Функции и методыПоле пропадает

const task = {
  title: "Сдать проект",
  deadline: new Date(0),    // дата → строка
  note: undefined,          // пропадёт
  remind() { console.log("!"); }, // пропадёт

const copy = JSON.parse(JSON.stringify(task));
console.log(JSON.stringify(copy));
console.log(typeof copy.deadline);  // → string
console.log(typeof copy.remind);    // → undefined

Вывод: в состоянии храните «простые» данные — строки, числа, булевы значения, массивы и объекты. Даты — как числа (Date.now()) или строки. Функции в состояние не кладут вообще: функции — это действия, они живут в коде.

Ошибки JSON

Правила формата строгие: ключи и строки только в двойных кавычках, без запятой после последнего элемента, без комментариев. Нарушили — JSON.parse бросит исключение SyntaxError, и приложение упадёт. Мы научимся этому противостоять в следующем разделе.

const raw = "{'text': 'нон'}";       // одинарные кавычки — это не JSON
const data = JSON.parse(raw);        // ✖ SyntaxError
console.log(data);
Совет

Чтобы быстро «разглядеть» большое состояние в консоли, вызывайте JSON.stringify(state, null, 2) — вывод будет с отступами, по две пробела на уровень. Для сохранения в localStorage отступы не нужны.

06 Пустые, битые и устаревшие данные

Код, который работает «когда всё хорошо», — это половина дела. Вторая половина — что произойдёт, когда данных нет, они повреждены или были записаны старой версией приложения. С localStorage такое случается постоянно:

  • Первый запуск. Пользователь пришёл впервые — в хранилище пусто, getItem вернёт null.
  • Мусор. Кто-то поправил запись в DevTools, запись оборвалась, другое приложение записало под тем же ключом что-то своё.
  • Устаревший формат. Вчера в состоянии не было поля filter, сегодня вы его добавили, а в браузере пользователя лежит вчерашний снимок.
Аналогия из жизни

Склад в Илмхоне перед началом занятий. Администратор открывает шкаф за маркерами: а вдруг шкаф пуст (первый день), маркеры высохли (битые данные) или вместо них лежат стикеры от прошлого семестра (старый формат)? Хороший администратор не паникует: у него есть запасной комплект. Запасной комплект в коде — это состояние по умолчанию.

Пустое хранилище

Если ключа нет, getItem возвращает null. Проверьте это явно и верните состояние по умолчанию:

function createStorage() {
  let data = {};
  return {
    getItem: (key) => (Object.hasOwn(data, key) ? data[key] : null),
    setItem: (key, value) => { data[key] = String(value); },
    removeItem: (key) => { delete data[key]; },
    clear: () => { data = {}; },
  };
}
const storage = createStorage();

const KEY = "todo-app:v1";
const DEFAULT_STATE = { nextId: 1, todos: [] };

function loadState() {
  const raw = storage.getItem(KEY);
  if (raw === null) return { ...DEFAULT_STATE, todos: [] }; // первый запуск
  return JSON.parse(raw);
}

console.log(JSON.stringify(loadState())); // хранилище пустое

Обратите внимание на { ...DEFAULT_STATE, todos: [] }: мы возвращаем копию по умолчанию, а не сам объект. Иначе все изменения попадут в «запасной комплект», и при следующем сбросе он будет уже не пустым.

Битый JSON: try / catch

Если в хранилище лежит строка, которая не является корректным JSON, JSON.parse бросает исключение. Его перехватывают через try / catch (вы уже видели это в уроке 7) и возвращаются к состоянию по умолчанию:

function safeParse(raw) {
  try {
    return JSON.parse(raw);
  } catch (error) {
    console.log("Данные повреждены:", error.name);
    return null;
  }
}

console.log(safeParse('{"ok":true}'));  // → { ok: true }
console.log(safeParse("{oops"));        // → Данные повреждены: SyntaxError, потом null

Неверная форма: проверяем, что внутри

Строка может быть корректным JSON, но совсем не тем, что мы ждали: число 42, строка, null, объект вместо массива. Поэтому после parse проверяем форму данных:

function isValidTodos(value) {
  return Array.isArray(value);
}

console.log(isValidTodos([]));            // → true
console.log(isValidTodos({ a: 1 }));      // → false — объект, а не массив
console.log(isValidTodos(JSON.parse("42"))); // → false — число
console.log(isValidTodos(JSON.parse("null"))); // → false
Любопытная ловушка

JSON.parse(null) не падает, а возвращает null — потому что null сначала превращается в строку "null", а это корректный JSON. В итоге JSON.parse(storage.getItem(key)) при пустом хранилище «работает», но возвращает null, и уже следующая строка state.todos падает с TypeError. Поэтому проверка raw === null нужна всегда.

Состояние устарело: подмешиваем значения по умолчанию

Когда в состоянии появляются новые поля, старые снимки их не содержат. Решение — начать с состояния по умолчанию и «наложить» поверх него то, что нашли в хранилище:

const DEFAULT_STATE = { filter: "all", theme: "light", todos: [] };

// вчерашний снимок: полей filter и theme ещё не было
const saved = { todos: [{ id: 1, text: "Нон", done: false }] };

const state = { ...DEFAULT_STATE, ...saved };
console.log(JSON.stringify(state));
// → поля filter и theme взяты по умолчанию, todos — из сохранённого

Всё вместе: надёжный loadState

  1. Достали строку через getItem. Если null — вернули состояние по умолчанию.
  2. Распаковали внутри try / catch. Ошибка — вернули состояние по умолчанию.
  3. Проверили форму: это вообще объект (а не число, строка, null, массив)? Нет — состояние по умолчанию.
  4. Подмешали значения по умолчанию для недостающих полей и проверили важные поля: например, todos обязан быть массивом.
function loadState() {
  const raw = storage.getItem(KEY);
  if (raw === null) return createDefaultState();     // 1. пусто

  let saved;
  try {
    saved = JSON.parse(raw);                         // 2. битый JSON
  } catch {
    return createDefaultState();
  }

  if (typeof saved !== "object" || saved === null || Array.isArray(saved)) {
    return createDefaultState();                     // 3. это не объект состояния
  }

  const state = { ...createDefaultState(), ...saved }; // 4. добавили недостающее
  if (!Array.isArray(state.todos)) state.todos = [];   //    и починили важное поле
  return state;
}

Выглядит громоздко, но написать это нужно один раз. Зато приложение не упадёт, что бы ни лежало в хранилище. Эту функцию вы возьмёте в свой проект.

07 ИИ-блок: просим предложить структуру состояния

Самый важный момент в любом приложении — какие данные вы храните и в каком виде. Ошибка здесь дорого обходится: переделывать структуру состояния, когда уже написаны render, действия и сохранение, — всё равно что перестраивать фундамент у готового дома. Поэтому именно сюда стоит привлечь ИИ — но как второго мнения, а не как автора.

Правила курса, которые здесь особенно важны

1) Сначала 15 минут сами: нарисуйте свой state на бумаге или в коде. 2) Только потом промпт. 3) Не вставляйте в проект код, который не можете объяснить строчку за строчкой. 4) Решение принимаете вы: ИИ предлагает, вы сравниваете и выбираете.

Порядок работы

  1. Своя версия. Опишите приложение одним предложением и набросайте объект state. Отметьте, что из него вы сохраните в localStorage.
  2. Промпт по формуле: контекст → задача → ограничения → формат ответа → проверка.
  3. Сравнение. Выпишите отличия в таблицу: поле — у меня — у ИИ — что решил и почему.
  4. Проверка. Для каждого спорного места спросите себя: «что будет, если здесь пусто или лежит мусор?».

Плохой и хороший промпт

Придумай как хранить данные для моего приложения

Почему плохо: ИИ не знает ни приложения, ни ваш уровень, ни где хранятся данные. Он выдаст общий совет или сразу огромную архитектуру на фреймворке, которого у вас нет.

Контекст: я новичок, пишу на чистом JavaScript без библиотек, учебный проект — трекер привычек. Пользователь может добавить привычку, отметить её выполненной сегодня, удалить, и переключать фильтр «все / не выполненные». Данные должны переживать перезагрузку страницы. Задача: предложи структуру объекта состояния и объясни, что из него класть в localStorage. Ограничения: только строки, числа, булевы значения, массивы и объекты (то, что переживёт JSON); не хранить то, что можно вычислить; у каждой привычки уникальный id. Формат ответа: сначала пример объекта state как JS-код; затем список полей — по строке «поле — зачем нужно»; затем что сохраняем, а что нет. Проверка: назови 2 случая, когда сохранённые данные могут оказаться некорректными, и как с ними справиться.

Это развёрнутый вариант шаблона из шпаргалки курса: «Предложи структуру объекта состояния для приложения [описание]. Объясни, почему такие поля и что положить в localStorage». Мы добавили контекст, ограничения и проверку — и получили ответ, который можно сравнивать.

Чек-лист: как проверять ответ ИИ

  • Нет ли производных данных. Если в состоянии лежит total, doneCount или готовый HTML — их можно вычислить, значит, они лишние.
  • Уникальные id. Откуда они берутся? Есть ли nextId, или ИИ предлагает length + 1 (мы видели, чем это кончается)?

  • Что сохранять. Нужно ли сохранять временное — например, текст, который пользователь набирает в поле прямо сейчас? Часто нет: после перезагрузки он не нужен.
  • Версия формата. Предложил ли ИИ ключ вида app:v1? Что произойдёт при смене структуры?

  1. Добавьте несколько элементов, обновите страницу (F5) — всё на месте?
  2. Откройте DevTools (F12) → Application → Local Storage. Найдите свой ключ, посмотрите, как выглядит значение.
  3. Испортите значение вручную: удалите последнюю скобку. Обновите страницу — приложение должно запуститься с начальным состоянием, а не упасть с ошибкой в консоли.
  4. Удалите ключ — страница должна открыться «как в первый раз».
  5. Нажмите «Сбросить» — данные исчезли и из экрана, и из хранилища?

Если страница открыта как файл

В большинстве браузеров localStorage работает и для файлов file://, но у разных файлов могут быть общие или раздельные данные — это зависит от браузера. Надёжнее запускать проект через Live Server в VS Code: тогда у него обычный адрес вида localhost:5500 и своё хранилище.

✓ Шпаргалка урока

  • Состояние — все изменяемые данные приложения в одном объекте state. Хранить только исходные факты; то, что можно посчитать (сумма, счётчик), считаем функцией.
  • render(state) рисует экран целиком и только по состоянию: ничего не меняет, не читает данные из DOM, умеет рисовать пустой список.
  • Цикл: событие → действие (addTodo, toggleTodo, removeTodo) → изменили state → render() → saveState().
  • Массивы в состоянии: добавить — [...arr, item], изменить — map, удалить — filter. Присваиваем результат обратно в state. Id берём из nextId, а не из length + 1.
  • localStorage: setItem(k, v), getItem(k) (нет ключа — null), removeItem(k), clear(). Хранит только строки, живёт после перезагрузки, около 5 МБ, свой для каждого сайта. Секреты не хранить.
  • В песочнице курса настоящий localStorage недоступен — используем заглушку storage с тем же API. На своём компьютере: const storage = window.localStorage;. Проверить настоящий можно в DevTools → Application → Local Storage.
  • JSON: JSON.stringify(state) перед записью, JSON.parse(raw) после чтения. Не переживают: undefined, функции, даты (станут строками).
  • Надёжный loadState: null → состояние по умолчанию; JSON.parse в try / catch; проверка формы; { ...defaults, ...saved } для новых полей. Ключ с префиксом и версией: app:v1.
  • ИИ: сначала своя структура состояния (15 минут), потом промпт по формуле и сравнение в таблице. Проверять: нет ли производных данных, откуда id, что сохранять, что с пустыми и битыми данными.
